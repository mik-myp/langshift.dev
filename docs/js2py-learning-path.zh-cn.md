## 1. 顺序与深度的共同约束

- 起点是成熟前端工程经验，而不是既有 Python、Express、SQL 或服务器运维经验。
- 终点是独立开发、测试、部署、维护真实用户可用的后端，不是只会看 API 或复制演示。
- 第 00 章只验收能解释、运行、修改和排错的小脚本。完整可复现工程放在 L10，不要求先学完整 Python 才开始实践。
- 名称/容器/循环/函数阶段持续形成小产物；模块和文件之后再综合工程能力。
- 每章先确定前置能力、正文目标、独立验收与不要求掌握的内容。先修章节编号不是“只读过标题”的证明。
- 使用层行为必须讲清，但不强求同时学会全部底层实现。例如 L07 讲清 with 的清理行为，L14 再实现自定义协议。
- 允许慢工出细活；章节过载就拆分，不为保留原章数压缩讲解，也不按周数推进。
- 测试随能力增长：先预测/核对输出，之后普通函数测试，再 API、数据库、授权与恢复测试。
- TypeSafe 给出的概率是审查辅助，不是教学效果证明；新章节仍需逐段检查隐含前提和实际执行。

## 2. 建议统一的技术路线

这是一条为本读者选择的教学路线，不是唯一标准，也不是已经验证过的完整版本组合。

| 职责 | 主线选择 | 边界与理由 |
| --- | --- | --- |
| Python | CPython 3.13 作为保守教学基线候选 | 不声称它是最新版本；实施时在仍受支持的小版本线上锁定补丁版本并测试。浏览器 Pyodide 单独注明版本（报告 S17/S18） |
| 环境与依赖 | uv + pyproject.toml + uv.lock | 一条初始化、安装、运行和复现路径；pip/venv 原理需要理解，Poetry/pyenv 作为识读附录（S19） |
| Web | FastAPI + Uvicorn | 区分框架、ASGI 服务器与 Python 解释器；具体兼容版本在样板项目通过测试后锁定（S04） |
| 模型与配置 | Pydantic 2.x + pydantic-settings | 学习必要的输入输出验证与配置；不从复杂自定义类型系统开始（S05/S15） |
| 数据库 | PostgreSQL | SQL/ORM/迁移阶段起使用同一数据库类型；测试与部署对齐。SQLite 可用于短小演示，但不是生产验收替身 |
| 数据访问 | SQLAlchemy 2.x 同步接口 + Alembic | 先理解 Session、事务和迁移；不同时强制学习 SQLModel 与异步 ORM（S07/S08） |
| 身份认证 | Argon2id 密码哈希 + 不透明随机 Bearer 会话；短期访问令牌 | 结合官方密码存储资料，补真实数据库、失效与授权测试；不自创密码学，不把 JWT 当作本课程已经实现的方案（S01/S02） |
| 质量 | Ruff 检查/格式化 + pytest + HTTPX/TestClient | 普通 Python 测试从基础阶段开始，API/数据库测试随功能增长（S13/S20） |
| 类型检查 | mypy 基础使用 | 学会读真实诊断，不把复杂类型编程或“零 Any”作为入门 KPI |
| 交付 | Docker/Compose、CI、HTTPS、日志与恢复手册 | 本地可复现后再选部署平台；不提前绑定某云厂商，也不执行付费开通（S14/S22） |

教学顺序与依赖安装顺序一致：第 00 章只用 uv 选择解释器，L08 才系统教学环境与锁文件；到数据库阶段再引入 ORM，到认证阶段再引入密码库，不在第一课列出几十个必须掌握的库。

特别说明：FastAPI 官方数据库示例采用 SQLModel。本方案选择 SQLAlchemy，是为了显式教学模型、Session 与事务，不是宣称官方推荐只有这一种（S06）。

## 4. 阶段交付仍然保留，但不再前置到第一章

### 阶段 A：能稳定运行和组织 Python（L01—L14）

产物：一个纯 Python 的任务管理程序，不需要 Web 框架。支持创建、筛选、修改状态、JSON 导入导出。

重点：语言差异、业务函数、异常、基础类型、简单对象、文件资源、模块和测试。复杂生成器/元类/类型协议不作门槛。

通过标准：

- [ ] 从新的工作目录或新终端复现环境，能够解释运行命令和导入路径。
- [ ] 为非法状态、空标题、缺失记录和非法 JSON 写测试。
- [ ] 能定位一处 traceback，修复而不是仅复制答案。
- [ ] 解释 Python 空集合、可变默认参数、None 和拷贝与 JS 的差异。
- [ ] 解释类型注解、dataclass 与外部输入验证不相同。

### 阶段 B：能设计并实现 API（H01—H06）

产物：把纯 Python 业务暴露为 FastAPI API，最初允许使用内存数据；明确重启丢数据，不允许作为上线版本。

通过标准：

- [ ] 先写一页接口契约，再完成创建、读取、列表、局部更新与删除。
- [ ] 能解释路径/查询/请求体参数，并区分校验错误、资源不存在和业务冲突。
- [ ] 更新请求中漏传字段不会错误清空已有值。
- [ ] 用 TestClient 验证成功与失败响应；不是仅在 Swagger 页面点击一次。
- [ ] 使用多文件路由与配置，不需要先实现复杂架构。
- [ ] 用已有前端或最小 fetch 页面完成一次联调；不要求花时间重新建设前端 UI。

### 阶段 C：能维护真实数据（D01—D06）

产物：PostgreSQL 持久化的任务 API，以及第一条有数据的升级迁移。

通过标准：

- [ ] 画出模型与关系，能亲自写基本 SQL，而非只会调用 ORM。
- [ ] 数据库约束能够拒绝重复/非法关联数据，失败后事务与 Session 正常恢复。
- [ ] 创建项目及其负责人关系作为一个整体成功或失败。
- [ ] 使用迁移建立空数据库并升级已有数据库；不会用删库重建解决结构变化。
- [ ] 解释连接、连接池、Session 与事务的区别。
- [ ] 集成测试使用独立 PostgreSQL 环境，不访问开发或生产数据库。

### 阶段 D：能安全地支持多个用户（S01—S03）

产物：真实用户、密码验证、令牌失效与项目成员权限。

通过标准：

- [ ] 密码只存哈希；响应和日志不泄露密码、哈希、Token 或秘密配置。
- [ ] 过期、篡改的 Token 和停用用户都被拒绝。
- [ ] Alice 不能读取或修改 Bob 的私有项目，即使知道对象 ID。
- [ ] 用户不能靠请求体里的 user_id、project_id 或角色字段提升权限。
- [ ] 修改密码/退出全部会话后，旧凭证按明确策略失效。
- [ ] 普通成员与负责人权限有自动化测试；测试初始化与清理可重复执行。

此阶段的身份流程是教学与首个自有应用的方案，不将 OAuth2PasswordBearer 等辅助组件误讲成完整的认证系统或通用第三方 OAuth 服务。

### 阶段 E：能解释并控制异步（A01—A02）

产物：一个可选的外部服务适配实验；外部服务失败不能影响项目核心 CRUD。

通过标准：

- [ ] 解释“调用 Python async 函数获得 coroutine”和“真正调度/等待它”的区别。
- [ ] 能选择 def + 同步依赖或 async def + awaitable 依赖，而不是机械加 async。
- [ ] 外部调用有超时、可控并发与失败测试，取消后资源得到释放。
- [ ] 不把进程内 BackgroundTasks 或 asyncio.Queue 宣称为可恢复的持久任务队列。
- [ ] CPU 重计算不因为改成 async 就被当作性能问题已解决。

高级异步数据库、Redis/Celery、分布式任务作为之后的选修；本阶段不要求重写已工作的同步 CRUD。

### 阶段 F：能发布、恢复并独立扩展（O01—G01）

产物：一个实际可访问、供受邀用户试用的部署；运维说明；一个独立完成的新需求。

通过标准：

- [ ] 从干净环境按 README 运行检查、测试、迁移和启动流程。
- [ ] HTTPS、生产配置、秘密注入、日志与健康检查可解释且经过验证。
- [ ] 重启服务不丢数据；故意配置错误时有可定位的日志且不泄密。
- [ ] 完成一次从备份恢复到隔离数据库的演练，而不只是“配置了备份”。
- [ ] 完成一次兼容性明确的应用回退；知道数据库降级不一定无损。
- [ ] 根据新需求独立增加模型/迁移、接口、权限、测试与文档。

具体契约与发布范围以配套毕业项目规格为准。

## 5. 贯穿整合项目：把实验合并成一份服务

分章实验解决单个责任，完整产品需要把这些责任放回同一份代码、同一套迁移和同一份运行记录。读者在 L10 之后建立自己的仓库，后续每个阶段都在这份仓库留下可运行提交；独立实验仍用于隔离学习机制，不要求复制到产品中。

推荐的整合顺序：

1. **V0（L10）**：保留纯 Python 业务函数、文件格式、普通测试和恢复记录，写下将来 API 要保持的业务规则。
2. **V1（H01—H06）**：把 V0 规则接入 FastAPI；先允许内存状态，但明确重启丢数据。每次改动同时更新接口契约、HTTP 测试和最小前端联调。
3. **V2（D01—D06）**：在产品仓库中建立 PostgreSQL 模型和第一条迁移，再把 V1 的内存读写替换成 SQLAlchemy Session。保留一条有数据升级记录，不以复制 D04/D05 答案代替自己的迁移。
4. **V3（S01—S03）**：以现有 V2 数据模型为基础加入用户、项目、成员、会话和对象权限。当前教学主线使用 Argon2id 与不透明随机 Bearer 会话；改用 JWT、Cookie 或第三方身份服务时，必须重新写认证、撤销、CSRF 和测试契约。
5. **V3.5（A01—A02）**：只为有明确收益的外部提示或可选依赖接入异步资源；核心 CRUD 不得依赖它。把超时、取消、重试和幂等记录放入产品测试，而不是只运行 A02 的故障替身。
6. **V4（O01—O06）**：用同一份产品仓库完成配置、容器/进程入口、HTTPS、发布回退、日志、备份和隔离恢复。O 阶段实验是检查工具，必须把真实路由、真实迁移、真实权限和真实数据范围接入验收。
7. **V5（G01）**：在已有产品上实现一项没有逐步代码答案的新需求，提交模型/迁移、接口、权限、测试、发布、回退和恢复证据。先独立设计，再参考已有章节的机制，不复制另一个实验目录。

每个整合检查点都要保留：代码版本、迁移版本、最后成功命令、通过的测试、失败与恢复记录、部署目标、下一步证据。`examples/js2py/s03-reliable-operations` 和 O04—O06 是参考材料，不是学习者产品的可直接上线替代品。
