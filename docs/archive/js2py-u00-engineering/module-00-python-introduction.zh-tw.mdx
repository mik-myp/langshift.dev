## 1. 這不是一張安裝命令清單

你已經能搭建前端項目、處理組件之間的數據流，也知道如何用 Promise 和 async/await 對接接口。因此，本章不會從“變量是什麼”講起，也不會假定你已經寫過 Express 服務、設計過數據庫或管理過服務器。

我們要補上一個經常被教程跳過的環節：**當你在終端輸入一條 Python 命令時，到底是誰在運行代碼，它從哪裡找到依賴，又為什麼會出現“編輯器不報錯，終端卻無法導入”的情況？** 如果這些問題沒有弄清，後面學 FastAPI 時，環境、代碼與服務端概念會混在一起，排錯只能靠反覆重裝。

本章的產物是一個很小但完整的本地項目：它讀取一份任務清單，輸出完成情況，並有自動化測試。功能刻意保持簡單，讓你把注意力放在運行過程與工程習慣上。它不是 Web 服務，也沒有用戶、數據庫或輸入驗證；這些會在後面的章節逐層加入，而不是在第一課留下幾個省略號就當作完成。

### 1.1 學完之後，應該能獨立回答什麼？

- Python 語言、CPython 解釋器、uv 和 FastAPI 分別負責什麼？
- 為什麼電腦能找到 Python，不代表當前項目能導入某個包？
- `.venv`、`.python-version`、`pyproject.toml` 和 `uv.lock` 為什麼不是同一種東西？
- 同一份文件，直接執行和被 `import` 時有什麼不同？
- 遇到錯誤時，怎樣先收集證據，再判斷是目錄、解釋器、依賴還是業務代碼的問題？
- 隔了兩週回到項目，怎樣恢復環境並確認程序仍然正確？

不要求你現在理解每一種 Python 語法。可以先把少量陌生寫法與熟悉的 JS 對照起來；本章會解釋運行本例所必需的部分，下一章再系統展開語言差異。

### 1.2 本章的運行約定

| 內容 | 在哪裡執行 | 不代表什麼 |
| --- | --- | --- |
| `bash` 命令 | 本地終端，位於說明指定的目錄 | 不是粘貼到 `.py` 文件中的 Python 代碼 |
| `main.py` 與測試 | 本地 CPython 3.13，由 uv 選擇項目環境 | 不是網頁中的 Pyodide 環境 |
| JSON、TOML、鎖文件 | 按文件名保存，由相應工具讀取 | 不是可以交給 Python 解釋器的腳本 |
| JS/Python 對照 | 幫助理解同一個行為，可複製到相應本地環境 | 不要求你先實現一個 Node.js 後端 |
| 標明“故障實驗”的步驟 | 僅在本章練習目錄中操作，隨後恢復 | 不是生產系統的操作建議 |

瀏覽器裡的 Python 適合短小的語法實驗，但它不等於你的電腦，也不自動具備數據庫、服務器端依賴和真實文件目錄。本章所有項目驗收都以本地運行結果為準。

## 2. 先建立心智模型：四個容易混淆的層次

前端工具已經幫你處理了很多工作。執行 `pnpm dev` 時，你通常不需要每次思考 Node 的路徑、包的查找方式和構建工具的入口。切換生態後，這些便利背後的分工值得重新看一遍。

### 2.1 語言不是解釋器，框架也不是解釋器

**Python** 是語言：規定函數、對象、異常、模塊等語法和行為。**CPython** 是本課程使用的語言實現：你執行的 `python` 通常指向它的可執行文件。它讀取源碼，完成解析、執行等工作。

**uv** 是工程工具，幫助選擇 Python 版本、管理項目環境、解析和安裝依賴、執行項目命令。它不替代 Python 語言，也不會替你實現業務邏輯。

**FastAPI** 是後面才會安裝的庫/框架。它讓 Python 程序以一套結構處理 HTTP 請求。真正啟動 API 服務時，還會涉及 ASGI 服務器，例如 Uvicorn。不要把這些名稱理解成幾種競爭關係的“Python 運行方式”。

```text
终端
  └─ uv run：找到项目，准备它的环境，选择解释器
       └─ CPython：执行 main.py
            ├─ 导入标准库 json、pathlib
            ├─ 读取 tasks.json
            └─ 执行业务函数并输出结果
```

在這個流程裡，uv 不理解“任務完成了幾個”；Python 不替你決定依賴該鎖在哪個版本；將來 FastAPI 也不會自動替你決定誰有權讀取某個用戶的數據。學習後端的一部分，就是逐漸理解這些職責邊界。

### 2.2 與前端經驗的對應關係，要連同邊界一起記

| 熟悉的概念 | 本課程中的對應物 | 類比的邊界 |
| --- | --- | --- |
| JavaScript 與 Node.js | Python 與 CPython | 語言與運行時的職責可以類比，不代表執行模型完全相同 |
| `package.json` | `pyproject.toml` | 都可聲明項目依賴，但字段規範和工具行為不同 |
| `pnpm-lock.yaml` | `uv.lock` | 都記錄依賴解析結果；不要把寬鬆的版本範圍誤當鎖文件 |
| `node_modules` | `.venv` 中安裝的包 | `.venv` 還關聯 Python 解釋器；二者不是完全同構的目錄 |
| `.nvmrc` | `.python-version` | 都可表達項目版本偏好，但不單獨承擔依賴鎖定 |
| `pnpm exec ...` | `uv run ...` | 都便於使用項目工具；uv 還可在運行前同步環境 |
| ESLint / Prettier | Ruff 檢查 / 格式化 | 檢查風格不等於驗證業務行為，測試仍不可缺少 |

### 2.3 為什麼不先讓你比較所有包管理器？

你可能聽過 pip、venv、virtualenv、Poetry、pyenv、pip-tools 和 uv。它們有歷史原因和不同職責，不是“全都安裝一遍，項目才專業”。

本課程先選 **uv 作為唯一操作主線**，同時解釋虛擬環境和依賴聲明的原理。你以後接手使用 pip 或 Poetry 的倉庫時，可以依據這些原理理解它們，而不是重新建立一套完全不同的知識。

pip 並沒有“過時”，venv 也不是“不能用”。收斂工作流，是為了讓首次學習後端時的變量更少。不要在同一個練習環境裡無目的地輪流使用多個工具安裝、升級和卸載包。

## 3. Python 版本與虛擬環境：到底隔離了什麼？

### 3.1 一臺電腦為什麼可能有不止一個 Python？

操作系統、Homebrew、其他工具和你自行安裝的版本，都可能提供名為 `python` 或 `python3` 的命令。終端根據 `PATH` 查找可執行文件；編輯器還可能獨立保存一個解釋器路徑。因此，“終端顯示 3.13”和“編輯器使用 3.13”不是天然等價的。

先記住一個比猜測更可靠的辦法：**讓正在運行的 Python 報告它自己的路徑。**

```bash
uv run --locked python -c "import sys; print(sys.executable); print(sys.version)"
```

這條命令在稍後準備好的練習項目裡執行。`-c` 後面是一小段 Python；`sys.executable` 是當前進程的解釋器路徑，`sys.version` 是當前解釋器的版本信息。它們是觀察結果，不是編輯器狀態欄的推測。

本章採用 CPython **3.13** 作為教學版本線，不意味著它永遠是“最新版本”。補丁版本可以變化；若需更嚴格的復現，可以將 `.python-version` 固定為經過測試的具體補丁版本。後端項目升級解釋器時，也要重新運行測試，而不是隻修改版本數字。

### 3.2 `.venv` 不只是一個裝包的文件夾

假設項目 A 依賴某庫的一個版本，項目 B 依賴另一個版本。如果都安裝到同一個共享環境，你在維護 B 時，可能無意改變 A 的運行條件。虛擬環境為項目提供獨立的包安裝位置與解釋器入口，避免這種日常衝突。

但“環境隔離”不等於安全沙箱。程序仍然可能訪問當前用戶有權限訪問的文件和網絡；虛擬環境不會自動隔離數據庫，更不會阻止代碼刪除文件。

還要區分“創建環境”和“激活環境”。激活通常只是讓當前終端優先找到該環境裡的命令。**使用 `uv run` 不要求先手動激活**，因為 uv 會為命令選擇項目環境。先採用這一種方式，避免把激活狀態當作額外的隱藏條件。

準備好項目後可以觀察：

```bash
uv run --locked python -c "import sys; print(sys.prefix); print(sys.base_prefix)"
```

在本課程的虛擬環境中，兩者應不同：前者指向當前環境，後者關聯基礎解釋器。具體路徑因電腦而異，不需要與書中的路徑一字不差。

> 不要通過修改系統 Python、使用 `sudo pip install` 或關閉系統保護來解決項目依賴問題。先檢查當前解釋器與當前項目，再決定操作。

## 4. 安裝工具，並先運行一份已知正確的項目

### 4.1 安裝 uv 與 Python

本章以 macOS 為主。若你已經使用 Homebrew，可以執行：

```bash
brew install uv
uv --version
uv python install 3.13
```

第一條安裝工程工具，第二條確認終端能找到它，第三條安裝課程採用的解釋器版本線。這不是給現有系統 Python 做原地升級。

如果沒有 Homebrew，或者使用 Windows/Linux，請從 [uv 官方安裝指南](https://docs.astral.sh/uv/getting-started/installation/)選擇對應方法。安裝腳本會修改本機環境，應閱讀其說明；不要為了照搬本章而額外搭建一套自己不用的系統工具鏈。

Windows 可使用 PowerShell 運行項目命令；後面涉及 `pwd`、`command -v` 等診斷時，書中會同時給出相應說明。

### 4.2 下載與進入項目

[下載本章完整練習工程](/learning-assets/js2py/u00-environment.zip)。解壓後進入 **包含 `pyproject.toml` 的 `u00-environment` 目錄**，不是它的上一級下載目錄。

你也可以在本站源碼中的 `examples/js2py/u00-environment` 找到同一份文件。網頁展示代碼和下載包都來自這些源文件，避免“書上一個版本，下載包另一個版本”。

```text
u00-environment/
├── .python-version
├── .gitignore
├── pyproject.toml
├── uv.lock
├── main.py
├── tasks.json
├── tests/
│   └── test_main.py
├── next_task.py
├── exercises/
│   └── test_next_task.py
└── solutions/
    └── next_task.py
```

`tests` 是本章已實現程序的驗收；`exercises` 是你要完成的獨立練習；`solutions` 是分開放置的參考答案。練習的初始實現故意未完成，所以不要把所有目錄的測試結果混為一談。

### 4.3 第一次復現

依次執行，每條完成後再看下一條：

```bash
uv sync --locked
uv run --locked python main.py
uv run --locked python -m pytest -q
uv run --locked ruff check .
uv run --locked ruff format --check .
```

`uv sync --locked` 根據已有聲明和鎖文件準備環境，並要求它們保持一致。如果鎖文件缺失或過期，命令應失敗，而不是悄悄更新後裝作復現成功。首次運行可能下載解釋器或包，具體日誌隨系統與緩存狀態變化。

運行應用應得到：

```text
Tasks: 3 | Done: 1 | Pending: 2
```

默認測試應全部通過，共 **6 個測試用例**。耗時和終端進度符號可能不同；重要的是退出碼為零、沒有失敗，而不是打印內容逐字一樣。

Ruff 的檢查和格式化檢查解決的是另一類問題：它們不保證任務計數正確。反過來，測試通過也不證明導入順序和格式統一。這幾條命令各自負責一個邊界。

如果這一步失敗，先閱讀第 10 節的診斷方法。不要一邊改變 Python 版本、一邊升級依賴、一邊修改程序；同時改變多個條件，會讓你無法知道哪個動作真正解決了問題。

## 5. 四份配置文件，逐個解釋

### 5.1 `.python-version`：選擇哪條解釋器版本線

<Code language="text">{getU00Example('.python-version')}</Code>

這告訴 uv 在本項目中選擇 Python 3.13。它不是 Python 代碼，也不是依賴清單。只修改它，並不會自動保證你的庫和業務代碼兼容另一個 Python 版本。

### 5.2 `pyproject.toml`：項目聲明，而非安裝結果

<Code language="toml">{getU00Example('pyproject.toml')}</Code>

逐段看，而不是把整段當成必須背下來的模板：

- `[project]` 描述項目。這裡的版本是**這個練習項目的版本**，不是 Python 或 FastAPI 的版本。
- `requires-python = ">=3.13,<3.14"` 表達本章驗證的解釋器範圍。它與 `.python-version` 分別承擔“允許範圍”和“本地選擇”的職責。
- `dependencies = []` 表示當前程序只用標準庫，不需要額外的運行時包。以後加入 FastAPI 時，應用依賴才會增加。
- `[dependency-groups]` 中的 `dev` 包含開發與測試工具。pytest 和 Ruff 不是當前業務函數運行所必需的庫。
- `[tool.pytest.ini_options]` 將默認測試範圍限定為 `tests`，因此尚未完成的挑戰題不會讓基線測試失敗。
- `[tool.ruff]` 和 `[tool.ruff.lint]` 配置本項目的代碼工具，不改變 Python 語言本身的語義。

這裡的文件夾名稱不要求等於項目名；名字中的連字符也不意味著你可以寫 `import js2py-u00-environment`。發行項目名稱、目錄名稱與 Python 導入名稱是不同層次，後面的模塊章節會繼續展開。

### 5.3 `uv.lock`：記錄解析後的選擇

`pyproject.toml` 裡的範圍可能允許多個版本。不同時間重新解析這些範圍，結果可能不同；依賴的依賴也會影響結果。`uv.lock` 記錄 uv 的解析選擇與相關信息，便於其他環境按照相同的依賴決策安裝。

不需要手工閱讀並維護鎖文件的每一行。可以觀察依賴關係：

```bash
uv tree
```

你可能看到 pytest 的間接依賴。不要因為自己沒有直接安裝過這些名字，就認定環境被汙染；先看它們是否是項目依賴圖的一部分。

鎖文件也不是整臺電腦的快照：操作系統、CPU 架構、外部數據庫、系統庫和 Python 補丁版本仍可能影響行為。復現是一組約束與驗證，不是一份文件替代一切。

### 5.4 `.gitignore`：哪些是聲明，哪些是機器生成物？

<Code language="text">{getU00Example('.gitignore')}</Code>

源碼、配置聲明、`.python-version` 和鎖文件應進入版本管理。`.venv` 與緩存由工具生成，不應該作為環境交接方式；真實 `.env` 也不應提交。將來要分享配置格式時，提交只有佔位值的示例配置，而不是複製個人的秘密。

“同事把整個虛擬環境壓縮給我”不等於可復現工程。環境可能包含本機路徑和平臺相關文件，正確的交接物應該是可重新創建環境的聲明、鎖文件和驗證步驟。

## 6. 現在從空目錄搭一次，而不只是使用下載包

已知正確的項目幫助你排除環境障礙；從空目錄重建，則能檢查你是否理解每個組成部分。

在一個新的練習位置執行，不要覆蓋剛才已運行成功的參考工程：

```bash
uv init --bare --vcs none --python 3.13 taskboard-lab
cd taskboard-lab
uv python pin 3.13
```

`--bare` 只生成最小項目聲明，避免自動生成的其他文件干擾本章解釋；`--vcs none` 不額外初始化 Git，方便你在已有學習倉庫中練習。之後可以按自己的版本管理習慣加入 Git。

將第 5 節給出的完整 `pyproject.toml` 保存到新目錄，再按後文創建 `main.py`、`tasks.json` 和 `tests/test_main.py`。此時還沒有鎖文件，首次執行：

```bash
uv sync
```

這裡不用 `--locked`，因為現在是在**創建**依賴解析結果，不是在驗證已有鎖文件。首次成功後，後續復現和驗收改用 `uv sync --locked`。不要為了讓鎖文件錯誤消失，永遠把 `--locked` 刪除；應該判斷當前是在有意修改依賴，還是本應復現一個既定環境。

如果你不想手寫開發依賴聲明，也可以在新建項目裡運行 `uv add --dev pytest ruff`，由工具更新聲明與鎖文件。但這樣得到的版本範圍可能與參考工程不同。本章使用下載包中的鎖文件作為已驗證的參考，而不是承諾所有未來版本結果相同。

## 7. 完整程序：先運行，再逐步理解

### 7.1 輸入文件 `tasks.json`

<Code language="json">{getU00Example('tasks.json')}</Code>

這裡使用 JSON 的 `true` 和 `false`。Python 的布爾字面量則是 `True` 和 `False`。為什麼文件裡仍然能寫小寫？因為它是交給 JSON 解析器讀取的數據，不是作為 Python 源碼執行。

這也是本章反覆強調“文件類型”的原因：依賴聲明、JSON 數據和程序都可能是純文本，但它們由不同規則解釋。

### 7.2 業務與入口文件 `main.py`

<Code language="python">{getU00Example('main.py')}</Code>

不要急著把整段記下來。沿著執行過程觀察：

**第一步：導入標準庫。** `json` 負責把 JSON 文本解析為 Python 對象；`Path` 幫助表達和操作文件路徑。它們屬於當前 Python 的標準庫，不需要 `uv add json` 或 `uv add pathlib`。

**第二步：確定數據文件的位置。** `__file__` 表示當前模塊文件的位置。`Path(__file__).with_name("tasks.json")` 取得與這個文件同目錄的任務文件，而不是假定終端當前目錄永遠正確。這個規則針對本例的本地文件佈局；並不是在承諾一切部署形式都可以這樣訪問資源。

**第三步：定義業務函數。** `def build_report(tasks):` 定義一個函數，定義時不會立即遍歷任務。`completed = 0` 是局部變量；`for task in tasks` 遍歷列表；`if task["done"]` 判斷完成狀態；縮進表達代碼塊。這裡沒有 `self`，因為它是普通函數，不是實例方法。

**第四步：返回而不是直接打印。** `build_report` 返回字符串，`main` 再負責打印。把計算與輸出分開後，測試可以直接比較返回值，不必為每次業務判斷啟動一個終端進程。

**第五步：讀取和解析數據。** `read_text(encoding="utf-8")` 得到字符串，`json.loads(...)` 再得到列表和字典。文本內容、解析後的對象、最終報告是不同階段，不要把它們當作同一份數據的不同叫法。

**第六步：選擇何時真正運行入口。** 當文件作為腳本執行時，`__name__` 為 `"__main__"`，底部條件成立，調用 `main()`。當測試導入這個模塊時，模塊仍會執行頂層語句並建立函數定義，但條件不成立，不會自動讀取任務並打印報告。

這種入口保護不意味著“import 不執行任何代碼”。它只控制條件內部的調用。如果你把網絡請求或文件讀取寫在條件外，導入時仍可能發生副作用。

### 7.3 用熟悉的 JS 看同一個業務函數

下面是靜態語言對照，使用同一份可信輸入；完整本地運行方式已經在前面給出。這裡沒有 Node 服務，也沒有數據庫。

<PythonEditor title="同一份任務清單，兩種計數實現（本地對照）" compare={true} canRun={false} height={430}>
```javascript !! js
function buildReport(tasks) {
  let completed = 0;
  for (const task of tasks) {
    if (task.done) {
      completed += 1;
    }
  }
  const total = tasks.length;
  return `Tasks: ${total} | Done: ${completed} | Pending: ${total - completed}`;

console.log(buildReport([{ done: true }, { done: false }]));
```

```python !! py
def build_report(tasks):
    completed = 0
    for task in tasks:
        if task["done"]:
            completed += 1
    total = len(tasks)
    return f"Tasks: {total} | Done: {completed} | Pending: {total - completed}"

print(build_report([{"done": True}, {"done": False}]))
```
</PythonEditor>

兩邊的預期結果都是 `Tasks: 2 | Done: 1 | Pending: 1`。值得注意的是字典取值、布爾字面量、`len`、縮進與 f-string，而不是“Python 就是把分號刪掉的 JS”。下一章還會看到真值、默認參數、對象共享等不能直接照搬的語義。

### 7.4 當前程序的邊界在哪裡？

本例信任隨課提供的 JSON：每項都有合法的 `done` 字段。它沒有驗證任意輸入，也沒有把修改寫回文件。因此它是**完整的環境與執行練習**，不是完整的任務管理產品。

如果輸入缺少字段，你可能遇到 `KeyError`；如果 JSON 損壞，解析會失敗。我們會在後續學習異常與輸入邊界時改進它。這裡不使用一個寬泛的 `except Exception: pass` 假裝程序已經健壯，否則真實問題反而被隱藏。

### 8.1 為什麼六個測試不是重複勞動？

前四個用例分別檢查空列表、全部完成、全部未完成與混合狀態。`@pytest.mark.parametrize` 讓同一項斷言接受多組輸入；可以把它先理解成“把這幾個例子分別交給同一套驗收邏輯”。裝飾器的具體機制稍後再學，不需要為了運行第一章先完成高級函數課程。

第五個用例從另一個當前目錄啟動程序，用於驗證數據文件定位。第六個用例只執行 `import main`，用於確認導入不會順帶打印報告。它們在檢查工程行為，而不只是業務計算。

`sys.executable` 讓子進程使用當前測試環境的同一個解釋器，避免機器上另一個名為 `python` 的命令混進驗收。`tmp_path` 由 pytest 提供臨時目錄，不是在真實項目裡刪除或移動文件。

### 8.2 為什麼寫 `python -m pytest`？

這會用 uv 選擇的 Python 解釋器來運行 pytest 模塊。這樣“測試工具裝在哪”和“測試由誰執行”之間的關係更明確。在本章簡單的根目錄佈局下，它也使從項目根目錄導入 `main` 的行為容易理解。

這不是說直接運行 `pytest` 永遠錯誤，而是為剛進入 Python 生態的讀者固定一條容易診斷的路徑。以後學習包結構後，再比較不同入口與導入方式。

### 8.3 做一次能恢復的失敗實驗

在自己的練習副本中，把業務函數里的 `pending = total - completed` 暫時改成 `pending = total`，再執行默認測試。

你應該看到具體的斷言差異，而不是一句模糊的“程序不對”。先指出哪個輸入暴露了問題，再恢復原實現並重新測試。如果沒有任何失敗，說明你很可能改了另一份文件，或者運行了另一個目錄裡的測試。

**不要改期望值來遷就錯誤實現。** 測試代表這裡已經確定的業務規則；當需求真的改變時，才應同時審查規則、實現與驗收。

## 9. 依賴維護不是“缺什麼就全局安裝什麼”

當後續項目需要一個新庫時，應在項目目錄中使用 `uv add 包名`，開發工具則使用 `uv add --dev 包名`。這不僅是把文件下載到環境中，還要更新可交接的項目聲明與鎖文件。

本章不需要額外安裝 HTTP 庫。若你想觀察依賴變化，可以在**單獨的練習副本**中用 `uv add httpx`，查看配置和 `uv tree` 的變化，再用 `uv remove httpx` 恢復。這只是工具練習，不會自動讓當前程序變成後端服務。

還要區分三件事：

1. **同步環境**：使當前環境符合項目聲明和既有鎖文件。
2. **新增依賴**：有意改變項目需要的庫，再審查聲明和鎖文件變化。
3. **升級依賴**：有意改變允許或選中的版本，並重新運行測試。

遇到導入失敗時直接升級所有包，會把問題定位和依賴升級混成一次高風險操作。先證明缺少的是哪個包、當前使用的是什麼解釋器，再做最小改動。

uv 創建的環境也不保證預裝 pip。如果 `python -m pip` 提示找不到模塊，不等於整個 Python 已損壞；本課程的包操作由 uv 管理。以後在使用 pip 的項目裡，再按那個項目的流程配置它。

## 10. 排錯不是記住錯誤名，而是建立證據鏈

### 10.1 一張固定的檢查清單

每次先記錄“在哪個目錄、執行了什麼命令、用了哪個解釋器、錯誤最後一行是什麼”，再分析。

```bash
pwd
uv run --locked python -c "import os, sys; print(os.getcwd()); print(sys.executable); print(sys.version)"
uv tree
```

macOS/Linux 可用 `command -v uv` 檢查工具路徑；PowerShell 可用 `Get-Location` 和 `Get-Command uv`。不要只截圖編輯器紅色波浪線，卻遺漏實際命令與解釋器。

### 10.2 症狀、原因與驗證動作

| 症狀 | 先懷疑什麼 | 怎樣驗證，而不是猜測 |
| --- | --- | --- |
| `uv: command not found` | 工具未安裝或當前終端 PATH 未更新 | 檢查安裝結果和命令路徑，必要時重新打開終端 |
| 找不到 `pyproject.toml` 或運行了別的項目 | 當前目錄錯誤 | 查看工作目錄和文件樹，進入本章項目根目錄 |
| `--locked` 報鎖文件不匹配 | 配置被修改、鎖文件缺失或版本不一致 | 比較聲明與鎖文件；決定是恢復參考狀態，還是有意重新解析 |
| `No module named pytest` | 沒安裝開發依賴，或解釋器選錯 | 用項目的 `uv sync --locked`，再用相同環境的 `python -m pytest` |
| 編輯器能補全，終端卻導入失敗 | 兩邊使用了不同解釋器 | 比較 `sys.executable` 與編輯器選擇的 `.venv` 解釋器 |
| `FileNotFoundError` | 文件缺失，或代碼把相對路徑基準理解錯了 | 看異常中的真實路徑，檢查 `tasks.json` 是否與源碼一起存在 |
| `JSONDecodeError` | 數據文件不符合 JSON 語法 | 依據行列號檢查引號、逗號、布爾值；不要先懷疑包版本 |
| `NameError` | 名稱未定義、拼寫錯誤或漏導入 | 看調用位置與當前文件的定義，不依賴之前運行過另一個代碼塊 |
| `IndentationError` | Python 代碼塊縮進不合法 | 檢查前後塊級關係和 Tab/空格，而非只調整報錯行 |

### 10.3 怎樣讀 traceback？

你可以在練習副本中暫時把 `json.loads(...)` 的 `json` 改成 `jsno`。錯誤最後一行會說明是未定義名稱；向上看對應文件和行號，定位是誰調用了它。修復後再運行，而不是把整段代碼包進 `try/except`。

traceback 是執行路徑的線索，不是一段應當隱藏的噪聲。在未來的服務端代碼裡，我們會學習如何保留服務端排錯信息，同時不把內部堆棧和秘密返回給客戶端。當前先把“能夠讀懂錯誤”作為能力，而不是以“終端裡從不出現錯誤”為目標。
