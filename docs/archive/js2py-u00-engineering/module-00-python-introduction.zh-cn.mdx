## 1. 这不是一张安装命令清单

你已经能搭建前端项目、处理组件之间的数据流，也知道如何用 Promise 和 async/await 对接接口。因此，本章不会从“变量是什么”讲起，也不会假定你已经写过 Express 服务、设计过数据库或管理过服务器。

我们要补上一个经常被教程跳过的环节：**当你在终端输入一条 Python 命令时，到底是谁在运行代码，它从哪里找到依赖，又为什么会出现“编辑器不报错，终端却无法导入”的情况？** 如果这些问题没有弄清，后面学 FastAPI 时，环境、代码与服务端概念会混在一起，排错只能靠反复重装。

本章的产物是一个很小但完整的本地项目：它读取一份任务清单，输出完成情况，并有自动化测试。功能刻意保持简单，让你把注意力放在运行过程与工程习惯上。它不是 Web 服务，也没有用户、数据库或输入验证；这些会在后面的章节逐层加入，而不是在第一课留下几个省略号就当作完成。

### 1.1 学完之后，应该能独立回答什么？

- Python 语言、CPython 解释器、uv 和 FastAPI 分别负责什么？
- 为什么电脑能找到 Python，不代表当前项目能导入某个包？
- `.venv`、`.python-version`、`pyproject.toml` 和 `uv.lock` 为什么不是同一种东西？
- 同一份文件，直接执行和被 `import` 时有什么不同？
- 遇到错误时，怎样先收集证据，再判断是目录、解释器、依赖还是业务代码的问题？
- 隔了两周回到项目，怎样恢复环境并确认程序仍然正确？

不要求你现在理解每一种 Python 语法。可以先把少量陌生写法与熟悉的 JS 对照起来；本章会解释运行本例所必需的部分，下一章再系统展开语言差异。

### 1.2 本章的运行约定

| 内容 | 在哪里执行 | 不代表什么 |
| --- | --- | --- |
| `bash` 命令 | 本地终端，位于说明指定的目录 | 不是粘贴到 `.py` 文件中的 Python 代码 |
| `main.py` 与测试 | 本地 CPython 3.13，由 uv 选择项目环境 | 不是网页中的 Pyodide 环境 |
| JSON、TOML、锁文件 | 按文件名保存，由相应工具读取 | 不是可以交给 Python 解释器的脚本 |
| JS/Python 对照 | 帮助理解同一个行为，可复制到相应本地环境 | 不要求你先实现一个 Node.js 后端 |
| 标明“故障实验”的步骤 | 仅在本章练习目录中操作，随后恢复 | 不是生产系统的操作建议 |

浏览器里的 Python 适合短小的语法实验，但它不等于你的电脑，也不自动具备数据库、服务器端依赖和真实文件目录。本章所有项目验收都以本地运行结果为准。

## 2. 先建立心智模型：四个容易混淆的层次

前端工具已经帮你处理了很多工作。执行 `pnpm dev` 时，你通常不需要每次思考 Node 的路径、包的查找方式和构建工具的入口。切换生态后，这些便利背后的分工值得重新看一遍。

### 2.1 语言不是解释器，框架也不是解释器

**Python** 是语言：规定函数、对象、异常、模块等语法和行为。**CPython** 是本课程使用的语言实现：你执行的 `python` 通常指向它的可执行文件。它读取源码，完成解析、执行等工作。

**uv** 是工程工具，帮助选择 Python 版本、管理项目环境、解析和安装依赖、执行项目命令。它不替代 Python 语言，也不会替你实现业务逻辑。

**FastAPI** 是后面才会安装的库/框架。它让 Python 程序以一套结构处理 HTTP 请求。真正启动 API 服务时，还会涉及 ASGI 服务器，例如 Uvicorn。不要把这些名称理解成几种竞争关系的“Python 运行方式”。

```text
终端
  └─ uv run：找到项目，准备它的环境，选择解释器
       └─ CPython：执行 main.py
            ├─ 导入标准库 json、pathlib
            ├─ 读取 tasks.json
            └─ 执行业务函数并输出结果
```

在这个流程里，uv 不理解“任务完成了几个”；Python 不替你决定依赖该锁在哪个版本；将来 FastAPI 也不会自动替你决定谁有权读取某个用户的数据。学习后端的一部分，就是逐渐理解这些职责边界。

### 2.2 与前端经验的对应关系，要连同边界一起记

| 熟悉的概念 | 本课程中的对应物 | 类比的边界 |
| --- | --- | --- |
| JavaScript 与 Node.js | Python 与 CPython | 语言与运行时的职责可以类比，不代表执行模型完全相同 |
| `package.json` | `pyproject.toml` | 都可声明项目依赖，但字段规范和工具行为不同 |
| `pnpm-lock.yaml` | `uv.lock` | 都记录依赖解析结果；不要把宽松的版本范围误当锁文件 |
| `node_modules` | `.venv` 中安装的包 | `.venv` 还关联 Python 解释器；二者不是完全同构的目录 |
| `.nvmrc` | `.python-version` | 都可表达项目版本偏好，但不单独承担依赖锁定 |
| `pnpm exec ...` | `uv run ...` | 都便于使用项目工具；uv 还可在运行前同步环境 |
| ESLint / Prettier | Ruff 检查 / 格式化 | 检查风格不等于验证业务行为，测试仍不可缺少 |

### 2.3 为什么不先让你比较所有包管理器？

你可能听过 pip、venv、virtualenv、Poetry、pyenv、pip-tools 和 uv。它们有历史原因和不同职责，不是“全都安装一遍，项目才专业”。

本课程先选 **uv 作为唯一操作主线**，同时解释虚拟环境和依赖声明的原理。你以后接手使用 pip 或 Poetry 的仓库时，可以依据这些原理理解它们，而不是重新建立一套完全不同的知识。

pip 并没有“过时”，venv 也不是“不能用”。收敛工作流，是为了让首次学习后端时的变量更少。不要在同一个练习环境里无目的地轮流使用多个工具安装、升级和卸载包。

## 3. Python 版本与虚拟环境：到底隔离了什么？

### 3.1 一台电脑为什么可能有不止一个 Python？

操作系统、Homebrew、其他工具和你自行安装的版本，都可能提供名为 `python` 或 `python3` 的命令。终端根据 `PATH` 查找可执行文件；编辑器还可能独立保存一个解释器路径。因此，“终端显示 3.13”和“编辑器使用 3.13”不是天然等价的。

先记住一个比猜测更可靠的办法：**让正在运行的 Python 报告它自己的路径。**

```bash
uv run --locked python -c "import sys; print(sys.executable); print(sys.version)"
```

这条命令在稍后准备好的练习项目里执行。`-c` 后面是一小段 Python；`sys.executable` 是当前进程的解释器路径，`sys.version` 是当前解释器的版本信息。它们是观察结果，不是编辑器状态栏的推测。

本章采用 CPython **3.13** 作为教学版本线，不意味着它永远是“最新版本”。补丁版本可以变化；若需更严格的复现，可以将 `.python-version` 固定为经过测试的具体补丁版本。后端项目升级解释器时，也要重新运行测试，而不是只修改版本数字。

### 3.2 `.venv` 不只是一个装包的文件夹

假设项目 A 依赖某库的一个版本，项目 B 依赖另一个版本。如果都安装到同一个共享环境，你在维护 B 时，可能无意改变 A 的运行条件。虚拟环境为项目提供独立的包安装位置与解释器入口，避免这种日常冲突。

但“环境隔离”不等于安全沙箱。程序仍然可能访问当前用户有权限访问的文件和网络；虚拟环境不会自动隔离数据库，更不会阻止代码删除文件。

还要区分“创建环境”和“激活环境”。激活通常只是让当前终端优先找到该环境里的命令。**使用 `uv run` 不要求先手动激活**，因为 uv 会为命令选择项目环境。先采用这一种方式，避免把激活状态当作额外的隐藏条件。

准备好项目后可以观察：

```bash
uv run --locked python -c "import sys; print(sys.prefix); print(sys.base_prefix)"
```

在本课程的虚拟环境中，两者应不同：前者指向当前环境，后者关联基础解释器。具体路径因电脑而异，不需要与书中的路径一字不差。

> 不要通过修改系统 Python、使用 `sudo pip install` 或关闭系统保护来解决项目依赖问题。先检查当前解释器与当前项目，再决定操作。

## 4. 安装工具，并先运行一份已知正确的项目

### 4.1 安装 uv 与 Python

本章以 macOS 为主。若你已经使用 Homebrew，可以执行：

```bash
brew install uv
uv --version
uv python install 3.13
```

第一条安装工程工具，第二条确认终端能找到它，第三条安装课程采用的解释器版本线。这不是给现有系统 Python 做原地升级。

如果没有 Homebrew，或者使用 Windows/Linux，请从 [uv 官方安装指南](https://docs.astral.sh/uv/getting-started/installation/)选择对应方法。安装脚本会修改本机环境，应阅读其说明；不要为了照搬本章而额外搭建一套自己不用的系统工具链。

Windows 可使用 PowerShell 运行项目命令；后面涉及 `pwd`、`command -v` 等诊断时，书中会同时给出相应说明。

[下载本章完整练习工程](/learning-assets/js2py/u00-environment.zip)。解压后进入 **包含 `pyproject.toml` 的 `u00-environment` 目录**，不是它的上一级下载目录。

你也可以在本站源码中的 `examples/js2py/u00-environment` 找到同一份文件。网页展示代码和下载包都来自这些源文件，避免“书上一个版本，下载包另一个版本”。

### 4.3 第一次复现

依次执行，每条完成后再看下一条：

```bash
uv sync --locked
uv run --locked python main.py
uv run --locked python -m pytest -q
uv run --locked ruff check .
uv run --locked ruff format --check .
```

`uv sync --locked` 根据已有声明和锁文件准备环境，并要求它们保持一致。如果锁文件缺失或过期，命令应失败，而不是悄悄更新后装作复现成功。首次运行可能下载解释器或包，具体日志随系统与缓存状态变化。

运行应用应得到：

```text
Tasks: 3 | Done: 1 | Pending: 2
```

默认测试应全部通过，共 **6 个测试用例**。耗时和终端进度符号可能不同；重要的是退出码为零、没有失败，而不是打印内容逐字一样。

Ruff 的检查和格式化检查解决的是另一类问题：它们不保证任务计数正确。反过来，测试通过也不证明导入顺序和格式统一。这几条命令各自负责一个边界。

如果这一步失败，先阅读第 10 节的诊断方法。不要一边改变 Python 版本、一边升级依赖、一边修改程序；同时改变多个条件，会让你无法知道哪个动作真正解决了问题。

## 5. 四份配置文件，逐个解释

### 5.1 `.python-version`：选择哪条解释器版本线

<Code language="text">{getU00Example('.python-version')}</Code>

这告诉 uv 在本项目中选择 Python 3.13。它不是 Python 代码，也不是依赖清单。只修改它，并不会自动保证你的库和业务代码兼容另一个 Python 版本。

### 5.2 `pyproject.toml`：项目声明，而非安装结果

<Code language="toml">{getU00Example('pyproject.toml')}</Code>

逐段看，而不是把整段当成必须背下来的模板：

- `[project]` 描述项目。这里的版本是**这个练习项目的版本**，不是 Python 或 FastAPI 的版本。
- `requires-python = ">=3.13,<3.14"` 表达本章验证的解释器范围。它与 `.python-version` 分别承担“允许范围”和“本地选择”的职责。
- `dependencies = []` 表示当前程序只用标准库，不需要额外的运行时包。以后加入 FastAPI 时，应用依赖才会增加。
- `[dependency-groups]` 中的 `dev` 包含开发与测试工具。pytest 和 Ruff 不是当前业务函数运行所必需的库。
- `[tool.pytest.ini_options]` 将默认测试范围限定为 `tests`，因此尚未完成的挑战题不会让基线测试失败。
- `[tool.ruff]` 和 `[tool.ruff.lint]` 配置本项目的代码工具，不改变 Python 语言本身的语义。

这里的文件夹名称不要求等于项目名；名字中的连字符也不意味着你可以写 `import js2py-u00-environment`。发行项目名称、目录名称与 Python 导入名称是不同层次，后面的模块章节会继续展开。

### 5.3 `uv.lock`：记录解析后的选择

`pyproject.toml` 里的范围可能允许多个版本。不同时间重新解析这些范围，结果可能不同；依赖的依赖也会影响结果。`uv.lock` 记录 uv 的解析选择与相关信息，便于其他环境按照相同的依赖决策安装。

不需要手工阅读并维护锁文件的每一行。可以观察依赖关系：

```bash
uv tree
```

你可能看到 pytest 的间接依赖。不要因为自己没有直接安装过这些名字，就认定环境被污染；先看它们是否是项目依赖图的一部分。

锁文件也不是整台电脑的快照：操作系统、CPU 架构、外部数据库、系统库和 Python 补丁版本仍可能影响行为。复现是一组约束与验证，不是一份文件替代一切。

### 5.4 `.gitignore`：哪些是声明，哪些是机器生成物？

<Code language="text">{getU00Example('.gitignore')}</Code>

源码、配置声明、`.python-version` 和锁文件应进入版本管理。`.venv` 与缓存由工具生成，不应该作为环境交接方式；真实 `.env` 也不应提交。将来要分享配置格式时，提交只有占位值的示例配置，而不是复制个人的秘密。

“同事把整个虚拟环境压缩给我”不等于可复现工程。环境可能包含本机路径和平台相关文件，正确的交接物应该是可重新创建环境的声明、锁文件和验证步骤。

## 6. 现在从空目录搭一次，而不只是使用下载包

已知正确的项目帮助你排除环境障碍；从空目录重建，则能检查你是否理解每个组成部分。

在一个新的练习位置执行，不要覆盖刚才已运行成功的参考工程：

```bash
uv init --bare --vcs none --python 3.13 taskboard-lab
cd taskboard-lab
uv python pin 3.13
```

`--bare` 只生成最小项目声明，避免自动生成的其他文件干扰本章解释；`--vcs none` 不额外初始化 Git，方便你在已有学习仓库中练习。之后可以按自己的版本管理习惯加入 Git。

将第 5 节给出的完整 `pyproject.toml` 保存到新目录，再按后文创建 `main.py`、`tasks.json` 和 `tests/test_main.py`。此时还没有锁文件，首次执行：

```bash
uv sync
```

这里不用 `--locked`，因为现在是在**创建**依赖解析结果，不是在验证已有锁文件。首次成功后，后续复现和验收改用 `uv sync --locked`。不要为了让锁文件错误消失，永远把 `--locked` 删除；应该判断当前是在有意修改依赖，还是本应复现一个既定环境。

如果你不想手写开发依赖声明，也可以在新建项目里运行 `uv add --dev pytest ruff`，由工具更新声明与锁文件。但这样得到的版本范围可能与参考工程不同。本章使用下载包中的锁文件作为已验证的参考，而不是承诺所有未来版本结果相同。

## 7. 完整程序：先运行，再逐步理解

### 7.1 输入文件 `tasks.json`

<Code language="json">{getU00Example('tasks.json')}</Code>

这里使用 JSON 的 `true` 和 `false`。Python 的布尔字面量则是 `True` 和 `False`。为什么文件里仍然能写小写？因为它是交给 JSON 解析器读取的数据，不是作为 Python 源码执行。

这也是本章反复强调“文件类型”的原因：依赖声明、JSON 数据和程序都可能是纯文本，但它们由不同规则解释。

### 7.2 业务与入口文件 `main.py`

<Code language="python">{getU00Example('main.py')}</Code>

不要急着把整段记下来。沿着执行过程观察：

**第一步：导入标准库。** `json` 负责把 JSON 文本解析为 Python 对象；`Path` 帮助表达和操作文件路径。它们属于当前 Python 的标准库，不需要 `uv add json` 或 `uv add pathlib`。

**第二步：确定数据文件的位置。** `__file__` 表示当前模块文件的位置。`Path(__file__).with_name("tasks.json")` 取得与这个文件同目录的任务文件，而不是假定终端当前目录永远正确。这个规则针对本例的本地文件布局；并不是在承诺一切部署形式都可以这样访问资源。

**第三步：定义业务函数。** `def build_report(tasks):` 定义一个函数，定义时不会立即遍历任务。`completed = 0` 是局部变量；`for task in tasks` 遍历列表；`if task["done"]` 判断完成状态；缩进表达代码块。这里没有 `self`，因为它是普通函数，不是实例方法。

**第四步：返回而不是直接打印。** `build_report` 返回字符串，`main` 再负责打印。把计算与输出分开后，测试可以直接比较返回值，不必为每次业务判断启动一个终端进程。

**第五步：读取和解析数据。** `read_text(encoding="utf-8")` 得到字符串，`json.loads(...)` 再得到列表和字典。文本内容、解析后的对象、最终报告是不同阶段，不要把它们当作同一份数据的不同叫法。

**第六步：选择何时真正运行入口。** 当文件作为脚本执行时，`__name__` 为 `"__main__"`，底部条件成立，调用 `main()`。当测试导入这个模块时，模块仍会执行顶层语句并建立函数定义，但条件不成立，不会自动读取任务并打印报告。

这种入口保护不意味着“import 不执行任何代码”。它只控制条件内部的调用。如果你把网络请求或文件读取写在条件外，导入时仍可能发生副作用。

### 7.3 用熟悉的 JS 看同一个业务函数

下面是静态语言对照，使用同一份可信输入；完整本地运行方式已经在前面给出。这里没有 Node 服务，也没有数据库。

<PythonEditor title="同一份任务清单，两种计数实现（本地对照）" compare={true} canRun={false} height={430}>
```javascript !! js
function buildReport(tasks) {
  let completed = 0;
  for (const task of tasks) {
    if (task.done) {
      completed += 1;
    }
  }
  const total = tasks.length;
  return `Tasks: ${total} | Done: ${completed} | Pending: ${total - completed}`;
}

console.log(buildReport([{ done: true }, { done: false }]));
```

```python !! py
def build_report(tasks):
    completed = 0
    for task in tasks:
        if task["done"]:
            completed += 1
    total = len(tasks)
    return f"Tasks: {total} | Done: {completed} | Pending: {total - completed}"

print(build_report([{"done": True}, {"done": False}]))
```
</PythonEditor>

两边的预期结果都是 `Tasks: 2 | Done: 1 | Pending: 1`。值得注意的是字典取值、布尔字面量、`len`、缩进与 f-string，而不是“Python 就是把分号删掉的 JS”。下一章还会看到真值、默认参数、对象共享等不能直接照搬的语义。

### 7.4 当前程序的边界在哪里？

本例信任随课提供的 JSON：每项都有合法的 `done` 字段。它没有验证任意输入，也没有把修改写回文件。因此它是**完整的环境与执行练习**，不是完整的任务管理产品。

如果输入缺少字段，你可能遇到 `KeyError`；如果 JSON 损坏，解析会失败。我们会在后续学习异常与输入边界时改进它。这里不使用一个宽泛的 `except Exception: pass` 假装程序已经健壮，否则真实问题反而被隐藏。

### 8.1 为什么六个测试不是重复劳动？

前四个用例分别检查空列表、全部完成、全部未完成与混合状态。`@pytest.mark.parametrize` 让同一项断言接受多组输入；可以把它先理解成“把这几个例子分别交给同一套验收逻辑”。装饰器的具体机制稍后再学，不需要为了运行第一章先完成高级函数课程。

第五个用例从另一个当前目录启动程序，用于验证数据文件定位。第六个用例只执行 `import main`，用于确认导入不会顺带打印报告。它们在检查工程行为，而不只是业务计算。

`sys.executable` 让子进程使用当前测试环境的同一个解释器，避免机器上另一个名为 `python` 的命令混进验收。`tmp_path` 由 pytest 提供临时目录，不是在真实项目里删除或移动文件。

### 8.2 为什么写 `python -m pytest`？

这会用 uv 选择的 Python 解释器来运行 pytest 模块。这样“测试工具装在哪”和“测试由谁执行”之间的关系更明确。在本章简单的根目录布局下，它也使从项目根目录导入 `main` 的行为容易理解。

这不是说直接运行 `pytest` 永远错误，而是为刚进入 Python 生态的读者固定一条容易诊断的路径。以后学习包结构后，再比较不同入口与导入方式。

### 8.3 做一次能恢复的失败实验

在自己的练习副本中，把业务函数里的 `pending = total - completed` 暂时改成 `pending = total`，再执行默认测试。

你应该看到具体的断言差异，而不是一句模糊的“程序不对”。先指出哪个输入暴露了问题，再恢复原实现并重新测试。如果没有任何失败，说明你很可能改了另一份文件，或者运行了另一个目录里的测试。

**不要改期望值来迁就错误实现。** 测试代表这里已经确定的业务规则；当需求真的改变时，才应同时审查规则、实现与验收。

## 9. 依赖维护不是“缺什么就全局安装什么”

当后续项目需要一个新库时，应在项目目录中使用 `uv add 包名`，开发工具则使用 `uv add --dev 包名`。这不仅是把文件下载到环境中，还要更新可交接的项目声明与锁文件。

本章不需要额外安装 HTTP 库。若你想观察依赖变化，可以在**单独的练习副本**中用 `uv add httpx`，查看配置和 `uv tree` 的变化，再用 `uv remove httpx` 恢复。这只是工具练习，不会自动让当前程序变成后端服务。

还要区分三件事：

1. **同步环境**：使当前环境符合项目声明和既有锁文件。
2. **新增依赖**：有意改变项目需要的库，再审查声明和锁文件变化。
3. **升级依赖**：有意改变允许或选中的版本，并重新运行测试。

遇到导入失败时直接升级所有包，会把问题定位和依赖升级混成一次高风险操作。先证明缺少的是哪个包、当前使用的是什么解释器，再做最小改动。

uv 创建的环境也不保证预装 pip。如果 `python -m pip` 提示找不到模块，不等于整个 Python 已损坏；本课程的包操作由 uv 管理。以后在使用 pip 的项目里，再按那个项目的流程配置它。

## 10. 排错不是记住错误名，而是建立证据链

### 10.1 一张固定的检查清单

每次先记录“在哪个目录、执行了什么命令、用了哪个解释器、错误最后一行是什么”，再分析。

```bash
pwd
uv run --locked python -c "import os, sys; print(os.getcwd()); print(sys.executable); print(sys.version)"
uv tree
```

macOS/Linux 可用 `command -v uv` 检查工具路径；PowerShell 可用 `Get-Location` 和 `Get-Command uv`。不要只截图编辑器红色波浪线，却遗漏实际命令与解释器。

### 10.2 症状、原因与验证动作

| 症状 | 先怀疑什么 | 怎样验证，而不是猜测 |
| --- | --- | --- |
| `uv: command not found` | 工具未安装或当前终端 PATH 未更新 | 检查安装结果和命令路径，必要时重新打开终端 |
| 找不到 `pyproject.toml` 或运行了别的项目 | 当前目录错误 | 查看工作目录和文件树，进入本章项目根目录 |
| `--locked` 报锁文件不匹配 | 配置被修改、锁文件缺失或版本不一致 | 比较声明与锁文件；决定是恢复参考状态，还是有意重新解析 |
| `No module named pytest` | 没安装开发依赖，或解释器选错 | 用项目的 `uv sync --locked`，再用相同环境的 `python -m pytest` |
| 编辑器能补全，终端却导入失败 | 两边使用了不同解释器 | 比较 `sys.executable` 与编辑器选择的 `.venv` 解释器 |
| `FileNotFoundError` | 文件缺失，或代码把相对路径基准理解错了 | 看异常中的真实路径，检查 `tasks.json` 是否与源码一起存在 |
| `JSONDecodeError` | 数据文件不符合 JSON 语法 | 依据行列号检查引号、逗号、布尔值；不要先怀疑包版本 |
| `NameError` | 名称未定义、拼写错误或漏导入 | 看调用位置与当前文件的定义，不依赖之前运行过另一个代码块 |
| `IndentationError` | Python 代码块缩进不合法 | 检查前后块级关系和 Tab/空格，而非只调整报错行 |

### 10.3 怎样读 traceback？

你可以在练习副本中暂时把 `json.loads(...)` 的 `json` 改成 `jsno`。错误最后一行会说明是未定义名称；向上看对应文件和行号，定位是谁调用了它。修复后再运行，而不是把整段代码包进 `try/except`。

traceback 是执行路径的线索，不是一段应当隐藏的噪声。在未来的服务端代码里，我们会学习如何保留服务端排错信息，同时不把内部堆栈和秘密返回给客户端。当前先把“能够读懂错误”作为能力，而不是以“终端里从不出现错误”为目标。
