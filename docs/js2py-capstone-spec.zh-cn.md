# js2py 贯穿项目与毕业验收：协作任务管理 API

初版：2026-09-23；更新：2026-09-28。状态：本规范定义学习交付目标；分阶段教材和实验不等于一个已经替读者完成毕业验收、可以直接公开运行的最终产品。G01 已提供独立需求与证据包，读者应用和真实试用仍须自己完成并验证。

关联：[审查报告](/Users/mikmyp/Documents/code-projects/langshift.dev/docs/js2py-curriculum-audit.zh-cn.md)、[学习路线](/Users/mikmyp/Documents/code-projects/langshift.dev/docs/js2py-learning-path.zh-cn.md)。技术依据沿用审查报告 S01—S22；以下业务规则与门槛是本课程的设计选择。

## 1. 为什么选这个项目

读者未指定业务类型，因此默认采用“多人协作任务管理”作为可替换的教学题材。它与前端经验容易衔接，并能自然覆盖用户、数据关系、权限、查询、测试、迁移与上线。

不要求重新制作复杂前端：API 文档、请求集合或一个简单的现有前端界面足够。重点始终是后端，不是把精力转回熟悉的 UI 工程。

如果以后换成书签、笔记或团队知识库，也应保留等价的多用户权限、数据一致性、测试和交付验收。

## 2. 首版边界

### 必须实现

- 受控创建用户、登录、修改密码、停用用户、退出全部会话。
- 创建项目，管理项目成员，区分负责人和普通成员。
- 任务创建、读取、筛选、分页、修改和删除。
- PostgreSQL 持久化、约束、迁移和事务。
- 自动化测试、CI、生产配置、HTTPS、日志、备份恢复。
- 少量受邀用户的真实试用，以及至少一次依据反馈完成的迭代。

### 首版不做

公开自助注册、完整邮件找回、第三方登录、支付、复杂文件上传、实时聊天、微服务、多地域、高可用集群、必须依赖外部 API 的核心功能。

**“受邀用户真实可用”不等于“面向所有人的公共注册产品已准备完成”。** 若开放自助注册，需另补验证与找回、反滥用、配额、账号生命周期等设计和测试。

## 3. 分阶段的项目形态

| 检查点 | 形态 | 教学目标 | 是否可上线给真实用户 |
| --- | --- | --- | --- |
| V0 | Python 业务函数与 JSON 文件 | 语言、模块、异常、测试 | 否 |
| V1 | FastAPI + 内存数据 | HTTP、验证、响应、路由 | 否，数据会丢失且无完整权限 |
| V2 | PostgreSQL + 迁移 | 持久化、约束、事务 | 否，先完成认证与权限 |
| V3 | 用户与对象级授权 | 多用户安全边界 | 尚需部署与运维验收 |
| V4 | 完整测试、部署、恢复演练 | 受控真实使用 | 通过发布清单后可以 |
| V5 | 无逐步教程的新需求 | 独立开发能力 | 通过相同发布流程再上线 |

每个检查点应有可运行的参考状态、读者任务和测试，不能只有一个最终大仓库让读者倒推过程。H 阶段的 `/tasks` 内存模型会在 D 阶段明确演进为项目/成员/关系型任务模型；A 的故障替身和 O 的运维切片是有边界的实验，不能拿它们覆盖已经实现的身份、权限或业务逻辑。独立毕业项目需要把已学能力落实到自己的完整服务。

## 4. 核心数据模型

| 模型 | 关键字段 / 关系 | 约束与规则 |
| --- | --- | --- |
| User | ID、登录标识、密码哈希、启用状态、auth_version、时间戳 | 登录标识唯一；哈希和认证版本不出现在普通响应里 |
| Project | ID、名称、创建者、时间戳 | 创建者成为负责人；首次建项目和负责人关系必须原子提交 |
| ProjectMember | project_id、user_id、角色 | 成员关系唯一；角色仅 owner/member；首版不提供负责人转移，拒绝移除负责人 |
| Task | ID、project_id、创建者、标题、描述、状态、可选截止时间、时间戳 | 项目与创建者必须存在；状态有明确允许集合；创建者由服务器确定 |

建议业务规则：

- 任务状态为 todo / doing / done；空白标题不合法，标题与描述有长度上限。
- 时间保存与 API 表达采用明确的时区策略，避免本地无时区时间与 UTC 混用。
- ID 由数据库或合适的 UUID 策略生成，不用当前秒数假装唯一。
- 数据库约束是底线，应用层负责友好的业务错误；两者不能互相替代。
- 首版不允许把任务直接迁移到其他项目，避免引入未讲清楚的跨项目权限变化。
- 项目删除若包含成员/任务，须定义事务内删除规则并要求负责人确认；不能靠捕获任意异常后静默跳过。

## 5. 权限矩阵

| 操作 | 未登录 | 非项目成员 | 普通成员 | 项目负责人 |
| --- | --- | --- | --- | --- |
| 创建自己的项目 | 拒绝 | 登录用户可创建 | 可 | 可 |
| 列出项目 | 拒绝 | 只列本人参与的项目 | 同左 | 同左 |
| 读取项目/任务 | 拒绝 | 拒绝 | 可 | 可 |
| 创建任务 | 拒绝 | 拒绝 | 可，创建者为本人 | 可，创建者为本人 |
| 修改/删除任务 | 拒绝 | 拒绝 | 仅本人创建的任务 | 可管理项目内全部任务 |
| 修改/删除项目 | 拒绝 | 拒绝 | 拒绝 | 可 |
| 增加/移除普通成员 | 拒绝 | 拒绝 | 拒绝 | 可，但不能移除负责人 |

权限基于服务器读取的用户与成员关系，不信任前端隐藏按钮，也不信任请求体自报角色。

对无权知道是否存在的项目/任务，可以统一返回 404；对已知项目中的受限操作返回 403。该策略必须在契约中一致，并由测试验证，不能任意混用。

必测：列表泄露、直接修改 URL 中的 ID、提交别人的 user_id、对子资源绕过父资源校验、成员被移除后的访问。

## 6. 建议接口范围

这些是课程业务契约，不是必须采用的唯一 REST 风格。

| 接口 | 用途 | 关键失败路径 |
| --- | --- | --- |
| POST /auth/token | 登录取得短期访问凭证 | 错误凭据、停用用户、限流 |
| POST /auth/logout-all | 当前用户使既有凭证全部失效 | 缺少/非法凭证 |
| GET /users/me | 读取当前用户资料 | 过期或失效凭证 |
| POST /users/me/password | 校验旧密码并修改密码 | 旧密码错误、新密码不满足策略 |
| POST /projects | 建立项目及负责人关系 | 输入错误、事务失败 |
| GET /projects | 列出本人参与的项目 | 非法分页参数 |
| GET/PATCH/DELETE /projects/{project_id} | 读取或管理项目 | 不存在、非成员、权限不足 |
| GET/POST /projects/{project_id}/members | 查看或增加已有用户为成员 | 非负责人、重复关系、用户不存在 |
| DELETE /projects/{project_id}/members/{user_id} | 移除成员 | 非负责人、试图移除负责人 |
| GET/POST /projects/{project_id}/tasks | 筛选/分页或创建任务 | 非成员、非法状态、超限参数 |
| GET/PATCH/DELETE /projects/{project_id}/tasks/{task_id} | 操作具体任务 | 任务不属于该项目、非创建者且非负责人 |
| GET /health/live | 判断应用进程是否能响应 | 不暴露配置或秘密 |
| GET /health/ready | 判断关键依赖是否可用 | 数据库不可达时返回非就绪 |

不在首版暴露公开用户注册与任意用户列表。管理命令和测试数据准备应与公开 API 分开。

状态码约定：创建通常 201，成功删除可用 204，未认证 401，授权失败按上节的 403/404 策略，重复/业务冲突 409，输入结构或约束错误 422。响应错误不能直接返回数据库异常、堆栈或秘密。

分页需设上限，并提供稳定排序；可从 offset/limit 开始，先说清并发写入时的局限，不强制首版实现游标分页。

## 7. 认证与安全的最低教学边界

此处是首版的设计范围，不是一次完整安全审计或对任意生产场景的安全保证。

- 使用经维护的密码哈希库与 JWT 库，不自行拼接签名和哈希协议。教学依托 FastAPI 官方安全资料，另加真实数据库与授权校验（报告 S09/S10）。
- 短期访问令牌应有过期时间；验证签名并限制预期算法，明确接受的声明。JWT 不是加密容器，不放密码或敏感业务数据。
- 每次受保护请求检查用户启用状态与认证版本；修改密码、停用用户和退出全部会话有明确失效策略。
- 首版可以不做刷新令牌，过期后重新登录。若增加刷新机制，需要单独设计存储、轮换、撤销与重复使用检测。
- 测试用前端可将短期 Bearer Token 保存在内存；不要把长期 Token 放入 localStorage 作为无条件推荐。改为 Cookie 方案时另补 CSRF、SameSite、Secure、HttpOnly 的完整设计。
- HTTPS 是发布前提；秘密从运行环境注入，演示配置只有占位值；日志与错误报告须脱敏。
- 登录失败不泄露账号是否存在；有可测试的速率限制和合理请求大小限制。若由网关/平台实现，也要记录配置并验证。
- CORS 仅允许需要的前端来源，不能把它当作认证或授权措施。
- 受控创建账号需明确初始凭据的安全交付与首次改密流程，不能把默认账号密码提交到仓库。
- 首批试用不使用敏感个人信息或高价值业务数据；用户反馈不应包含凭证。

## 8. 自动化验收场景

每个场景需要可重复的测试或明确的运行证据，不以覆盖率数字替代。

### 功能与协议

- [ ] 正常任务 CRUD；更新与读取结果一致。
- [ ] 空标题、非法状态、超长输入、非法分页参数被拒绝。
- [ ] PATCH 漏传字段与显式 null 被正确区分。
- [ ] 响应模型没有额外泄漏内部字段。
- [ ] 分页采用稳定排序，过滤条件组合有测试。

### 数据与迁移

- [ ] 应用重启后数据仍存在。
- [ ] 重复用户/成员关系被数据库约束拒绝，错误转成可理解的响应。
- [ ] 项目建立失败时不存在“只有项目、没有负责人”的半完成状态。
- [ ] 失败事务回滚后，该请求资源被释放，后续请求可正常运行。
- [ ] 空数据库能按迁移创建结构；已有数据能执行至少一次非破坏性升级。
- [ ] 迁移自动生成内容经人工检查；不以 create_all 代替升级历史。

### 身份与授权

- [ ] 正确登录成功；错误密码、过期/篡改凭证、停用账号被拒绝。
- [ ] 密码修改与退出全部会话使旧 Token 按策略失效。
- [ ] Alice 无法读取、修改或枚举 Bob 的私有项目及任务。
- [ ] 修改 URL 父项目 ID 或请求体身份字段无法绕过权限。
- [ ] 普通成员无法管理成员或删除项目；不能移除负责人。
- [ ] 成员被移除后，已有登录凭证也不能继续访问项目。

### 工程与故障

- [ ] API/数据库测试使用专用数据库与测试账号，不触碰生产数据。
- [ ] 测试可反复运行，互不依赖执行顺序；外部服务默认使用替身。
- [ ] 外部调用超时/失败有明确行为，不拖垮核心 CRUD。
- [ ] 配置缺失导致清楚、脱敏的启动失败，而不是默默使用不安全默认值。
- [ ] CI 在干净环境安装锁定依赖，运行检查、测试、迁移验证与构建。

## 9. 真实上线验收

以下清单全部通过，才把 V4 提供给受邀用户。

### 可复现发布

- [ ] README 包含环境、启动、测试、迁移、配置说明与常见故障定位。
- [ ] 配置示例不含真实秘密；开发、测试、生产数据库明确隔离。
- [ ] 应用与迁移身份分离；按真实路由／作业收窄表和序列权限，并验证必要操作成功、不需要的修改／删除被拒绝。仅证明不能 ALTER/DROP，不等于已落实最小 DML 权限。
- [ ] 交付物能从干净环境构建，应用与数据库数据不依赖开发机临时目录。
- [ ] 发布前迁移独立受控执行，不让多个应用进程竞相执行结构变更。
- [ ] HTTPS、域名/代理与允许来源已经实测；生产不使用开发热重载流程。

### 可维护性

- [ ] 日志包含足够的请求关联信息，但没有密码、Token 与敏感正文。
- [ ] 有健康检查、错误观测和最基本的异常通知路径。
- [ ] 进程异常退出后可恢复；重启不会丢失已提交数据。
- [ ] 记录受控试用的容量/配额与已知限制，不承诺未做压测的并发能力。

### 数据恢复与回退

- [ ] 有定期备份、保留策略与备份访问控制。
- [ ] 真正从备份恢复到隔离数据库，并验证关键业务记录。
- [ ] 记录可接受数据丢失窗口与恢复时间目标，并根据演练修正，而非随意承诺。
- [ ] 演练应用版本回退；说明该回退是否兼容数据库结构。
- [ ] 对破坏性数据库变更先设计备份、迁移和恢复步骤；不承诺 downgrade 总能无损恢复。

恢复/破坏性演练只能在明确隔离的测试环境中进行，不拿真实用户数据做实验。开通云服务、域名或执行真实部署前，单独确认预算、账户与目标环境。

## 10. 毕业任务：只给需求，不给实现步骤

本书 G01 的正式验收包采用 **“任务评论”扩展**，详见 [G01 正文](/Users/mikmyp/Documents/code-projects/langshift.dev/content/docs/js2py/module-38-graduation.zh-cn.mdx) 与 [需求契约](/Users/mikmyp/Documents/code-projects/langshift.dev/examples/js2py/g01-graduation/requirements.json)。它给出作者/负责人权限、撤权、并发修改、撤回、重复请求、升级回退、隔离恢复与受邀反馈的要求，不提供表结构或实现步骤。24 个业务场景初始均为 `not_run`；材料格式检查器不运行学生后端，也不授予毕业或上线资格。

下面保留初版的 **“项目内任务标签”备选需求**。二者选其一，不要求重复做两份；选标签时也必须保持同等强度的权限、并发一致性、迁移、发布与恢复验收。不能因为备选列表文字较短就省掉这些责任。

在 V4 基础上增加“项目内任务标签”功能：

- 标签属于项目，同项目标签名不允许重复。
- 一项任务可以有多个标签；列表可以按标签筛选。
- 不允许把其他项目的标签附到本项目任务。
- 修改关系、删除标签、成员权限与已有任务数据有明确处理规则。

必须独立提交：

1. 数据关系与接口设计说明。
2. 可审查的数据库迁移。
3. 功能实现与权限检查。
4. 正常、非法输入、重复、跨项目越权和数据升级的测试。
5. 更新后的运行文档与一次发布记录。
6. 对一个自己遇到的问题的定位过程说明。

允许查文档和使用辅助工具，但不能仅交付无法解释的大段生成代码。验收时现场调整一个业务条件，观察是否仍能修改实现和测试。

## 11. 最终交付物

- 可独立运行的后端代码与锁定依赖。
- 数据模型、迁移历史和测试数据准备方式。
- API 契约、测试和持续集成配置。
- 部署地址、受控试用范围、运维/恢复说明。
- 已知限制、待办事项与独立功能的实现记录。

本规格不承诺课程完成后自然获得所有后端架构能力；它提供一个可检查的起点，之后再按真实需求扩展生态。
