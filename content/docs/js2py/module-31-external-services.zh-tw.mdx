## 1. 外部提示可以失敗，保存任務不能陪它失敗

場景是為任務提供可選的優先級提示。把遠端請求直接塞進創建任務的事務，外部服務一變慢，就可能讓連接、事務與請求一起長時間佔住。更危險的是，客戶端超時並不證明遠端沒發生效果；盲目重試可能重複發送通知或創建賬單。

本章先設計責任邊界：**核心 CRUD 自己完成；可選提示單獨查詢；一個應用生命週期擁有一個外部客戶端；一個請求只借用它**。我們不真實聯繫第三方，不上傳用戶任務正文，也不需要憑證。

## 3. 先沿著一條請求追蹤誰擁有什麼

瀏覽器/調用者 → 本地 FastAPI → 提示服務對象 → 共享 HTTPX 客戶端及其連接池 → 本地故障服務。響應反向迴流時，必須重新驗證外部數據，最後只返回允許的狀態與枚舉。

- 應用擁有客戶端、連接池和整個依賴的 semaphore；每次請求只是借用。
- 一次嘗試擁有 response stream，在任何退出路徑上關閉它。關閉響應不等於關閉共享客戶端；連接可能回到池中複用。
- 一次提示操作擁有排隊、重試、退避的總預算；核心 CRUD 不進入這條調用鏈。
- 服務停機時 lifespan 釋放應用級客戶端，而不是在某次請求後誤關其他請求正在借用的對象。

這與前端複用一個 API 客戶端有相似處，但服務器要併發借用、明確關池並處理停機取消。模塊 import 就創建客戶端，會讓所有權、運行循環與測試隔離變得含糊。每個請求都 `async with AsyncClient()` 又會不斷重建池，失去跨請求的連接複用。

## 4. 從 L14 的 with 到 async with：先講協議，再看裝飾器

L14 中 `@contextmanager` 把普通生成器適配成 with 的進入/退出協議。這裡只有一個必要變化：獲取或釋放可能需要 await，因此協議需要等待 `__aenter__` 與 `__aexit__`。`async with` 不會讓任意同步 close 自動非阻塞；被調用的實現必須提供相應異步行為。

`managed_client` 是帶 yield 的 async def，因此是**異步生成器函數**，不是 A01 中直接 await 得到結果的普通 coroutine function。`@asynccontextmanager` 把它適配成異步上下文管理器工廠，使用方式是 async with，而不是直接 await 這個管理器。

<Code language="python">{getExternalServiceExample('lifecycle.py')}</Code>

按順序讀一次：

1. validate_origin 在獲取資源前驗證配置。失敗時沒有客戶端，沒有進入塊，也沒有“等退出再補救”的機會。
2. 構造 AsyncClient 配置連接池；通常尚未建立實際網絡連接，連接會按請求需要創建。
3. 執行到唯一的 yield，把客戶端借給 async with 塊；此時管理器暫停，資源仍屬於它。
4. 塊正常結束則恢復 yield 後的代碼；塊拋異常/取消則在暫停點恢復相應異常路徑。無論哪種，finally 負責關閉。
5. `await client.aclose()` 完成後才結束退出階段。清理不是業務回滾，已經到達遠端的副作用不會因此消失。

裝飾器協議要求恰好 yield 一次；不 yield 或 yield 兩次都是協議錯誤。獲取多個資源時應逐個建立管理邊界，不能先獲取所有資源，賭最後一個 finally 能處理前面任何失敗。對照 L14 可以看到：異步化改變的是可等待的進入/退出，不是資源所有權原則。

## 5. finally 裡也可能等待：取消清理為何有一個小保護區

FastAPI/Starlette 的併發基礎會使用 AnyIO。這裡不用它堆出另一套 Task API，只解釋清理需要的 cancel scope。AnyIO 的取消作用域可讓已取消區域在每個等待點繼續觸發取消；於是終於進入 finally，並不意味著 finally 裡的 await 自動安全。

`with anyio.move_on_after(2, shield=True)` 建立一個**有時間上限的同步上下文取消作用域**，所以使用 with 而非 async with。shield 暫時屏蔽外層 AnyIO 作用域的取消，讓 aclose 有機會完成；自己的兩秒清理預算仍有效。如果預算觸發，cancel_called 為真，我們拋清楚的清理失敗，而不是對外謊稱成功關閉。

這不是給整個請求“不可取消”待遇。範圍僅包住釋放；請求本身的取消仍應傳播。也不要把 AnyIO shield 理解為可防任意重複的原始 Task.cancel、進程強殺或系統崩潰。實測覆蓋 asyncio 後端的一次 Task 取消和一個已取消的 AnyIO scope；其他後端與強制退出未證明。

`client.is_closed` 是必要但不充分的證據：實現可能先標記關閉再嘗試釋放底層資源。因此後面的測試還讓真實 TCP 對端看到 EOF，並驗證關閉後的客戶端拒絕使用，而不只檢查屬性或日誌。

<details>
<summary>解釋性檢查答案：一個請求失敗，應該關閉誰？</summary>

先關這個請求擁有的 response stream，釋放許可並傳播取消/返回設計好的降級；不關閉應用共享的 AsyncClient。應用退出才關客戶端。一個正常、一個失敗、一個取消的擁有者作用域都要經過釋放；asynccontextmanager 的 yield 是把借用交給調用者的邊界，不是把所有權永久送出去。關閉連接也不等於撤銷外部效果。

create_app 只是應用工廠。其內部 lifespan 在應用啟動時執行到 yield：進入 managed_client，保存客戶端和 HintService，準備實驗字典。應用隨後處理多個請求；退出時繼續執行，離開 managed_client 關閉客戶端。每個 worker 進程各有自己的生命週期，不是跨進程共享一個池。

CRUD 路由沒有遠端調用，純 require_task 仍是同步函數。本實驗路由中的小段字典讀寫沒有 await，運行在同一 loop，適合觀察隔離關係；不能把這個條件外推成多 worker 下的持久或併發一致性。真實 SQL 的事務和驅動邊界沿用已經學過的方案，不在這裡機械改成 async。FastAPI 普通 def 路由會由框架放在線程池；這不表示你在 async 路由裡直接調用任何同步庫都被自動搬走。

測試用 HTTPX ASGITransport 時框架生命週期不會自動啟動，因此測試顯式 `async with app.router.lifespan_context(app)`。真實 Uvicorn 的測試則讓服務器負責啟動/退出。若 app.state.hints 不存在，首先檢查生命週期有沒有進入，不要臨時在模塊頂層塞一個全局客戶端。

## 7. 四個階段的超時，與整件事的 deadline

HTTPX 的 connect 控制建立連接等待，read 控制等待下一批響應數據，write 控制發送數據等待，pool 控制等連接池許可。不是“四個值相加就是總耗時”，更不是 `Timeout(0.2)` 保證整個請求 0.2 秒內絕對結束。遠端若持續在 read 空閒窗口內送來少量數據，完整響應可以持續更久。

生命週期配置故意把四個值都寫出，避免誤讀單位或默認值。連接數上限限制 transport 連接，HintService 的 semaphore 限制整個邏輯操作；一個操作可能含兩次連接嘗試和一次退避，兩者不是同一個對象。

外層 `asyncio.timeout(self.deadline)` 包住**等待 semaphore → 獲取池連接 → 網絡 → 有限重試 → 退避**。若把 timeout 只放在 _once 內，排隊與退避就能悄悄耗盡你的用戶體驗預算。測試把許可全部佔住，確認到期前一次遠端請求都沒發；另一個測試讓退避超過剩餘預算，確認不會啟動第二次嘗試。它們驗證預算範圍，不比較不穩定的毫秒耗時。

這些數值是教學用的小預算。超時依然協作式：阻塞事件循環或緩慢清理會推遲實際退出。真實系統根據依賴 SLO、負載、調用鏈剩餘預算和失敗行為設參數，不照抄 0.2 或 0.7。

## 8. 完整適配器：小範圍重試、不信任響應、取消不降級

**先理解接下來讀取正文的 async for。** `response.aiter_raw()` 提供非同步位元組區塊迭代器，不是已經下載好的列表。`async for` 向它逐次請求下一塊，並 await 這次取得結果的操作：得到一塊才執行迴圈主體，處理完才取下一塊。等待尚未到達的資料時可以讓出事件迴圈；如果資料已經就緒，一次 await 不保證必然切換任務。它不會為每塊建立 Task，也不是平行下載。

普通 `for` 使用同步迭代協定，不能直接遍歷這裡只提供非同步協定的物件；給普通 for 的迴圈主體加 await 也不會替它非同步取得下一塊。非同步迭代器以 `StopAsyncIteration` 表示「沒有下一塊」，async for 會處理這個結束訊號，繼續執行迴圈後的語句；它不是壞 JSON，也不是要重試的網路錯誤。取消和其他例外則不是正常迭代結束。

下面的 `_once` 用 `bytearray` 保存可累加的位元組。每塊先比較「已保留長度 + 新塊長度」與 1024，再決定是否 `extend`。假設依次收到 700 和 400 位元組：第一塊留下 700 位元組，第二塊在追加前被拒絕，緩衝不會增至 1100。1024 是位元組數而非字元數；區塊也不是一條完整 JSON 訊息，字元或 JSON 片段可能跨塊，所以正常讀完後才用 `bytes(body)` 交給模型驗證。限額只約束這裡保留的正文，不保證底層網路堆疊從未分配過更大的區塊。

等待下一塊時若收到取消，例外沿著迴圈退出；async for 本身不負責關閉回應或共享客戶端。包住讀取過程的 `async with client.stream(...)` 負責在離開其範圍時退出這次回應，外層許可範圍再歸還 semaphore；應用 lifespan 仍擁有共享 client，直到應用退出才關閉整個池。取消不應被改成 `StopAsyncIteration` 或成功降級，非同步退出也不能被理解為抵禦強制終止的保證。

讀原始碼前先口述：700 + 400 為什麼拒絕、保留多少？若正等第二塊時取消，哪些範圍退出，為什麼不關閉其他請求正在借用的 client？再沿下面的巢狀範圍核對答案。

外部 200 也不自動可信：要求 JSON 類型；不跟隨重定向；只接受未壓縮響應；按 raw 字節累計限制為 1024；通過嚴格 Pydantic 模型，僅允許 low/normal/high，拒絕未知字段。邊界限制了**應用保留的正文**，不是對整個網絡棧峰值分配的安全承諾。無效 JSON、錯誤枚舉、HTML、超大體積都轉成同一小型降級結果，不回傳原始遠端正文、URL或異常消息。

`InvalidHint` 是不可盲目重試的數據邊界錯誤；`TransientFailure` 是本例明確允許重試的窄範圍。它們不是所有異常的大垃圾桶。TimeoutError/HTTPX RequestError 可以在業務邊界轉成 unavailable，但 CancelledError 不在這個捕獲集合中。擁有者取消要及時停止，不應偷偷重試或返回“成功降級”。

## 13. 獨立變式：回覆丟了，如何避免重複副作用

暫不打開答案。設計一個純本地“創建回執”客戶端與假提供者。提供者第一次已經產生效果並保存回執，卻拋 ReadTimeout 模擬回覆丟失。客戶端允許最多兩次嘗試，同一邏輯操作必須複用同一 Idempotency-Key 和正文；相同 key 不同正文返回 409；新 key 是新操作。

驗收：同一 key 的丟回覆重試與再次查詢只產生一次效果；改變正文不能複用舊 key；取消不重試；換 key 會產生新效果。再重建一個空提供者，證明內存賬本丟失後重復效果仍可能發生。必須解釋為什麼“客戶端加一個 key 頭”本身不能保證冪等，以及為什麼普通 POST 不能照搬前面的 GET 重試。

## 14. 不要把後臺執行誤稱可靠交付

FastAPI BackgroundTasks 可以把工作安排到發送響應之後，但仍在進程內；進程退出、任務失敗或重啟可能丟失工作。內存 asyncio.Queue 也不會因為名字叫 queue 就自動持久化。它們都不是具有持久記錄、確認、重試、去重和恢復語義的可靠任務系統。

本實驗因此不在保存任務後暗中發“必須送達”的通知，也不展示一個永遠無人觀察的 create_task。將來若通知成為業務要求，應單獨設計數據庫提交與任務記錄的一致性、持久投遞和可恢復消費者；不是在這份客戶端適配器後加一行後臺調用便完成。
