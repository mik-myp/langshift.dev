## 1. 业务函数通过，接口仍可能坏在哪里？

L09 已能写普通测试函数、断言与 pytest.raises；L13 已知道参数化如何把多组数据变成独立用例。H05 的 store 测试可以证明 PATCH 合并规则，却没有证明 /tasks 已被注册、请求 JSON 被解析、错误状态正确，或输出模型真的过滤内部字段。手动 curl 能看到这些，但每次修改都靠记忆重放容易遗漏。

本章先增加一层自动化：测试从 HTTP 请求形状进入真实 FastAPI 应用，再检查状态、响应和后续数据。随后才抽出 fixture，避免把没有解释的 conftest.py 当作“测试框架魔法”。最后启动真正服务并打开浏览器，补上内存内测试不经过的边界。

## 2. 先分清三种“客户端”

TestClient 把请求交给同一 Python 进程里的 ASGI 应用，经过真实路由、依赖、Pydantic 验证和响应处理；它不需要 Uvicorn 监听端口。**它不是把每条路由都 mock 成一个固定 JSON。** 但网络、进程启动和浏览器安全策略不在这条路径上。

HTTPX Client 向真正地址发请求，会经过本机 TCP 端口和 Uvicorn；连接拒绝是可观察故障。真实浏览器又多了一层 Origin 与 CORS 执行：服务器允许头是否足够、预检是否成功、前端能否读取响应，要由浏览器实际证明。三者互补，不应拿“测试很快”推导“已经端到端上线”。

| 检查入口 | 本章能够证明 | 不能由它单独证明 |
| --- | --- | --- |
| 普通 store/config 测试 | 具体 Python 行为、配置解析 | 路由/HTTP/监听 |
| TestClient，未覆写业务依赖 | 输入到输出的进程内 API 行为 | Uvicorn 导入入口、端口、浏览器 CORS |
| TestClient，加依赖替身 | 替身场景下的消费方行为 | 被替换的真实依赖及其子依赖正常 |
| 真实 HTTPX/urllib | 实际进程、端口和 HTTP 契约 | 浏览器执行 CORS、生产网络、TLS |
| 真实浏览器 fetch | 本次页面来源的可读取响应与预检 | 用户身份、对象权限、所有浏览器环境 |

## 5. fixture 解决的是准备与清理，不是自动 mock

多个测试都写 create_app/with TestClient 容易遗漏关闭，也容易偷懒把 app 变成模块全局。pytest fixture 是带名称的准备函数：用 `@pytest.fixture` 登记；测试形参写 client，pytest 找到名为 client 的 fixture，先运行它，再把产物传给测试。不是靠 Python 自动猜参数，也不是写个同名全局变量。

fixture 自己也可以要求其他 fixture：client 的形参 app 让 pytest 先创建 app。默认 scope 是 function，每个测试用例重新准备；同一测试里 client 和 overrides 都需要 app 时，拿到的是同一个本次 app，而不是两个不相干的应用。参数化的每一行也各自得到这套准备。

<Code language="python">{getApiTestingExample('tests/conftest.py')}</Code>

conftest.py 是 pytest 会在目录作用域发现的 fixture 文件；普通测试不需要手动 import client。这里 app fixture 用 return，因为它没有额外退出动作；client fixture 用 yield，测试执行完（包括断言失败）后继续退出 with，关闭客户端。overrides 的 finally 在第 9 节解释。**fixture 的 yield 与 FastAPI 依赖的 yield 由不同框架驱动**，只是共同建立在 L14 的暂停/恢复机制上。

创建前就失败、根本没到 yield 的 fixture，不会神奇地执行写在 yield 后的所有语句。需要为实际已经取得的资源安排 try/finally 或 with；不能写“只要有 yield 就一定安全”。本例客户端由 with 管理，覆写由 finally 管理。

<details>
<summary>解释题答案：把 fixture 改成 session scope 会更快，所以更好吗？</summary>

不一定。共享整个测试会话里的 MemoryStore 会让后执行测试看到前面的任务和递增编号，测试开始依赖顺序。当前对象很轻，function scope 直接表达“每例一份状态”。若将来资源昂贵，要另设计隔离策略，不是只为缩短耗时扩大作用域。fixture 本身既不是 mock，也不保证它返回的对象是干净的；干净来自这里的工厂和生命周期设计。

</details>

## 6. 状态、正文与后续读取要一起检查

<Code language="python">{getApiTestingExample('tests/test_contract.py')}</Code>

参数化的 note 三态测试还分别为遗漏、替换和 null 构造完整预期任务：先核对 PATCH 响应，再 GET 同一个 ID，核对状态 200 与整条预期记录。只有响应断言，可能放过“返回旧内容、存储已经损坏”的实现。

先读 test_crud，不要一口气背所有方法。201 证明创建状态符合契约，完整或关键字段断言证明结果形状，后续 GET 证明修改确实写入当前存储，204 的 `content == b""` 证明删除没有错误地返回 JSON，随后 404 证明资源不再可读。只断言 status_code < 500，会把业务拒绝、错误路由和成功都混成一类。

`set(task)` 在字典上取得键集合，检测内部字段是否泄漏；`type(id) is int` 避免把 Python bool 当整数。本例第一项测试对完整响应相等，也同时证明标题空格保留和默认值正确。不要为了测试方便把响应中的所有“多余”字段先删掉再比较，那会掩盖输出白名单失效。

test_each_case_starts_empty 用两行参数各执行一次：每项先观察 total=0，再创建自己的记录并得到 id=1。若一个用例需要另一个用例先创建数据，它不是独立测试。涉及多步业务的一个测试内部可以有顺序；不同测试之间不该通过遗留数据互相喂输入。

## 7. 错误测试要证明“正确地失败，而且没有写坏数据”

这里分三类故障：坏 JSON 文本返回 json_invalid；JSON 合法但 minutes=true/"3"/3.0 等不符合模型，返回 422 且定位 body 字段；合法 ID 查不到对象返回 404 和稳定的业务 detail。它们不应该被统一成一个模糊的“有错误”。

参数化按 field/value 展开严格校验，不使用一堆 copy-paste 测试。检查 detail 中的 loc，确认错误发生在 body/query/path 的预期位置；不过不硬编码整段 Pydantic 人类可读错误文案、文档 URL 和所有版本相关字段。对自己拥有的 404 detail 则可以完整断言，它属于本章接口契约。

非法创建之后检查 total 仍为 0；混合非法 PATCH 后重新 GET，确认任何字段都没有偷偷改变。只检查 422 不足以排除“先写入部分值，再报错”。注意当前代码的候选记录验证与替换顺序只保障这些顺序执行路径，不是在承诺并发事务。

PATCH note 的三行分别表达不改、赋新文本、显式清空；非 note 字段的 null 被拒绝。`if payload.note` 无法表达三态，因为空字符串和 None 都是假值；本例使用显式字段集合生成的 exclude_unset 结果。需要断言行为，而不是要求学习者记住某段框架实现。

<details>
<summary>带提示答案：如何设计一个能抓住“错误 PATCH 先改了一部分”的测试？</summary>

先创建 title="Keep"、minutes=5、note="keep"，保存完整响应；PATCH 同时提交合法的新 title、非法 minutes=true 和 note=null；确认 422 后重新 GET，与原响应完整相等。若只测试一个非法字段，未必暴露实现提前写入其他字段的问题。独立题会要求你自己写出这个测试，而不是只口头描述。

</details>

## 8. 应用异常与 HTTP 错误不是同一个观察方式

未处理 RuntimeError 是应用缺陷，不是你有意抛出的 HTTPException。TestClient 默认把这类服务端异常重新抛给测试，方便看到原始 traceback；因此一个期待 response.status_code 的测试可能在 client.get 处就停了。

要验收对外 500 响应，局部创建 `TestClient(app, raise_server_exceptions=False)`；再检查状态和文本。默认非 debug 应用的 500 正文是 Internal Server Error，不是 JSON，不能无条件 response.json()。这不是让测试忽略缺陷：一个测试检查异常传播，另一个检查对外错误面，两者目的不同。

<Code language="python">{getApiTestingExample('tests/test_dependencies.py')}</Code>

test_unhandled_errors_raise_by_default 使用故意抛错的依赖，分别观察两种客户端模式；这只能证明这个受控失败路径，不代表生产故障观测已做好。capsys 是 pytest 自带的捕获输出 fixture，读取本次 stdout；test_real_trace_cached_and_closed 检查原依赖一次 acquire、两次使用、一次 release。它没有替换 trace，所以确实执行了真实临时文件逻辑。

即使 capsys 在客户端返回后读到了 release，也不能据此确定 release 与响应发送的先后。H05 的版本化时序与维护用 ASGI 探针负责那项更细的证据；本章不偷加异步测试前置。

## 9. dependency_overrides：替换哪个函数，丢失哪部分证据

app.dependency_overrides 是字典：键为路由声明时使用的**原函数对象**，值为替代提供者函数。`overrides[get_store] = replacement_store` 正确；字符串 "get_store"、get_store() 的结果或另写一个同名函数都不是同一键。框架解析请求依赖时才查这张表，它不重写 Python 模块里的全部函数调用。

test_override_store 返回预置记录的另一份 MemoryStore，让列表行为可控；同时断言 app.state.store 仍为空，明确说明真实提供者被绕过。get_store 原本依赖 request_trace；覆写 get_store 的列表测试不会执行原 get_store，也不会执行它原有的 trace 子依赖。不能拿这项绿色结果宣称资源创建/清理正确。

test_dependency_rejection 用替身抛 503，证明消费方能得到预定状态和正文；它没有真的拔网线、制造磁盘故障或验证恢复策略。这里使用普通函数作为 stub（提供预设结果的替身），没有必要先引入 unittest.mock。mock 是宽泛术语时，应说清替换边界，而不是声称“有 mock 就是完整集成测试”。

覆写仅作用于依赖解析。真实环境在 create_app 时已被读取；事后覆写 get_settings 不能倒流修复一个已经失败的工厂。这个区别解释了为什么测试使用显式 Settings 后，还要单独启动真实进程检验环境。

## 10. 覆写必须恢复，而且要在失败时也恢复

不要写“请求、断言、最后清空”三个普通语句：断言一失败，清空就不执行。conftest 中 overrides fixture 先复制原映射，再 try/yield/finally；无论测试是否通过都清除本次改动并恢复原映射。恢复快照比永远赋空字典更稳妥，因为调用者可能原本有别的受控覆写。

即使本章每测试新建 app，也保留这个清理习惯：共享 app 的诊断、一个测试里的多个阶段、以后改变 fixture scope，都可能让残留产生误判。下面故意让一项测试失败，并保留同一个 app 的引用供下一项检查；这是**有意按顺序的清理探针**，不是普通测试互相依赖的推荐模式。

<details>
<summary>故障诊断答案：第二项也失败，应该修哪一层？</summary>

先确认运行的是整个诊断文件，而不是只挑第二项；这个特定探针需要前一项保留引用。再检查 overrides fixture 是否把恢复放在 finally，是否误覆写另一个 app，或把快照本身当成同一个可变字典。恢复清理后应重新得到 1 failed, 1 passed，再跑正常套件。不要修改第二项为“允许覆写残留”，也不要将它当作日常测试顺序依赖的模板。

</details>

## 11. 正常自动验收与独立变式

```bash
uv run --locked python -m pytest -q
```

```text
48 passed
```

这是 48 个实际收集的用例，不是 48 个函数或断言。原来的 44 项涵盖进程内 CRUD、严格输入、PATCH 三态、错误定位、缺失资源、分页、隔离、原依赖清理、替身错误、500 模式及 CORS 响应头。新增 2 项用自有本地故障服务器验证真实客户端清理，另 2 项在可丢弃副本验证验收能抓住“旧响应掩盖坏状态”的 mutant。重复运行不应依赖上一次数据。故障服务器提供的是狭义真实端口证据，不代表健康服务完整流程或浏览器可读。

维护检查 tests/test_patch_readback_regression.py 只把必要输入复制到临时目录，在那里植入原盲区：空 PATCH 返回旧记录，却把存储字段改成默认值。它分别运行加强后的基础 note 三态测试和独立空 PATCH 测试；子 pytest 必须退出 1，并且确实失败在后续 GET 的完整内容断言，导入错误不算抓住缺陷。外层回归观察到这种预期拒绝才通过。canonical 服务从未被改坏，内层测试也不调用另一个测试函数：

```bash
uv run --locked python -m pytest -q tests/test_patch_readback_regression.py
```

```text
2 passed
```

这项维护探针不是独立编写普通 TestClient 测试的新先修要求。

独立任务，先不看答案：

1. 创建 A/B/C，删除中间 ID，再创建 D；证明新 ID 不复用删除的值，limit=1&offset=1 取得 C，total 是现存总数 3，而不是页长 1 或最大 ID。
2. 对有 note 的任务发送合法 title、非法 minutes=true 和 note=null 的混合 PATCH；证明 422 且原记录逐字段不变。
3. 创建 done=true、非零 minutes、有 note 的任务；发送空 PATCH，再 GET 同一个 ID。两次响应都必须为 200，完整 JSON 都与原记录相等，证明全部非默认值保持。只看貌似正确的 PATCH 响应不能证明存储未变；“都是默认初始数据”的测试也可能放过错误合并。

## 13. CORS 先解释参与者，再加中间件

浏览器页面 http://127.0.0.1:5506 与 API http://127.0.0.1:8006 端口不同，因此不同源。Origin 由协议、主机、端口组成；localhost 和 127.0.0.1 也不是字符串相同的来源。CORS 是浏览器决定是否允许页面脚本读取跨源响应的协议，不是登录或服务端对象权限。

浏览器发送 Content-Type: application/json 的跨源 POST 前，通常先发 OPTIONS 预检，带 Origin、Access-Control-Request-Method 和 Access-Control-Request-Headers。CORSMiddleware 在路由外处理这类预检，并为符合配置的响应添加允许头；不是要求每条路由自己写 OPTIONS。中间件是包在应用请求/响应外的一层处理器，这里只使用这个明确功能，不讲任意中间件架构。

<Code language="python">{getApiTestingExample('task_api/main.py')}</Code>

允许来源只有 http://127.0.0.1:5506，允许本章方法与 Content-Type，不携带 credentials。没有用星号扩大来源，也没有 token/cookie 认证。已解释的普通 create_app 工厂仍然是唯一组合入口；不用异步 lifespan。

<Code language="python">{getApiTestingExample('tests/test_cors.py')}</Code>

允许预检得到 200 与精确来源头；5507 的预检得到 400 且没有允许来源头。更重要的第三项：直接 GET 即使带一个不允许的 Origin，也可能得到 200，只是没有允许浏览器读取的头；不带 Origin 的非浏览器客户端仍可访问。因此 **CORS 不是把非允许调用者挡在服务之外的认证机制**。

TestClient 只检查服务发出的头与状态，不会像浏览器一样阻止脚本读取响应。到这里仍不算前后端联调完成。

## 15. 故障定位、恢复记录与证据边界

| 现象 | 区分原因 | 恢复与复验 |
| --- | --- | --- |
| fixture 'client' not found | 文件不在对应 conftest 目录作用域 | 放回 tests，或像独立答案那样声明本地 fixture |
| 单测单独过，整套失败 | 共享 app、共享可变输入、未恢复覆写 | 回到 function scope 和工厂；重跑单项、整套、第二次整套 |
| client.get 直接抛 RuntimeError | 默认传播服务异常 | 修实现；若故意验收 500，局部关闭传播并断言正文 |
| JSONDecodeError | 500 文本或 204 空正文被当 JSON | 先检查状态/Content-Type；204 检查空 bytes |
| TestClient 过，HTTPX 连接拒绝 | 服务未启动、工厂失败、端口不一致 | 看服务日志，重启正确入口后再验收 |
| HTTPX 过，浏览器 fetch 失败 | 来源或预检，或页面请求错误 | 查 Network；保持安全边界，不扩大允许表掩盖问题 |
| mock 测试过，真实 trace 无日志 | 替换跳过真实依赖与子依赖 | 保留替身测试，再增加未覆写的真实路径证据 |

暂停记录：当前目录与锁版本；基础套件实际 count；独立题实际 count；故障探针是否得到 1 failed, 1 passed；覆写在哪个 app 上且是否已恢复；真实服务启动命令/PID/端口；两个浏览器 Origin 的结果；任务清理与进程停止情况；尚未验证项与下次第一步。不要只写“全部通过”。

毕业门槛是能解释每层证据、独立补测试、让受控缺陷被抓住并恢复、完成真实浏览器联调。下载 allowlist 排除环境、缓存、.env、日志和秘密。当前的 48+3 项与真实进程/浏览器验收不证明数据库、认证授权、生产并发、部署、TLS、性能或所有浏览器兼容性；这些仍要在后续阶段建立。
