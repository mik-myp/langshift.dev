## 2. 先固定不變的業務，再決定如何拆

任務仍由服務端生成正整數 id；title 長度 1..120，拒絕全空白，但保留合法文本原有大小寫和首尾空格；minutes 是普通非負 JSON 整數，拒絕 bool、字符串、浮點；done 是嚴格 bool，默認 false；note 是最多 1000 字符的可空文本，默認 null。PATCH 只合並顯式傳入的字段，只有 note 可以賦 null。客戶端不能提交 id 或額外字段，響應不洩露 internal_tag。

POST /tasks 返回 201；列表、單項讀取和 PATCH 返回 200；DELETE 返回沒有正文的 204。合法但不存在的正整數 ID 返回 404，非法輸入返回 422。列表形狀是 items/limit/offset/total，按 id 排序；默認 limit=20、offset=0，limit 為 1..100，offset 非負。offset 是跳過多少條**現存記錄**，不是從哪個 ID 開始。

## 4. APIRouter 登記路由，不負責啟動服務

APIRouter 像一張可組裝的路由登記表。`prefix="/tasks"` 與 `@router.get("")` 合成 /tasks；`@router.get("/{task_id}")` 合成 `/tasks/{task_id}`。不要在裝飾器裡再寫一遍 /tasks，否則得到 /tasks/tasks。這裡使用空字符串而不是末尾 /，避免實驗無意依賴重定向。

模塊導入時裝飾器登記函數；main 調用 `app.include_router(router)` 時把路由加入應用。兩步都不是在監聽端口。Uvicorn 仍負責啟動服務。忘記 include_router 時，Python 導入可能成功，/health 也可能正常，但 /tasks 是 404；這不是模型驗證錯誤。

先認識接下來源碼裡尚未展開的記號：`Depends(get_store)` 是交給框架的聲明，不是拿到 store 的普通函數調用。下一節先拆解機制，再閱讀整個路由文件。

## 5. Depends：函數值、調用者與返回值

回憶 L13：寫 get_store 是傳函數對象，寫 get_store(...) 才立即調用。`Depends(get_store)` 保存“處理請求時需要調用哪個提供者”的元數據。FastAPI 檢查路由參數，找出依賴，準備依賴所需參數，調用依賴，再把結果當成路由參數傳入。

一次列表請求的路徑是：請求攜帶查詢文本 → get_page 校驗查詢參數並獲得 settings → get_store 獲得當前 app 的 MemoryStore → list_tasks 使用兩者 → 返回字典 → response_model 驗證和過濾 → HTTP 響應。若提供者還有依賴，框架先滿足它們；這形成一張小的調用關係圖，不是一個讀取全局魔法變量的黑箱。

`Request` 是 FastAPI 提供的當前請求對象，不是 JSON 請求體模型。`request.app.state` 是我們掛在**當前應用實例**上的狀態容器。state 不會自動建立 store，也不會驗證其類型；這些對象由工廠顯式寫進去。settings 是應用級配置，store 是應用級內存；它們不是每請求重建的對象。

在同一次請求中，相同依賴按默認策略複用解析結果。本例 create_task 直接請求 request_trace，get_store 也請求同一個 request_trace；兩處使用相同 function scope，因此只獲得一個跟蹤資源。下一次請求會重新創建這個資源，不會複用已經關閉的文件。這個緩存不是跨請求數據緩存，也不讓多個應用共享 store。

<details>
<summary>解釋題答案：為何不能把 Depends(get_store) 改成 Depends(get_store())？</summary>

前者把函數交給框架，後者在模塊導入時就嘗試調用 get_store，而且沒有本次 Request。它會在服務啟動前失敗，或把錯誤的調用結果當提供者。反過來，直接從普通 Python 調用一個帶 Depends 默認參數的路由，也不會觸發自動注入：默認參數仍是聲明對象。調用普通業務函數進行單元測試，與走框架請求解析，是兩個不同入口。

</details>

## 6. 同步 yield：取得一份臨時資源，然後交還控制權

這次不用數據庫冒充教學資源。每個依賴創建一個真實 TemporaryFile 文本句柄，路由寫入動作名，finally 關閉它；只在終端輸出不含請求體的 acquire/use/release 信息。臨時文件不是長期審計記錄，關掉後不再讀取它。

<Code language="python">{getDependencyExample('task_api/dependencies.py')}</Code>

request_trace 是普通同步生成器函數。框架開始處理依賴時推進到 yield；yield 的 RequestTrace 對象交給使用者；退出時恢復生成器，讓 finally 關閉文件。L14 的暫停/恢復沒有改變，只是推進與退出的主人從手寫 with 變成框架。不要再給這個提供者加 `@contextmanager`：FastAPI 需要這裡的生成器函數，並負責管理它。

文件創建失敗時尚未 yield，路由拿不到假資源；已經成功獲取且進入 try 的資源，正常返回或異常傳播時都會經過 finally。本例沒有 except 吞掉 HTTPException，也沒有“失敗後返回空列表”偽裝成功。如果強制殺進程、解釋器崩潰或機器斷電，不能承諾 Python finally 一定運行。

RequestTrace 的 mark 使用文件，close 負責釋放。get_store 只是借用這個資源記錄一次動作，不能自行 close。資源的所有者與使用者不同，正是需要依賴生命週期的原因。但釋放不回滾任務修改，也不證明響應已送達客戶端。

## 7. 版本和 scope 決定“清理在什麼時候”

本實驗固定 FastAPI 0.135.1。自 0.121.0 起支持這裡使用的 `Depends(..., scope="function")`。本例明確選 function，因為響應已是普通 JSON 數據，不需要繼續讀臨時文件：正常路由完成後、響應發往客戶端之前清理。

對 yield 依賴，未指定 scope 的默認值是 request：**正常響應路徑**會在響應發送之後清理。這不是“yield 總在發送前執行”的通則。歷史版本變過行為，不能只引用一張舊時序圖。若在依賴或路由拋出受處理的 HTTPException，異常展開會先清理，再由異常處理器發送錯誤響應；不要把正常成功時序機械套到所有錯誤。

```text
function, success: acquire -> use -> release -> response send
request, success:  acquire -> use -> response send -> release
handled HTTPException: acquire -> use -> release -> error response send
```

一個 request-scope 的 yield 依賴不能依賴更早關閉的 function-scope yield 子依賴，因為它自己的退出代碼可能仍需要子依賴。function-scope 依賴則可以使用 function 或 request 子依賴。本例 get_store 本身不 yield；所有臨時 trace 的聲明顯式使用相同 function scope，不製造混合壽命。

2026-09-28 維護驗收不僅觀察打印，還截取了實際 ASGI response.start/body 的發送位置，分別確認兩種 scope 的成功和受處理錯誤，共四種時序。該探針涉及底層異步協議，只在維護腳本里，不把它變成讀者的前置要求。**客戶端已經收到響應後才查看“closed=True”，無法單獨證明關閉發生在發送前還是發送後。**

<details>
<summary>預測題答案：一次 POST 會打開兩份 trace 嗎？失敗的 GET 會漏清理嗎？</summary>

不會因兩處依賴聲明打開兩份：本次請求中它們共享同一個已解析依賴。正常 POST 的動作順序是 acquire、get_store、create_task、release。合法但不存在的 ID 會先取得 store，再由 require_task 拋出 404；已經取得的 trace 仍經 finally 關閉。如果錯誤發生在取得資源之前，就沒有那個資源需要關閉。不要要求所有 422 都必須執行相同依賴集合。

</details>

finally 不是“裡面每條語句都會成功”的保證。客戶端對本次創建的每個 ID 單獨 try/except：記錄該 ID 的清理失敗，再嘗試其他自有 ID，不清空整個服務。循環結束輸出 CLEANUP FAILED、清理未確認的 ID 及各自診斷。“未確認”不聲稱超時刪除到底有沒有生效；重放前只檢查這些自有 ID。主體已完成時，清理失敗拋出 RuntimeError，進程非零退出；主體本來就失敗時，body_succeeded 仍為 false，清理錯誤照樣報告，但 finally 不再拋替代異常，也不 return，因此原 traceback 繼續傳播。逐項捕獲清理錯誤不等於把整次運行偽裝成功；一個簡單標誌即可保留兩類診斷，不需要異常組框架。

這是通過 urllib 訪問真正端口的獨立客戶端，沒有調用 Python 路由函數。HTTPError 仍攜帶錯誤狀態和正文，因此客戶端把它當可檢查的 HTTP 響應；連接拒絕則連 HTTP 響應都沒有。斷言失敗時先看對應請求和服務端日誌，不把“程序沒拋異常”當唯一標準。它只在空的可丟棄服務運行，記錄本次創建的 ID 並在 finally 刪除；不會清空不屬於它的全部記錄。

## 12. 帶提示修改：讓錯誤暴露狀態歸屬
