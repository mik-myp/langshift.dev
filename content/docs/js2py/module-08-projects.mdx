## 1. Why introduce a project environment now?

L00–L07 taught you to run, split, diagnose and persist a Python program. Only now do we introduce complete environment declarations: you can distinguish a business defect from an interpreter missing a dependency, and you know that a configuration file does not execute your business code.

Imagine sending a working directory to a colleague. Their Python differs, or your machine happened to have a globally installed package that the source never declared. **Identical source does not imply identical execution conditions.** Environment management turns hidden assumptions into inspectable files and recovery steps, rather than asking someone to reconstruct your terminal history.

We use one deliberately small external feature: display 1536 bytes as `1.5 KiB`. The objective is not a formatting API catalogue. It is a visible consequence for dependency absence, interpreter selection and recovery from declarations.

| Contract | Requirement |
| --- | --- |
| Prerequisites | L06 imports, module search and entry points; L07 files and paths |
| New capabilities | Interpreter selection, isolation, declaration, resolution, installation, locking and reconstruction |
| Independent acceptance | Rebuild a small application from an empty directory and diagnose a dependency failure |
| Not required yet | Publishing, build backends, competing package managers, pytest, containers or FastAPI |

Download [L08 experiments and reference answers](/learning-assets/js2py/u08-environments.zip). Extract the complete `u08-environments` directory and open a terminal there. **Do not keep adding `--no-project` to these commands.** Earlier chapters intentionally ignored an enclosing project; now we explicitly need this project's declarations.

Verified baseline: **September 28, 2026: CPython 3.13.15, uv 0.12.13 and humanize 4.13.0**. This is an observed combination, not a newest-version or permanent security claim. Initial recovery may download an interpreter and distribution files. A lockfile is not an offline installer.

## 2. Separate four participants

The **Python interpreter** executes Python. **uv** manages interpreters and dependencies and launches project commands; it is not itself the Python interpreter. A **virtual environment** supplies a project's interpreter entry and installed packages. **Application source** defines business behavior. Sharing one terminal does not make these the same thing.

Your frontend experience with source, package.json, a lockfile and node_modules helps distinguish declarations from installed results. The analogy has limits: `.venv` also has interpreter entry points, prefixes and package search paths. Which Python you actually run determines which installed packages it can import.

In an unactivated terminal, a bare `python` or `python3` is resolved through the shell's PATH. An editor's Run button may select another interpreter. “I just installed humanize” is not evidence that the current Python can import it.

Check the tool before installing more things:

```bash
uv --version
```

If the shell cannot find this command, no Python business code has run. Return to L00's installation/PATH checks and verify the tool location or reopen the terminal. Do not rewrite the application to hide a missing tool.

## 3. Which files are inputs, and which are results?

The important root files are below. Exercise and answer directories have separate declarations; stay at the root first:

```text
u08-environments/
  .python-version
  pyproject.toml
  uv.lock
  app.py
  probe.py
  .venv/              # created locally; not in the download
```

| Item | Owner and purpose | What it does not establish |
| --- | --- | --- |
| `.python-version` | Author selects a Python request for uv | It neither installs dependencies nor replaces the compatibility range |
| `pyproject.toml` | Author declares metadata, Python compatibility and direct dependencies | An allowed range is not a selected full dependency graph |
| `uv.lock` | uv resolves; author reviews versions, sources, hashes and relationships | It contains no package payload, security certification or complete OS snapshot |
| `.venv/` | uv creates/synchronizes the local installation | It is not portable project source or something to copy between machines |
| Application/test source | Author describes business behavior and checks | Source alone does not specify the external execution conditions |

Version-control the source, declarations, version selection and lock. Exclude environments, caches and real secrets. Shared work must not depend on an environment you happened to activate previously. This example needs no private registry, credential or `.env` file.

`pyproject.toml`:

<Code language="toml">{getEnvironmentExample('pyproject.toml')}</Code>

This is TOML, not Python or JSON. `[project]` starts a configuration table; following key/value assignments belong to it. Quoted values are strings and comma-separated items in brackets form an array. `[tool.uv]` is uv-specific configuration. Understand these forms without first memorizing the entire TOML specification.

- `name` identifies project metadata; it does not automatically create a Python module. `version` belongs to this project, not to the interpreter.
- `requires-python = ">=3.13,<3.14"` allows the 3.13 series. The version file selects a particular interpreter within that range. Contradictory declarations need repair, not ignored errors.
- `dependencies` names runtime **distributions**. `humanize==4.13.0` deliberately selects an exact version here; the declaration is not executing an import.
- `package = false` makes the non-packaged local application explicit. We run a file from its project directory, without first teaching publishing or a build system.

Distribution names belong to installers; import names belong to Python's module search. They need not match. This example happens to use humanize for both. Do not guess and install an identically named online package whenever you encounter an unfamiliar import. Consult that library's official installation instructions. Standard-library modules such as json and pathlib are not extra runtime distributions to add.

The first command reads the project and compatible lock, selects Python, and creates/synchronizes `.venv`. The second launches that project's Python, which executes the probe. ## 6. Declaration, resolution, locking and synchronization are different

For a new project without a lock, `uv lock` resolves concrete versions from the declaration and writes the lock. Synchronization makes the environment satisfy that selection. Ordinary `uv run` also checks the project and may lock/synchronize before launching the requested command.

The useful question is **which state each operation may change**, not how many flags you can memorize:

| Command | Purpose | Changes or limits to observe |
| --- | --- | --- |
| `uv add "humanize==4.13.0"` | Intentionally add a direct runtime dependency | Normally updates declaration, lock and environment |
| `uv lock` | Resolve or update the lock | Not installation, and not a forced upgrade of every package |
| `uv sync --locked` | Restore from a compatible lock | Refuses implicit lock changes; default exact synchronization removes extraneous packages |
| `uv run --locked python app.py` | Check the lock and run in the project | uv run defaults to inexact synchronization; success does not prove there are no extra packages |
| `uv remove humanize` | Intentionally remove a direct dependency | Does not remove imports from your application source |

**`--locked` and `--frozen` are not interchangeable.** Locked checks compatibility between declaration and lock and fails if an update is required. Frozen uses the existing lock without that freshness check. We choose locked to expose drift, not frozen to make a red command appear green. `--no-sync` likewise skips a check rather than repairing installation.

To establish that declared dependencies suffice, first use exact `uv sync --locked`, then run the program. A solitary successful `uv run` is weaker evidence because an accidental extra installation may remain available.

## 7. Keep the lock without treating it as magic

The complete experimental `uv.lock`:

<Code language="toml">{getEnvironmentExample('uv.lock')}</Code>

Locate two package entries: the humanize distribution and the local virtual project. The distribution records its version, public source, available files and hashes. The project connects its requirements to that selection. Here the graph is tiny; later, a direct dependency can bring several indirect dependencies. Copying only a top-level version does not reconstruct the full resolution.

You should not hand-type these long URLs or hashes. **Declarations state intent, the resolver generates the lock, and authors review changes.** Editing one lockfile version by hand can leave the source, file hashes and relationships inconsistent.

The lock does not replace interpreter selection, OS requirements, a database version, secret configuration, backups or tests. A distribution hash helps verify the retrieved file; it does not prove that file contains vulnerability-free code. Cross-platform lock information cannot promise every native extension and system library will build on every machine.

This first environment exercise uses a small pure-Python dependency from public PyPI to avoid introducing native build diagnostics simultaneously. That is a teaching boundary, not a claim that future dependencies are always pure Python.

## 8. Actually create a stale lock

Prepare a **new disposable copy without `.venv` or caches**. Change the root declaration from humanize 4.13.0 to 4.12.0 but retain the old lock:

```bash
uv run --locked python app.py
```

Expect **uv to reject the stale lock before starting Python**. The old 4.13.0 selection cannot satisfy the new exact request. This is neither a business traceback nor an accumulation defect. Editing app.py would be solving the wrong layer.

If you want the original lesson state, restore the original declaration and synchronize/run again. If you genuinely intend a dependency change, intentionally update the declaration and lock, review the diff, recover the environment and verify behavior. Both are reasonable actions for different goals.

A changed range that still admits the locked version does not necessarily make the lock stale. This experiment deliberately excludes the previous selection. We are testing compatibility, not the false rule that any textual edit must produce an error.

### A missing declaration

The separate exercise project does not declare humanize:

```bash
uv add "humanize==4.13.0"
uv run --locked python app.py
cd ../..
```

The repaired output is `2.0 KiB`. Inspect both changed files: declaration and lock. Installing into an incidental environment without declaring the dependency does not repair independent reconstruction.

### Installed distribution, wrong imported module

The root project has humanize installed, yet this still fails:

<Code language="python">{getEnvironmentExample('errors/humanize.py')}</Code>

<Code language="python">{getEnvironmentExample('errors/show_shadow.py')}</Code>

```bash
uv run --locked python errors/show_shadow.py
```

It prints the actual path of `errors/humanize.py`, then raises **AttributeError** because that local module has no naturalsize. L06's search rules still apply inside virtual environments. Reinstalling the distribution does not fix local naming. In the disposable copy, rename the conflicting local file and start a new process. Do not edit site-packages.

### Download failure before imports are possible

DNS, networking, registry authentication, TLS and unavailable distribution files can stop synchronization. An offline machine with a cold cache cannot manufacture package payload from a lock. Read uv's resolution/download diagnostic rather than adding except to app.py. Do not disable certificate verification or paste real registry credentials into lessons or logs.

Ask in order: **Can the tool run? Which project and interpreter? Is the lock compatible? Was installation successful? What was actually imported? Is the business behavior correct?**

## 10. Activation is neither mandatory nor environment copying

Activation mainly changes the current shell's search/environment so a bare python command can find `.venv`. It neither installs packages into source nor permanently affects all terminals. Shell activation syntax varies, so this course uses `uv run` as its main path to reduce hidden session state.

Do not carry another project's activated environment into this work and assume every tool will infer your intent. If VIRTUAL_ENV conflicts with the selected project environment, identify the intended target before choosing an option that uses the active environment.

Recovery means preparing a clean second directory with **source, declaration, version selection and lock**, not copying `.venv`:

```bash
uv sync --locked
uv run --locked python app.py
```

This is safer than deleting your only working environment and hoping recovery succeeds. It also exposes undeclared dependencies. Business data, secrets and external services are separate future recovery responsibilities, not proven by reinstalling packages.
