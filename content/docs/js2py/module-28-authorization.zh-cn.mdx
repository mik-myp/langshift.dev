## 1. 认证给出 actor，授权才回答这个操作是否允许

S01 已经能把有效会话变成一个服务验证过的用户。现在 Alice 把 URL 中的项目 ID 改成 Bob 的项目，会发生什么？若代码只判断“已登录”，数据库外键和响应模型都不会替你拒绝。**对象授权需要同时知道当前用户、目标对象及操作。** 它不是前端按钮是否显示，也不是 CORS 策略。

## 2. 先把权限写成可证伪的表

| 操作 | 未认证 | 非成员 | 普通成员 | 项目 owner |
| --- | --- | --- | --- | --- |
| 创建项目 | 401 | 登录用户可创建自己的项目 | 可 | 可 |
| 项目列表 | 401 | 只列本人参与的项目 | 同左 | 同左 |
| 读取项目/成员/任务 | 401 | 404 | 可 | 可 |
| 创建任务 | 401 | 404 | 可，创建者为本人 | 可，创建者为本人 |
| 修改/删除任务 | 401 | 404 | 仅本人创建的任务，否则 403 | 可操作项目内任务 |
| 修改/删除项目、管理成员 | 401 | 404 | 403 | 可 |
| 删除 owner 成员记录 | 401 | 404 | 403 | 409，明确禁止 |

表中的身份/对象状态以格式合法的请求为前提；框架可能先用脱敏 422 拒绝非法结构，这不意味着允许读取对象。这里的 404 故意不告诉外人项目是不存在还是不可见；已经是成员但缺少操作权限时用 403。它是本实验一致的业务契约，不是所有产品必须采用的唯一策略。不要让不同路由随意泄露不同程度的信息。

默认拒绝的含义是：没有一条明确允许规则，就停止。不是先取出完整对象返回给前端再“建议不要显示”。请求体不允许 owner_id、created_by 或 role 自授权。邀请成员时的 user_id 是**待加入的目标用户**，不是调用者身份，且服务固定写入 member。

<details>
<summary>解释性答案：有外键和无法猜测的 ID，为什么还需要授权？</summary>

外键证明引用存在，不证明调用者有权使用它。随机或难猜的 ID 只能降低偶然发现概率，不能作为授权证据：URL、日志、分享内容都可能暴露 ID。验证必须在已知真实 ID 的情况下仍然正确，所以本章负向测试直接把 Bob 的真实 ID 交给 Alice，而不是只试一个不存在的数字。

</details>

## 5. 为什么权限检查与写入要留在同一个事务里

想象请求 A 查到 Alice 是成员，随后请求 B 删除 Alice 的成员关系，最后 A 才写入。仅仅“每个端点都检查过一次”还没说明两者如何排序。本实验约定进入具体项目的对象操作持项目共享锁，成员变更/项目删除持项目排他锁，直到事务结束。项目总列表使用带成员条件的 SQL 语句快照，不声称把已经开始的列表响应撤回，也不保证并发分页与 total 来自同一快照。移除成员必须等待已持锁操作结束；移除提交后的新请求查不到关系。

这不是回收已经发送的数据，也不是强行终止正在执行的授权请求。它是一个明确可解释的串行顺序。所有相关写入者都必须遵循相同锁协议；绕过应用直接改库的管理员仍可破坏服务不变量。不要把它称为数据库 RLS 或任意 SQL 都安全。

创建项目是另一个事务问题：先 INSERT project、flush 得到 id，再 INSERT owner，最后由调用层一起 commit。flush 只是发送 SQL、分配 id，不是落定业务成功。第二步失败，第一步也必须回滚；repository/helper 里不能提前 commit，把两步拆成不可恢复的半成品。

<details>
<summary>事务检查答案：为什么“先保存项目，再补 owner”不够？</summary>

如果先提交项目，后面的 owner 插入因为外键、唯一约束或异常失败，会留下无人管理的项目。部分唯一索引只限制 owner 数量，不能补出缺失的 owner。本章测试让第二条 INSERT 真实触发外键错误，然后用新事务查询项目不存在；随后正常创建应成功，证明不是只捕获异常却保留坏 Session。

</details>

## 8. 让 Alice 直接拿到 Bob 的真实对象 ID，再试越权

先由 Bob 创建第一个项目和任务；记录响应中的项目和任务 id。以下假设二者都是 1：

```bash
uv run --locked python client.py --port 8062 --session .session-bob.json request POST /projects --json '{"name":"Bob private"}'
uv run --locked python client.py --port 8062 --session .session-bob.json request POST /projects/1/tasks --json '{"title":"Bob task","minutes":25}'
uv run --locked python client.py --port 8062 --session .session-alice.json request GET /projects
uv run --locked python client.py --port 8062 --session .session-alice.json request GET /projects/1
uv run --locked python client.py --port 8062 --session .session-alice.json request PATCH /projects/1/tasks/1 --json '{"status":"done"}'
```

Bob 的两次创建为 201，Alice 的列表为 200 但没有 Bob 项目，直接读和改均为 404。随后 Bob 加 Alice 为普通成员，注意这个 user_id 是目标邀请人：

```bash
uv run --locked python client.py --port 8062 --session .session-bob.json request POST /projects/1/members --json '{"user_id":1}'
uv run --locked python client.py --port 8062 --session .session-alice.json request GET /projects/1/tasks/1
uv run --locked python client.py --port 8062 --session .session-alice.json request PATCH /projects/1/tasks/1 --json '{"status":"done"}'
uv run --locked python client.py --port 8062 --session .session-alice.json request POST /projects/1/tasks --json '{"title":"Alice task","created_by":2}'
```

现在 Alice 可以读（200），但不能改 Bob 创建的任务（403），自报 created_by 被模型拒绝（422）。删掉伪造字段后由 Alice 正常创建，响应 created_by 必须是 Alice。不要只验证列表；直接对象 URL、子资源 URL、PATCH、DELETE 都需要负向测试。

## 9. 撤成员不是撤身份，但必须立即撤掉对象权限

```bash
uv run --locked python client.py --port 8062 --session .session-bob.json request DELETE /projects/1/members/2
uv run --locked python client.py --port 8062 --session .session-bob.json request DELETE /projects/1/members/1
uv run --locked python client.py --port 8062 --session .session-alice.json request GET /users/me
uv run --locked python client.py --port 8062 --session .session-alice.json request GET /projects/1
```

第一条试图删除 Bob 自己的 owner 成员记录，应为 409；第二条移除 Alice，应为 204。Alice 的凭证仍有效，所以 /users/me 为 200，但项目读取为 404。它不是等令牌过期才失权，因为角色和成员关系根本不缓存在令牌里。

恢复实验可以由 Bob 重新邀请 Alice；不是让 Alice 提交 role="owner"，也不是关闭认证。重复邀请由数据库主键拒绝并转换为脱敏 409；事务结束后下一条合法请求仍应成功。失效 Session 不得留在全局继续使用。

<details>
<summary>边界答案：Alice 是任务创建者，移除后为什么仍不能修改？</summary>

任务创建者规则是在当前项目成员的前提下增加允许条件，不是永久所有权通行证。入口先查当前成员关系，移除后在这里返回 404，根本不会继续调用 may_edit_task。仅凭历史 created_by 授权，会让已经离开项目的人保留写权限；认证仍有效也不能补足这个缺失关系。

</details>
