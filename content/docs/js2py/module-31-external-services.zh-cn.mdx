## 1. 外部提示可以失败，保存任务不能陪它失败

场景是为任务提供可选的优先级提示。把远端请求直接塞进创建任务的事务，外部服务一变慢，就可能让连接、事务与请求一起长时间占住。更危险的是，客户端超时并不证明远端没发生效果；盲目重试可能重复发送通知或创建账单。

本章先设计责任边界：**核心 CRUD 自己完成；可选提示单独查询；一个应用生命周期拥有一个外部客户端；一个请求只借用它**。我们不真实联系第三方，不上传用户任务正文，也不需要凭证。

| --- | --- |
| 前置 | A01 的 coroutine/Task、取消与预算；L14 的上下文管理器和 yield/finally；H05 的服务生命周期；位置在 S03 之后 |
| 新能力 | asynccontextmanager、lifespan、HTTPX 客户端复用与关闭、阶段超时与总预算、有限重试、边界校验 |
| 独立验收 | 外部失败或悬停时 CRUD 仍工作；正常、异常、取消均验证真实资源释放；解释幂等变式 |

## 3. 先沿着一条请求追踪谁拥有什么

浏览器/调用者 → 本地 FastAPI → 提示服务对象 → 共享 HTTPX 客户端及其连接池 → 本地故障服务。响应反向回流时，必须重新验证外部数据，最后只返回允许的状态与枚举。

- 应用拥有客户端、连接池和整个依赖的 semaphore；每次请求只是借用。
- 一次尝试拥有 response stream，在任何退出路径上关闭它。关闭响应不等于关闭共享客户端；连接可能回到池中复用。
- 一次提示操作拥有排队、重试、退避的总预算；核心 CRUD 不进入这条调用链。
- 服务停机时 lifespan 释放应用级客户端，而不是在某次请求后误关其他请求正在借用的对象。

这与前端复用一个 API 客户端有相似处，但服务器要并发借用、明确关池并处理停机取消。模块 import 就创建客户端，会让所有权、运行循环与测试隔离变得含糊。每个请求都 `async with AsyncClient()` 又会不断重建池，失去跨请求的连接复用。

## 4. 从 L14 的 with 到 async with：先讲协议，再看装饰器

L14 中 `@contextmanager` 把普通生成器适配成 with 的进入/退出协议。这里只有一个必要变化：获取或释放可能需要 await，因此协议需要等待 `__aenter__` 与 `__aexit__`。`async with` 不会让任意同步 close 自动非阻塞；被调用的实现必须提供相应异步行为。

`managed_client` 是带 yield 的 async def，因此是**异步生成器函数**，不是 A01 中直接 await 得到结果的普通 coroutine function。`@asynccontextmanager` 把它适配成异步上下文管理器工厂，使用方式是 async with，而不是直接 await 这个管理器。

<Code language="python">{getExternalServiceExample('lifecycle.py')}</Code>

按顺序读一次：

1. validate_origin 在获取资源前验证配置。失败时没有客户端，没有进入块，也没有“等退出再补救”的机会。
2. 构造 AsyncClient 配置连接池；通常尚未建立实际网络连接，连接会按请求需要创建。
3. 执行到唯一的 yield，把客户端借给 async with 块；此时管理器暂停，资源仍属于它。
4. 块正常结束则恢复 yield 后的代码；块抛异常/取消则在暂停点恢复相应异常路径。无论哪种，finally 负责关闭。
5. `await client.aclose()` 完成后才结束退出阶段。清理不是业务回滚，已经到达远端的副作用不会因此消失。

装饰器协议要求恰好 yield 一次；不 yield 或 yield 两次都是协议错误。获取多个资源时应逐个建立管理边界，不能先获取所有资源，赌最后一个 finally 能处理前面任何失败。对照 L14 可以看到：异步化改变的是可等待的进入/退出，不是资源所有权原则。

## 5. finally 里也可能等待：取消清理为何有一个小保护区

FastAPI/Starlette 的并发基础会使用 AnyIO。这里不用它堆出另一套 Task API，只解释清理需要的 cancel scope。AnyIO 的取消作用域可让已取消区域在每个等待点继续触发取消；于是终于进入 finally，并不意味着 finally 里的 await 自动安全。

`with anyio.move_on_after(2, shield=True)` 建立一个**有时间上限的同步上下文取消作用域**，所以使用 with 而非 async with。shield 暂时屏蔽外层 AnyIO 作用域的取消，让 aclose 有机会完成；自己的两秒清理预算仍有效。如果预算触发，cancel_called 为真，我们抛清楚的清理失败，而不是对外谎称成功关闭。

这不是给整个请求“不可取消”待遇。范围仅包住释放；请求本身的取消仍应传播。也不要把 AnyIO shield 理解为可防任意重复的原始 Task.cancel、进程强杀或系统崩溃。实测覆盖 asyncio 后端的一次 Task 取消和一个已取消的 AnyIO scope；其他后端与强制退出未证明。

`client.is_closed` 是必要但不充分的证据：实现可能先标记关闭再尝试释放底层资源。因此后面的测试还让真实 TCP 对端看到 EOF，并验证关闭后的客户端拒绝使用，而不只检查属性或日志。

<details>
<summary>解释性检查答案：一个请求失败，应该关闭谁？</summary>

先关这个请求拥有的 response stream，释放许可并传播取消/返回设计好的降级；不关闭应用共享的 AsyncClient。应用退出才关客户端。一个正常、一个失败、一个取消的拥有者作用域都要经过释放；asynccontextmanager 的 yield 是把借用交给调用者的边界，不是把所有权永久送出去。关闭连接也不等于撤销外部效果。

</details>

## 6. lifespan：一进一出，不是每请求初始化

<Code language="python">{getExternalServiceExample('app.py')}</Code>

create_app 只是应用工厂。其内部 lifespan 在应用启动时执行到 yield：进入 managed_client，保存客户端和 HintService，准备实验字典。应用随后处理多个请求；退出时继续执行，离开 managed_client 关闭客户端。每个 worker 进程各有自己的生命周期，不是跨进程共享一个池。

这里启动不探测可选远端，健康接口也不调用它。否则可选依赖坏了就会让核心服务启动失败，与你声称的可选相矛盾。生产 readiness 应验证真正关键的依赖，例如数据库，而不是一概包含所有推荐/提示 API。

CRUD 路由没有远端调用，纯 require_task 仍是同步函数。本实验路由中的小段字典读写没有 await，运行在同一 loop，适合观察隔离关系；不能把这个条件外推成多 worker 下的持久或并发一致性。真实 SQL 的事务和驱动边界沿用已经学过的方案，不在这里机械改成 async。FastAPI 普通 def 路由会由框架放在线程池；这不表示你在 async 路由里直接调用任何同步库都被自动搬走。

测试用 HTTPX ASGITransport 时框架生命周期不会自动启动，因此测试显式 `async with app.router.lifespan_context(app)`。真实 Uvicorn 的测试则让服务器负责启动/退出。若 app.state.hints 不存在，首先检查生命周期有没有进入，不要临时在模块顶层塞一个全局客户端。

## 7. 四个阶段的超时，与整件事的 deadline

HTTPX 的 connect 控制建立连接等待，read 控制等待下一批响应数据，write 控制发送数据等待，pool 控制等连接池许可。不是“四个值相加就是总耗时”，更不是 `Timeout(0.2)` 保证整个请求 0.2 秒内绝对结束。远端若持续在 read 空闲窗口内送来少量数据，完整响应可以持续更久。

生命周期配置故意把四个值都写出，避免误读单位或默认值。连接数上限限制 transport 连接，HintService 的 semaphore 限制整个逻辑操作；一个操作可能含两次连接尝试和一次退避，两者不是同一个对象。

外层 `asyncio.timeout(self.deadline)` 包住**等待 semaphore → 获取池连接 → 网络 → 有限重试 → 退避**。若把 timeout 只放在 _once 内，排队与退避就能悄悄耗尽你的用户体验预算。测试把许可全部占住，确认到期前一次远端请求都没发；另一个测试让退避超过剩余预算，确认不会启动第二次尝试。它们验证预算范围，不比较不稳定的毫秒耗时。

这些数值是教学用的小预算。超时依然协作式：阻塞事件循环或缓慢清理会推迟实际退出。真实系统根据依赖 SLO、负载、调用链剩余预算和失败行为设参数，不照抄 0.2 或 0.7。

## 8. 完整适配器：小范围重试、不信任响应、取消不降级

**先理解接下来读取正文的 async for。** `response.aiter_raw()` 提供异步字节块迭代器，不是已经下载好的列表。`async for` 向它逐次请求下一块，并 await 这次取得结果的操作：得到一块才执行循环体，处理完才取下一块。等待尚未到达的数据时可以让出事件循环；如果数据已经就绪，一次 await 不保证必然切换任务。它不会为每块建立 Task，也不是并行下载。

普通 `for` 使用同步迭代协议，不能直接遍历这里只提供异步协议的对象；给普通 for 的循环体加 await 也不会替它异步取得下一块。异步迭代器以 `StopAsyncIteration` 表示「没有下一块」，async for 会处理这个结束信号，继续执行循环后的语句；它不是坏 JSON，也不是要重试的网络错误。取消和其他异常则不是正常迭代结束。

下面的 `_once` 用 `bytearray` 保存可累加的字节。每块先比较「已保留长度 + 新块长度」与 1024，再决定是否 `extend`。假设依次收到 700 和 400 字节：第一块留下 700 字节，第二块在追加前被拒绝，缓冲不会增至 1100。1024 是字节数而非字符数；块也不是一条完整 JSON 消息，字符或 JSON 片段可能跨块，所以正常读完后才用 `bytes(body)` 交给模型验证。限额只约束这里保留的正文，不保证底层网络栈从未分配过更大的块。

等待下一块时若收到取消，异常沿着循环退出；async for 本身不负责关闭响应或共享客户端。包住读取过程的 `async with client.stream(...)` 负责在离开其范围时退出这次响应，外层许可范围再归还 semaphore；应用 lifespan 仍拥有共享 client，直到应用退出才关闭整个池。取消不应被改成 `StopAsyncIteration` 或成功降级，异步退出也不能被理解为抵御强杀的保证。

读源码前先口述：700 + 400 为什么拒绝、保留多少？若正等第二块时取消，哪些范围退出，为什么不关闭其他请求正在借用的 client？再沿下面的嵌套范围核对答案。

`InvalidHint` 是不可盲目重试的数据边界错误；`TransientFailure` 是本例明确允许重试的窄范围。它们不是所有异常的大垃圾桶。TimeoutError/HTTPX RequestError 可以在业务边界转成 unavailable，但 CancelledError 不在这个捕获集合中。拥有者取消要及时停止，不应偷偷重试或返回“成功降级”。

## 13. 独立变式：回复丢了，如何避免重复副作用

暂不打开答案。设计一个纯本地“创建回执”客户端与假提供者。提供者第一次已经产生效果并保存回执，却抛 ReadTimeout 模拟回复丢失。客户端允许最多两次尝试，同一逻辑操作必须复用同一 Idempotency-Key 和正文；相同 key 不同正文返回 409；新 key 是新操作。

## 14. 不要把后台执行误称可靠交付

FastAPI BackgroundTasks 可以把工作安排到发送响应之后，但仍在进程内；进程退出、任务失败或重启可能丢失工作。内存 asyncio.Queue 也不会因为名字叫 queue 就自动持久化。它们都不是具有持久记录、确认、重试、去重和恢复语义的可靠任务系统。

本实验因此不在保存任务后暗中发“必须送达”的通知，也不展示一个永远无人观察的 create_task。将来若通知成为业务要求，应单独设计数据库提交与任务记录的一致性、持久投递和可恢复消费者；不是在这份客户端适配器后加一行后台调用便完成。
