JS async 函數調用會執行函數體到第一個暫停點，返回 Promise；Python 的 `async def` 定義 coroutine function，調用得到 **coroutine object**，函數體尚未開始。對象保存的是一次可恢復的執行，不是已經啟動的網絡請求，也不是自動排隊的後臺任務。直接丟棄它通常會得到 `RuntimeWarning: coroutine was never awaited`，而不會替你完成工作。

`await pending` 讓當前執行沿著這個 coroutine 前進；`asyncio.create_task(pending)` 則把它包裝成 Task 並交給當前運行的 loop 調度。Task 保存執行狀態、結果/異常和取消狀態，擁有者要保留引用並最終觀察結果。本實驗使用 Python 3.13 的**默認任務工廠**；沒有啟用 eager task factory，不能把這裡“create_task 後還未運行”的觀察擴展到一切自定義任務工廠。

## 4. 一次調用中的四個角色，不是四種線程

想象一個服務進程中的一個事件循環線程：loop 維護已就緒的回調與待完成 I/O，挑可運行的工作繼續；Task 驅動 coroutine，直到其完成、失敗或等待尚未就緒的東西。`await` 表示“依賴這個可等待對象的結果”，不是“新建線程”，也不是無條件的讓出。

如果 await 的對象已經就緒，當前 Task 可能直接繼續；測試裡對已 set 的 Event 執行 wait，預先排隊的回調仍沒運行。若等待的是未 set 的 Event，Task 暫停，loop 才能推進其他就緒工作。因此 CPU 長循環裡塞一個已完成的 await，並不能保證服務響應。

`asyncio.run(main())` 在獨立程序入口管理循環生命週期，運行 main 並最終關閉循環。框架內部已有循環時不再套 run；應在 async 調用鏈內 await。也不要把不同循環創建的異步資源長期塞進一個模塊全局後到處複用。

## 5. 直接 await 的順序，與顯式調度的重疊

`sequential` 先完整 await A，再調用並 await B。A 裡的 `sleep(0)` 確實給循環一個調度機會，但 B 尚未被創建，不會憑空併發。這與連續兩句 `await fetch(...)` 的 JS 經驗相通；差別在於 Python 提前調用兩個 async 函數也僅產生兩個 coroutine，仍未啟動它們。

`scheduled` 則先創建兩個 Task，隨後擁有者等待兩個 entered 門閂，再放行 B、觀察 B 完成，最後放行 A。所有權與完成順序是顯式的。輸出中 A/B 的 start 順序是本次默認調度的觀察；可移植驗收只要求**兩個 start 都發生在 both-entered 之前，而兩個 end 都在之後**，不把無關的隊列先後當作業務協議。

`finally` 中的 `drain` 先取消所有未結束孩子，再用 `gather(..., return_exceptions=True)` 等待所有終態。此處 gather 是收尾工具：返回的位置對應輸入，異常/取消成為結果項，便於不因某一個孩子取消就漏收其他孩子。它不會自動賦予任意程序“失敗即取消其他孩子”的政策。我們的正常路徑已經觀察目標結果；示例清理階段不重新拋次生錯誤。生產監督若需要保留所有次生錯誤，必須另行記錄/報告，不能把這些返回值長期當垃圾丟掉。

<details>
<summary>解釋性檢查答案：先調用兩個 coroutine，再逐個 await，會不會自動併發？</summary>

不會。創建 coroutine object 本身沒有把它加入 loop 的就緒工作。第一個被 await 時才開始，等其結束後才執行第二個。要重疊進行，須先顯式創建兩個 Task，或使用有明確調度語義的組合器，並擁有兩者的生命週期。另一個陷阱是 await 不必總暫停：已經就緒的 Event 可以立即返回。

</details>

## 6. 阻塞不是“等得久”，而是把循環線程佔住

`blocking` 先用 `loop.call_soon` 排入一個就緒回調，再在循環線程執行同步 `time.sleep(0.02)`。sleep 期間 CPU 可以閒下來，但這個線程沒有返回事件循環；因此同步段結束時回調仍未運行。只有執行真正讓出的 `await asyncio.sleep(0)`，回調才出現。

我們斷言的是回調與同步段的先後，不是“20 ms 應當跑完”之類易受系統負載影響的時鐘閾值。這個例子證明 loop 不能穿插推進其他工作，不是性能基準，也不意味著只要回調晚到就必然能定位到某一行阻塞。

`offloaded` 把一個必須同步調用的阻塞庫放到 `asyncio.to_thread`。線程用 `call_soon_threadsafe` 報告已進入，並等待線程專用的 `threading.Event`；主循環此時仍能記錄事件、釋放線程，最後明確 await 加入收尾。不要從工作線程直接調用 asyncio.Event.set 來偷跨線程訪問。這裡兩個 Event 屬於不同併發模型，有各自用途。

選擇邊界時先問：純標題校驗、字典讀寫保持普通函數；已有真正異步 I/O 客戶端才 await；不可替換的同步 I/O 可考慮線程橋接；長 CPU 運算不能因為包進 async 就變成並行。取消等待 to_thread 的 Task 也**不能強制殺死底層線程**，阻塞庫自己仍需超時/停止協議。本例明確 release 並等待線程退出，不把遺留線程交給運氣。

## 7. 取消是請求，不是立即中斷，也不是成功結果

<Code language="python">{getAsyncModelExample('ownership.py')}</Code>

`task.cancel()` 請求把 `asyncio.CancelledError` 注入目標執行；它不會同步把線程停在任意機器指令。目標通常在下一次可取消等待處感知請求，然後經過 finally。擁有者仍須 await Task，觀察它真正結束。CancelledError 屬於 BaseException 而不是普通 Exception；不要用裸 except/BaseException 把取消當網絡故障。

如果需要記錄取消，可捕獲後清理並原樣 `raise`；本例根本不攔截工作中的取消，只用 finally 關閉文件。擁有者的 except 則是**邊界觀察**：它知道自己剛請求結束該任務，記錄 owner:cancelled，而不是讓業務結果變成成功。清理若自己報錯，原來的取消也可能被新的錯誤遮蓋，不能用日誌一句話宣稱“永遠可靠”。

還有一個容易遺漏的邊界：默認工廠下，Task 尚未開始就取消，函數體和 finally 都沒有運行。因為資源獲取也在函數體裡，此時沒有文件需要關閉。若把資源先開在外面再交給未啟動的 Task，外層必須繼續承擔所有權。

## 8. 超時建立預算，不保證牆鐘上的強制終止

`timed_out` 用 `asyncio.timeout(0)` 人為安排在下一輪循環到期：當前任務仍會開文件，到等待未就緒 Event 時觸發取消，finally 關文件，退出 timeout 上下文後才在外面捕獲 TimeoutError。零秒是可重複的機制實驗，不是實際網絡預算建議。

timeout 針對當前任務的取消被上下文轉換為 TimeoutError；外部獨立取消仍應傳播為 CancelledError。應在 timeout 塊外捕獲超時，才能清楚地區分預算到期與塊內業務異常。真實總預算以後應覆蓋排隊、多個嘗試和退避，而不是每一步偷偷重置。

超時是協作式的：循環被同步代碼佔住時，定時器也無法及時執行；清理本身可能需要時間。不要承諾“到 N 秒操作一定已停止”，更不能推導“遠端寫入一定未發生”。A02 會進一步區分 HTTP 分階段超時與整個操作 deadline。

## 9. 併發上限不是把無限請求變得免費

<Code language="python">{getAsyncModelExample('capacity.py')}</Code>

Semaphore 是許可計數器。進入 `async with slots` 取得一個許可，沒有許可就等待；退出時歸還。Meter 只統計已准入的工作，不統計等在外面的 Task。四個任務、兩個許可時，只有兩個 entered 為真；放行一箇舊任務後，才觀察到新的 entered。正常與取消都經過 finally 減 active，上下文歸還許可。

把 semaphore 建在每次請求內部會使每個請求都有自己的上限，無法限制共享依賴的總壓力。A02 會把它放在應用生命週期內。本例最多創建四個任務，獨立變式最多八個；**即使 semaphore 只有兩個，預先創建一百萬個 Task 仍會佔用內存**。無限輸入需要有界接收、背壓與其他設計，不在這裡冒充已經解決。

帶提示修改：把 limit 從 2 改為 1，再改為 3。不要改成 assert “運行時間翻倍/縮短”；驗收 peak 等於新 limit、結束時 active 為零，並解釋一個等待許可的 Task 被取消為何不應額外歸還一個未取得的許可。
