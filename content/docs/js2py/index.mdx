## Who is this course for?

You can structure frontend projects, integrate APIs, use Promises and async/await, and understand basic TypeScript types. You have not yet implemented a backend or database yourself. That is this course's starting point.

You do not need to learn Express first, and advanced type-level programming is not a prerequisite. Engineering experience helps with organization, tests, and collaboration, but does not replace practice with schemas, transactions, authorization, and operations. These responsibilities need explanations and exercises, not just a table of library names and APIs.

## The objective is delivery, not recognition

The target is to design, implement, test, deploy, and maintain a small-to-medium backend for invited users, consulting documentation as needed. You should also complete a new feature without a step-by-step implementation tutorial.

Reading every page is not sufficient evidence. Each stage needs a concrete deliverable, success and failure cases, acceptance checks, and an explanation of its decisions. Public self-registration and similar features require additional security and operational checks; a demo is not automatically a complete product.

## How to work through a topic

1. Start with a concrete problem and why the concept is needed.
2. Connect it to frontend experience while identifying the analogy's limits.
3. Explain the concept and execution mechanism before listing syntax and APIs.
4. Run a complete example; predict and explain its inputs, outputs, and failures.
5. Make a guided change, then implement a variation independently.
6. Validate the result before opening a separately provided reference answer.

Not every example belongs in a browser. Small language experiments may; multi-file applications, dependencies, databases, and servers need an explicitly described local environment. A configuration file, intentional error, or server program does not become browser-runnable merely by appearing in an editor.

## Capability stages

| Stage | Capability | Deliverable |
| --- | --- | --- |
| Python foundations | Semantics, functions, types, modules, errors, resources, and tests | A reproducible local task application |
| HTTP and FastAPI | Contracts, validation, responses, routing, dependencies, and settings | An API that a frontend can integrate |
| Databases | SQL, relationships, constraints, transactions, ORM, and migrations | Persistent data rather than process-local state |
| Multiple users | Identity, password handling, credential invalidation, object-level authorization | User boundaries enforced by the server |
| Reliability | API/database tests, async boundaries, timeouts, and failure handling | Behavior that remains explainable when something fails |
| Delivery | Deployment, logs, backup recovery, iteration, and rollback | A controlled live release and an independently developed feature |

Build correct synchronous behavior first, then introduce async for concrete use cases. Data analysis, metaclasses, advanced generics, and distributed tasks remain optional extensions rather than blockers. This is about ordering prerequisites, not making the foundational teaching shallow.

## Sequence before volume

The new Python route progresses through **a first run → names and values → containers → control flow → functions → exceptions → modules → files/JSON → environments/dependencies → basic tests → a first independent reproducible application**. Types, classes, decorators, and resource lifecycles then prepare the transition to server development and FastAPI.

Each step includes a small program explainable with current knowledge, neither an unexplained full project nor a long theory-only delay. Advance by prerequisite-based acceptance, not a calendar. Advance in the listed order after demonstrating each chapter’s acceptance, not simply reading it. Setup, credential handling, migration safety, and recovery have their own lessons and evidence; later chapters do not silently turn a local demonstration into a production service.

## Where to start

Begin with [module 00: understand and run your first script](/en/docs/js2py/module-00-python-introduction). Here uv only obtains and selects CPython 3.13. Environments, lockfiles, and pytest receive their own instruction after the necessary language and module foundations.

An ordinary Python function uses `def` and does not require `self`; an instance method introduces the explicit instance parameter. Python's async/await also cannot be equated with JavaScript's scheduling behavior merely because the syntax looks familiar. We establish useful connections through experiments without flattening important differences.

Study time can be irregular. End each session with the current state, passing checks, unresolved questions, and the next concrete action. Progress is measured by capability, not weekly deadlines.
