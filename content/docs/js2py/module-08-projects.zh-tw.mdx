## 1. 現在才建立工程環境，解決的是哪個問題？

L00—L07 已經讓你獨立運行、拆分、排錯和保存一個 Python 程序。直到這裡，我們才引入完整的環境聲明：你現在能夠區分“業務程序寫錯了”和“運行程序的解釋器缺少依賴”，也知道配置文件本身不會替你執行代碼。

想象你給同事發了一個可以運行的目錄。同事的 Python 版本不同，或者你的電腦曾經全局裝過一個包，而源碼沒有說明。**相同源碼不等於相同運行條件。** 環境管理要把這些隱含條件變成可檢查的文件和重建步驟，而不是讓別人猜你的終端歷史。

本章使用一個極小的第三方功能：把 1536 字節顯示為 `1.5 KiB`。它不是為了介紹所有格式化 API，而是讓“缺少依賴、選錯解釋器、從聲明恢復”產生看得見的結果。

| 契約 | 本章要求 |
| --- | --- |
| 前置 | L06 的導入、模塊搜索與入口；L07 的文件與路徑 |
| 新能力 | 解釋器定位、隔離環境、聲明、解析、安裝、鎖定與重建 |
| 獨立驗收 | 從空目錄構建小應用，恢復依賴，定位至少一次依賴失敗 |
| 暫不要求 | 發佈包、構建後端、多個包管理器、pytest、容器和 FastAPI |

## 2. 先區分四個參與者

**Python 解釋器**讀取並執行 Python 代碼。**uv** 是管理解釋器、解析依賴和運行項目命令的工具，本身不是 Python 解釋器。**虛擬環境**是某個項目使用的解釋器入口與安裝目錄。**項目源碼**才定義業務行為。四者不能因為終端裡都出現一個命令而混為一談。

你在前端熟悉的“源碼 + package.json + 鎖文件 + node_modules”可以幫助建立類比：聲明和安裝結果不是同一種文件。但不要直接把 `.venv` 當成純粹換名的 `node_modules`：Python 環境還有自己的解釋器入口、前綴和包搜索路徑；運行哪一個 Python，決定了它能夠導入哪些安裝內容。

在未激活環境的終端裡，裸寫 `python` 或 `python3`，Shell 會按自己的 PATH 找程序。編輯器運行按鈕也可能選另一個解釋器。不能憑“我剛裝過 humanize”推斷當前進程一定能導入它。

先檢查工具，而不是先安裝一堆東西：

```bash
uv --version
```

如果連這個命令都找不到，Python 源碼尚未運行。回到 L00 的安裝與終端 PATH 檢查；重新打開終端或核對工具位置，不要把業務文件改成能夠繞過工具缺失的樣子。

## 3. 一個目錄裡，哪些是輸入，哪些是結果？

實驗根目錄的重要部分如下；練習和答案目錄各自另有聲明，先不要進入它們：

```text
u08-environments/
  .python-version
  pyproject.toml
  uv.lock
  app.py
  probe.py
  .venv/              # created locally; not in the download
```

| 文件或目錄 | 誰負責 | 它解決什麼問題 | 它不保證什麼 |
| --- | --- | --- | --- |
| `.python-version` | 作者選擇，uv 讀取 | 本項目請求哪一個 Python 版本 | 不安裝第三方依賴，也不替代兼容範圍 |
| `pyproject.toml` | 作者維護 | 項目元數據、Python 兼容範圍與直接依賴 | 一個允許範圍不等於已經選定的整棵依賴圖 |
| `uv.lock` | uv 解析生成，作者審查 | 記錄選定版本、來源、文件哈希和相關解析信息 | 不攜帶包內容、不證明包安全、不鎖住全部操作系統條件 |
| `.venv/` | uv 創建/同步 | 本機實際安裝結果 | 不適合複製到不同目錄/機器，不是應提交的項目源碼 |
| 應用與測試源碼 | 作者維護 | 業務邏輯及其驗收 | 不能單獨說明解釋器和外部包條件 |

提交到版本控制的是源碼、聲明、版本選擇與鎖文件；不要提交 `.venv`、緩存或真實秘密。共享項目也不能依賴你已經激活的某個環境。這裡的示例沒有私有包源、密鑰或 `.env`。

`pyproject.toml`：

這不是 Python 或 JSON，而是 TOML。`[project]` 打開一個配置表，後面的 `key = value` 屬於該表；雙引號是字符串，方括號中的逗號分隔項是數組。`[tool.uv]` 是 uv 專屬配置。你需要讀懂本例用到的幾種形式，不需要先背完整 TOML 規範。

- `name` 是項目元數據的名稱，不是讓 Python 自動生成一個同名模塊。`version` 是這個項目自身的版本，不是解釋器版本。
- `requires-python = ">=3.13,<3.14"` 說明接受 3.13 系列。它是範圍；具體選擇由版本文件和工具共同確定。兩者互相矛盾時應修復聲明，而不是忽略錯誤。
- `dependencies` 是程序運行時需要的**發行包**。`humanize==4.13.0` 在本次課程中精確選擇版本；它不是在執行 `import`。
- `package = false` 明確本例是無需安裝自身的本地應用。我們從項目目錄運行文件；暫時不製作可發佈發行包，不需要提前引入構建系統。

發行包名是安裝工具識別的名稱，導入名是 Python 尋找模塊的名稱，兩者不保證相同。本例恰好都叫 humanize；不要看到一個陌生 import 就去網絡上猜同名包安裝。先查該庫的官方安裝說明，也不要把標準庫 `json`、`pathlib` 當成缺失的第三方依賴。

## 6. 聲明、解析、鎖定、同步不是同一個動作

創建一個沒有鎖文件的新項目時，`uv lock` 根據聲明解析出具體版本並生成鎖文件；`uv sync` 再使環境滿足選定依賴。日常 `uv run` 也會檢查項目，並按需要鎖定和同步後再運行命令。

關鍵不是背命令數量，而是理解**誰會改變哪個狀態**：

| 命令 | 主要用途 | 本章需要觀察的變化 |
| --- | --- | --- |
| `uv add "humanize==4.13.0"` | 有意增加直接運行依賴 | 聲明、鎖文件與環境通常一起更新 |
| `uv lock` | 從聲明解析或更新鎖 | 不等於安裝，也不等於強制升級所有包 |
| `uv sync --locked` | 按相容鎖文件恢復環境 | 不允許悄悄修改鎖；默認精確同步會移除多餘安裝包 |
| `uv run --locked python app.py` | 檢查鎖並在項目環境運行 | uv run 默認非精確同步，不能據此證明多餘包不存在 |
| `uv remove humanize` | 有意移除直接依賴 | 更新聲明/鎖/環境，但不會替你刪除源碼裡的 import |

**`--locked` 不是 `--frozen`。** 前者要求鎖與聲明相容，否則失敗；後者使用已有鎖而不檢查它是否仍符合聲明。這裡用 `--locked` 是為了暴露陳舊鎖，不建議遇到錯誤就換 `--frozen` 隱藏矛盾。`--no-sync` 也不是修復命令，它會跳過你本來需要檢查的環境同步。

對於驗證“只有聲明過的依賴也能運行”，先執行 `uv sync --locked`，再運行程序，比單獨看到一次 `uv run` 成功更有證據。不要把工具默認保留的額外安裝誤當作程序已經可復現。

## 7. 鎖文件為什麼需要保留，又為什麼不能神化？

實驗的完整 `uv.lock`：

<Code language="toml">{getEnvironmentExample('uv.lock')}</Code>

先找到兩個 package 條目：一個是 humanize 發行包，一個是本地虛擬項目。前者包含版本、公共來源、可用發行文件及其哈希；後者連接本項目的依賴要求。當前依賴很小，所以圖很簡單。後續一個直接依賴可能再依賴多個包，鎖文件會記錄解析結果，不能只抄頂層版本就稱作完整恢復。

你無需手寫這些長 URL 或哈希。**聲明表達意圖，解析器生成鎖，作者審查變化。** 不要為了讓檢查變綠手改鎖中的版本號，因為來源、文件哈希和依賴關係可能已經不相符。

鎖文件不能代替 Python 選擇、操作系統說明、數據庫版本、秘密配置、數據備份或測試。哈希幫助核對取得的發行文件，不證明其中的代碼沒有漏洞。跨平臺的鎖信息也不保證所有本地擴展和系統庫都能在每臺機器上編譯。

本例只使用公共 PyPI，選擇純 Python 依賴減少第一輪環境實踐中的系統構建噪聲。這是教學邊界，不是以後只會遇到純 Python 包的承諾。

## 8. 親手製造陳舊鎖，而不是隻讀“應該提交鎖文件”

先複製整個下載到一個**新的實驗目錄，但不要複製 `.venv` 和緩存**。在副本中，把根聲明的 humanize 版本從 4.13.0 改為 4.12.0，保留舊鎖文件：

```bash
uv run --locked python app.py
```

預期是 **uv 在啟動 Python 之前拒絕陳舊鎖**。4.13.0 已經不滿足新的精確要求；這不是業務 traceback，也不是 app 的求和錯誤。不要改業務文件來修環境。

若目的是回到教材原樣，恢復原來的聲明，再執行同步與運行。若你確實打算變更依賴，則有意更新聲明與鎖，檢查變更，恢復環境，再驗證程序行為。二者都是合理動作，但表達了不同意圖。

僅改變一個仍然允許當前鎖定版本的範圍，不一定導致鎖失效，因此本實驗用**排除舊版本的精確要求**。我們驗證的是相容關係，不是“文件有改動就必須報錯”的錯誤模型。

## 9. 三種“包的問題”，不能用同一個重裝命令解決

### 缺少聲明

進入獨立練習目錄。它自己的聲明沒有 humanize：

<Code language="toml">{getEnvironmentExample('exercises/missing-declaration/pyproject.toml')}</Code>

<Code language="python">{getEnvironmentExample('exercises/missing-declaration/app.py')}</Code>

```bash
cd exercises/missing-declaration
uv sync --locked
uv run --locked python app.py
```

這裡應出現 **ModuleNotFoundError**。先確認 cwd 與本項目環境，再把實際運行依賴加入聲明：

```bash
uv add "humanize==4.13.0"
uv run --locked python app.py
cd ../..
```

修復後輸出 `2.0 KiB`。檢查兩個文件：聲明新增了依賴，鎖中也出現了對應解析。只在某個環境裡臨時安裝成功、卻不修改聲明，不算修好獨立重建能力。

### 安裝成功，但導入了本地同名文件

根目錄的已安裝包不缺失，下面仍然會失敗：

<Code language="python">{getEnvironmentExample('errors/humanize.py')}</Code>

<Code language="python">{getEnvironmentExample('errors/show_shadow.py')}</Code>

```bash
uv run --locked python errors/show_shadow.py
```

先打印的是 `errors/humanize.py` 的實際路徑，再出現 **AttributeError**：這個本地模塊沒有 `naturalsize`。L06 的模塊搜索規則沒有因為建立 `.venv` 就失效。重裝發行包不會改變本地命名衝突。在副本中將這個本地文件改名，再啟動一個新進程觀察實際來源；不要修改 site-packages。

### 下載失敗，還沒輪到 import

DNS、網絡、包源認證、TLS 或沒有對應發行文件，都可能讓同步失敗。離線且冷緩存的機器不能憑 `uv.lock` 生成包內容。此時應閱讀 uv 的下載/解析診斷，不要給 app 添加 except，也不要關閉證書校驗或把真實私有源憑據粘貼進教材和日誌。

按順序問：**工具能否啟動 → 項目與解釋器選對了嗎 → 聲明和鎖相容嗎 → 安裝完成了嗎 → 實際導入來源是什麼 → 業務運行是否正確？**

## 10. 激活不是必須，也不是在複製一個環境

激活主要改變當前 Shell 的命令搜索與環境，使你直接寫 `python` 更容易選中 `.venv`。它沒有把依賴裝進源碼，也不會永久修改所有終端。不同 Shell 的激活命令不同，所以本書的主路徑統一使用 `uv run`，減少隱藏會話狀態。

不要把其他項目已激活的環境帶入本項目並假設工具一定按你的意圖選擇。若工具提示 VIRTUAL_ENV 與項目環境不一致，先確認你要操作的是哪個項目，不要隨意加“使用當前活動環境”的開關。

恢復驗證的方法不是複製 `.venv`，而是準備另一個乾淨目錄，複製**源碼、聲明、版本文件與鎖**，執行：

```bash
uv sync --locked
uv run --locked python app.py
```

這比刪除唯一工作環境再祈禱能恢復更安全，也會暴露漏提交的依賴。原始數據、秘密與其他外部服務不在這份環境恢復證據裡，未來要分別驗收。

## 11. 三層練習：解釋、修復、獨立恢復

### A. 先預測，再運行

1. 鎖文件存在，是否代表 `.venv` 已經安裝？
2. `uv run --locked` 成功，是否代表沒有額外包？
3. ModuleNotFoundError、陳舊鎖拒絕、同名遮蔽 AttributeError 分別發生在哪一層？
4. 安裝了某個發行包，為什麼仍要查看 `__file__`？

<details>
<summary>解釋核對——先寫自己的依據</summary>

鎖只是解析信息，不是安裝目錄。uv run 默認非精確同步，不能證明沒有額外包；需要受控的精確同步或乾淨恢復。陳舊鎖在啟動業務前由工具拒絕；缺少模塊在 Python 導入時失敗；本地同名文件則可能成功導入錯誤模塊，再訪問不存在的屬性。發行元數據與實際模塊來源需要分別觀察。

</details>

### B. 修復但不掩蓋

在下載副本中完成缺聲明和同名遮蔽兩個實驗。保留失敗命令、退出是否非零、報錯層次、修改了哪些文件，以及新進程的成功輸出。不要把原本應失敗的命令包裝成忽略錯誤，也不要刪掉 import 讓“功能不再存在”充當修復。

<details>
<summary>修復核對——為什麼這些改動才解決根因？</summary>

缺聲明：在練習自己的項目目錄中 `uv add "humanize==4.13.0"`，審查聲明和鎖，再運行。遮蔽：在副本將 `errors/humanize.py` 改成非衝突名稱，再運行原入口；安裝包仍保持原樣。兩者都應在沒有原環境的乾淨目錄再次驗收，才能排除終端歷史留下的偶然條件。

### C. 獨立字節統計應用
