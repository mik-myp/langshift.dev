## 1. Two correct SQL statements can still produce incorrect business state

Creating a project requires inserting projects and then inserting its owner membership. Each statement can be valid while the overall operation is unreliable. If the first commits independently and the second fails, an ownerless project remains. Python try/except changes control flow; it cannot reverse an already committed change in another process. Promise.all is not database all-or-nothing behavior either.

A transaction is a database-recognized operation boundary: commit all committable changes in that unit or discard the uncommitted unit. The business caller selects the boundary, constraints decide whether writes are valid, and the driver transports commands and exposes errors. These responsibilities do not replace one another.

## 3. A connection is not a transaction; a cursor is not another session

A connection represents a server session and can complete many transactions sequentially. Cursors on that connection share its current transaction. A separate connection is needed to observe what an external session can currently see. Reusing a connection does not reuse a committed transaction, and closing a cursor does not commit.

In SQL, BEGIN starts an explicit transaction, COMMIT requests its completion, and ROLLBACK discards uncommitted changes. With psycopg's default `autocommit=False`, the first query starts a transaction implicitly, **including SELECT**. Creating the connection or cursor alone does not execute BEGIN; the first statement activates the transaction. After commit/rollback, the connection remains usable and a later statement can start another transaction.

```text
connected, no transaction
  -> first statement / BEGIN
  -> active transaction
       -> COMMIT succeeds -> no transaction, connection reusable
       -> SQL error -> failed transaction -> ROLLBACK -> reusable
       -> close before commit -> uncommitted work discarded
```

D02 autocommit completed each statement independently; it did not eliminate database transactions. If the two writes run that way, rollback after the second cannot undo the already committed first. Conversely, leaving a default connection idle after a SELECT can retain snapshots or locks and occupy resources: idle in transaction. Do not hold a business transaction while waiting for a user interaction.

`with conn.cursor()` manages only the cursor. `with psycopg.connect(...) as conn` commits on normal exit, rolls back on exceptional exit and closes the connection. Closing is not committing: `.close()` does not convert pending work into success. `conn.execute` is a cursor convenience, not another connection.

<details>
<summary>Explanation answer: can two functions, each with its own connect context, form one transaction?</summary>

No. Each connection has its own transaction, and the second failure does not undo the first's committed work. A business operation should own a connection and pass it to SQL helpers that do not commit internally. The outer boundary decides success. One HTTP request is not automatically one transaction either; choose the unit according to consistency needs, not function or cursor count.

</details>

## 5. Why even SELECT fails after an error

This file intentionally performs both writes, a subsequent query, rollback and a recovery query on one psql connection. Expected failures are labeled; only this experiment permits continuing after errors.

<Code language="sql">{getTransactionExample('sql/failed_transaction.sql')}</Code>

```bash
uv run --locked python labctl.py psql --file sql/failed_transaction.sql
```

The second step reports `23503`; the following SELECT reports `25P02` because the current transaction is failed. After ROLLBACK, the Broken SQL count is 0 and SELECT 1 succeeds. The connection is not permanently broken; its failed transaction must end.

Catching and swallowing the Python exception inside with, then executing more SQL, similarly produces InFailedSqlTransaction. Prefer allowing the original exception to leave the transaction boundary and converting it into a business error outside. If managing a connection manually, explicitly roll back before reuse. A blanket `except Exception: return None` hides the real failure and can leave a failed session for subsequent code.

Constraints remain essential. An API precheck that a user exists can improve messages, but another session can change state between check and write. Do not remove foreign keys merely because Python validates input. Do not classify all database exceptions as input errors either: disconnections, storage faults and constraint conflicts call for different responses.

## 6. What ACID usefully means, and what it cannot promise

| Property | Evidence in this lab | Not a promise of |
| --- | --- | --- |
| Atomicity | Second-step failure leaves no first-step write | Rolling back an email or external HTTP call |
| Consistency | CHECK, foreign-key and unique constraints reject invalid states | Discovering every business rule, such as requiring an owner |
| Isolation | Visibility, waiting and conflicts follow the chosen isolation level | A single global lock serializing all work |
| Durability | Committed rows survive normal stop/start | No need for backups, or proof of hardware-failure recovery |

Identity allocation is not rolled back. Gaps after failures or rollback are normal; a missing number is not a residual record. IDs identify records, not counts or successful-operation totals. External side effects are outside PostgreSQL rollback, so do not casually send notifications or charge payments inside retryable code.

Another recovery boundary: a network failure during commit may leave the client unable to tell whether the server committed. This lab does not simulate that ambiguous outcome. Production needs an idempotency key or queryable business identifier/state; blindly replaying an operation that may already have succeeded is unsafe.

## 7. Which version can two connections see?

PostgreSQL's multiversion behavior lets reads determine visibility through snapshots rather than having every reader lock the whole table. The complete experiment creates genuinely separate connections. Its runner resets between cases and prints the critical results.

<Code language="python">{getTransactionExample('concurrency.py')}</Code>

In snapshot, reader first gets 30 for task 1; writer adds 10 and commits; reader reads again within its original transaction. Default Read Committed gives a new visibility snapshot per statement and returns `[30, 40]`. Repeatable Read reuses the transaction snapshot and returns `[30, 30]`. The first read establishes the observation point here; merely opening a connection does not freeze the database.

This is not a speed comparison or a claim that reads never wait. Stronger isolation can reject a concurrent update and require the application to decide again. Arbitrary old snapshots cannot all write successfully without conflict. Serializable offers stronger execution semantics but can still require retries. Its full anomaly matrix is not tested here; a Repeatable Read experiment is not Serializable acceptance.

## 8. Lost updates: adding BEGIN does not fix stale read-modify-write

Lost_update lets A and B both read 30. A computes 35 in Python and commits; B computes 37 from its old value and commits. The final result is 37, not 42. Both UPDATE transactions are valid. The database cannot infer that the supplied constant 37 really meant “add 7 to the newest value.” The application turned a relative operation into an outdated absolute replacement.

For this increment requirement, express the operation in one statement: `SET minutes = minutes + %s`. B waits while A holds the conflicting row lock. After A commits, B under Read Committed adds 7 to the current updatable version, producing 42. This is not a sleep-based guess that B is slow: a third connection observes pg_stat_activity until B's wait_event_type is Lock, then A is permitted to commit. Timeouts prevent an indefinitely hung experiment.

For a genuine multi-field read/decision/write, `SELECT ... FOR UPDATE` can lock relevant rows within a short transaction before deciding. Another option is an optimistic conditional update using an old version and checking affected rows. A row lock does not lock every business invariant: rules involving multiple rows or absent rows need separate reasoning. Do not generalize one FOR UPDATE into a universal race solution.

<details>
<summary>Guided modification answer: is adding FOR UPDATE to both lost_update SELECTs enough?</summary>

Not with the same single-threaded interleaving. A obtains the lock, B waits, and the script has not yet reached A's commit: it may wait until timeout. Change scheduling so A can finish while B waits, or use the worker-thread pattern in this lab. Atomic UPDATE is simpler for addition. If locks are used, read, decision and write must share the lock-holding transaction, and locks should be released promptly.

</details>

## 9. Constraint races, lock timeouts and complete retries

In unique_race, A inserts login=race without committing and B tries the same value. B waits for A's outcome; after A commits, B receives `23505`. Exactly one row remains. An application SELECT checking absence cannot prevent both sessions passing a precheck. UNIQUE covers every writer. CHECK/FK/UNIQUE here are database guarantees, not a single-process in-memory lock.

In lock_timeout, A holds a FOR UPDATE row lock. B sets a 200ms transaction-local lock wait limit and attempts an update. The real result is `55P03`. After B rolls back, its query succeeds and minutes remains 30. This is not a network timeout; changing host is not a remedy. Production timeout values require policy; this small value makes the failure quick and recoverable for teaching.

In serialization_conflict, both sessions first read an old version under Repeatable Read. A adds 5 and commits; B's conflicting write receives `40001`. B rolls back and starts a **new transaction**, rereads, makes the decision again, adds 7 and gets 42. Retrying only the last statement is insufficient because earlier reads and decisions are stale.

This controlled case retries once to demonstrate the whole unit. Production should retry only appropriate failures, with bounded attempts, backoff and a total time budget, then surface a comprehensible failure. Do not retry every constraint error or loop within the same failed transaction. Different lock acquisition orders can also deadlock. Consistent ordering and short transactions reduce risk, but deadlock detection and full retry behavior require separate testing; no real deadlock drill is claimed here.

## 12. Recovery ownership, resource release and the ORM handoff

Identify the failure layer before recovering. Validate input before SQL. Explain constraint failures after rolling back the business transaction. For 25P02, find the earlier SQL failure. For 40001, redo the whole unit. For a broken connection, close it and address ambiguous outcomes rather than continuing to query. Tests use bounded timeouts; a finally block releases A's locks and connection contexts close resources on both sides. A failing assertion is not an excuse to leave background sessions behind.

```bash
uv run --locked python labctl.py stop
uv run --locked python labctl.py status
```

Stop affects only the identity-checked owned cluster, with an explicit data directory, fast mode and a wait for completion. Evidence is `running: false`, `pg_ctl_status: 3`. Files and logs remain for start to resume; use reset only when intentionally returning to seed state. Record final output, SQLSTATE, connection begin/commit order, passed tests and the next action so you can reconstruct the timeline after a break instead of memorizing ACID again.

The later ORM must preserve DDL fields/constraints, the timestamptz policy, nonautomatic updated_at and these failure tests. An ORM Session is another abstraction; it does not replace the distinction between connection, transaction and business unit. Authentication, at least/exactly one owner, creator membership and object permissions still need service rules and tests. Current foreign keys prove existence only. Do not hide those gaps behind “the database handles it.”
