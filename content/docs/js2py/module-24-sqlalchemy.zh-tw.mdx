## 1. 要保證的不是“兩條 INSERT 都寫了”，而是“一件事完成了”

創建項目時，先插入 projects，再插入負責人關係 project_members。第二步若失敗，前端收到錯誤，卻能在列表看見沒有負責人的項目，這是業務失敗，不是把錯誤文案改好便解決。D03 已經用 SQL 事務表達“全有或全無”；本章的問題是：HTTP 請求、Python 對象和數據庫連接之間，誰把這個承諾一直保持到提交結束？

ORM 是對象與關係表之間的映射工具，不是數據庫的替代品。它可生成參數化 SQL、追蹤待寫對象、按主鍵複用同一會話裡的對象；但不會替你決定業務邊界、自動給任意請求加權限，或消除數據庫約束錯誤。先學生命週期，再學調用方法，才不會把 add/commit 當作魔法咒語。

## 4. Engine、池、連接與 Session：四層不能混成一個變量

從請求向下看：路由借 Session → Session 需要執行 SQL 時向 Engine 借 Connection → 連接池提供 psycopg 的數據庫連接 → PostgreSQL 中的後端進程執行事務。Session 對 Python 對象的管理與數據庫連接的生命週期相關，但不是同一個東西。

| 對象 | 保管什麼 | 誰擁有，何時結束 |
| --- | --- | --- |
| Engine | 驅動/SQL 方言配置與連接池入口 | 一個應用進程通常建一次，進程退出時 dispose |
| Pool | 可重用的物理客戶端連接 | Engine 管理；不是啟動時立刻開滿所有連接 |
| Connection | 一段時間內借出的數據庫連接及事務訪問 | Session 內部或顯式 with 塊借用；close 通常歸還池 |
| Session | identity map、待寫對象、當前工作單元/事務狀態 | 一個請求一次使用，不在併發請求間共享；結束 close |

可以把 Session 的 identity map 類比組件樹內按 key 保留同一對象，但它不是 React 狀態庫，更不是自動訂閱全數據庫變化的全局緩存。兩個請求有兩個 Session，它們可能讀到不同時間的數據；數據庫隔離級別仍然決定可見性。

池可減少反覆建立連接的開銷，不能讓一條連接同時執行兩個互不相干的業務事務。示例 pool_size=2、max_overflow=0 是為了讓洩漏容易觀察，不是生產配置建議；多個 worker 各有自己的池，總連接預算不能只看一處的 2。pool_pre_ping 可在借出時檢查失效連接，但無法自動挽救事務中途斷線，也不能安全地替你重試未知是否提交成功的操作。

## 5. Session 的工作單元：排隊、發送、提交不是同一件事

構造 User 或 Project 只是建立 Python 對象。add 把它納入 Session 管理；flush 把待寫變化轉成 SQL 發往數據庫，可能取得 identity，也可能立刻碰到 CHECK/FK 錯誤。flush 成功不等於其他事務已經看見，更不等於持久化成功；隨後 rollback 仍可撤銷這些插入。

commit 通常先 flush，再要求數據庫結束事務。某些約束可延期到提交，磁盤/網絡也可能在這一階段失敗，所以“函數正常走到 return 前”不能代替“commit 已成功”。查詢前還可能 autoflush，不能假定只有手寫 flush 那一行才會觸發寫入錯誤。

Session 默認 autobegin：第一次需要數據庫的讀/寫就進入事務。GET 的 SELECT 也可能借連接並開啟事務；不關閉它就可能長期 idle in transaction。`with Session(...)` 負責關閉，不負責成功時自動提交；`with session.begin()` 才負責成功提交、異常回滾。顯式 begin 應包在首次讀寫外面，不能先 SELECT 開了事務再盲目 begin。

默認 expire_on_commit=True 會使持久對象的屬性過期，後續訪問可能再查數據庫；關閉後的對象也不應被響應序列化器拿來偷偷加載。這裡在事務內複製純 dict，並在提交成功之後才返回它，不把懶加載和關閉順序交給運氣。dict 在提交前構造不代表提前對外發送，commit 若失敗，返回路徑根本不會執行。

## 7. 業務函數借 Session，調用層擁有事務

create_project 先 flush 項目以得到 id，再用它寫負責人關係。兩個 flush 在同一事務內；第二步出錯時，調用層能撤銷第一步。如果函數內部先 commit 項目，外層再 catch/rollback 已來不及抹去已提交事實。不是“多加一個 rollback”能修好錯誤的事務歸屬。

## 8. HTTP 邊界：提交先完成，響應才宣稱成功

<Code language="python">{getOrmExample('api.py')}</Code>

依賴 get_session 只負責創建和 finally 關閉；寫路由的 begin 負責提交/回滾。退出 begin 後才 return，因此 deferred constraint 在 commit 失敗時仍能變成錯誤響應，而不是先發 201 再發現失敗。IntegrityError 在 begin 外捕獲，此時事務管理器已處理回滾；本教學接口把數據庫完整性衝突歸為脫敏的 409，不把 SQL、表細節或輸入回顯給用戶。

並非所有異常都應翻譯為 409。連接不可達、代碼錯誤等不在這個捕獲範圍內，應交給服務層的錯誤觀測和失敗政策。請求結構錯誤由 Pydantic 返回 422，父項目不存在為 404。正式產品應進一步按約束名細分業務錯誤，而不是吞掉所有數據庫異常。

路由用普通 def，數據庫調用都是同步的。lifespan 的 asynccontextmanager 只是 ASGI 的啟動/關閉協議包裝，不是異步 ORM；數據庫資源仍在明確同步代碼中使用。一個 Session 不可由兩個併發任務/線程同時操作，也不能全局緩存供所有請求共用。

輸入 owner_id/created_by 是本地教學臨時契約，不是認證方案。S 章節必須從驗證後的當前用戶推導這些值，移除客戶端自報身份，並增加成員權限校驗；本章 API 僅綁定迴環地址，不可發佈。

## 10. 故障實驗：真正在 COMMIT 時失敗

<Code language="python">{getOrmExample('commit_failure.py')}</Code>

```bash
uv run --locked python pg_sandbox.py -- python commit_failure.py
```

```text
two INSERT values accepted; deferred check awaits COMMIT
COMMIT failed
Session refuses reuse before rollback
rollback restored Session; next transaction committed one row
checked out: 0
```

額外的 commit_probe 表只屬於本次故障實驗，不改變業務四表。UNIQUE 被標記 DEFERRABLE INITIALLY DEFERRED，因此重複的 7 能先發送成功，commit 才拒絕。這與 flush 時 CHECK 失敗是不同時間點，不能用後者冒充提交失敗。

失敗後繼續 SELECT，會被 SQLAlchemy 的失效事務狀態拒絕。顯式 rollback 不只處理數據庫，也重置 Session 的事務記賬；然後開啟新的工作單元插入 8 才有意義。關閉失敗 Session 並用新 Session 處理下一請求也是正確政策。不要在異常捕獲後繼續把舊的待寫對象當成已持久化對象。

本例錯誤是服務器明確拒絕約束，因而能斷言沒有提交。若提交期間網絡斷開，客戶端可能不知道服務器是否已經提交；不能把“沒收到成功”一律當成“絕對沒寫入”。真實服務需要冪等設計/查詢確認，本章不偽裝成已解決這種不確定性。

## 12. 三層練習：先作答，再展開

**解釋題。** create_project 的第一個 flush 後已有 id。此時第二步失敗，為什麼項目仍可消失？為什麼 id 不必再從 1 連續分配？

<details>
<summary>答案：可用的主鍵不等於事務已提交</summary>

flush 發送了 INSERT 並取回 identity，但仍處在調用層未提交的事務。第二步失敗讓整個事務回滾，項目行隨之撤銷；序列分配不承諾隨事務回收，空洞不代表丟了業務記錄。不要以連續 ID 作為驗收。

</details>

**帶提示修改。** 把 Session 關閉邊界移除，再連發多個請求預測會發生什麼。不要把洩漏版留在參考實現。提示：將池維持為 2，不增加 overflow，分別觀察 HTTP 錯誤和借出計數。

## 14. 暫停記錄與下一次入口

暫停時寫下：當前分支/代碼差異；最後成功命令；10 項測試中已通過的項目；能否解釋 create/flush/commit/close 各自責任；尚未解決的錯誤及下次第一步。臨時庫退出就清理，所以保存的是生成數據的腳本，不是拷貝 DB data。

獨立離開本章前，應能不看答案畫出“請求→Session→Connection/池→數據庫”的生命週期，並說明為什麼 helper 內 commit 會破壞組合事務。若還認為 close 會自動提交，先回到測試，不急著進入遷移。下一章改變的是已存在數據庫的結構，不再靠 create_all。
