## 1. 备份的价值在于你能恢复什么

“每天有一个 .dump 文件”没有回答它属于哪个数据库、是否包含必要表、能否被读取、谁能访问、恢复要多久，以及恢复后的用户是否仍然安全。一个空文件也可以有正确名字；一个能列目录的归档也可能在执行恢复时失败。

本章把验收终点放在**隔离恢复后的可用性与权限**：实际 pg_restore → 数据指纹相同 → 约束仍拒绝坏数据 → 序列能继续写入 → 运行角色不是所有者 → 老凭证失效 → 合法用户只能访问自己的项目。最后才讨论是否满足受邀试用的上线门槛。

前端习惯说“刷新页面重试”。服务器数据没有这条退路：数据库损坏不会因重启自愈，唯一的恢复路径是把验证过的备份恢复到隔离目标。这就是本章把验收终点放在“恢复被证明可用”、而不是“备份文件存在”的原因。

## 2. 先明确备份范围，再选择工具

pg_dump 针对一个数据库生成一致性快照。本实验使用 custom 格式，交给 pg_restore 恢复；不是把 SQL 文本重定向给 psql。users、projects、project_members、tasks、auth_sessions、task_operations 和 alembic_version 全部纳入，包括一条真实非空的合成幂等回执，不能只备任务标题就声称业务完整。

单库 pg_dump 不包含集群级角色和表空间，也不替你保存服务配置、部署制品、加密密钥、对象存储文件、日志与外部安全变更记录。这里显式使用 no-owner/no-privileges，角色由私有集群工具重新准备，权限通过审查的 grants.sql 恢复，而不是盲目复制旧环境的超级用户身份。

## 3. RPO 与 RTO：先给定义，再量一次

RPO 是业务可接受的最大数据损失时间窗口；RTO 是业务可接受的恢复服务时间目标。它们是目标，不会因为写在 README 里就成为保证。每天一次备份也不自然满足“最多丢一天”：任务失败、备份不可读、复制延迟、发现故障较晚都可能扩大实际风险。

本实验在快照后再提交一条任务，恢复后明确观察它不在目标库中；因此已知损失是一条 post-snapshot 记录。还测量从开始恢复到完成数据、安全和真实 API 验证的时间，输出 restore_and_validation_seconds。snapshot_age_seconds 记录这份小快照在检查时的年龄，不把它等同于生产实际 RPO。

本机小数据、同版本工具、同一宿主、无远程传输的亚秒或数秒结果，不能外推到大库、故障网络或跨机恢复。真实演练还要把发现、决策、取回归档、解密、容量准备、验证和批准开放的时间纳入约定范围。

<details>
<summary>解释题答案：为什么“pg_restore 只花一秒”不等于 RTO 一秒？</summary>

服务还可能没有正确角色、凭证、DNS/代理入口或兼容应用；恢复数据也可能缺了表、违反预期权限，或把已撤销的会话复活。计时只覆盖数据库导入会漏掉这些必要步骤。应先声明 RTO 的起止事件，再从一次完整、代表性的演练记录各阶段耗时，并保留不确定性。

</details>

## 4. 不允许凭一个外部 URL 选择恢复目标

覆盖错误数据库是比恢复失败更糟的事故。工具从不接受现有 DATABASE_URL，只能创建允许名字中的**新**数据库；名字已经创建过就拒绝，不提供 --clean 覆盖捷径。目录也必须是本次进程拥有的私有路径，并核对 UID、模式、标记与非符号链接条件。

数据库只用私有 Unix socket，不占用用户的 TCP 5432；恢复源和目标是同一自有集群里的不同数据库。这个隔离足以避免改写源数据，但**不是异机灾难恢复验证**。应用子进程只监听 127.0.0.1 动态端口；finally 停自己的进程、关闭端口、删除自己的目录，绝不扫描并停止其他 PostgreSQL 服务。

恢复目标创建时撤销 PUBLIC 的 CONNECT；数据、约束和安全处理尚未通过之前，不授予运行角色连接权限。单纯“不告诉别人地址”不如明确的权限隔离，尤其是同集群数据库里角色是全局对象。

传入私有 socket 的 host 还不够：libpq 仍可能从 `PGHOSTADDR`、`PGSERVICE`、`PGSERVICEFILE` 等环境变量取得另一个连接默认值。`reject_connection_environment` 在创建临时目录之前，以及每次直接连接、迁移和服务启动之前，拒绝继承的全部 `PG*` 变量，唯一例外是只定位可执行文件的 `PG_BIN`。错误只列变量名，不打印值，也不修改调用者环境。Python 连接、SQLAlchemy 的连接创建器和 PG 子命令都使用自有目录内的空白 0600 `empty.pgpass`，不读取用户的默认密码文件。直接运行 `demo.py` 或 `ci.py` 也执行这些防护，不依赖仓库总 runner 先替它清理。

启动 API 不再先探测空闲端口、关闭探测 socket，再要求另一个进程抢占同一号码。Uvicorn 自己用 `--port 0` 完成绑定；控制器从**该子进程自己的私有启动日志**读取实际端口，再请求 readiness。`--no-access-log` 不关闭 info 级启动 banner；控制器固定无颜色日志和单 worker。两个同版本服务也使用不同日志文件。测试实际同时启动两个服务，核对两个不同端口、各自 banner、真实请求和退出清理。这消除了选端口后释放再绑定的窗口，不是对任意并发故障的保证；未来 Uvicorn 改变 banner 格式时会超时拒绝，不猜测端口。

## 6. 恢复认证表会带回什么风险？

S 合同里的 opaque token 是否有效取决于数据库状态。备份后用户退出全部会话、被停用或成员关系被移除；如果把较早的 users/auth_sessions/project_members 恢复回来，旧 token 可能再次符合当时的 auth_version/expiry，旧成员关系也可能重新出现。恢复“每行都一样”本身就可能重新引入权限风险。

因此目标库仍隔离时，quarantine_sessions 先停用所有恢复用户、递增 auth_version、删除恢复出的会话。之后必须根据**备份之外的可信安全变更记录**核对账号和成员关系，再明确批准启用。本实验的合成变更记录是 Bob 已被移出 Alice 项目；参考过程重放这条变更，批准两个合成账户，操作员生成新的测试会话。

这不是“恢复时自动给所有用户重新登录”。如果真实环境没有可信的较新权限记录，就保持隔离或账户停用，交由授权操作员人工审核；不能用陈旧备份证明“应该还是这些成员”。密码修改后的旧密码哈希也是需要核对的资产，实际系统可能需要强制重置、另行保留撤销记录或其他恢复政策。

服务只做这次运维切片的项目读写与会话检查，没有公开登录或重新激活账户的后门。项目不可访问时仍返回 404。运行角色对 users/auth_sessions 只有读取权限，不能通过本实验应用自己恢复管理权限。

<details>
<summary>安全检查答案：只删除 auth_sessions，不核对 project_members，够不够？</summary>

不够。旧 token 虽然失效，但用户后来通过合法登录取得新 token 后，仍可能凭恢复出的过时成员关系访问已经被撤销的项目。会话失效和对象权限恢复是两件事。需要先隔离、处理凭证状态，再核对账号与成员权限，最后批准开放；没有权威记录时应失败关闭，而不是猜测。

</details>

仓库总 runner 为子进程重建环境：丢弃继承的 `UV_*`、虚拟环境选择与 Python 注入设置，再固定课程 cache/Python 安装目录、public PyPI 和 `UV_NO_CONFIG=1`；`PG*` 也只保留 `PG_BIN`。实测使用自己创建的“外部虚拟环境”诱饵、错误解释器路径和无效用户 uv 配置，确认安装只发生在当前干净副本的 `.venv`，诱饵目录内容不变。不要把这些防护误解为能修复已经在脚本启动前运行的外层 uv：手动执行下方 uv 命令前，应退出其他虚拟环境并使用干净终端；清除 `VIRTUAL_ENV`、`UV_PROJECT_ENVIRONMENT`、`UV_ACTIVE`、`UV_PYTHON`、`UV_CONFIG_FILE` 等覆盖项，并设置 `UV_NO_CONFIG=1`。若直接 Python 入口拒绝 PG 变量，只在本次实验环境中移除它报告的名字，不修改生产配置、更不打印其值。

```bash
uv sync --locked
uv run --locked python ci.py
uv run --locked python demo.py
```

ci.py 已运行一次演练；单独 demo 是可重复重放。关键稳定输出：

```text
PASS backup: custom archive and inventory created privately; restore still required
PASS restore: actual pg_restore, all table fingerprints match; corrupt restore rejected
PASS security: stale/expired tokens denied; reviewed memberships; cross-user 404; app cannot DROP
CLEANUP PASS: source/targets/archive/private logs and owned processes removed
```

程序还输出 MEASURED JSON，真实耗时每次不同。不能把计时值写死来“稳定测试”。流程先故意损坏一份副本，验证校验和拒绝，并且让 pg_restore 本身实际读损坏归档而失败；坏目标保持没有用户表。随后恢复完整归档，逐表指纹通过后验证：

- 重复 login、缺失父项目、负 minutes、第二个 owner 都被真实约束拒绝；失败事务退出后还能查数据。
- 观察旧 Alice token 在尚未开放的恢复库里原本会复活，再执行账户/会话隔离与权限核对。
- 通过真实 Uvicorn 请求，旧 token、过期 token 和无效 token 返回 401；新 Alice 能读自己的项目，读 Bob 项目是 404；新 Bob 不能读 Alice 项目。
- 恢复后的 identity 序列能生成新项目 ID，不与旧数据冲突；应用角色 DROP TABLE 被拒绝。
- source 中快照后新增的第三条任务仍在，restored 只有快照中的两条；恢复没有改写源库。

这比“pg_dump 返回 0”多了哪些证据，应能逐条解释。恢复不是把文件拷贝到 data 目录；逻辑归档也不是物理数据目录备份。

## 10. 一份能执行的恢复手册

在真实环境之前，用本实验的顺序写明操作责任人和证据位置：

1. 宣布事件范围，暂停危险写入或入口；不要先覆盖现有数据再询问。
2. 选择可信、可解密且有明确时间点的备份，核对版本、范围和保留策略。
3. 准备容量足够的全新隔离目标、角色与私密目录，禁止普通客户端连接。
4. 执行恢复，记录工具退出码与耗时；任何失败都不开放服务。
5. 核对数据指纹/业务样本、约束、序列、迁移版本、应用兼容性和最小权限。
6. 处理账号、密码/会话状态、成员权限及其他备份后安全变更；批准前保持停用。
7. 用新凭证和两个用户跑成功/拒绝场景，检查日志脱敏，再由授权人员批准入口切换。
8. 观察错误、延迟与数据差异，保留原环境作为调查证据，按审查过的保留政策清理。

不要在手册里写真实 token、密码或完整连接秘密。把能恢复的时间点、已知损失、实际耗时与未解决风险报告给使用者；不是只报告“服务绿了”。本实验只完成本地部分，不能伪造生产操作者审批或公网切换结果。

## 11. 受邀上线门槛，不是开放注册
