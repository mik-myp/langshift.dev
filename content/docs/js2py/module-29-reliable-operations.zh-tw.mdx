## 1. 沒收到響應，不等於服務器沒做事

前端禁用提交按鈕可以減少重複點擊，卻擋不住網絡中斷、頁面刷新、代理重試或兩個客戶端同時提交。假設服務器已經插入任務並提交，但響應在路上丟失：客戶端只知道“沒有收到結果”，無法據此斷言事務回滾。直接再發一次 POST，可能產生第二個任務。把每次重試都包裝成新事務，並不能解決這個問題。

| 本章契約 | 範圍 |
| --- | --- |
| 前置 | S02 的身份、對象權限和同步 API；D03 的事務、約束與兩連接；D06 的真實 PG/HTTP fixture |
| 新能力 | 定義冪等範圍、規範化請求、保存公開回執、原子提交、觀察唯一索引競爭、重放前重驗權限、明確 TTL/清理邊界 |
| 獨立驗收 | 同 key 同 payload 返回同一任務；不同 payload 得 409；同時請求只提交一項；回滾不留下半成品；撤權後不能取回舊回執 |
| 暫不實現 | 恰好一次投遞、跨服務事務、消息隊列/outbox、任意故障自動重試、生產清理調度與容量承諾 |

## 2. 先把“相同請求”變成明確契約

本章客戶端為**一個邏輯創建操作**生成 UUIDv4，放在 Idempotency-Key 請求頭。請求結果未知時，重發同一個 key 和同一個邏輯 payload；真正要再創建一項時才換 key。UUID 不證明身份，也不是不可猜測對象權限的替代。服務仍先驗證 Bearer 和當前成員關係。

| 情況 | 本例響應 | 數據庫結果 |
| --- | --- | --- |
| 新 key、合法成員、合法任務 | 201；Idempotency-Replayed: false | 任務和回執一起提交 |
| 有效期內，同範圍同 key 同 payload | 原來的 201；Idempotency-Replayed: true | 不插入第二項 |
| 同範圍同 key，不同 payload | 409 | 不改原任務和回執 |
| key 缺失、不是規範小寫 UUIDv4 | 脫敏 422 | 不產生任務 |
| 過期但仍保留的回執 | 409，要求核對結果 | 不自動重新執行 |
| 會話失效 / 項目權限已撤銷 | 401 / 404 | 不返回歷史回執 |

範圍是 actor_id + project_id + operation + key。actor_id 從認證取得，operation 由服務固定為 create-task-v1，不接受客戶端自選。Alice 與 Bob 即使使用同一個 key，也不是同一次操作；同一人在兩個項目使用同 key 也獨立。這樣不會把一個用戶的響應誤發給另一個用戶。未來變更操作語義，需要顯式考慮 operation 版本，而不是讓舊回執被新代碼隨意解釋。

## 3. 從故障窗口推導事務邊界

```text
request -> authenticate -> guard current project membership
                          |
                  unique receipt claim
                  /                  
            winner                    existing key
              |                           |
        insert task                 read committed receipt
        fill public receipt         expiry + digest checks
              |                           |
       commit BOTH                  replay original response
              |
       HTTP response may be lost
```

如果先提交任務、再寫回執，進程在中間退出就會留下“任務已存在但沒有去重依據”。如果先提交一個空回執再創建任務，失敗可能讓重試永遠拿到空結果。因此一個事務必須包含認領 key、創建任務、填寫回執。任何提交前異常都回滾三者；提交後丟失響應由同 key 重放解決，而不是猜測服務是否曾執行。

這隻覆蓋本地數據庫寫入。事務裡調用外部郵件/支付服務不會自動加入 PostgreSQL 回滾；不能把本例函數包住網絡調用就宣稱跨系統恰好一次。可靠外部副作用需要另一套可審查協議，本章不隱瞞這個缺口。

## 5. 規範化先於摘要，不對原始 JSON 字符串做比較

<Code language="python">{getReliableOperationExample('schemas.py')}</Code>

TaskInput 先做運行時驗證：title 非空白但保留原字形；minutes 普通非負 int，拒絕 bool/text/float；status 有限枚舉；額外字段禁止。缺省值補齊後，model_dump(mode="json") 得到明確表示，再按字段名排序，用固定分隔符序列化並求 SHA-256。客戶端 JSON 字段順序不同不算不同請求；省略 minutes 與顯式 minutes=0 等價。

due_at 是一個特別需要先講清的轉換：JSON 沒有 datetime 類型，因此代碼只在這個邊界明確解析帶偏移的 ISO 時間並轉 UTC，其餘字段仍嚴格驗證。同一時刻的 +08:00 與 +00:00 歸一化後相同。沒有偏移的時間被拒絕，不猜測客戶端時區。title 則不 trim："Review" 與 " Review " 在本章是不同 payload，不因為它們看起來相似就合併用戶意圖。

<details>
<summary>解釋性答案：為什麼不直接 hash(request.body())？</summary>

</details>

## 6. 跟隨認領者與等待者，理解為何要第二條 SQL

<Code language="python">{getReliableOperationExample('reliable.py')}</Code>

create_task_once 一進入就調用 guard_project，取得項目共享鎖並檢查當前成員。然後嘗試 INSERT ... ON CONFLICT DO NOTHING RETURNING key。插入成功的請求是認領者；它調用 create_task，驗證公開模型，填入回執，最後由 HTTP 入口提交，輔助函數不偷偷 commit。

另一個連接可能同時認領同一複合主鍵。PostgreSQL 唯一索引會等待未提交的競爭事務。若先行者提交，後來的 INSERT 不插入；若先行者回滾，後來的 INSERT 可以成功。本章沒有使用 Python 字典或線程鎖假裝跨進程唯一保證。

<Code language="python">{getReliableOperationExample('db.py')}</Code>

引擎顯式使用 READ COMMITTED。每條語句取得自己的已提交視圖；ON CONFLICT DO NOTHING 可能因為另一個事務的行而放棄插入，即使那個行不在本條 INSERT 最初的快照中。因此等待結束後要執行**新的 SELECT**，並對回執取排他鎖，再檢查過期與摘要。不能在原快照裡反覆尋找，不能把“這次沒有 RETURNING 值”誤讀成“任務不存在”。

若運維同時清理過期回執，新的 SELECT 也可能找不到；本例返回 409 要求核對，不悄悄創建另一項。所有鎖都持有到事務結束；約定順序為用戶、會話、項目、任務/回執。已測路徑不等於任意新業務組合都無死鎖，更不自動帶來無界吞吐。

<details>
<summary>故障推演答案：認領後插入任務，再拋異常會怎樣？</summary>

只要還在同一個 Session.begin 裡，任務和暫存回執都回滾。下次請求可以認領同 key 並創建一項。自增序列可能已經前進，ID 出現間隙並不是偷偷多提交了一項。測試應數已提交行、檢查回執與結果，而不是要求每次失敗後 ID 連續。若你把輔助函數里的 flush 改成 commit，就破壞了這個推理，必須讓故障測試抓住它。

</details>

## 7. 重放仍是受保護的數據讀取

<Code language="python">{getReliableOperationExample('app.py')}</Code>

入口先認證，再調用事務內的冪等服務。重放不是“緩存命中就跳過所有邏輯”：持有舊 key 的已移除成員必須得到 404；已退出或改密後的舊令牌必須得到 401。保存的公開結果也屬於項目數據，不能因為是歷史回執就對任何知道 key 的人公開。

這裡的撤權保證有明確順序：已持用戶/項目共享鎖的操作可以完成，改密、停用或成員移除等待相應排他鎖；撤權事務提交後，新的受保護操作觀察到新狀態並被拒絕。不能追回已授權發出的響應。全局項目列表仍是 S02 的成員過濾語句快照，不具有逐項目鎖或 items/total 一致快照承諾。

登錄、驗證錯誤與數據庫失敗繼續使用 S01 脫敏策略；SQL 參數隱藏不是驅動異常文本自動安全的證明，數據庫異常適配器只返回通用 409/503，不輸出異常 repr。測試檢查應用及 PostgreSQL 日誌中的秘密標記。任意未來日誌、反向代理、APM 和未知第三方異常需要額外審查。

## 9. 真實請求：重放、衝突、撤權與恢復

```bash
uv run --locked python client.py --port 8063 --session .session-alice.json login Alice
uv run --locked python client.py --port 8063 --session .session-bob.json login Bob
uv run --locked python client.py --port 8063 --session .session-bob.json request POST /projects --json '{"name":"Reliability lab"}'
uv run --locked python client.py --port 8063 --session .session-bob.json request POST /projects/1/members --json '{"user_id":1}'
KEY="$(uv run --locked python -c 'import uuid; print(uuid.uuid4())')"
uv run --locked python client.py --port 8063 --session .session-alice.json request POST /projects/1/tasks --key "$KEY" --json '{"title":"Review","minutes":15}'
uv run --locked python client.py --port 8063 --session .session-alice.json request POST /projects/1/tasks --key "$KEY" --json '{"minutes":15,"title":"Review"}'
uv run --locked python client.py --port 8063 --session .session-alice.json request POST /projects/1/tasks --key "$KEY" --json '{"title":"Review","minutes":16}'
uv run --locked python client.py --port 8063 --session .session-bob.json request GET '/projects/1/tasks?limit=10&offset=0'
```

前兩次任務創建都為 201，返回同一個 id，頭依次為 false/true；第三次為 409；列表 total 為 1。key 是操作標識，不是憑證，可以記錄用於核對，但也不該無限收集業務關聯元數據。Bearer 從不在 --json 或 --key 傳遞，客戶端不打印原令牌。

```bash
uv run --locked python client.py --port 8063 --session .session-bob.json request DELETE /projects/1/members/1
uv run --locked python client.py --port 8063 --session .session-alice.json request POST /projects/1/tasks --key "$KEY" --json '{"title":"Review","minutes":15}'
uv run --locked python client.py --port 8063 --session .session-alice.json request GET /users/me
```

依次為 204、404、200：Alice 仍是已認證用戶，卻已不能重放項目數據。恢復由 owner 重新邀請；如果回執仍在有效期內，同 key 可取回原結果。不能讓 Alice 提交 role 來恢復權限，也不能換 key 逃過權限檢查。

另做缺 key、UUIDv1/大寫 key、無偏移 due_at 的失敗實驗，預期 422 且不產生任務。把響應丟失理解為“結果未知”：保留同一 key 重試並核對；409 不應被一個 while True 盲重試掩蓋。

## 11. TTL 是保留協議，不是魔法過期刪除器

默認回執有效期 86400 秒，IDEMPOTENCY_TTL_SECONDS 允許 60–604800。過期但保留的 key 返回 409，要求客戶端先核對是否已有任務；不能直接把過期當作“從未執行”。本地應用使用 UTC 時鐘，多實例需要額外時間同步和偏差策略。

<Code language="python">{getReliableOperationExample('purge_expired.py')}</Code>

```bash
uv run --locked python purge_expired.py
uv run --locked python purge_expired.py --apply
```

第一條只報告待刪數量，第二條是明確的運維刪除操作。清理後服務器已不記得舊 key，重用它可能創建第二項。測試在專用庫調整過期時間，驗證保留期衝突、顯式清理及去重邊界結束；不讓讀者等待一天才有證據。生產需要約定客戶端最長重試窗口、回執保留/備份、刪除責任、審計和調度，不應照搬本實驗手動清理就對外承諾永久去重。

<details>
<summary>邊界答案：保留更久是不是總能解決可靠性？</summary>

更長保留能覆蓋更長重試窗口，但有存儲、隱私、索引和刪除成本，也不能解決客戶端換 key 或外部副作用。這個協議只對同一範圍、同 key、同規範化 payload、有效權限和保留規則成立。過期回執刪除後，不存在一個隱藏的“永遠記得執行過”的機制。必須把邊界寫進 API 與運維契約，而不是把數據庫表稱作永久緩存。

</details>

## 13. 獨立重建與可驗收變式

**獨立重建：** 只攜帶環境、既有身份/權限契約及 001–005 遷移，在新目錄自己設計 006、payload 規範化、認領與重放服務。不要導入參考 reliable.py。先預測故障窗口，再重做同 key、異 payload、兩連接提交/回滾、撤權、API/PG 重啟和過期清理。提交狀態碼、已提交行數與阻塞關係，不提交秘密或只提交綠燈截圖。

**變式 A：** 故意把 minutes 缺省省略，與顯式 0 的請求比較；再改成 1，證明只有最後一個衝突。改變 title 首尾空格不得被誤認為同一請求。解釋你的規範化契約，而不修改規則去迎合現有測試。
