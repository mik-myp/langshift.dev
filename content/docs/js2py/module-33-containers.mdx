## 1. Why a container does not let you skip the operating system

You can now explain cwd, environments, permissions, ports, and signals. Containers organize those conditions into repeatable boundaries; they do not abolish them. A wrong directory still loses files, a non-root account may still lack volume permissions, and the process receiving a stop signal must handle it correctly. Copying a Dockerfile without identifying state ownership can make removing and recreating an instance delete your only data.

## 2. Separate image, container, host, and engine

An image consists of filesystem layers and startup metadata, serving as a common starting point for multiple instances. A container is an instance created from that image, with process/network isolation and a writable layer. It is not a complete second computer; it normally shares its Linux host’s kernel. macOS commonly needs a Linux VM to host these containers. Having Python, Homebrew, or a Docker CLI does not establish an available Linux engine.

The Docker CLI sends requests to an engine. Its context or DOCKER_HOST can point remotely, so a local command can affect somebody else’s server. This lab never uses the default context, lists all user containers, or prunes resources. Its runner requires an explicit local UNIX socket and controlled-engine confirmation, and uses an empty temporary Docker configuration rather than reading credential helpers. Engine-socket access is powerful and does not belong inside an ordinary business container.

An image tag is a movable name, not a content checksum. Pinning a Python version is clearer than latest, but without resolving and recording the actual digest we cannot claim byte-identical image reproduction or completed supply-chain review.

## 4. Build context: secrets should not be sent even if not copied

In `docker build .`, the final dot identifies the build context, normally the current directory. COPY source paths come from that context. Using a repository root, home directory, or cache directory can submit unrelated files, .env values, credentials, and large caches to the builder. A few selective COPY statements are not the entire boundary: minimize the submitted inputs too.

## 5. Non-root and a read-only root: permit only necessary writes

Building an image commonly requires privilege to create directories and users, but running it should not retain that authority. The Dockerfile creates numeric UID/GID 10001, owning /data but not application source. `USER` selects the default identity; Compose declares the same identity for review. Numeric ownership affects volume access: an account named app inside a container does not automatically make a host directory writable.

Compose’s read_only restricts the container root filesystem. The /data named volume is the declared persistent write location; /tmp is a size-bounded temporary memory filesystem. cap_drop ALL removes additional Linux capabilities and no-new-privileges constrains privilege gain through execution. These reduce risk, not all kernel vulnerabilities, and do not implement authorization. Disabling Python bytecode writes avoids unnecessary attempts to modify read-only source directories.

<Code language="json">{getContainerOpsExample('compose.json')}</Code>

We deliberately use JSON for the Compose file. Compose accepts this YAML subset, but select it explicitly with `-f compose.json` rather than assuming automatic discovery. `init: true` adds a small init for orphan reaping and signal forwarding; exec-form CMD does not interpose a shell. stop_grace_period allows normal stopping, while restart=no keeps failures observable without automatic restart. ## 6. Configuration and secrets: export is not a vault

OPS_DATA_DIR is non-secret path configuration and can appear openly in Compose. Database passwords and Bearer tokens are different: do not put them in Dockerfile ENV/ARG, image layers, build logs, command-line arguments, or the example ZIP. Deleting a file in a later image layer does not prove it is absent from earlier layers. Ignoring .env reduces build exposure; it does not secure the file’s contents.

A controlled platform can mount a secret read-only into the authorized service or inject it using a reviewed secret manager. Compose secrets provide per-service file mounting, not automatic host-file protection, backup, rotation, or revocation. ## 7. Network namespaces: do not confuse two loopbacks

Host 127.0.0.1 refers to the host network, while a container’s 127.0.0.1 refers to its own network. If an application binds only container loopback, connections forwarded from outside that namespace generally cannot reach it. The Dockerfile therefore listens on **container-internal** 0.0.0.0:8000, while Compose publishes only **host-side** 127.0.0.1:8033:8000. This is not an instruction to listen publicly on the host; both boundaries matter.

EXPOSE 8000 is metadata, not a host-port publication. Another container also cannot find this service at its own 127.0.0.1; controlled container networking and a service name are normally needed. This lab has no database container and never connects to the user’s PostgreSQL. Real deployment must also verify host firewalls, IPv6, and VM forwarding rather than inferring all network safety from one ports line.

Docker documents a localhost-publication exception for same-L2 hosts with engines older than 28.0.0. The runner therefore requires Linux Engine >=28. Checking that version addresses this known gate, not a complete security audit.

## 8. Volumes and writable layers: restart is not recreation

“Containers lose their data whenever restarted” is an incorrect slogan. **Stopping and starting the same container normally preserves its writable layer**. Removing it and creating a new container from the image does not automatically transfer that layer. A named volume has an independent lifecycle and can be reattached to a new instance, but it can still be explicitly deleted or lost with host storage. A persistent volume is not a backup.

volume_probe maintains a disposable counter in an explicit directory. Separate processes reading the same path can preserve it, which alone does not verify Docker volumes. The real runner checks three cases: a named volume retains 1 after recreation; a writable layer retains 1 after stop/start of the same container; a newly created unmounted container begins at 0. File replacement provides neither concurrent transactions nor power-loss guarantees. Do not apply this copying method to a live PostgreSQL data directory.

## 9. Health: alive, ready, and business-correct are three claims

`/health/live` returning 200 proves only that its handler answers. `/health/ready` attempts a temporary write in the data directory and returns 503 on failure. Its dependency is a writable teaching directory, not a database connection. S03 needs its own DB-backed readiness; migration, permissions, and business tests remain separate. A service leaking Bob’s data to Alice can stay healthy indefinitely.

Docker HEALTHCHECK periodically executes healthcheck.py and uses its exit status as health information. Ordinary Docker does not automatically restart this container merely because it becomes unhealthy. Restart policies primarily respond to process exits; scheduling and traffic decisions depend on other platform rules. Avoid amplifying a short DB failure by repeatedly killing processes through an inappropriate liveness check. Health responses must not expose connection strings or secrets.

## 11. Failure diagnosis: locate the boundary before granting power

| Failure | Likely boundary | Next step |
| --- | --- | --- |
| CLI/socket absent | No local runtime | Record environment_pending; do not silently install or connect remotely |
| Image/dependency download fails | Tag, architecture, network, or index | Inspect the build stage; switching to latest does not prove reproduction |
| Application cannot write /data | UID and volume ownership mismatch | Inspect the dedicated volume, not permissions on real user directories |
| Host connection fails while process lives | Internal binding and host publication | Inspect both boundaries instead of exposing the service publicly |
| healthy but /tasks=404 | Only the smoke app was deployed | Not a CORS fault; the authorized business app is not integrated |
| Counter lost after recreation | Writable layer or wrong/new volume | Compare restart and reattachment before deleting volumes to retry |

Do not replace the image, volume, and application version simultaneously and guess what fixed it. Change one boundary at a time and retain the last successful observation. Real databases require the later backup/recovery material, not this disposable-file exercise dressed up as recovery.

## 12. Explanation checkpoint: reject three convenient inferences

Explain why stop/start can retain data without a volume while recreation does not, why container-internal 0.0.0.0 does not necessarily publish the host publicly, and why healthy cannot prove an Alice/Bob authorization test passed. Name the boundary instead of answering “because Docker.”

<details>
<summary>Answer and explanation</summary>

The same instance retains its writable layer; a new one begins from its image and explicitly mounted state, without inheriting the old layer. Internal listening belongs to the container network namespace; host publication depends separately on ports, engine behavior, and firewall rules. A health script checks declared technical dependencies, not two users’ identities and resource permissions. Each false inference substitutes success at one layer for a guarantee at another.
