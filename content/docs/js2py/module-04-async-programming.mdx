## 1. Why put code into functions only now?

L03 processed changing numbers of tasks and explained how empty input, unknown estimates and a zero budget move through control flow. Now the same rules must serve both 20-minute and 40-minute study arrangements, then run again after inputs change.

Copying an entire script may produce a result temporarily, but it creates multiple versions of the rules. Updating one and forgetting another can make them disagree about whether zero minutes are valid. We want to name existing logic, specify its inputs, outputs and mutation behavior, and call it from different places.

**A function is not a box that makes code look more engineered. It is a callable object with an input, output and side-effect contract.** We explain execution first, then apply it to task rules. Learning def does not require classes, decorators, module splitting or FastAPI.

## 2. Defining is not calling: establish execution order first

File: `definition_and_call.py`.

<Code language="python">{getFunctionExample('definition_and_call.py')}</Code>

Expected:

```text
Before definition
After definition
Inside call
25
```

There are two distinct actions here:

- Executing `def add_buffer(minutes):` creates a function object and binds add_buffer to it. **The body does not execute yet.** Minutes is a parameter: a name for a value this logic needs to receive.
- `add_buffer(20)` calls it. Twenty is the argument; this call binds the local name minutes to that integer and starts executing the indented body.

`return minutes + 5` computes a result, ends **this particular function call**, and supplies the value to the call expression. Thus `result = add_buffer(20)` waits for the synchronous call to finish, binds the returned 25 to result, and continues to the next statement.

Trace it as: top-level statement → execute def → top-level statement → enter call → execute body → return to call site → subsequent top-level statements. Inside call is diagnostic output to reveal timing; calculation rules do not need to keep such prints permanently.

Notice three details:

1. A function uses a colon and indentation like if/for, but also establishes its own local namespace. We will explain that gradually.
2. Blank lines separate code for readability; they do not start or end a function. Returning to the outer indentation level resumes top-level code.
3. An ordinary function does not require self. Instance methods belong to the later class material, not a universal Python-function template.

## 3. return versus print: passing a result versus producing output

### 3.1 A call expression has a result, even when it is None

Print writes to standard output; return gives an object to the caller. Seeing a number in the terminal does not mean the caller received that number.

File: `return_paths.py`.

<Code language="python">{getFunctionExample('return_paths.py')}</Code>

Expected:

```text
done
unknown
pending
Ready: Read
None
None
```

Distinguish these three functions:

- `status_label` ends the current call at the first reached return. A completed task returns done without checking its estimate; a zero-minute pending task returns pending. Returning a string does not automatically print it.
- `announce` executes print but has no return statement. Reaching the end implicitly returns None. Ready: Read is the function's output; the following None is the caller printing the returned value afterward.
- `maybe_announce` uses a bare return for an empty title: it returns None immediately without printing a title. For a nonempty title it prints, reaches the end and also returns None. These paths have different side effects but the same return value.

Return exits the current function, not merely an if or loop. It does not directly terminate the entire script. A function promising a business result needs every return path checked, rather than returning on only one branch and accidentally falling through to None elsewhere.

## 4. Parameters and arguments: which name receives which value?

Parameters are names in def; arguments are objects or expressions supplied by a particular call. They are different levels: one definition can serve many calls with different inputs.

File: `arguments.py`.

<Code language="python">{getFunctionExample('arguments.py')}</Code>

Expected:

```text
25
45
20
40
```

| Call | This call's minutes / repeats / extra | Explanation |
| --- | --- | --- |
| `estimate(20)` | 20 / 1 / 5 | Minutes is required; other parameters use defaults |
| `estimate(20, 2)` | 20 / 2 / 5 | Positional arguments follow parameter order |
| `estimate(20, extra=0)` | 20 / 1 / 0 | Name extra without supplying repeats first |
| `estimate(repeats=2, minutes=20, extra=0)` | 20 / 2 / 0 | Keywords match by name, not their written order here |

In this ordinary signature, required positional parameters come before those with defaults. At a call site, extra=0 is a keyword argument, not a new caller-side variable. It is the same mechanism as L03's `enumerate(..., start=1)`.

Python binds arguments before entering this function's body. Unsuitable counts or names fail, but **successful binding does not validate business types or ranges**. This example expects appropriate numeric inputs; it does not automatically parse `"20"` or reject negatives.

## 5. Binding parameters does not copy objects: bring L02's model into functions

A call binds a local parameter name to an argument object. **There is no automatic deep copy, and rebinding a parameter does not automatically redirect the caller's name.** Rather than relying on the overly short labels “by value” or “by reference,” inspect the actual objects and bindings.

File: `argument_binding.py`.

<Code language="python">{getFunctionExample('argument_binding.py')}</Code>

Expected:

```text
Read
Local
False
None
['python', 'functions']
```

| Operation | What changes? | What does the caller observe? |
| --- | --- | --- |
| Enter replace_local | Local task and original refer to the same dictionary | No mutation yet |
| `task = {...}` | Rebind only the local task to a new dictionary | Original still refers to the old object |
| `return task` | Give the new dictionary to the caller as replacement | Replacement and original differ |
| `task["tags"].append(topic)` | Retrieve and mutate the inner list through a shared dictionary | Original's tags change |

`add_topic` is designed to mutate the supplied object, so returning None is intentional rather than an omission. Conversely, unexpected None is wrong when a function promises data for further calculation. Neither “all functions must be side-effect-free” nor “returning None is always bad” replaces a concrete contract.

Using local parameters does not make a function fully isolated from its surroundings. Returning a new list does not guarantee new dictionaries inside it either. Analyze copied layers using L02's data shapes. Our task constructor will explicitly isolate a caller-supplied tag list.

## 6. When are defaults established, and why can a second call affect the first?

### 6.1 Default expressions are evaluated when def executes

File: `default_values.py`.

<Code language="python">{getFunctionExample('default_values.py')}</Code>

Expected:

```text
20
0
None
35
```

Each time **this def statement executes**, its default expressions are evaluated once and the resulting objects retained as that function's defaults. The expressions are not reread on every call. Here default_minutes was 20 when def executed. Rebinding it to 35 later does not replace the default object already stored by the function.

Only omitting minutes uses its default. Explicit zero remains zero; explicit None remains None. Python does not automatically treat None as “argument omitted.” The final call explicitly reads the current default_minutes and therefore passes 35.

This does not mean defaults are evaluated only once for an entire process. Executing a def repeatedly inside another function would create distinct function objects with their own defaults. For now, distinguish a particular definition from its subsequent calls.

There are two separate design decisions:

1. When tags is None, create an empty list inside the body. This executes on every call, giving two tasks with omitted tags separate lists.

## 7. Scope: where does a name come from, and why can an outer name still fail?

### 7.1 Every call has its own local bindings

File: `local_scope.py`.

<Code language="python">{getFunctionExample('local_scope.py')}</Code>

Expected:

```text
local: Read
module
20
35
```

`format_label`'s parameter label is local to this call and shadows the top-level label. Prefix is local too. The top-level label remains module afterward. Separate calls have their own local bindings; using the same names does not automatically create global state.

`current_limit` does not bind limit locally, so it reads the file's top-level limit. Between calls, top-level code rebinds it from 20 to 35, and the next call reads 35. This differs from a default object **already evaluated and stored**: here the body looks up the name while running.

For the ordinary functions in this chapter, start with this lookup model:

| Level | Where to look | Example |
| --- | --- | --- |
| Local | Current call's local bindings, including parameters | label, prefix |
| Enclosing | Bindings in enclosing functions, if definitions are nested | The upcoming closure's budget |
| Global | This file's top-level names, later called module-level names | limit |
| Built-in | Names provided by Python | len, print |

LEGB is a common abbreviation, but reciting it is not acceptance. It is not an unconditional rule that an unbound local always falls back to outer scopes. The next section demonstrates that boundary. This simplified diagram does not cover future class-body or annotation mechanisms.

A local name does not become top-level merely because its call ended. This is a standalone expected-failure experiment:


Output before failure:

## 9. Simple closures: a returned rule retains one configuration

### 9.1 Separate what the two calls accomplish

We want a 20-minute rule and a 40-minute rule without passing the budget again for every judgment. A function can receive configuration and return another function.

File: `closure_factory.py`.

<Code language="python">{getFunctionExample('closure_factory.py')}</Code>

Expected:

```text
False
True
True
False
```

Break the lifetime into steps:

1. Calling `make_budget_rule(20)` establishes limit for that outer call.
2. Executing the inner def creates fits. It will use the enclosing limit, but its body does not run yet.
3. `return fits` gives the function object to the caller. It is not `return fits(...)`, so no duration is judged at this point.
4. The outer call has ended. Later, `small_rule(25)` runs the returned function and reads its associated enclosing limit.
5. A second factory call creates a separate binding and another function object. The 20 and 40 rules therefore coexist without overwriting each other.

The function together with the enclosing function bindings it uses forms the **closure** discussed here. The entire outer execution is not running continuously in the background, nor are all locals exported globally. The returned function can still access the bindings it needs.

Factory, inner function and closure are not three additional framework APIs. They are combinations of def, calls, return and name lookup that the earlier sections established.

### 9.2 A closure is not a snapshot of values at definition time

File: `closure_binding.py`.

<Code language="python">{getFunctionExample('closure_binding.py')}</Code>

Expected:

```text

```

Limit was ten when fits was created, but the same outer call rebound it to thirty before returning. Rule reads that enclosing binding when called, so twenty qualifies. Do not confuse closure lookup with evaluation of a default expression at definition time.

Rebinding a caller-side budget variable to another integer does not automatically rewrite the parameter binding established by an earlier factory call. Captured mutable objects still require a sharing analysis; closures do not deep-copy them.

## 10. Write a contract before extracting a function

Not every few lines deserve a function, and not every function needs the entire system's data. Answer four questions before choosing a boundary:

| Question | Example classification-rule answer |
| --- | --- |
| What is the input? | None or an integer estimate; bool and strings are excluded |
| What is returned? | One of unknown, invalid or known |
| What changes or prints? | No mutation of caller objects and no output |
| What is not handled? | Parsing external text, catching exceptions or saving data |

Separate a classifier from a summary because the former determines one value's meaning while the latter traverses and accumulates. Leave display to the caller. Other code can then reuse returned data without first parsing printed text.

The next file uses **docstrings**: a triple-quoted string as the body's first statement briefly documents purpose and contract. It is not runtime validation or return; execution continues with the following statements. Triple quotes can hold multiple lines, though our descriptions are short. Documentation generators and annotations are not prerequisites.

This separation improves verifiability but is not a rule that every function must be pure. `add_topic` deliberately mutates input. What matters is a visible contract and predictable side effects rather than surprises from hidden state.
