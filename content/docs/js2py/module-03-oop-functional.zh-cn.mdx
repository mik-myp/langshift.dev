## 1. 从两条记录，到数量会变化的数据

L02 的学习计划只有两条，我们可以直接访问 `plans[0]` 和 `plans[1]`。现在想象三个变化：今天没有计划；明天有五条；有些已经完成，有些还没有预计时长。继续写死下标不仅重复，而且会把“数据数量变了”变成程序错误。

本章要解决两个问题：**哪些语句应该执行，以及同一套操作应该对哪些数据重复执行。** 这叫控制流。你熟悉 JS 的分支与循环，但 Python 的缩进、容器真值、遍历方式和名称绑定有自己的规则，不能只把花括号换成冒号。

## 2. 分支：冒号和缩进决定哪些语句属于一起

### 2.1 先读控制流，再记语法

我们先按预计分钟数给一项任务分类。当前输入保证是整数；如何处理来自外部的任意文本不在本节范围。

文件：`branches.py`。

<Code language="python">{getControlFlowExample('branches.py')}</Code>

预期：

```text
Short session
Checked
```

按执行顺序解释：

1. 先把 25 绑定给 `minutes`。
2. `if` 检查第一个条件，False 时继续检查 `elif`，即“否则，如果”。
3. 遇到第一个为真的条件，只执行它对应的缩进语句块；同一条分支链中的后续条件不再检查。
4. 如果前面都不成立，才进入 `else`；`else` 后没有条件。
5. `print("Checked")` 已退回最外层缩进，因此无论选中了哪一支，正常执行都会来到这里。

`if`、`elif`、`else` 这几行以冒号结束。条件不必像 JS 一样套在括号里；需要分组时仍可用括号。使用四个空格表示一个缩进层级；四个空格是惯例，而**同一个块的缩进一致**是语法要求。不要混用 Tab 与空格。

这不是视觉排版：把最后一行缩进到 `else` 内，含义就会变成“仅在长任务时打印 Checked”，即使没有异常也已经改了程序。

先预测，再只修改第一行输入：

| minutes | 分类输出 | 为什么 |
| --- | --- | --- |
| -1 | Invalid estimate | 先拒绝负数，后续分支不参与 |
| 0 | No time required | 0 是单独的边界，不被短时长分支吞掉 |
| 1、25 | Short session | 上界包含 25 |
| 26 | Long session | 前三个条件都不满足 |

每一种还应打印 `Checked`。如果把 `minutes <= 25` 放在负数与 0 的检查前面，后两者也会先匹配它；分支顺序表达业务优先级，不是任意排列的标签。

### 2.2 多个 if 不等于一条 if/elif 链

以下是完整、独立的对照：

```python case=separate_if
minutes = 0
if minutes == 0:
    print("Zero")
if minutes <= 25:
    print("Short")
else:
    print("Long")
```

预期：

```text
Zero
Short
```

两个 `if` 都会分别检查；`else` 属于紧挨着它、同一缩进层级的第二个 `if`，不是第一个。规则互斥时适合一条链；多个条件可以同时成立时，独立的 `if` 可能正是需要的行为。不要因为输出多了一行就机械地删除分支。

### 2.3 第一个失败：没有缩进，不会先打印一部分

以下是**预期语法失败**，不是可交付脚本。可以单独保存为 `missing_indent.py` 实验：

```python expected-error=SyntaxError case=missing_indent
if True:
print("Inside")
print("After")
```

在执行任何一行之前，Python 就会报告 `IndentationError`，它属于语法错误的一种；本例指向应有缩进的第二行，没有标准输出。补上第二行的四个空格、保留第三行顶格后，才会依次输出 `Inside`、`After`。

缺冒号通常报告 `SyntaxError`；混用缩进可能报告 `TabError`。先核对冒号、块的起点与退回的位置，再看业务条件。**能解析不代表逻辑正确**，下一节以后仍需通过输入变化来验证。

## 3. 真值与逻辑运算：空容器不是 JS 的空对象

### 3.1 条件不要求表达式本身就是 bool

Python 在条件位置判断一个值的真值。`bool(value)` 可以把这种判断显式显示为 True 或 False；这是转换，不是在解析字符串中的英文词语。

本章用到的假值包括 `None`、`False`、数值零、空字符串以及空的列表、元组、字典、集合。非空容器为真，即使里面只放了 False；非空字符串 `"False"` 和 `"0"` 也都为真。

文件：`truthiness.py`。

<Code language="python">{getControlFlowExample('truthiness.py')}</Code>

预期：

```text
False
False
False
False
False
False
True
True
No tasks
```

`if tasks` 在此表达“列表里有没有条目”，不是“每一条任务是否合格”。`bool([False])` 为 True 正好提醒我们：容器是否非空，与条目的真假是两个问题。

下面是静态语法对照，使用本地脚本验收，不依赖网页运行器：

<PythonEditor title="空容器的真值差异" compare={true} canRun={false}>
```javascript case=truth_comparison

console.log(Boolean({}));
console.log(Boolean("False"));
```

```python case=truth_comparison
print(bool([]))
print(bool({}))
print(bool("False"))
```
</PythonEditor>

Python 输出：

```text
False
False
True
```

JS 输出：

```text
true
true
true
```

不能直接把前端 `if (items)` 的含义照搬过来；对 JS 数组你通常还需要看 `.length`，这里 Python 空列表本身是假值。规则依据 [Python 真值测试](https://docs.python.org/3.13/library/stdtypes.html#truth-value-testing) 与 [MDN Truthy](https://developer.mozilla.org/en-US/docs/Glossary/Truthy)。

### 3.2 and/or 会短路，也可能返回非 bool 值

| 运算 | 求值过程 | 结果 |
| --- | --- | --- |
| `x and y` | 先判断 x；x 为假就不计算 y | 假的 x，或计算得到的 y |
| `x or y` | 先判断 x；x 为真就不计算 y | 真的 x，或计算得到的 y |
| `not x` | 判断 x 的真值并取反 | 总是 bool |

这与 JS 的 `&&`、`||`、`!` 有相似之处，但参加判断的值遵循 Python 的真值规则。短路意味着右边**可能根本不执行**，不只是最后结果相同。

文件：`logical.py`。

<Code language="python">{getControlFlowExample('logical.py')}</Code>

预期：

```text
False
Untitled
Ready
True
25
0
```

- 空列表使 `titles and ...` 停在左边，`titles[0]` 没有求值，因此没有 IndexError；外面的 bool 把返回的空列表变成 False。颠倒两边就失去这层保护。
- `"" or "Untitled"` 返回的是字符串，不是 True；`"Read" and "Ready"` 同样返回一个操作数。
- `minutes or 25` 会把合法的 0 改成 25。如果规则是“仅 None 使用默认时长”，就显式写 `if minutes is None`。它不是 JS `??` 的同义写法。
- 缺失字段与已有 None 仍然不同；要区分它们，继续用 L02 的键成员检查，而不是靠真假推断。

`not` 比 `and` 优先，`and` 比 `or` 优先；比较通常先于这三个运算。初学时把意图写清楚，例如 `(minutes >= 0) and (minutes <= 25)`。本章不依赖复杂运算符组合来考记忆。

## 4. 普通 for：每次绑定一个条目，再执行同一块代码

### 4.1 循环不是先把所有语句复制很多份

对于数量变化的一组任务，我们需要：开始前准备累计值，每次处理一条，最后再输出总结果。

文件：`for_tasks.py`。

<Code language="python">{getControlFlowExample('for_tasks.py')}</Code>

预期：

```text
Tasks: 3; total: 55 minutes
Pending: 2
```

`for task in tasks:` 从列表依次取得条目，每次把名称 `task` 绑定到当前字典，再执行整个缩进块。本例里内层 `if` 多缩进一级；循环结束后的两个 print 退回最外层，只执行一次。

`total = total + task["minutes"]` 先用旧 total 算出新值，再重新绑定；不是数学方程。本章先用完整赋值看清状态变化，不靠缩写隐藏它。

| 时刻 | 当前 minutes / done | total | pending |
| --- | --- | --- | --- |
| 循环前 | 还没有当前条目 | 0 | 0 |
| 第一轮后 | 20 / True | 20 | 0 |
| 第二轮后 | 35 / False | 55 | 1 |
| 第三轮后 | 0 / False | 55 | 2 |

把 `tasks` 改成空列表，循环体执行零次，最终总时长和待办数都为 0。初始化在循环前，所以仍有合法的结果。如果把 total 的初始化挪到循环里，每次就会清零；空列表时甚至根本没有执行赋值。

当前保证每条记录有这三个字段，minutes 是非负整数，done 是 bool。`for` 不会自动验证记录结构；少键依然可能 KeyError。这不是处理任意外部输入的校验器。

## 5. range：明确起点、终点与步长

需要重复若干次或生成整数位置时才引入 `range`，不必把每一次列表遍历都改写成索引操作。最简单的 `range(stop)` 从 0 开始、步长为 1，**不包含 stop**。

三实参形式是 `range(start, stop, step)`；负步长向下走，零步长不合法。本节新增的 `list(...)` 会把可逐项取得的数据收集成一个列表，方便观察，不是所有循环前都必须做一次转换。

文件：`ranges.py`。

<Code language="python">{getControlFlowExample('ranges.py')}</Code>

预期：

```text
range(0, 3)
[0, 1, 2]
[1, 3, 5]
[3, 2, 1]
[]
[]
1
2
3
```

最后循环中的 `range(1, 4)` 才会给出 1、2、3。`range(3, 0)` 默认向上走，而起点已经超过终点，所以为空；想倒数需要显式负步长。

`range` 是一种可重复遍历的整数序列对象，不是已经展开的列表，也不是生成器。你现在只需理解“可迭代”：for 能从中依次取得条目直到结束。`range` 不事先保存整个整数列表；只有这里为展示而写的 list 转换才收集条目。不要为了打印而展开极大的范围。

第一行即产生 `ValueError`，不会运行到 print。修复方法是选择非零且符合方向的步长，不是调整缩进。接着把 `range(1, 4)` 改成 `range(1, 1)`，先解释为什么零次迭代是正确行为，再运行。

### 6.2 enumerate 把计数与条目放在一起

<Code language="python">{getControlFlowExample('numbered_tasks.py')}</Code>

`enumerate(titles, start=1)` 中，`start=1` 是**关键字实参**：把这个调用的 start 设置为 1，不是在外面创建一个名叫 start 的变量。省略它，计数默认从 0 开始。完整的参数机制放 L04，现在只需要会读这个调用。

## 7. 字典遍历：默认拿到键，不是键值对

文件：`dict_iteration.py`。

<Code language="python">{getControlFlowExample('dict_iteration.py')}</Code>

预期：

```text
title
minutes
title: Read
minutes: 20
```

`for key in task` 每次取得一个键。`task.items()` 返回字典键值条目的视图，可逐项取得 `(key, value)` 对；因此第二个循环需要两个解包目标。这个视图不是冻结的快照，也不是列表；本章读取期间不修改字典。

把 `for key, value in task` 当作缩写是错误的：它会尝试把每个键本身解包，而不是自动查询对应的值。有些字符串键长度恰好为 2，甚至可能不报错却给出两个字符，更危险。选择 `.items()` 是在表达需要键与值两者。

字典按插入顺序遍历，这不是按键自动排序；集合不提供这样的顺序承诺。遍历字典时增加或删除键可能触发 RuntimeError 或漏掉条目，本章不依赖这种行为。容器的访问方式不同，不能只更换变量名就期待同一种循环语义。

## 8. while：除了条件，还必须说明如何向结束推进

for 适合“对这些条目逐一操作”；while 适合“只要条件仍成立，就再做一轮”。while 在每轮开始前检查条件，第一次就为假时，一轮也不执行。

我们把一段非负整数分钟数拆成最多 20 分钟的小块。不是等待用户输入，也不是访问服务器，只在已有整数上计算。

文件：`while_budget.py`。

<Code language="python">{getControlFlowExample('while_budget.py')}</Code>

预期：

```text
Block: 20 minutes
Block: 20 minutes
Block: 10 minutes
Blocks: 3; remaining: 0
```

| 轮次 | 开始时 remaining | used | 更新后 remaining |
| --- | --- | --- | --- |
| 1 | 50 | 20 | 30 |
| 2 | 30 | 20 | 10 |
| 3 | 10 | 10 | 0 |
| 下一次检查 | 0 | 不进入循环 | 结束 |

每轮开始 remaining 为正；used 要么是 20，要么是剩余的正数，因此每轮都让 remaining 减少且不小于 0。**“每轮发生什么进展”与“什么条件结束”要一起解释。** 只写了 `while remaining > 0` 并不保证终止。

验证输入 0、1、20、21，分别应得到 0、1、1、2 块，最后 remaining 都为 0。负数不属于此例约定的输入；它会跳过循环但保留负数，并不等于程序已经校验并修复了数据。

如果误删更新 remaining 的那一行，当前正数输入会无限重复打印。不要为了练习刻意放任它运行；终端出现持续重复时用 `Ctrl+C` 中断，再检查推进语句的位置与数值方向。中断可能显示 `KeyboardInterrupt`，不是系统替你修好了循环。本章不要求捕获这个异常。

## 9. continue 与 break：跳过本轮，不等于结束全部

普通遍历已经学会后，再处理两个具体需求：已完成的任务直接跳过；找到第一项可在预算内完成的待办，就不必再找。

文件：`loop_controls.py`。

<Code language="python">{getControlFlowExample('loop_controls.py')}</Code>

预期：

```text
Check: Finished
Check: Long practice
Check: Zero estimate
First match: Zero estimate
```

- `continue` 跳过**当前这一轮的剩余语句**，从下一轮继续，所以 Finished 不参加预算比较。
- Long practice 未匹配，也会自然进入下一轮；不需要为每一轮都写 continue。
- `break` 结束**最近一层循环**，随后执行循环外代码；不会直接结束整个脚本，也不会自动退出所有外层循环。
- `found = None` 在循环前表示尚未找到。匹配后它指向当前任务字典，没有复制；循环后明确用 `is None` 区分无匹配与已匹配。
- `Check:` 是诊断输出，告诉你实际访问了哪些条目；最后的 Read 没有被访问，是提前结束的证据。

这里保证 minutes 非负且字段存在，budget 也是非负整数。0 分钟待办是合法候选，不应被 `if task["minutes"]` 排除。`task['title']` 在 f-string 花括号里仍是普通字典访问；内外引号不同，便于阅读。

把输入改成空列表，或全部完成，结果应为 `No match`；把 budget 改为 0，Zero estimate 仍然匹配。若把 continue 用在 while 里，必须确认它没有跳过推进变量的更新，否则可能一直停在同一个状态。本章不引入循环的 else 子句或嵌套搜索，避免把基本流程藏起来。

## 10. 逻辑错误实验：一边遍历，一边删除，为什么漏了一项？

文件：`pitfalls/mutation_skip.py`。这是可运行的**错误方案**，没有异常不代表结果正确。

<Code language="python">{getControlFlowExample('pitfalls/mutation_skip.py')}</Code>

实际输出：

```text
[{'title': 'Second', 'done': True}, {'title': 'Third', 'done': False}]
```

意图是删除所有已完成任务，但 Second 留下了：

1. 第一轮读到位置 0 的 First，并删除它。
2. Second 左移到位置 0，Third 左移到位置 1。
3. 列表遍历继续读取下一个位置 1，拿到 Third；Second 没有再被检查。

`enumerate` 只是附带计数，不会为你冻结列表。不要把“修改当前字典的字段”与“改变正在遍历的列表长度”混成同一种修改；前者改变记录内容，后者会改变后续读取的位置。

改为读取原列表、构建新列表。文件：`safe_filter.py`。

<Code language="python">{getControlFlowExample('safe_filter.py')}</Code>

预期：

```text

3
False
```

原列表仍有三条，新列表只有待办；False 说明结果列表与原列表不是同一个外层对象，筛选没有删除源数据。

但 **新建结果列表不是深复制**。用下面这个独立的单项实验检查内层共享，而不是在通用筛选脚本末尾写死某个下标：

```python case=filtered_sharing
task = {"title": "Read", "done": False}
tasks = [task]
pending_tasks = []
for current in tasks:
    if not current["done"]:
        pending_tasks.append(current)
print(pending_tasks[0] is tasks[0])
pending_tasks[0]["title"] = "Changed"
print(tasks[0]["title"])
```

预期：

```text
True
Changed
```

append 保存的是原字典的引用，修改结果列表里的字典也会影响源任务。将来需要隔离编辑，仍要按照 L02 分析可变层。

## 11. 最后才学列表推导式：缩短已理解的循环

当逻辑只有“遍历 → 可选筛选 → 计算一个结果 → 收集”时，可以用列表推导式表达。它不是一种必须替代所有 for 的高级写法。

文件：`comprehensions.py`。

<Code language="python">{getControlFlowExample('comprehensions.py')}</Code>

预期：

```text
['Practice', 'Review']
['Practice', 'Review']
True
False
```

读法是：从 tasks 逐项取 task；保留 `not task["done"]` 成立的项；把 `task["title"]` 放进新的列表。语法把“要放入的表达式”写在最前面，理解时仍从中间的 for 开始读。

没有筛选时可去掉末尾的 if。结果列表保留遍历中的相对顺序，空输入会得到空列表；这里两个结果内容相等，但不是同一个列表对象。这里收集的是字符串；若改成收集 task，就又会共享字典，不能认为推导式自动复制了任务。

与普通 for 还有一个必须知道的差异：推导式的目标名称不泄漏到外面。

```python case=comprehension_binding
title = "Outside"
labels = [title for title in ["Read", "Practice"]]
print(title)
print(labels)
```

预期：

```text
Outside
['Read', 'Practice']
```

因此这里只说“生成的列表内容等价”，不说“任何状态变化都与普通循环一样”。完整作用域在 L04 继续展开。不要为了追求一行写法加入多层 for、打印副作用、赋值技巧或复杂条件；一旦需要累计多种状态、break 或清晰的错误分类，保留普通循环更合适。

**暂停点 C**：解释 while 的终止、break 与 continue 的区别，复现删除漏项，再把一个普通筛选循环改成简单推导式。不能解释中间状态时，先保留长写法，不算退步。

## 12. 串起来：不写死数量的任务汇总

现在把分支、累计、空输入和编号组合起来，而不是新增一批 API。这个脚本的输入契约是：tasks 为列表；每项含字符串 title、bool done、非负整数 minutes。

文件：`task_summary.py`。

<Code language="python">{getControlFlowExample('task_summary.py')}</Code>

预期：

```text
Tasks: 3
Done: 1; pending: 2
Remaining: 35 minutes
Pending average: 17.5 minutes
1. Practice loops
2. Check boundaries
```

为什么这样安排？

- 计数器、累计分钟与结果列表都在循环前初始化，所以零轮也是完整执行路径。
- 每项要么进入完成分支，要么进入待办分支，不会被重复统计；完成数量与待办数量之和应等于输入数量。
- 只有待办时长加入 remaining；0 分钟仍然是一项待办，也计入平均值分母。
- 先判断 pending_count 大于 0，才做除法，避免没有待办时除以零。没有平均值用 `n/a` 表达，不虚构一个业务上有效的 0。
- `:.1f` 表示把数值显示为一位小数，是格式化，不改变 average 的内部值。最后再用 enumerate 给已收集标题编号。

只改输入，不改统计逻辑，完成下面的检查：

| 输入变化 | 必须观察到的结果 |
| --- | --- |
| tasks 改成空列表 | Tasks: 0；done/pending/remaining 都是 0；平均值 n/a；没有编号行 |
| 所有 done 改成 True | pending 为 0，平均值 n/a；不会除以零 |
| 只留一条 0 分钟待办 | pending 为 1，平均值 0.0；仍有一行编号 |
| 再追加一条 5 分钟待办 | 原例 pending 为 3、remaining 为 40、平均值显示 13.3 |

如果少了 minutes，本脚本仍可能失败；我们没有用异常捕获掩盖字段契约。下一道独立练习会明确增加“时长未知”的业务规则，而不是假装所有数据一直完美。
