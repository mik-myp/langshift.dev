## 2. 先把數據與行為契約寫完整

文件中是一份 JSON 數組，每項恰好有 title、minutes、done。title 是非空白 str，保持原拼寫；minutes 是普通非負 int，不接受 bool、float、數字字符串；done 只能是 bool。空數組、零分鐘與重複標題都合法，保持原順序。缺字段和多字段均拒絕。

與前端表單校驗相比，這裏的邊界刻意更嚴格。JavaScript 會在算術和寬鬆比較中把字符串 "30" 轉換成數字 30；Python 保持 str 與 int 是不同類型，本章契約直接拒絕數字字符串。同樣，JS 對象讀取缺失鍵得到 undefined 並繼續運行，而 Python 字典的 `data["missing"]` 會拋出 KeyError——這就是把損壞輸入當作可見失敗、而不是靜默默認值的語言基礎。

讀取缺失與讀取損壞是不同事件。現有文件編碼錯誤、JSON 語法錯誤、業務形狀錯誤時，必須非零失敗並保留原字節，不得初始化、保存空數組或只警告後繼續。權限與未知 I/O 錯誤也不能變成“新用戶沒有任務”。

## 3. 沿數據流分責任，而不是為了目錄多而分層

畫出數據流：**路徑 → 打開的文件 → 文本解析 → 數據校驗 → 業務變化 → 彙總 → 序列化 → 保存 → 展示**。每個邊界回答兩個問題：輸入由誰保證？失敗由誰負責解釋或傳播？

- validation：驗證數據並返回新列表、新字典。調用者修改返回值不得影響原輸入。
- rules：標記完成與計算彙總；不打開文件、不打印、不創建目錄。它不依賴一個全局可變“任務數據庫”。
- storage：讀取和保存文件，使用校驗；load 傳播缺失，不擅自決定是否初始化；save 在破壞性打開之前完成校驗與序列化。
- app：選擇固定路徑、創建自己擁有的父目錄、決定何時初始化、安排調用順序，並在損壞輸入後停止。

這些是普通模塊和函數，不是要求現在學習企業架構術語。可以選擇同樣清晰的文件名，但要能解釋職責。程序小不等於允許在導入時讀寫真實文件；文件多也不自動產生正確的邊界。

寫下自己的模塊草圖和每個函數的輸入/輸出/錯誤，再打開答案。函數簽名暫時不要求註解，靜態類型在 L11 專門教學。

## 5. 在寫實現之前定義驗收表

第一次和第二次運行的輸出應分別為：

```text
Source: new file
Changed: 1
Tasks: 3
Pending minutes: 35
```

```text
Source: existing file
Changed: 0
Tasks: 3
Pending minutes: 35
```

這兩次必須是新的 Python 進程。不能只在同一進程裡保留列表，然後聲稱已經讀迴文件。第二次 changed 為零體現的是當前操作的業務約定，不是承諾所有程序都有“重複運行永遠無副作用”的性質。

還要驗收：

| 情況 | 應觀察到什麼 |
| --- | --- |
| 導入 app/storage | 僅導入探針輸出，無創建目錄/讀寫文件/業務入口 |
| 已存空數組 | 保持空數組；計數、變更、未完成時間均為零 |
| 多個 Read，其中部分已完成 | 全部匹配，但只統計這次新完成的數量 |
| Practice 的分鐘數改為 36 | 新進程彙總必須變為 36，不硬編碼 35 |
| 壞 JSON、錯誤編碼、錯誤業務形狀 | 失敗、原字節不變，沒有成功保存提示 |
| 不存在的父目錄 | 由 app 創建自己指定的父目錄，不是 storage 偷偷創建任意目錄 |
| 換 cwd | 入口仍訪問約定的項目數據位置，不能在調用者目錄意外創建另一份數據 |

保存前拒絕無效值必須保護舊文件；**寫入過程中斷仍可能損壞文件**。本章沿用 L07 的明確限制，不把 with、測試或單文檔格式誇大成數據庫事務。

## 6. 文件測試先獲得自己的可丟棄目錄

不能讓測試把你正在使用的任務文件改壞，也不能要求讀者先學 fixture。這裡補充一個小型標準庫工具：TemporaryDirectory 創建臨時目錄，with 結束時清理它擁有的目錄和內容，正常與異常退出都走清理路徑。

<Code language="python">{getProjectExample('demo_resource.py')}</Code>

```bash
uv run --locked python demo_resource.py
```

```text
Inside: True
After: False
```

directory 是臨時目錄的字符串路徑；Path 把它變成你已經會使用的路徑對象。測試只能在這個目錄內創建自己的文件，不把真實用戶路徑傳進去。退出後 path 名稱仍存在，但資源位置已被清理；這沿用 L07“名稱存在不等於資源可用”的模型。

測試採用同樣結構，每項自己創建目錄。一個讀取函數不必知道自己正在被測試；它只接受 Path。app 也可以把固定默認路徑的選擇與 main(path) 的調用邊界分開，讓測試傳入自己的目錄。這只是普通函數參數，不是提前引入框架依賴注入，也不是開放任意上傳路徑的安全承諾。

## 7. 分階段做，避免一次寫完再找幾十個原因

建議按可驗證的最小步推進，但具體代碼由你決定：

1. 先寫純校驗與規則，用普通測試確認空、零、重複標題和不修改輸入。
2. 加讀取和保存，在臨時目錄完成往返；寫入兩次後仍是一份合法文檔。
3. 加 app 協調與固定路徑，驗證首次/再次/現有空數組。
4. 複製壞輸入到自己的實驗目標，確認失敗前後字節相等；不要原地修 fixtures。
5. 從另一個目錄使用外層入口運行，證明路徑錨點正確；用導入探針確認導入不啟動業務。
6. 第二個乾淨目錄恢復環境並重跑整個驗收表，最後做獨立變式。

某一步紅了，先找到失敗層次，不要一口氣升級 Python、換包源、改 JSON、改斷言。每次最小修改後先跑相關測試，再跑全套，保留能解釋的進展。

## 10. 診斷一次壞數據，而不是刪除文件了事

下載中的兩份壞輸入分別為：

<Code language="text">{getProjectExample('fixtures/broken.json')}</Code>

<Code language="json">{getProjectExample('fixtures/wrong-shape.json')}</Code>

在項目副本中，先運行正常程序得到自己的輸出文件，保留其備份；再把壞輸入複製到這個副本的 _output/tasks.json。執行相同入口，觀察非零失敗，再用編輯器或已學過的 read_bytes 比較目標是否仍等於複製進去的壞字節。原始 fixtures 只作輸入，不被修改。

第一份沒有合法 JSON，第二份能解析但根對象不符合業務數組要求。它們都不應觸發初始化。完成觀察後，有意識地恢復剛才備份的好數據，再運行；不能以“刪除壞文件後應用能啟動”聲稱已經處理損壞。恢復數據、修復程序與重新初始化是三種不同操作。

同樣，不要把 PermissionError 恢復為空列表，不要為演示隨意放開系統目錄權限。未知錯誤應保留可診斷的失敗，而不是製造一個看似成功的新文件。

## 12. 畢業於這一階段，不等於已經能上線

階段退出要求：能從需求解釋自己的模塊設計；空目錄建立代碼與環境；有意製造一個業務缺陷並讓測試抓住它；在新進程讀回；錯誤數據拒絕覆蓋；第二目錄恢復；獨立完成預算變式；明確陳述尚無併發、權限、事務和服務運行能力。

給自己的 README 寫清命令的工作目錄、版本、首輪/重複輸出、刻意失敗、安全輸出目錄和恢復辦法。暫停記錄源碼版本/改動、最後測試命令與數量、當前數據是否損壞、備份位置、下一步要證明的行為。不要只記錄“今天學到第幾頁”。

下一章 L11 才把類型註解加到已理解的函數與容器上，比較靜態檢查和運行時校驗。類型、模型、裝飾器和資源協議的基礎完成後，再進入 HTTP 與 FastAPI，不把工程綜合作業變成突然跨入服務端的捷徑。
