JS async 函数调用会执行函数体到第一个暂停点，返回 Promise；Python 的 `async def` 定义 coroutine function，调用得到 **coroutine object**，函数体尚未开始。对象保存的是一次可恢复的执行，不是已经启动的网络请求，也不是自动排队的后台任务。直接丢弃它通常会得到 `RuntimeWarning: coroutine was never awaited`，而不会替你完成工作。

`await pending` 让当前执行沿着这个 coroutine 前进；`asyncio.create_task(pending)` 则把它包装成 Task 并交给当前运行的 loop 调度。Task 保存执行状态、结果/异常和取消状态，拥有者要保留引用并最终观察结果。本实验使用 Python 3.13 的**默认任务工厂**；没有启用 eager task factory，不能把这里“create_task 后还未运行”的观察扩展到一切自定义任务工厂。

## 4. 一次调用中的四个角色，不是四种线程

想象一个服务进程中的一个事件循环线程：loop 维护已就绪的回调与待完成 I/O，挑可运行的工作继续；Task 驱动 coroutine，直到其完成、失败或等待尚未就绪的东西。`await` 表示“依赖这个可等待对象的结果”，不是“新建线程”，也不是无条件的让出。

如果 await 的对象已经就绪，当前 Task 可能直接继续；测试里对已 set 的 Event 执行 wait，预先排队的回调仍没运行。若等待的是未 set 的 Event，Task 暂停，loop 才能推进其他就绪工作。因此 CPU 长循环里塞一个已完成的 await，并不能保证服务响应。

`asyncio.run(main())` 在独立程序入口管理循环生命周期，运行 main 并最终关闭循环。框架内部已有循环时不再套 run；应在 async 调用链内 await。也不要把不同循环创建的异步资源长期塞进一个模块全局后到处复用。

## 5. 直接 await 的顺序，与显式调度的重叠

`sequential` 先完整 await A，再调用并 await B。A 里的 `sleep(0)` 确实给循环一个调度机会，但 B 尚未被创建，不会凭空并发。这与连续两句 `await fetch(...)` 的 JS 经验相通；差别在于 Python 提前调用两个 async 函数也仅产生两个 coroutine，仍未启动它们。

`scheduled` 则先创建两个 Task，随后拥有者等待两个 entered 门闩，再放行 B、观察 B 完成，最后放行 A。所有权与完成顺序是显式的。输出中 A/B 的 start 顺序是本次默认调度的观察；可移植验收只要求**两个 start 都发生在 both-entered 之前，而两个 end 都在之后**，不把无关的队列先后当作业务协议。

`finally` 中的 `drain` 先取消所有未结束孩子，再用 `gather(..., return_exceptions=True)` 等待所有终态。此处 gather 是收尾工具：返回的位置对应输入，异常/取消成为结果项，便于不因某一个孩子取消就漏收其他孩子。它不会自动赋予任意程序“失败即取消其他孩子”的政策。我们的正常路径已经观察目标结果；示例清理阶段不重新抛次生错误。生产监督若需要保留所有次生错误，必须另行记录/报告，不能把这些返回值长期当垃圾丢掉。

<details>
<summary>解释性检查答案：先调用两个 coroutine，再逐个 await，会不会自动并发？</summary>

不会。创建 coroutine object 本身没有把它加入 loop 的就绪工作。第一个被 await 时才开始，等其结束后才执行第二个。要重叠进行，须先显式创建两个 Task，或使用有明确调度语义的组合器，并拥有两者的生命周期。另一个陷阱是 await 不必总暂停：已经就绪的 Event 可以立即返回。

</details>

## 6. 阻塞不是“等得久”，而是把循环线程占住

`blocking` 先用 `loop.call_soon` 排入一个就绪回调，再在循环线程执行同步 `time.sleep(0.02)`。sleep 期间 CPU 可以闲下来，但这个线程没有返回事件循环；因此同步段结束时回调仍未运行。只有执行真正让出的 `await asyncio.sleep(0)`，回调才出现。

我们断言的是回调与同步段的先后，不是“20 ms 应当跑完”之类易受系统负载影响的时钟阈值。这个例子证明 loop 不能穿插推进其他工作，不是性能基准，也不意味着只要回调晚到就必然能定位到某一行阻塞。

`offloaded` 把一个必须同步调用的阻塞库放到 `asyncio.to_thread`。线程用 `call_soon_threadsafe` 报告已进入，并等待线程专用的 `threading.Event`；主循环此时仍能记录事件、释放线程，最后明确 await 加入收尾。不要从工作线程直接调用 asyncio.Event.set 来偷跨线程访问。这里两个 Event 属于不同并发模型，有各自用途。

选择边界时先问：纯标题校验、字典读写保持普通函数；已有真正异步 I/O 客户端才 await；不可替换的同步 I/O 可考虑线程桥接；长 CPU 运算不能因为包进 async 就变成并行。取消等待 to_thread 的 Task 也**不能强制杀死底层线程**，阻塞库自己仍需超时/停止协议。本例明确 release 并等待线程退出，不把遗留线程交给运气。

## 7. 取消是请求，不是立即中断，也不是成功结果

<Code language="python">{getAsyncModelExample('ownership.py')}</Code>

`task.cancel()` 请求把 `asyncio.CancelledError` 注入目标执行；它不会同步把线程停在任意机器指令。目标通常在下一次可取消等待处感知请求，然后经过 finally。拥有者仍须 await Task，观察它真正结束。CancelledError 属于 BaseException 而不是普通 Exception；不要用裸 except/BaseException 把取消当网络故障。

如果需要记录取消，可捕获后清理并原样 `raise`；本例根本不拦截工作中的取消，只用 finally 关闭文件。拥有者的 except 则是**边界观察**：它知道自己刚请求结束该任务，记录 owner:cancelled，而不是让业务结果变成成功。清理若自己报错，原来的取消也可能被新的错误遮盖，不能用日志一句话宣称“永远可靠”。

还有一个容易遗漏的边界：默认工厂下，Task 尚未开始就取消，函数体和 finally 都没有运行。因为资源获取也在函数体里，此时没有文件需要关闭。若把资源先开在外面再交给未启动的 Task，外层必须继续承担所有权。

## 8. 超时建立预算，不保证墙钟上的强制终止

`timed_out` 用 `asyncio.timeout(0)` 人为安排在下一轮循环到期：当前任务仍会开文件，到等待未就绪 Event 时触发取消，finally 关文件，退出 timeout 上下文后才在外面捕获 TimeoutError。零秒是可重复的机制实验，不是实际网络预算建议。

timeout 针对当前任务的取消被上下文转换为 TimeoutError；外部独立取消仍应传播为 CancelledError。应在 timeout 块外捕获超时，才能清楚地区分预算到期与块内业务异常。真实总预算以后应覆盖排队、多个尝试和退避，而不是每一步偷偷重置。

超时是协作式的：循环被同步代码占住时，定时器也无法及时执行；清理本身可能需要时间。不要承诺“到 N 秒操作一定已停止”，更不能推导“远端写入一定未发生”。A02 会进一步区分 HTTP 分阶段超时与整个操作 deadline。

## 9. 并发上限不是把无限请求变得免费

<Code language="python">{getAsyncModelExample('capacity.py')}</Code>

Semaphore 是许可计数器。进入 `async with slots` 取得一个许可，没有许可就等待；退出时归还。Meter 只统计已准入的工作，不统计等在外面的 Task。四个任务、两个许可时，只有两个 entered 为真；放行一个旧任务后，才观察到新的 entered。正常与取消都经过 finally 减 active，上下文归还许可。

把 semaphore 建在每次请求内部会使每个请求都有自己的上限，无法限制共享依赖的总压力。A02 会把它放在应用生命周期内。本例最多创建四个任务，独立变式最多八个；**即使 semaphore 只有两个，预先创建一百万个 Task 仍会占用内存**。无限输入需要有界接收、背压与其他设计，不在这里冒充已经解决。

带提示修改：把 limit 从 2 改为 1，再改为 3。不要改成 assert “运行时间翻倍/缩短”；验收 peak 等于新 limit、结束时 active 为零，并解释一个等待许可的 Task 被取消为何不应额外归还一个未取得的许可。
