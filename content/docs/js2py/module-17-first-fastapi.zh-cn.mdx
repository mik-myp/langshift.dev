## 1. 从“我会请求接口”走到“谁在接收请求”

前端的 fetch 调用只暴露了一端：发送 URL，等待状态码和正文。现在我们实现另一端。一个 Python 函数返回字典，还不等于有了 HTTP 服务：谁占用端口、谁把请求定位到函数、谁把字典编码成 JSON，必须分别有人负责。

| 本章契约 | 范围 |
| --- | --- |
| 前置 | H02 的方法、状态码、资源与分页语义；L13 装饰器；已有模块、函数和容器基础 |
| 新能力 | 解释服务器与框架分工；正确导入 app；编写同步路由；从另一个终端观察响应和失败 |
| 独立验收 | 不复制参考 app，从空文件重建只读任务接口，完成成功、缺失、非法参数与退出后的请求 |
| 明确排除 | async def、应用 lifespan、数据库、依赖注入、认证、请求体模型和 API 测试 fixture |

下载 [H03 完整实验](/learning-assets/js2py/h03-first-fastapi.zip)。这是**本地 API 实验**：需要操作系统端口和两个终端，不能在浏览器 Python 编辑器里启动。网页代码由实验源码读取；H06 才正式引入 API 自动测试，本章的 curl 是真实客户端，不是隐藏的测试框架先修。

我们只实现 capstone 的 V1 前半步，不冒充最终协作系统。这里没有项目、用户、状态枚举或权限关系：只有两个只读任务。为衔接语言阶段，字段为服务提供的 id、原样 title、非负 minutes、done、可空 note。它们是明确的本章小契约，不依赖另一章的代码或运行进程。

## 2. 先画清一次请求的责任链

```text
curl -> TCP 127.0.0.1:8003 -> Uvicorn -> ASGI -> FastAPI
                                                  |
                                      route + validate parameters
                                                  |
                                          def read_task(...)
                                                  |
client <- HTTP status + JSON bytes <- response serialization
```

**Uvicorn 是服务器。** 它监听地址和端口，接收连接，把 HTTP 请求交给应用，并把应用产生的状态、头和正文发送回客户端。**FastAPI 是框架。** 它持有路由规则，提取和验证参数，调用你的函数，组织响应。**我们的函数是业务处理。** 它决定任务是否存在、返回哪个对象；不用自己解析 TCP 字节。

ASGI 是服务器和 Python Web 应用之间的接口约定，不是又一个要启动的服务。框架替本章实现它。它支持异步通信，不表示每个业务函数都必须写成 async def；这里所有路由都是普通 def。不要把“代码里没有 await”理解成“全服务器一次只能接一条请求”：FastAPI 会把普通同步路由安排在线程池中执行，其他请求仍可能同时进行。我们只读取固定数据，因此没有在本章承诺共享写入的安全性。

与前端路由的可迁移经验是“方法与路径选中处理者”；不同的是，此处在服务进程里运行，不能访问浏览器 DOM，也不需要先显示页面才会被 curl 调用。ASGI、线程池和服务器分工依据本章末尾的一手资料；暂不要求自己实现事件循环。

uv run --locked python -m uvicorn app:app --host 127.0.0.1 --port 8003 --workers 1

逐段拆开这条命令，而不是背诵：

- uv run --locked 选择本项目的环境；python -m uvicorn 让该 Python 执行已安装的 Uvicorn 模块，避免误用另一个环境的命令。
- app:app 的左边是**模块名 app**，不是 app.py 文件路径；右边是导入后取得的对象名 app，即 FastAPI() 的结果。文件若叫 service.py，左边才改成 service。
- Uvicorn 默认从当前工作目录寻找应用模块。能找到依赖不等于能找到 app.py：环境选择与模块查找是两个问题。
- --host 127.0.0.1 只监听本机回环地址；不要改为 0.0.0.0。本例没有用户认证，不该给局域网或互联网访问。
- --port 8003 是本实验选择的端口，不是 FastAPI 内置端口；客户端必须访问同一个端口。
- --workers 1 明确只启动一个服务工作进程，不受外部 WEB_CONCURRENCY 默认值影响。本章不用 --reload，修改后手动退出再启动，避免重启行为被隐藏。

启动会导入 app 模块：创建 FastAPI 对象、建立 TASKS、执行装饰器以登记路由。此时不会为你执行一次 read_task。只有匹配请求到来，框架才调用处理函数。直接执行 uv run --locked python app.py 会完成这些定义然后正常退出；文件里没有监听命令，所以它不会留下一个 HTTP 服务。

## 4. 从装饰器和参数看清框架何时介入

`@app.get("/tasks/{task_id}")` 把“GET 加路径模式”关联到 read_task。花括号是 URL 中的一段，不是 Python 字典。路径里的 task_id 与参数同名，框架才知道把那段文字交给它。

请求 /tasks/1 时，路径最初带来的是文本 "1"。框架根据 int 注解转换并验证，再把整数 1 交给函数。Path(gt=0) 是参数的额外约束：gt 表示严格大于。本章采用这种直接声明写法，避免为了第一条路由先学习 Annotated。非法文本或非正数在框架入口被拦下，函数体不会开始查表。

limit、offset 没有出现在路径模板里，因此这里的标量参数来自查询字符串。Query(default=20, ge=1, le=100) 同时提供缺省值和上下限，ge/le 是大于等于/小于等于。查询字符串中的数字也是文本，需要解析；不能把下一章 JSON 正文的严格整数规则机械套在 URL 文本上。

list_tasks 先按 id 排序，再用 offset:offset + limit 切片，最后返回总数。total 是全部任务数，不是这一页长度；offset 超出范围得到空 items，仍是合法 200。当前只读数据不变化，顺序稳定；这不能推广成“并发增删时 offset 分页也不会漏项或重复”。

read_task 内部拿到合法整数后才判断存在性。raise HTTPException 终止当前处理，让框架生成 404。这里是已知业务结果，不是 Python 崩溃；不要把所有异常都包成 404，否则代码错误也会被伪装成“没找到”。

## 5. 用终端 B 真正观察请求与响应

终端 A 继续运行。另开终端 B，执行：

```bash
curl -sS -i http://127.0.0.1:8003/health
curl -sS -i http://127.0.0.1:8003/tasks/1
curl -sS -i 'http://127.0.0.1:8003/tasks?limit=1&offset=1'
```

-sS 隐藏进度条但保留连接错误，-i 把 HTTP 状态行和响应头也显示出来。查询 URL 加单引号，避免 shell 把 & 当作后台执行符号。不要只看 curl 的进程退出码：默认情况下收到 404/422 仍可能退出 0，HTTP 状态才回答应用如何处理请求。

下面是 /tasks/1 的实际状态与正文（省略会变化的 Date 等头，不是完整原始报文）：

```http
HTTP/1.1 200 OK
content-type: application/json

{"id":1,"title":"Read HTTP","minutes":25,"done":false,"note":null}
```

函数返回的是 Python dict，不是已经发送的字符串。FastAPI 的响应处理把它编码为 JSON：False 变 false，None 变 null，再由服务器写到连接上。终端 A 的访问日志此时才出现 GET 记录。一个请求完成后进程仍等待下一个请求；返回函数不等于退出服务器。

分页请求应得到：

```json
{"items":[{"id":2,"title":"Try curl","minutes":10,"done":true,"note":"local only"}],"limit":1,"offset":1,"total":2}
```

/health 的 200 只证明进程能处理这个请求。这里没有数据库，所以它不证明数据库、身份系统或所有业务操作就绪。/docs 提供交互文档，/openapi.json 提供机器可读契约；它们方便探索，但能打开文档不是 CRUD 已验收。

## 6. 把“失败”定位到正确一层

<Code language="bash">{getFastApiExample('requests.sh')}</Code>

先预测每条，再单独执行，最后可用 bash requests.sh 重放全部 11 条；脚本只是可见请求清单，不会替你判定结果。

| 请求或动作 | 预期 | 原因与下一步 |
| --- | --- | --- |
| GET /tasks/999 | 404，detail 为 Task not found | 参数合法，处理函数没找到记录；核对 id |
| GET /missing | 404，detail 为 Not Found | 没匹配路由；核对路径 |
| GET /tasks/nope | 422，loc 为 path/task_id | 无法解析整数；换成合法 id |
| GET /tasks/0 | 422 | 解析成功但不大于 0 |
| GET /tasks?limit=0 或 offset=-1 | 422 | 查询约束失败；修正分页参数 |
| POST /tasks | 405 | 本章尚未注册创建路由；不是输入模型问题 |
| GET /tasks?offset=99 | 200，items 为空，total 为 2 | 合法空页，不应制造 404 |

/tasks/nope 的实际正文：

```json
{"detail":[{"type":"int_parsing","loc":["path","task_id"],"msg":"Input should be a valid integer, unable to parse string as an integer","input":"nope"}]}
```

读取 loc 知道错误来源，type 表示错误类别；不要把整个英文 msg 当作永远不变的客户端协议。输入错误、资源缺失、传输错误是三件事。若 curl 提示连接失败，根本没有收到 HTTP 状态，先看服务是否启动、地址端口是否一致，再查业务代码。

<details>
<summary>解释性检查答案：为什么 /tasks/nope 与 /tasks/999 不一样？</summary>

前者在参数解析阶段失败，read_task 没运行；后者得到整数 999 后进入函数，由业务存在性判断抛出 404。把两者都解释成“字典里没有这个键”会失去入口校验的意义。直接调用 read_task(999) 只会抛 Python 异常，没有服务器替你发送 HTTP；测试函数与发请求也不是一回事。

</details>

## 7. 启动失败不是接口的 500

在终端 A 保持运行时，终端 B 用同一条启动命令再启动一次。第二个进程退出非零，并出现 address already in use；macOS 实测为 Errno 48，其他系统错误编号可能不同。第一个进程仍能响应 /health。**不要为了排错批量杀掉占用端口的进程。** 回到自己启动它的终端按 Ctrl-C，或者为自己这次实验换成空闲端口并同步修改 curl URL。

再单独做模块定位实验：先退出自己的服务，在实验目录的父目录执行：

```bash
uv run --project h03-first-fastapi --locked python -m uvicorn app:app --host 127.0.0.1 --port 8003 --workers 1
```

实测报 Could not import module "app"。--project 找到了项目环境，但没有把工作目录变成 app.py 所在目录。恢复方式是 cd h03-first-fastapi 后重用正常命令；也可以在父目录显式加 --app-dir h03-first-fastapi 指定查找目录。不要把“加随机 sys.path”作为习惯性修复。

若 app:app 写成 app:missing，则模块找得到，但报 Attribute "missing" not found。分别检查冒号两侧，别用重装依赖处理对象拼写错误。这些失败发生在提供服务之前，没有一条业务 HTTP 500 可供客户端接收。

<details>
<summary>带提示排错答案：环境正常，却无法导入应用</summary>

先运行 pwd、ls app.py，确认当前目录；再核对 app:app 的文件模块名和对象名。uv run --locked python -c 'import app; print(type(app.app).__name__)' 应打印 FastAPI。导入成功只说明对象可取得，接着仍必须启动 Uvicorn 并请求 /health 才算服务恢复。若端口冲突，确认失败的是第二个进程；不要关闭别人的进程。

</details>

## 8. 一个故意的 500：客户端与服务日志看到的不同

<Code language="python">{getFastApiExample('errors/broken_app.py')}</Code>

它是明确的失败实验，不是正常参考 app。退出自己的正常服务后，在实验根目录启动：

```bash
uv run --locked python -m uvicorn errors.broken_app:app --host 127.0.0.1 --port 8003 --workers 1
```

在另一终端请求：

```bash
curl -sS -i http://127.0.0.1:8003/broken
```

实际为 500，正文是 Internal Server Error，而终端 A 出现 RuntimeError: deliberate failure for H03 的回溯。这是处理函数已经运行但失败，既不是 422 也不是端口冲突。不要把原始回溯、配置或秘密返回给客户端，也不要开启调试页面来“修复”它。

恢复：Ctrl-C 退出这个故意错误的服务，重新启动 app:app，再请求 /health 和 /tasks/1，确认二者为 200。最后 Ctrl-C 退出自己的服务，再发 /health，观察连接失败而不是 404；没有监听者就没有 HTTP 应用响应。

## 9. 独立重建与变式，不以复制后启动为终点

**独立重建：** 在新的本地目录，只带 pyproject.toml、uv.lock、.python-version，自己写 app.py。按本章契约重建 /health、分页 /tasks、`/tasks/{task_id}`，包含同样的两个种子任务。先不看参考文件，用请求记录说明正常、缺失、错误类型、错误范围和空页分别怎样发生。

**变式：** 加 GET /summary，只统计尚未完成任务的 count 与 minutes，总计应是 1 与 25。它是全体数据的统计，不受列表分页影响；不能返回 TASKS 整个字典来回避聚合。提示只到这里：遍历 values，筛选 done 为 False，再汇总。

## 10. 暂停恢复记录与本章出口

不要只记录“读到第 8 节”。在自己的笔记保存：工作目录、当前 app 文件、锁定版本、最后成功命令、监听端口、启动它的终端、已观察的状态与正文、仍未解决的问题、下次第一条命令。例如：

```text

```

出口需要你口头解释 import、路由注册、参数解析、函数执行、序列化五个阶段；独立启动服务并保留成功/失败的真实请求记录；亲自恢复一次启动失败；能退出自己启动的进程。py_compile、能 import、网页编译成功都不能替代这些证据。

已验证边界：本地回环、单工作进程、顺序请求、只读种子。本章不验证性能、并发写入、权限、CORS 浏览器行为、代理、HTTPS、跨平台服务管理或生产部署。下一章加入输入输出模型与内存写入，但不会自动解除这些边界。
