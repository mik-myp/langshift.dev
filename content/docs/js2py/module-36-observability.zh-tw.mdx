## 1. 用戶說“剛才失敗了”，你準備從哪裡開始？

O04 能發佈和回退，但如果只能看到一行 503，很難知道是哪個請求、哪條路由、哪個時間窗口開始異常。把整個 Request、異常對象、SQL 參數打印出來看似方便，卻可能把密碼、Cookie、Bearer token 和正文放進長期日誌。可觀測性要同時回答“發生什麼”和“哪些內容不能收集”。

本章不先安裝儀表盤。我們讓一個真實請求遇到受控數據庫權限故障，拿響應裡的關聯 ID 找到結構化記錄，根據變化檢查授權，再恢復權限並觀察錯誤窗口下降。最後用合成秘密掃描實際日誌，證明沒有通過另一條輸出路徑洩露。

## 2. 日誌、指標與追蹤，不是同一種資料

日誌記錄一個事件的上下文；指標把一段時間的事件聚合成數量、比例或分佈；追蹤用多個跨度描述一次跨組件調用。三者可以相關聯，但一份 JSON 日誌並不自動建立完整分佈式追蹤，日誌條數也不等於吞吐能力。

本實驗每個完成到“響應頭已準備好”階段的請求寫一個事件，字段只包括 event、request_id、timestamp、method、route、status、ready_ms、error_type。這樣既能按 request_id 查一項，也能聚合 5xx 比例與 p95。字段一旦被消費，就成為需要維護的數據契約，不應隨意換名或把數字變成自然語言段落。

route 記錄模板 `/projects/{project_id}`，不是具體 URL；否則每個 ID、查詢參數都可能變成新標籤，既膨脹指標維度，又洩露業務標識或秘密。未匹配路由用固定 unmatched，未知方法歸到 OTHER。

## 3. 關聯 ID 由服務器生成，不盲信客戶端

瀏覽器或 HTTPX 收到 X-Request-ID 後，可以把它交給維護者定位記錄。它只是相關性標識，不證明用戶身份，也不是授權憑證。服務端本例每次生成新 UUID；即使調用者提交同名請求頭，也不寫入日誌。

為什麼不只檢查客戶端 ID 的長度和字符？一個合法的隨機 Bearer token 也可能正好符合安全字符規則；原樣記錄這個頭，仍會把 token 寫進日誌。因此“格式合法”不等於“允許記錄”。以後若接受受信任代理產生的上游 ID，要單獨定義代理可信邊界，而不是信任所有來源。

## 4. 耗時從哪裡開始，到哪裡結束？

timestamp 用牆上時鐘定位大致時間；ready_ms 用 perf_counter 的差值計持續時間，避免把系統校時跳變當成請求耗時。兩者有不同用途，不能只因為都用秒就互換。

這裡 ready_ms 結束於 call_next 返回、響應頭準備好時，**不是最後一個響應字節送達客戶端的時間**，也不覆蓋慢速流式響應、網絡下載或瀏覽器渲染。p95_ready_ms 使用同一邊界。請求 ID 與日誌字段必須一起解釋，否則一個漂亮的低延遲數字可能只是測量範圍很窄。

對沒有觀察到的請求不能補寫虛構成功日誌。健康探測也是真實請求，會進入計數；演練報告說明包含 readiness 探測，不把它當業務用戶數。跨多個進程時各自日誌、時鐘偏差、採樣與重複都要另設計，本章沒有做分佈式合併保證。

## 5. 從事件計算窗口，而不是用平均值掩蓋錯誤

summarize 對給定的有限事件集合計算請求數、5xx 數、錯誤比例和 nearest-rank p95。排序後取向上取整的 95% 位置；只有 20 項時，尾部統計仍很粗。p95 不是最大值，也不表示“95% 用戶都滿意”。不同窗口的 p95 不能簡單平均成全局 p95。

本實驗規則是至少 20 個樣本，5xx 比例達到 5% 才進入 page 狀態；不足樣本是 insufficient_data，不是假裝健康。422 是客戶端輸入拒絕，不計入這個服務端故障分子，但 4xx 突增仍可能提示前端版本不兼容或攻擊，需要另一條規則觀察。

這個 page 只是規則返回值，沒有真實發送短信、郵件或值班通知。真實告警還要定義時間窗口、最小請求量、持續時間、抑制/恢復策略、責任人和操作手冊。閾值是本實驗的可解釋選擇，不是通用生產 SLO。

傳入私有 socket 的 host 還不夠：libpq 仍可能從 `PGHOSTADDR`、`PGSERVICE`、`PGSERVICEFILE` 等環境變量取得另一個連接默認值。`reject_connection_environment` 在創建臨時目錄之前，以及每次直接連接、遷移和服務啟動之前，拒絕繼承的全部 `PG*` 變量，唯一例外是隻定位可執行文件的 `PG_BIN`。錯誤只列變量名，不打印值，也不修改調用者環境。Python 連接、SQLAlchemy 的連接創建器和 PG 子命令都使用自有目錄內的空白 0600 `empty.pgpass`，不讀取用戶的默認密碼文件。直接運行 `demo.py` 或 `ci.py` 也執行這些防護，不依賴倉庫總 runner 先替它清理。

## 8. 秘密掃描要檢查所有實際輸出

演練把隨機合成 canary 放進非法 password 字段、Cookie、查詢參數和不可信請求 ID，併發送真實 Bearer token。隨後掃描事件文件、服務 stdout/stderr 日誌和 PostgreSQL 日誌，要求原始 canary 與 token 均未出現。校驗失敗正文也不能回顯那個值。

這證明本次已執行路徑沒有洩漏這些標記，不是證明任意第三方庫、未來路由、代理、瀏覽器控制檯或異常路徑都永遠安全。新增日誌字段/錯誤處理後要重跑，並審查收集範圍。也不要為了調試一次失敗把測試變量中的完整 token 打印出來；回執用狀態、計數與關聯 ID 足夠。

日誌文件本身也需要訪問權限、保留期限與刪除政策。當前腳本退出會刪除整份臨時目錄，因此最終交付沒有日誌裡的秘密或業務數據。真實系統不能靠“日誌不留存”逃避維護，需要設計受控保存與刪除，而不是把 .log 全打進發布 ZIP。

## 10. 容量觀察與暫停恢復記錄

演練記錄實際請求數、錯誤數、響應準備時間與總觀察耗時，可用來發現明顯迴歸，卻不是生產容量測試。這裡是一臺機器、一個 worker、順序合成請求，小數據、熱本地緩存；沒有真實併發用戶、遠程數據庫、哈希登錄負載、長連接或持久日誌採集器。不能把請求數除以這個時間就宣稱“生產可服務多少用戶”。

上線前先給受控試用限定用戶數/速率/數據量，記錄 CPU、內存、連接池、隊列、磁盤與錯誤/延遲趨勢，再在隔離環境逐步增加代表性負載；超限要有拒絕或降級策略。單看平均延遲或裝好儀表盤不能替代這些驗證。

暫停記錄最後關聯 ID（不是 token）、應用版本、觀察窗口、受影響路由與狀態、權限變更、已驗證修復、日誌私密性檢查、子進程與臨時目錄是否清理、下次第一步。恢復先重跑正常聚合測試，再用新集群重放故障；不要連接用戶數據庫撤權。
