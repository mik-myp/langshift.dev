## 1. The requirement is one completed operation, not two attempted INSERTs

Creating a project requires a projects row and a project_members row identifying its owner. If the second insert fails but the first survives, the UI can list a project that nobody owns. A nicer error message cannot repair this state. D03 expressed all-or-nothing behavior with SQL transactions. Now we must preserve it across an HTTP request, Python objects and a borrowed database connection.

An ORM maps objects to tables and coordinates SQL for tracked changes. It does not replace the database, choose your business transaction boundary, establish permissions, or make integrity errors impossible. Learning add and commit without identifying their owner leaves the most important question unanswered.

## 2. Installing a driver does not start a database server

Python executes the program; uv installs Python packages; psycopg is the client driver. PostgreSQL's postgres runs the server, initdb initializes a new cluster directory, pg_ctl manages the server for that directory, and psql sends SQL. A cluster can contain multiple databases. Each test owns a newly named database within our disposable cluster.

## 3. Make the H-to-database model transition explicit

Moving from one person's in-memory tasks to persistent project tasks is a model change, not merely swapping a storage adapter.

| H field | Database equivalent | Meaning |
| --- | --- | --- |
| id | tasks.id, bigint identity | Database assigned; no automatic import of old IDs; sequence gaps are normal |
| title | title varchar(120) | Retained, with API and database validation |
| minutes | integer, nonnegative, default 0 | Retained estimate; an optional capstone extension |
| done | status | false→todo, true→done; doing is a new state |
| note | nullable description | Renamed; NULL differs from a supplied empty string |

As in D01–D03, users has id/login; projects has name/created_by/created_at; project_members has a composite project_id/user_id primary key; tasks adds project/creator references, deadlines and timestamps. All foreign keys use RESTRICT. Do not silently replace that policy with ORM deletion cascades. Login comparison is currently case-sensitive.

Password hashes, active state, auth_version and user timestamps are intentionally absent. S chapters must add them through migrations, not fake password defaults. The exact-one-owner/creator-is-owner invariant is a service responsibility not fully enforced by this DDL. A valid foreign key establishes existence, not membership or authorization.

## 4. Four layers: Engine, pool, Connection, Session

A request borrows a Session. When SQL is required, the Session obtains a Connection through the Engine; its pool supplies a psycopg connection, and a PostgreSQL backend executes the transaction. Object tracking and physical connection ownership are related, but distinct.

| Layer | Responsibility | Lifetime owner |
| --- | --- | --- |
| Engine | Dialect/driver configuration and pool entry point | Usually once per application process; dispose at shutdown |
| Pool | Reusable physical client connections | Engine; not all connections are opened immediately |
| Connection | A checked-out connection and transaction access | Session or an explicit with block; close normally returns it |
| Session | Identity map, pending changes, transaction bookkeeping | One request/unit of work; never shared concurrently |

An identity map resembles retaining an object by key inside a component tree, but is not a React store or a global cache subscribed to every database change. Separate Sessions can observe different database states. SQL isolation rules still apply.

A pool avoids repeatedly establishing connections; it does not let one connection host unrelated simultaneous transactions. pool_size=2 and max_overflow=0 make leaks easy to see, not a production sizing recommendation. Each worker has its own pool. pool_pre_ping can detect a stale connection when checking it out; it cannot rescue a transaction whose connection dies midway or safely retry an operation with an unknown commit outcome.

## 5. A unit of work has several distinct milestones

Constructing a Project creates only a Python object. add enrolls it in Session tracking. flush sends pending SQL, obtains generated IDs and may raise CHECK/FK errors. A successful flush is not a durable commit: a subsequent rollback can still remove every inserted row.

commit normally flushes, then asks PostgreSQL to finish the transaction. Deferred constraints and other failures can occur at that point. Queries may trigger autoflush too; explicit flush is not the only line that can fail because of pending writes.

Session autobegin means the first database operation, including a SELECT, can begin a transaction and borrow a connection. An unclosed read can remain idle in transaction. `with Session(...)` closes the Session but does not automatically commit successful work. `with session.begin()` commits on success and rolls back on exception. Place begin outside the first read/write; blindly calling it after a SELECT may encounter an already-started transaction.

By default, expire_on_commit=True expires object attributes, so later access can issue another query. Detached objects should not be handed to a serializer that might try to load them after cleanup. This example copies plain dictionaries while the transaction is active and returns only after commit succeeds. Constructing a dict before commit is not sending it to the client; a commit failure prevents the return path entirely.

## 7. Business functions borrow the Session; callers own the transaction

<Code language="python">{getOrmExample('services.py')}</Code>

create_project flushes the project to obtain its ID, then flushes its owner membership. Both remain inside the caller's transaction. If a helper committed the project first, an outer rollback could not undo it. Adding another catch block cannot repair ownership split across two commits.

owner_role exists for controlled failure injection; it is not an API input. Ordinary requests always use owner. Helpers do not create their own Sessions or commit, so a higher-level operation can compose project, owner and first task into one transaction. Do not put an email or another external side effect into that transaction and expect database rollback to undo it.

list_tasks builds select/where/order_by/limit/offset expressions and consumes scalars while the Session is alive. Values are bound parameters rather than SQL text fragments. Ordering by id stabilizes pagination for an unchanged dataset, not during arbitrary concurrent insertions/deletions. Filtering by project avoids a wrong query scope but does not authorize the requester.

## 8. At the HTTP boundary, success follows commit

<Code language="python">{getOrmExample('api.py')}</Code>

get_session owns creation and closure, not a hidden commit after yield. Write endpoints own begin. Returning happens after the transaction manager has successfully committed, so a deferred constraint cannot turn an already-announced 201 into a late database failure. IntegrityError is caught outside begin, after rollback handling, and translated into a sanitized 409.

Not every exception is an integrity conflict. Connection failure and programming errors must retain their separate failure/observability paths rather than becoming 409 indiscriminately. Pydantic rejects malformed input with 422; missing parents produce 404. A real product should further classify known constraint names into business errors instead of returning database internals.

The endpoints use ordinary def and synchronous database operations. The asynccontextmanager in lifespan is the ASGI startup/shutdown wrapper, not async ORM. Never let concurrent requests or tasks share a Session. The application factory takes responsibility for disposing its Engine at shutdown.

owner_id and created_by are temporary, local-only teaching inputs. S chapters must derive both from validated identity and check project membership; the public input models must stop accepting self-reported identity. Bind this unauthenticated example to loopback only and never publish it.

## 10. Failure lab: rejection at COMMIT, not just during flush

<Code language="python">{getOrmExample('commit_failure.py')}</Code>

```bash
uv run --locked python pg_sandbox.py -- python commit_failure.py
```

```text
two INSERT values accepted; deferred check awaits COMMIT
COMMIT failed
Session refuses reuse before rollback
rollback restored Session; next transaction committed one row
checked out: 0
```

commit_probe is a separate lab-only table. Its unique constraint is DEFERRABLE INITIALLY DEFERRED. Two values of 7 are accepted initially and rejected when committing. This proves an actual commit-time failure; a CHECK failure during flush is a different event.

Attempting another SELECT before recovery is rejected by the Session's failed transaction state. Explicit rollback resets that bookkeeping as well as ending the failed unit of work. A new transaction can then insert 8 and commit. Discarding the failed Session and creating a fresh one for the next request is also valid. Previously tracked objects must not be treated as successfully persisted simply because they still exist in Python.

This server explicitly rejected the commit, so zero residue is a valid assertion. A lost network response during COMMIT is different: the client may not know whether the server committed. Do not equate “no success response” with “definitely no write.” Idempotency and outcome reconciliation are outside this lab.

<summary>Answer: obtaining an ID is not committing a transaction</summary>

The INSERT ran inside an uncommitted transaction. Rolling it back removes the row. Identity sequences need not return allocated values on rollback, so gaps are expected and must not be interpreted as lost business records. Test row contents, not consecutive IDs.

<details>
<summary>Answer: find the borrower instead of enlarging the pool</summary>

Even a read transaction can retain a connection. Once all are borrowed, the next operation waits until pool_timeout rather than failing a CHECK constraint. Reinstate with/dependency cleanup on both success and exception, then prove checkedout returns to zero. Accidental garbage collection is not an ownership policy; one apparently successful run cannot establish safety.
