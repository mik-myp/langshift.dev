## 1. 这次不是再照着搭一个框架

到这里，你已经学过值、容器、控制流、函数、异常、模块、文件、环境和普通自动化测试。现在把这些能力组合起来：**先给需求与验收，你独立设计和实现，再用参考实现核对责任边界。** 不要求一口气从记忆写出所有 API，允许查前面章节和官方文档。

产物是一个本地任务程序，不是 Web 后端，也不是生产级持久化系统。它足够小，便于追踪每一次数据变化，又包含真正工程中不能回避的输入契约、文件失败、依赖恢复、测试和需求变更。数据库、权限与上线仍需要后面的专门教学。

## 2. 先把数据与行为契约写完整

文件中是一份 JSON 数组，每项恰好有 title、minutes、done。title 是非空白 str，保持原拼写；minutes 是普通非负 int，不接受 bool、float、数字字符串；done 只能是 bool。空数组、零分钟与重复标题都合法，保持原顺序。缺字段和多字段均拒绝。

首次运行仅在目标文件**缺失**时使用以下初始数据，已经存在的空数组不能被当成缺失：

<Code language="json">{getProjectExample('fixtures/initial.json')}</Code>

每次正常运行，把标题精确等于 Read 的所有未完成项标为完成；已完成项不重复计入 changed。然后保存一次，报告变更数量、总任务数和仍未完成的分钟数。标题不是唯一 ID，因此匹配重复标题时全部处理；本章不会暗中把“查找第一项”当成约定。

读取缺失与读取损坏是不同事件。现有文件编码错误、JSON 语法错误、业务形状错误时，必须非零失败并保留原字节，不得初始化、保存空数组或只警告后继续。权限与未知 I/O 错误也不能变成“新用户没有任务”。

## 3. 沿数据流分责任，而不是为了目录多而分层

画出数据流：**路径 → 打开的文件 → 文本解析 → 数据校验 → 业务变化 → 汇总 → 序列化 → 保存 → 展示**。每个边界回答两个问题：输入由谁保证？失败由谁负责解释或传播？

- validation：验证数据并返回新列表、新字典。调用者修改返回值不得影响原输入。
- rules：标记完成与计算汇总；不打开文件、不打印、不创建目录。它不依赖一个全局可变“任务数据库”。
- storage：读取和保存文件，使用校验；load 传播缺失，不擅自决定是否初始化；save 在破坏性打开之前完成校验与序列化。
- app：选择固定路径、创建自己拥有的父目录、决定何时初始化、安排调用顺序，并在损坏输入后停止。

这些是普通模块和函数，不是要求现在学习企业架构术语。可以选择同样清晰的文件名，但要能解释职责。程序小不等于允许在导入时读写真实文件；文件多也不自动产生正确的边界。

写下自己的模块草图和每个函数的输入/输出/错误，再打开答案。函数签名暂时不要求注解，静态类型在 L11 专门教学。

## 5. 在写实现之前定义验收表

第一次和第二次运行的输出应分别为：

```text
Source: new file
Changed: 1
Tasks: 3
Pending minutes: 35
```

```text
Source: existing file
Changed: 0
Tasks: 3
Pending minutes: 35
```

这两次必须是新的 Python 进程。不能只在同一进程里保留列表，然后声称已经读回文件。第二次 changed 为零体现的是当前操作的业务约定，不是承诺所有程序都有“重复运行永远无副作用”的性质。

还要验收：

| 情况 | 应观察到什么 |
| --- | --- |
| 导入 app/storage | 仅导入探针输出，无创建目录/读写文件/业务入口 |
| 已存空数组 | 保持空数组；计数、变更、未完成时间均为零 |
| 多个 Read，其中部分已完成 | 全部匹配，但只统计这次新完成的数量 |
| Practice 的分钟数改为 36 | 新进程汇总必须变为 36，不硬编码 35 |
| 坏 JSON、错误编码、错误业务形状 | 失败、原字节不变，没有成功保存提示 |
| 不存在的父目录 | 由 app 创建自己指定的父目录，不是 storage 偷偷创建任意目录 |
| 换 cwd | 入口仍访问约定的项目数据位置，不能在调用者目录意外创建另一份数据 |

保存前拒绝无效值必须保护旧文件；**写入过程中断仍可能损坏文件**。本章沿用 L07 的明确限制，不把 with、测试或单文档格式夸大成数据库事务。

## 6. 文件测试先获得自己的可丢弃目录

不能让测试把你正在使用的任务文件改坏，也不能要求读者先学 fixture。这里补充一个小型标准库工具：TemporaryDirectory 创建临时目录，with 结束时清理它拥有的目录和内容，正常与异常退出都走清理路径。

<Code language="python">{getProjectExample('demo_resource.py')}</Code>

```bash
uv run --locked python demo_resource.py
```

```text
Inside: True
After: False
```

directory 是临时目录的字符串路径；Path 把它变成你已经会使用的路径对象。测试只能在这个目录内创建自己的文件，不把真实用户路径传进去。退出后 path 名称仍存在，但资源位置已被清理；这沿用 L07“名称存在不等于资源可用”的模型。

测试采用同样结构，每项自己创建目录。一个读取函数不必知道自己正在被测试；它只接受 Path。app 也可以把固定默认路径的选择与 main(path) 的调用边界分开，让测试传入自己的目录。这只是普通函数参数，不是提前引入框架依赖注入，也不是开放任意上传路径的安全承诺。

## 7. 分阶段做，避免一次写完再找几十个原因

建议按可验证的最小步推进，但具体代码由你决定：

1. 先写纯校验与规则，用普通测试确认空、零、重复标题和不修改输入。
2. 加读取和保存，在临时目录完成往返；写入两次后仍是一份合法文档。
3. 加 app 协调与固定路径，验证首次/再次/现有空数组。
4. 复制坏输入到自己的实验目标，确认失败前后字节相等；不要原地修 fixtures。
5. 从另一个目录使用外层入口运行，证明路径锚点正确；用导入探针确认导入不启动业务。
6. 第二个干净目录恢复环境并重跑整个验收表，最后做独立变式。

某一步红了，先找到失败层次，不要一口气升级 Python、换包源、改 JSON、改断言。每次最小修改后先跑相关测试，再跑全套，保留能解释的进展。

## 10. 诊断一次坏数据，而不是删除文件了事

下载中的两份坏输入分别为：

<Code language="text">{getProjectExample('fixtures/broken.json')}</Code>

<Code language="json">{getProjectExample('fixtures/wrong-shape.json')}</Code>

在项目副本中，先运行正常程序得到自己的输出文件，保留其备份；再把坏输入复制到这个副本的 _output/tasks.json。执行相同入口，观察非零失败，再用编辑器或已学过的 read_bytes 比较目标是否仍等于复制进去的坏字节。原始 fixtures 只作输入，不被修改。

第一份没有合法 JSON，第二份能解析但根对象不符合业务数组要求。它们都不应触发初始化。完成观察后，有意识地恢复刚才备份的好数据，再运行；不能以“删除坏文件后应用能启动”声称已经处理损坏。恢复数据、修复程序与重新初始化是三种不同操作。

同样，不要把 PermissionError 恢复为空列表，不要为演示随意放开系统目录权限。未知错误应保留可诊断的失败，而不是制造一个看似成功的新文件。

## 11. 独立需求变式：按预算选一份计划

不提供逐行步骤。增加一个纯函数，输入合法任务与普通非负 int 预算。按原顺序只考虑未完成任务；如果当前任务放不下，跳过它但继续看后面；恰好放下和零分钟都允许。返回独立的新任务记录与已使用分钟数，不修改输入，不写文件。

这不是全局最优背包算法，不允许为了“装得更多”重排输入。请先自行决定函数签名，写出能区分 break/continue、等号边界、完成项、bool 预算与共享引用的测试，再实现。原应用的 15 项仍需保持通过。

## 12. 毕业于这一阶段，不等于已经能上线

阶段退出要求：能从需求解释自己的模块设计；空目录建立代码与环境；有意制造一个业务缺陷并让测试抓住它；在新进程读回；错误数据拒绝覆盖；第二目录恢复；独立完成预算变式；明确陈述尚无并发、权限、事务和服务运行能力。

给自己的 README 写清命令的工作目录、版本、首轮/重复输出、刻意失败、安全输出目录和恢复办法。暂停记录源码版本/改动、最后测试命令与数量、当前数据是否损坏、备份位置、下一步要证明的行为。不要只记录“今天学到第几页”。

下一章 L11 才把类型注解加到已理解的函数与容器上，比较静态检查和运行时校验。类型、模型、装饰器和资源协议的基础完成后，再进入 HTTP 与 FastAPI，不把工程综合作业变成突然跨入服务端的捷径。
