## 1. A backup matters because of what you can recover

“A .dump file appears every day” does not identify its database, required tables, readability, access controls, recovery time, or restored-user safety. An empty file can have the right name. An archive whose inventory can be listed can still fail during restoration.

Our acceptance endpoint is **useful, authorized behavior after an isolated restore**: real pg_restore → matching data fingerprints → constraints still reject invalid records → sequences support new writes → runtime identity is not owner → old credentials fail → valid users can access only their own projects. Only then do we discuss the gates for invited use.

Download the [independent O06 lab](/learning-assets/js2py/o06-recovery.zip) and enter `o06-recovery`. All data is generated. Only an owned mkdtemp cluster and fresh source/restored/damaged databases are created. No existing user database, real backup, or production credential is read.

Frontend habit says “refresh the page and retry.” Server data has no such escape: a damaged database does not heal by restarting. The only way back is a verified backup restored into an isolated target — which is why this chapter's acceptance ends at a proven restore, not at a file existing.

## 2. Define backup scope before selecting tools

Pg_dump creates a consistent snapshot of one database. We use custom format with pg_restore, not SQL text redirected into psql. The archive includes users, projects, project_members, tasks, auth_sessions, task_operations, and alembic_version, including a nonempty synthetic idempotency receipt. Saving task titles alone would not preserve the application.

A single-database dump excludes cluster-global roles and tablespaces. It also does not save application configuration, deployment artifacts, encryption keys, object storage, logs, or separate security-change records. We explicitly choose no-owner/no-privileges, prepare roles in the private cluster, and reapply reviewed grants rather than blindly transporting old superuser identities.

## 3. Define RPO and RTO, then measure a rehearsal

RPO is the maximum data-loss time window the business can accept. RTO is the target time to restore service. Writing targets in a README does not guarantee them. Daily backups do not automatically guarantee at most one day lost: failed jobs, unreadable archives, replication delays, and late discovery can increase exposure.

We commit one task after the snapshot and explicitly observe its absence in the restored target. The known loss is one post-snapshot row. We measure from beginning restoration through data, security, and real-API checks as restore_and_validation_seconds. Snapshot_age_seconds is the age of this small snapshot at inspection, not a production RPO measurement.

Sub-second or few-second results for tiny data on the same host and tool version, without remote transfer, cannot predict a large database or cross-host disaster. Real drills must define whether detection, decisions, retrieval, decryption, capacity preparation, validation, and reopening approval are included in timing.

<details>
<summary>Explanation answer: why is “pg_restore took a second” not a one-second RTO?</summary>

Roles, credentials, DNS/proxy routing, or compatible applications may still be missing. Data may omit tables, violate expected authorization, or revive revoked sessions. Timing only import excludes required recovery work. Define the start/end events first, then measure a representative complete drill by stage and retain uncertainty.

</details>

## 4. An external URL must not choose the restore target

Overwriting the wrong database is worse than a failed restore. The tool never accepts an existing DATABASE_URL. It creates only **new** databases from an allowlist, rejects names already created, and offers no --clean overwrite shortcut. The directory must also belong to this run, with UID, mode, ownership marker, and symlink checks.

PostgreSQL uses a private Unix socket and never claims the user's TCP 5432. Source and target are separate databases in the same owned cluster. That prevents rewriting the source but **does not verify disaster recovery onto another host**. Application processes listen only on temporary 127.0.0.1 ports. Finally stops owned processes, closes their ports, and deletes owned paths; it never scans for other PostgreSQL services to stop.

New restore databases revoke PUBLIC CONNECT. The runtime role receives no connection grant until data, constraints, and security handling have passed. Explicit isolation is stronger than merely hiding an address, especially because roles are shared across databases within a cluster.

Passing a private-socket host is not sufficient by itself: libpq can still obtain other connection defaults from `PGHOSTADDR`, `PGSERVICE`, `PGSERVICEFILE`, and related variables. `reject_connection_environment` rejects every inherited `PG*` name before temporary-directory creation and before each direct connection, migration, or server launch. The only exception is `PG_BIN`, which locates executables, not a database. Errors list names only, never their values, and do not mutate the caller's environment. Python connections, SQLAlchemy's connection creator, and PostgreSQL subprocesses use an empty mode0600 `empty.pgpass` in the owned directory rather than the user's default password file. Direct `demo.py` and `ci.py` execution have these guards too; safety does not depend on the repository runner cleaning up first.

The controller no longer probes an unused port, closes that socket, and asks another process to acquire the same number. Uvicorn binds `--port 0` itself. The controller reads the actual port from **that child's own private startup log**, then requests readiness. `--no-access-log` does not suppress the info-level startup banner; the controller explicitly selects uncolored logs and one worker. Concurrent identical releases have distinct log files. A real test starts two servers together and checks their different ports, corresponding banners, actual requests, and cleanup. This removes the probe-close-rebind window, not every possible concurrency failure. A future incompatible Uvicorn banner format fails by deadline rather than guessing a port.

Backup records table counts and stable content digests, invokes real pg_dump, calculates archive hash/size, and checks inventory with pg_restore --list. **A readable inventory is one small gate, not restoration success.** Restore verifies its path/checksum, creates a fresh target, executes pg_restore with exit-on-error/single-transaction, and compares every table.

The archive hash detects accidental damage; it does not authenticate the publisher. PostgreSQL dumps from malicious or unknown sources can execute code. Do not restore unfamiliar archives merely because they have a SHA-256 value. Production needs trusted provenance, access controls/signatures, and appropriate review.

There are no concurrent writes during fingerprinting and dump in this exercise, making their consistency boundary explicit. On a busy system, counts queried at one time cannot simply be compared with a later dump as if both shared a snapshot. Coordinate snapshots or use meaningful restored-business invariants. This chapter does not silently introduce WAL/PITR or promise zero loss.

## 6. What security state can a backup bring back?

Under the S contract, opaque-token validity depends on database state. After a backup, a user may log out everywhere, be disabled, or lose membership. Restoring older users/auth_sessions/project_members may make an old token satisfy the earlier auth_version/expiry and reintroduce old memberships. Exact row restoration can itself restore a security risk.

While the target remains isolated, quarantine_sessions disables every restored user, increments auth_version, and deletes restored sessions. Accounts and memberships must then be reconciled against **trusted security changes outside the backup** before explicit approval to enable them. Our known synthetic ledger says Bob was removed from Alice's project. The fixture reapplies that change, approves the two synthetic accounts, and creates new test sessions as an operator.

This is not automatically signing every user back in. Without trustworthy newer authorization records, keep the target isolated or accounts disabled pending authorized review. A stale backup cannot establish current membership. Old password hashes restored after password changes also need consideration; real recovery may require resets, separately retained revocation history, or another explicit policy.

<details>
<summary>Security answer: is deleting auth_sessions without checking project_members enough?</summary>

No. Old tokens fail, but a user who later obtains a legitimate new token may still use restored, outdated membership to access a revoked project. Session invalidation and object authorization are separate responsibilities. Isolate, handle credentials, reconcile accounts/memberships, then approve reopening. Without an authoritative record, fail closed rather than guess.

</details>

- The old Alice token would have become valid in the still-isolated restored database. Account/session quarantine and membership reconciliation happen before access is granted.
- Real Uvicorn requests reject old, expired, and invalid tokens with 401. Fresh Alice reads her own project but receives 404 for Bob's. Fresh Bob cannot read Alice's project.
- Restored identity sequences generate new project IDs without colliding. The application role cannot DROP TABLE.
- Source retains its third post-snapshot task while restored has the two snapshot tasks. Restoration never overwrites the source.

The three restore-focused cases create real PostgreSQL: full restore/constraints, checksum rejection before target creation, and refusing an existing target. SQLite cannot simulate pg_restore semantics; actual PostgreSQL tools and server behavior are the subject.

| Failure | Correct response | Unacceptable shortcut |
| --- | --- | --- |
| Checksum mismatch | Leave target uncreated; retrieve a trusted archive again | Change the manifest hash to accept damaged bytes |
| Nonzero pg_restore | Keep the target isolated; investigate archive/tool/role; use a new target | Ignore exit status and open the app |
| Fingerprint/business constraints differ | Mark restore incomplete and check scope/consistency | Delete assertions or compare counts alone |
| Old token works | Stop reopening; enforce session/account/membership recovery policy | Call revived credentials good compatibility |
| App can DROP a table | Review owner/ACL separation | Run the app as the same superuser |

<details>
<summary>Guided recovery answer: why exercise both checksum rejection and real corrupt restore?</summary>

The checksum gate rejects accidental damage before creating a target. A real pg_restore failure verifies that tool errors are not ignored and an unsuccessful target cannot masquerade as a healthy service. Those are distinct responsibilities. Only an owned truncated copy is damaged here; no real backup is used for destructive experimentation and --clean never targets the source.

</details>

## 10. A recovery runbook with actionable gates

Before touching a real environment, name an operator and evidence location for each stage:

1. Declare incident scope and suspend dangerous writes/ingress. Do not overwrite first and ask afterwards.
2. Choose a trusted, decryptable backup with a clear time point; review version, scope, and retention.
3. Prepare a new adequately sized isolated target, roles, and private directories; deny ordinary clients.
4. Restore and record exit status/duration. Never reopen after a failed tool run.
5. Check fingerprints/business samples, constraints, sequences, revision, application compatibility, and least privilege.
6. Reconcile accounts, password/session state, memberships, and other post-backup security changes; keep accounts disabled until approval.
7. Test fresh credentials with two users on allowed and denied paths, verify log privacy, and obtain authorized approval for ingress switching.
8. Observe errors, latency, and differences; preserve the original environment for investigation; clean up under reviewed retention rules.

Do not put real tokens, passwords, or complete connection secrets in the runbook. Report the recoverable point, known losses, measured duration, and unresolved risks—not just a green service indicator. This lab executes only local stages and cannot manufacture production approval or a public traffic switch.
