## 1. What evidence is still missing after tests pass?

H06 tests APIs, D05/D06 test migrations and real databases, and O01–O03 establish process, container, and network boundaries. Putting those commands in YAML does not itself make a release safe. Tests may connect to the wrong database; multiple workers may change tables simultaneously; old code may not understand a new schema; reverting code does not undo new data.

We separate the sequence: check the candidate → verify migrations and interfaces in an owned test database → review the compatibility matrix → migrate as a separate operation → start the candidate and check readiness → approve traffic switching. Failure at one stage must stop later stages rather than be reported as success.

## 2. Preserve the D/S contract without pretending this is the whole product

The package retains the D/S users/projects/project_members/tasks, auth_sessions, and task_operations fields. Tasks use status/description/priority, not the H-stage done/note names. Authentication uses opaque Bearer tokens with only SHA-256 digests stored; each request checks expiry, revocation, account activation, and auth_version. A digest of a random token is not password hashing; synthetic passwords still use the Argon2id library.

The **operational API slice** exposes health, authenticated project reading, and project creation. It does not reimplement login, password changes, membership management, or the full S03 idempotency service. An operator fixture creates synthetic sessions in the private database; this is not a new public login bypass. Replacing a full application with this slice would lose functionality.

V1 returns project id/name; v2 adds nullable description. Old code names the columns it reads/writes and ignores the new field. The new column permits old inserts to omit it. These are application versions, not PostgreSQL versions.

## 3. Isolation begins with connections and ownership

A test database is not merely a name containing test. Tests need ownership of creation and cleanup and must not accept a production URL accidentally. This lab ignores ambient business DATABASE_URL values and connects only to a private Unix socket inside its own `/tmp/ls-ops-*` directory. Database names are explicitly allowlisted too.

Mkdtemp creates an exclusive directory; mode 0700 restricts access; a marker records the UID and a random ownership value. Cleanup rechecks paths, ownership, modes, markers, and symlinks. PostgreSQL listens on no TCP interface, while the API uses a temporary 127.0.0.1 port. Trust authentication on this private socket is a short-lived local teaching policy, **not production authentication**. The operating-system account remains a trust boundary.

Development, tests, staging, and production should use separate databases, accounts, and secrets. Deployment and runtime identities should differ too. We verify an isolated test environment here, not an already deployed staging system. If versions or ownership checks fail, investigate; do not redirect the script to an existing user database to make it run.

Passing a private-socket host is not sufficient by itself: libpq can still obtain other connection defaults from `PGHOSTADDR`, `PGSERVICE`, `PGSERVICEFILE`, and related variables. `reject_connection_environment` rejects every inherited `PG*` name before temporary-directory creation and before each direct connection, migration, or server launch. The only exception is `PG_BIN`, which locates executables, not a database. Errors list names only, never their values, and do not mutate the caller's environment. Python connections, SQLAlchemy's connection creator, and PostgreSQL subprocesses use an empty mode0600 `empty.pgpass` in the owned directory rather than the user's default password file. Direct `demo.py` and `ci.py` execution have these guards too; safety does not depend on the repository runner cleaning up first.

The controller no longer probes an unused port, closes that socket, and asks another process to acquire the same number. Uvicorn binds `--port 0` itself. The controller reads the actual port from **that child's own private startup log**, then requests readiness. `--no-access-log` does not suppress the info-level startup banner; the controller explicitly selects uncolored logs and one worker. Concurrent identical releases have distinct log files. A real test starts two servers together and checks their different ports, corresponding banners, actual requests, and cleanup. This removes the probe-close-rebind window, not every possible concurrency failure. A future incompatible Uvicorn banner format fails by deadline rather than guessing a port.

The controller migrates transactionally with an administrative identity and lock_timeout. Failure stops the release. Ordinary workers do not compete for DDL during startup. Our drill has one serial operator; **the function is not a distributed migration lock across deployment systems**. A real pipeline must enforce a single coordinator and plan timing around table sizes, lock waits, and compatibility windows.

Downgrade deliberately refuses automatic destructive reversal. Dropping description would destroy values already written by v2. Being able to write DROP COLUMN does not make it part of an ordinary code rollback. Restoring a backup also loses post-snapshot data; the recovery chapter treats that separately.

<details>
<summary>Explanation answer: why not have every worker run upgrade head?</summary>

Workers can read migration state concurrently, wait for or contend on locks, and begin serving at different stages. Runtime accounts would also need DDL privileges. A separate controlled migration step lets you observe failure before starting compatible processes. It does not promise lock-free or zero-downtime migration; that depends on the actual change and data scale.

</details>

## 6. Describe compatibility with a matrix

| Application / schema | 006, no description | 007, nullable description |
| --- | --- | --- |
| v1, named id/name reads/writes | Supported | Supported; omitted new field becomes null |
| v2, needs description | Startup refused | Supported |

For this rollback, forward compatibility means old code can operate against the already-expanded schema. A nullable column makes this example compatible, not every ADD COLUMN safe. Constraints, defaults, enums, request formats, and changed meanings can all break old code.

If frontend clients already require description after v2 launches, returning to v1 can break their response contract. A rollback plan therefore also needs a client compatibility window, feature control, or coordinated suspension of new functionality. This drill deliberately uses a controlled client appropriate to each version. It does not claim a real-user transition has no impact.

## 8. A failed migration is not permission to rebuild the database

The NOT NULL failure means historical rows have no value, not that Alembic is broken. Review the requirement: expand with a nullable field; deploy compatible code; backfill under an explicit business policy; verify no nulls; add the constraint in a separate controlled revision. Deleting user data to make a migration green is not a repair.

Locate other failures by stage: versions at the environment gate; revisions at migration/compatibility checks; role privileges at database authorization; readiness deadlines at startup/database paths. Public reachability belongs to an ingress boundary this drill does not cover. Dumping the environment, SQL parameters, or Bearer tokens is not appropriate diagnosis.

<details>
<summary>Guided repair: how do you prove there is no partial migration?</summary>

Do more than assert the exception. Reconnect and verify the original three projects and revision 006, then apply the reviewed 007. Transactional DDL failure rolls back here, but that does not prove every external side effect or migration operation is reversible. Concurrent index creation, external calls, and long backfills require their own analysis.

</details>

## 10. A release record you can resume from

Record candidate code identity, lock hash, application version, target environment identity, migration revisions before/after, commands and results, migration approval, readiness, and rollback version/conditions. This lab makes no Git commit, push, or published artifact, so do not invent a commit SHA or deployment URL.

When pausing, record the last successful stage, owned processes still running, whether the database was cleaned, intentional failures, and the clean starting state for replay. Demo/CI stops its API/PG processes and removes its directory. Resume by rerunning rather than looking for a deleted socket. The download allowlist contains source, SQL, lock, and documentation—not environments, logs, database directories, backups, or secrets.

A real release still requires O03's controlled HTTPS ingress, production secrets/permissions, actually executed CI, monitoring, tested backups/restores, and a rollback rehearsal. What is complete here is a reproducible local database/application delivery mechanism, not a public V4 launch.
