## 2. A path names a location; it is not an open file

In L06, current directory and script directory could differ. File operations have the same distinction: a relative path is interpreted against the process's current working directory, not automatically against the source file containing it.

We will use `Path` from the standard library. `Path("fixtures")` creates a path object; it does not create a directory or open anything. You have already called methods on lists and dictionaries. Here you use an existing library type and its methods; you do not need to implement a class.

File: `paths.py`.

<Code language="python">{getFileExample('paths.py')}</Code>

```bash
uv run --no-project --python 3.13 python paths.py
```

Expected display below uses `<LAB>` for your real absolute extracted directory. It is a placeholder in output, not a command to type:

```text
Cwd: <LAB>
Relative: fixtures/notes.txt
Absolute: True
Name: notes.txt
Parent name: fixtures
Target: <LAB>/fixtures/notes.txt
```

The operations have different responsibilities:

1. `Path.cwd()` observes where the process is working.
2. `/` joins path components when the left operand is a Path. It is not numeric division here. You do not manually concatenate platform separators.
3. `Path(__file__).resolve().parent` starts from the current source file, resolves its absolute location and selects its containing directory. `resolve()` also resolves symbolic links; it is not a guarantee of existence, readability or security.
4. `.name` is the final component's string; `.parent` is another path object. The object still does not hold the file's contents.

An absolute right-hand component can replace the earlier path, rather than stay below it. Our programs use fixed, trusted components. **Path joining is not a sandbox for arbitrary user-supplied paths**; handling those belongs with the later server/security boundary.

```bash

cd ..
```

Only `Cwd:` changes to `<LAB>/fixtures`; the anchored `Target:` stays the same. Paths use `/` in these macOS verification displays; your system may display separators differently. Anchoring beside the script is suitable for this writable local exercise, not a claim that installed application source directories are always writable places for production data.

## 3. Read one complete file and see the resource boundary

The UTF-8 fixture `fixtures/notes.txt` has two lines. Its second line has **two leading and two trailing spaces**, and both lines end with a newline. We will use `repr` to make invisible characters observable rather than silently trim them.

File: `read_text.py`.

<Code language="python">{getFileExample('read_text.py')}</Code>

```bash
uv run --no-project --python 3.13 python read_text.py
```

```text
Inside closed: False
Text: 'Python 学习\n  keep spaces  \n'
After closed: True
```

Read the expression `with path.open("r", encoding="utf-8") as stream:` as a sequence:

1. `path.open(...)` asks the operating system to open that path for reading. If it fails, the indented block does not run.
2. On successful entry, `stream` refers to a **file object** that tracks the open resource and its current read position. It is not the Path and not the text.
3. `.read()` obtains text through that resource. The `encoding` setting tells the text stream how to decode stored bytes.
4. Leaving this file's `with` block closes the resource, even on the ordinary exception and return paths we will examine. `.closed` lets us observe that state.

`text` is an independent string already read into memory; closing the stream does not erase it or delete the file. The name `stream` still exists after the block, but its resource is closed. This is not JavaScript-style block-local name creation.

`Path.open(...)` serves the same basic purpose as built-in `open(path, ...)`. We consistently use the former here to keep path handling visible. `with` is the resource-use construct; it is not an import, loop or exception handler that automatically turns failure into success.

The path is anchored, so this also reads the same fixture:

```bash
cd fixtures
uv run --no-project --python 3.13 python ../read_text.py
cd ..
```

## 4. Reads move a cursor; iteration preserves the data you actually read

File: `read_cursor.py`.

<Code language="python">{getFileExample('read_cursor.py')}</Code>

```bash
uv run --no-project --python 3.13 python read_cursor.py
```

```text
First: 'Python'
Rest: ' 学习\n  keep spaces  \n'
At end: ''
Reopened: 'Python'
```

`read(6)` reads up to six characters in this text stream and advances its position. A later `read()` continues from there; it does not start over. At end of file, an unrestricted read returns an empty string. Opening a new read stream starts a new cursor at the beginning. We do not need random-access positioning to understand sequential reading.

Calling `.read()` without a limit can load the entire file. That is acceptable for these tiny fixtures, not an unlimited-memory strategy for uploads or logs. For sequential text, iterate over the file:

<Code language="python">{getFileExample('read_lines.py')}</Code>

```bash

```

```text

2 '  keep spaces  \n'
```

The loop uses the iterator behavior of the file; each iteration supplies a line. Line endings are generally included when present, and a final line need not have a newline. Do not assume every line is terminated merely because this fixture is.

`.strip()` would remove the second line's meaningful spaces as well as its newline. It is a data transformation, not a compulsory step in reading a file. `print(line)` can also show extra blank lines because the line may already end with `\n` and print adds another. `repr` makes those mechanisms visible without changing the input.

## 5. Text is not bytes, and encoding is not a cosmetic option

A Python `str` represents Unicode text. A file stores bytes. Encoding maps text to bytes; decoding interprets bytes as text. These are not JSON operations. UTF-8 is the explicit agreement used by our files, so results do not depend on an implicit machine encoding.

File: `encoding_bytes.py`.

<Code language="python">{getFileExample('encoding_bytes.py')}</Code>

```bash
uv run --no-project --python 3.13 python encoding_bytes.py
```

```text
Text length: 2
Byte length: 6
Bytes: b'\xe5\xad\xa6\xe4\xb9\xa0'
Decoded: 学习
```

These two Chinese characters each take three UTF-8 bytes. `b'...'` denotes a bytes value, not an ordinary text string with a decorative prefix. `len(str)` counts Unicode code points; complex visible symbols can contain more than one code point, so it is not a universal count of what a user perceives as characters. `len(bytes)` counts bytes.

A text stream does the decoding for you. Binary mode returns bytes instead. File: `read_binary.py`.

<Code language="python">{getFileExample('read_binary.py')}</Code>

```bash
uv run --no-project --python 3.13 python read_binary.py
```

```text
Is bytes: True
Decoded: 'Python 学习\n  keep spaces  \n'
```

`"rb"` means read binary. Do not pass `encoding` to a binary open; decode separately when you actually know the format. Text writes expect str and binary writes expect bytes. This small comparison establishes the boundary; it is not a binary-file-format course.

Now intentionally choose the wrong decoder in `error_wrong_encoding.py`:

<Code language="python">{getFileExample('error_wrong_encoding.py')}</Code>

```bash
uv run --no-project --python 3.13 python error_wrong_encoding.py
```

It prints `After error closed: True`, then exits with **UnicodeDecodeError**: ASCII cannot decode the fixture's Chinese bytes. Opening succeeded; decoding failed during read; leaving with still closed the file before the outer handler ran. This handler refers to `stream` only for that known post-open decode failure, not for every possible open error.

Changing the declared encoding does not convert a damaged file's bytes into the intended text. Do not add `errors="ignore"` just to hide an exception: discarded bytes may be meaningful. Establish the actual source encoding or refuse the input. The download also includes `invalid-utf8.bin`, a single byte `0xff` deliberately invalid as a standalone UTF-8 sequence, for a later diagnostic experiment.

## 6. Write modes are data-loss decisions

Before writing, inspect the destination path. The programs below create `_output/` with `.mkdir(exist_ok=True)`. Its parent already exists. `exist_ok=True` accepts an already existing directory; it does not turn a file into a directory or ignore permissions. Missing intermediate directories require a deliberate directory-creation policy, not a magical behavior of open.

File: `write_text.py`.

<Code language="python">{getFileExample('write_text.py')}</Code>

```bash
uv run --no-project --python 3.13 python write_text.py
```

```text
Characters written: 10
Read back: '学习 Python\n'
```

`write` does not add a newline automatically, so the string includes one. The returned 10 counts text characters here, **not bytes**; the generated UTF-8 file is 14 bytes. `newline="\n"` prevents platform-specific translation of our written newline, keeping the exercise's output bytes deterministic. Text reading with the default newline behavior normalizes common line endings to `\n`; binary reading does not make that translation.

| Mode used here | Missing target | Existing target | Main risk |
| --- | --- | --- | --- |
| `r` | Fails | Reads without intentional writing | Incorrect path/encoding or unbounded reads |
| `w` | Creates if the parent exists | Truncates on opening, before your first write | Old contents can disappear even if later work fails |
| `a` | Creates if the parent exists | Appends writes at the end | Repeated runs add data; not a whole-JSON update protocol |
| `x` | Creates a new file | Fails with FileExistsError | Caller must choose what an existing file means |



## 7. Closing is deterministic cleanup, not rollback

A file object holds operating-system resources and buffered state. Do not rely on a variable being discarded or on the interpreter eventually cleaning it up. Put acquisition and use under an explicit lifetime.

First run `closed_stream.py`, an **expected failure**:

<Code language="python">{getFileExample('closed_stream.py')}</Code>

```bash
uv run --no-project --python 3.13 python closed_stream.py
```

It prints the previously read string, then raises **ValueError: I/O operation on closed file**. The string is usable, but the closed stream is not. Returning data from a reading function is useful; returning a resource that has already been closed by that function is usually not.

### Normal completion, return, failure and failed acquisition

File: `cleanup_paths.py` makes each path observable. `stream = None` records that no file has yet been acquired; it prevents the observer itself from using an unbound name if opening fails.

<Code language="python">{getFileExample('cleanup_paths.py')}</Code>

```bash
uv run --no-project --python 3.13 python cleanup_paths.py
```

```text
Mode: normal
Inside closed: False
After block closed: True
Finally closed: True
Result: normal
Mode: return
Inside closed: False
Finally closed: True
Result: early
Mode: error
Inside closed: False
Finally closed: True
Caught: ValueError
Mode: missing
No stream acquired
Caught: FileNotFoundError
```

The normal path reaches the statement after with. The return path does not, but leaving the with block still closes the file before the surrounding finally runs. The error path closes first, then propagates ValueError to the caller. The missing path never enters the body or obtains a stream. The observer's finally does not perform a second close; it only reports the resulting state.

This teaches **using built-in file resources**, not implementing a custom context-manager protocol. Other context managers can have different exception policies. We also do not promise cleanup after forceful process termination or power loss. Buffered writes and closing can themselves fail; a successful call to write is not a crash-durability guarantee.

## 9. JSON converts values to text; saving is a separate step

JSON is a data-interchange format, not Python source and not a database. A file called `tasks.json` still contains bytes; its extension does not validate them. A syntactically valid JSON document can also contain the wrong kind of value for your program.

The complete path is:

```text
Python values -> JSON text (str) -> UTF-8 bytes in a file
file bytes -> decoded text -> parsed Python values -> business validation
```

File: `json_values.py` performs only the value/text steps. It does not create a file:

<Code language="python">{getFileExample('json_values.py')}</Code>

```bash
uv run --no-project --python 3.13 python json_values.py
```

```text
Is text: True
{
  "title": "学习",
  "minutes": 20,
  "done": false,
  "note": null
}
Equal value: True
Same object: False
Escaped: "\u5b66\u4e60"
```

`dumps` returns a JSON string; `loads` parses a string into Python values. The `s` versions operate on a string rather than an already opened file. The restored dictionary is a new object. `indent=2` controls formatting; it does not make the document more valid.

`ensure_ascii=False` keeps characters such as 学习 visibly present in the JSON text. The default escaped spelling `"\u5b66\u4e60"` represents the same JSON string after parsing. **Escaping is not file encoding.** Both representations can be written using UTF-8. `allow_nan=False` rejects non-finite output numbers, discussed next.

## 10. JSON is not a universal copy of every Python object

| JSON value | Typical Python value after decoding |
| --- | --- |
| object with string member names | dict with str keys |
| array | list |
| string | str |
| integer / fractional number | int / float under the default decoder |
| true / false | True / False |
| null | None |

JSON does not preserve Python tuple identity, set values, functions or arbitrary objects. In portable JSON, object member names are strings. Python's encoder accepts some other key types by converting them; that can change meaning or cause collisions, so our task format uses fixed string keys.

File: `json_limits.py`:

<Code language="python">{getFileExample('json_limits.py')}</Code>

```bash
uv run --no-project --python 3.13 python json_limits.py
```

```text
Restored: {'pair': [20, 35], 'labels': {'1': 'one'}}
Equal: False
Set is not JSON-serializable
Non-finite output rejected
Default decoder accepts NaN: True
Repeated key: {'minutes': 20}
Python repr is not JSON
```

Trace the differences rather than treating round-trip equality as universal:

- The tuple becomes a list, and the integer key becomes a string.
- A set is unsupported by the default encoder. Do not silence the error with a generic conversion without defining the data format.
- Standard JSON does not include NaN or Infinity. Python's default JSON behavior has extensions; `allow_nan=False` controls **encoding**, not `loads`. The default decoder can accept NaN. JavaScript's `JSON.stringify(NaN)` instead produces `null`; do not assume identical failure behavior.
- Repeated object names keep the last value with Python's default decoder. That is not duplicate detection.
- `str`/`repr` of a dictionary can contain single quotes and Python False, so they are not JSON encoders. Never use `eval` as a JSON parser.

Our later task validator restricts minutes to ordinary nonnegative integers, rejecting bool and float values, including NaN. It does **not** detect duplicate keys in the original text, implement a general strict JSON decoder or set size/depth limits. This is a small owned-file format, not a policy for arbitrary untrusted uploads. Such input needs explicit limits and parsing policies at the later backend boundary.

## 11. Save one JSON document, and do fallible preparation before opening w

The file variants take an **open file object**, not a path string. File: `json_file.py`.

<Code language="python">{getFileExample('json_file.py')}</Code>

```bash
uv run --no-project --python 3.13 python json_file.py
```

```text
dump returned: None
Title: 学习
Equal value: True
```

`dump(value, stream)` writes JSON text to the text stream. It returns None rather than the generated text. `load(stream)` reads and decodes one JSON document. The stream handles UTF-8, while the JSON functions handle JSON syntax and values. Neither automatically closes a caller-owned stream; its with block owns the lifetime. We add a final newline explicitly because dump does not add one for us.

| Pair | Takes / returns | Resource ownership here |
| --- | --- | --- |
| dumps / loads | Python value ↔ string | No file opened by these calls |
| dump / load | Value → writable stream; readable stream → value | Caller opens and closes the file |

### Appending documents is not updating an array

`pitfall_two_documents.py` is an **expected failure**. It writes only its own `_output/two-documents.json`:


```text

```

Two adjacent JSON objects are not one JSON document. Opening with append mode does not insert array punctuation or merge objects either. To save a small list as one document, construct the list in memory and serialize that list once. Line-delimited JSON is a different agreed format and reader, not a property that `json.load` silently supplies.

### Prepare before a destructive open, without promising atomicity

## 12. Parse success is not business validation: identify the failing layer

All four input strings are parseable JSON. The second has the wrong root shape. The third uses a string where our format requires an integer. The fourth uses a boolean, which must not sneak through as an integer: `type(minutes) is int` expresses this strict boundary. Unlike L05's form-like text input, this file format stores numbers as numbers. Automatically calling `int` would conceal that contract mismatch.

Now inspect six distinct cases without changing their files. `inspect_documents.py` imports the already explained function:

<Code language="python">{getFileExample('inspect_documents.py')}</Code>

```bash

```

```text
absent.json: missing file
invalid-utf8.bin: invalid UTF-8
malformed.json: invalid JSON at line 1, column 2
wrong-root.json: invalid data: root must be a list
wrong-types.json: invalid data: row 1 minutes must be a non-negative integer
```

Follow the boundaries:

1. Opening can fail before any contents are available.
2. Decoding bytes can fail before there is valid text.
3. Parsing text can raise `json.JSONDecodeError`; `.lineno` and `.colno` help locate the syntax error, not validate business meaning.
4. Validation happens after the reading with block, so the file is already closed. It can reject perfectly parseable values.

JSONDecodeError and UnicodeDecodeError are ValueError subclasses. Putting one broad ValueError handler first would erase these distinctions. Here the reading handlers are specific, and the validator's ValueError handler belongs to a separate call. PermissionError and unknown failures are not reinterpreted as missing data or successful zero totals.

The inspector reports a bad file and continues because inspecting a known batch is its explicit job. A task-saving program has a different responsibility: **after a damaged input, it must stop before overwriting that input**. Do not copy a recovery policy without its purpose.

### C. Independently build a small local task store

Create a genuinely empty directory **outside the download**, then build this layout yourself. The output directory should be created only when the program entry runs, not on import:

```text
my_tasks/
  check_import.py
  run_store.py
  task_store/
    __init__.py
    validation.py
    storage.py
    app.py
```

Use plain modules and functions from L06, not classes, a database or a framework.

**Data contract:** one JSON array. Every item is a dictionary with **exactly** `title`, `minutes` and `done`. Title must be str and not whitespace-only; preserve its original spelling rather than silently trimming it. Minutes must be an ordinary nonnegative int, rejecting bool, float, numeric text and None. Done must be bool, not 0, 1 or a string. Empty arrays and zero minutes are valid. Preserve item order; duplicate task titles are allowed because titles are not defined as IDs here.

**Responsibilities:**

- `validation.py`: `validate_tasks(value)` returns fresh task dictionaries in a fresh list, without mutating the source. Reject wrong root/items, missing/extra keys and invalid fields with ValueError messages identifying the row/field. This is validation of the agreed small format, not general schema tooling.
- `storage.py`: `load_tasks(path)` opens UTF-8 text with with, parses one document, closes it and validates the result. It must propagate FileNotFoundError; the library must not assume that every caller wants initialization.
- `save_tasks(path, value)` validates and serializes **before** opening w. Write readable UTF-8 JSON with two-space indentation, literal Unicode characters, no non-finite output and one final newline. The caller passes a Path and owns parent-directory creation. Invalid values must leave an existing destination unchanged and must not create a missing one.
- `app.py`: put directory creation, initialization, reading, mutation, saving and display inside guarded `main`. Use `_output/tasks.json` under the `my_tasks` directory, anchored independently of cwd. Only a missing file permits the two initial tasks below. Existing corrupt/invalid data must cause a visible failure before saving, not a silent reset.
- On every valid run, mark all tasks titled `Read` as done, save once, and sum the minutes of unfinished tasks. A valid empty array must stay empty rather than being mistaken for a missing file.
- `run_store.py`: an alternative file entry. Import `main` from `task_store.app` and call it under its own main guard. This wrapper lets a direct file command find the package through the wrapper's directory, using the L06 mechanism, without changing search paths.
- `check_import.py`: import app and storage and print only `Imported: task_store.app task_store.storage`. Import must not create `_output`, read data or start the business entry.

## 14. Exit gate, recovery after a pause and the next chapter

You can continue when you can independently:

- Distinguish Path, open stream, text, bytes and decoded business data.
- Predict cursor position, mode effects and the location used when cwd changes.
- Explain encoding versus JSON escaping, and serialization versus file saving.
- Track closing on success, return, exception and failed acquisition without promising rollback.
- Locate the failing layer and justify which caller can recover, instead of treating every error as empty data.
- Reconstruct the task store from an empty directory, run it in fresh processes and verify preservation on rejected input.

When stopping, record the **current directory, last command, which output files now exist, whether this was a first or repeated run, observed result, and the next unchecked variation**. A saved `_output/once.txt` or `_output/tasks.json` changes the next run's preconditions. Resume by inspecting that state and predicting one small experiment; do not erase it blindly or rebuild the entire environment.

## 15. Sources and deliberate limits

Technical sources checked on 2026-09-24 against the Python 3.13 baseline:

- [Reading and writing files](https://docs.python.org/3.13/tutorial/inputoutput.html#reading-and-writing-files): text/binary operations, cursors, iteration, closing and serialization.
- [pathlib](https://docs.python.org/3.13/library/pathlib.html): path construction, resolve, parent, open and explicit directory creation.
- [Built-in open](https://docs.python.org/3.13/library/functions.html#open) and [I/O](https://docs.python.org/3.13/library/io.html): modes, encoding, newline translation, buffered streams and closing.
- [Unicode HOWTO](https://docs.python.org/3.13/howto/unicode.html): code points, encoding and decoding.
- [with statement](https://docs.python.org/3.13/reference/compound_stmts.html#the-with-statement) and [built-in exceptions](https://docs.python.org/3.13/library/exceptions.html): acquisition/exit and failure categories.
- [Python JSON](https://docs.python.org/3.13/library/json.html), [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259) and [MDN JSON.stringify](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/JSON/stringify): conversion rules, one-document framing, non-finite numbers, repeated names and JavaScript differences.

Custom context-manager protocols, generators, async file APIs, atomic replacement, locking, backups, database transactions, arbitrary upload validation, CSV, regular expressions and data analysis are not mandatory in this chapter. They require their own motivation and full teaching, not a one-line API list attached to an already dense foundation.
