## 1. Passing an HTTP test does not establish a database guarantee

H06 used dependency replacements to test routing behavior, and D05 examined schema history. A dictionary fake does not execute foreign keys. SQLite is not PostgreSQL's type system, transaction implementation or query planner. Both can help test some application rules; neither can substitute for the PostgreSQL acceptance in this chapter.

Instead of pursuing a coverage percentage, design an experiment that could disprove each claim. Does the first row survive a second-write failure? Can a failed Session be used without recovery? Does fixture setup leave a connection when it fails before yield? Could a generated migration erase existing text? Does an index change the database work, rather than the query merely finishing quickly once?

| Chapter contract | Scope |
| --- | --- |
| Prerequisites | D05 migration history/recovery limits; H06 pytest fixtures, dependency replacement and assertions |
| New capability | Dedicated real databases, resource-safe fixtures, constraint/transaction/migration tests, query-plan evidence |
| Independent acceptance | Never target dev/prod; repeatable tests without ordering dependencies; failure cleanup/recovery; explain a real query improvement |
| Exclusions | SQLite as acceptance replacement, production capacity claims, fixed costs, complete performance engineering or backup rehearsal |

Download the [complete D06 lab](/learning-assets/js2py/d06-database-testing.zip) and work in d06-database-testing. It contains frozen D05 revisions and the final model, without sibling-directory imports. Webpage code and ZIP share the same explicit source allowlist.

Frontend tests often mock `fetch`; database testing inverts that habit. Mocking the SQL layer only proves the mock works — constraints, transaction semantics and planner behavior must be verified against real PostgreSQL. That is why this chapter rejects SQLite or in-memory doubles as acceptance evidence.

## 3. Isolation is more than “clear the tables before testing”

<Code language="python">{getDatabaseTestingExample('safety.py')}</Code>

The wrapper owns a mkdtemp cluster directory and a private 0700 Unix socket, with no TCP listener. It removes inherited PG settings and common database URLs, creates a non-superuser lab_owner, and passes a random LAB_DATABASE_URL plus marker only to its child. The guard verifies directory, token, driver, username, socket, port, database-name format and server marker. Renaming an arbitrary URL environment variable does not make it acceptable.

Local trust is appropriate only to this short-lived cluster controlled by the same OS user. The marker protects against mistakes, not malicious processes running as that user. CREATEDB exists here for fixtures, not as a recommended production API privilege.

Each test owns a UUID-named database. DROP receives only an internally generated identifier quoted with psycopg Identifier, not a request-controlled SQL fragment. Close every Session/Connection, dispose the pool, then drop the database. No FORCE clause terminates leaked connections merely to hide cleanup failure.

Acceptance also queries the server version, current_database, non-superuser role and NULL inet_server_addr for a Unix socket. SQLite, a shared developer database or a mock cannot satisfy this contract. The guard is a laboratory safety mechanism, not a general destructive administration tool for arbitrary URLs.

## 4. Fixture setup can fail before yield

<Code language="python">{getDatabaseTestingExample('testing.py')}</Code>

<Code language="python">{getDatabaseTestingExample('tests/conftest.py')}</Code>

A yield fixture resembles H05's request dependency: acquire first, release afterward. But a migration can fail after acquiring resources and before reaching yield. Cleanup written only after that point must not be assumed to run. migrated_engine wraps preparation itself in try/finally, installing a cleanup boundary before risky setup begins.

Ownership is nested: fresh_database owns the database, migrated_engine owns the Engine, and inner Session/Connection contexts own checkouts. Borrowers finish before the owner destroys their container. dispose closes idle pooled connections, not still-borrowed Sessions, so the fixture checks outstanding checkouts before dropping the database. A failed drop remains visible rather than expanding the cleanup target.

<Code language="python">{getDatabaseTestingExample('tests/test_resource_safety.py')}</Code>

One test creates a CHECK-constrained table and inserts -1 during preparation, ensuring yield is never reached. It still expects a physical connection close event and absence of that database from pg_database. Another raises inside the test body and checks the same cleanup order. These failures establish more than a happy-path finally block.

## 5. Why not wrap every test in a transaction that never commits?

An outer transaction with SAVEPOINTs can accelerate some tests. But if the application's commit only releases a savepoint, real COMMIT-time constraints, connection release and cross-connection visibility may not be exercised. The technique is not inherently wrong; it cannot replace this chapter's particular acceptance.

Separate databases let the system under test commit and roll back for real, then let new connections inspect the outcome. Creation and migration cost more, but transaction semantics are not rewritten by the test harness. No test relies on a previous test creating alice. The runner repeats suites serially; untested xdist execution or arbitrary random ordering is not claimed as verified.

## 7. Inspect state outside the original failed unit of work

The project/owner test injects an invalid role into the second flush. A new Session must find zero rows in both tables, and a subsequent transaction must succeed. A function failing to return or an empty Python list would not prove rollback.

<Code language="python">{getDatabaseTestingExample('commit_failure.py')}</Code>

```bash
uv run --locked python pg_sandbox.py -- python commit_failure.py
```

```text
two INSERT values accepted; deferred check awaits COMMIT
COMMIT failed
Session refuses reuse before rollback
rollback restored Session; next transaction committed one row
checked out: 0
```

A deferred UNIQUE constraint moves rejection to an actual COMMIT; this is not relabeling a flush error. Queries before rollback must fail. After recovery, a new transaction inserts 8, commits, and another connection sees only 8. A newly borrowed Connection may reuse the same pooled physical connection: the assertion concerns a new transaction outside the failed Session, not a requirement for a new socket. Cleanup, rollback and successful persistence are separate facts requiring separate observations. Network-induced unknown commit outcomes are not covered; these results do not justify blind retries after every error.

D06's ordinary engine fixture upgrades to head. Migration-history tests deliberately override it to obtain an empty database, then begin at 001 or 002 as required. Using final-model create_all everywhere would bypass the migration chain entirely.

<Code language="python">{getDatabaseTestingExample('tests/test_migration_history.py')}</Code>

Tests exercise data-preserving upgrades, compatible old writers, rollback of version/DDL/backfill after bad data, refusal of lossy downgrade, and real rename-candidate generation. Alembic check compares supported metadata features; it does not prove that historical text survived or that all CHECK expressions are equivalent.

## 9. Query correctness comes before query speed

First establish project scoping, status filtering, id ordering, pagination, empty results and the unfiltered case. A one-millisecond query leaking another project's tasks is still wrong. Stable ordering for a fixed dataset does not make offset pages immune to concurrent changes.

Then ask how PostgreSQL obtains the rows. WHERE does not mean only matching rows are physically visited. A primary-key index exists, but may not suit a project/status list query. Reading a plan requires the index name, conditions and filtering work, not merely spotting the words Index Scan.

## 10. Create meaningful data before inspecting the plan

<Code language="python">{getDatabaseTestingExample('query_plan.py')}</Code>

The experiment creates 200 projects and 60,000 tasks: 300 per project, 30 of them doing. Tasks are interleaved and include moderately sized descriptions. This avoids claiming an index is worthwhile from a three-row toy table. The query selects one project and status, orders by id and returns 20 rows. Actual returned project IDs are bound; identities need not start at one.

ANALYZE refreshes statistics. The script saves both results and a JSON plan before the composite index, creates `(project_id, status, id)`, analyzes again, and saves the second pair. It never sets enable_seqscan=off to force the desired result. Tests first compare exact result rows, then verify that the experimental index was selected.

The observed PostgreSQL 18.6 output was:

```text
plan before: [('Limit', None), ('Index Scan', 'tasks_pkey')]
plan after: [('Limit', None), ('Index Scan', 'ix_tasks_project_status_id')]
same result rows: 20
```

This is an observation, not an invariant plan tree across machines/releases. Both plans contain Index Scan, but the first scans primary-key order and filters unrelated projects/statuses. The composite index narrows the candidate set by project/status while supplying id order. Looking only at node type misses the change. The pre-index plan need not be a sequential scan.

## 11. Interpret EXPLAIN fields, not memorized cost numbers

EXPLAIN shows planner estimates. EXPLAIN ANALYZE actually executes the statement and adds measurements; using it on a write really writes. Do not casually apply it to destructive production SQL. Our statement is SELECT in a dedicated test database.

| Field | Interpretation and common mistake |
| --- | --- |
| Startup Cost / Total Cost | Relative planner units, not milliseconds or money; parent cost includes children, so do not sum every level |
| Plan Rows / Actual Rows | Estimates can differ from observations; repeated nodes also require Actual Loops context |
| Index Cond / Filter | Index conditions narrow candidates; filters reject remaining rows; Rows Removed by Filter reveals discarded work |
| shared hit/read Buffers | Cached/read block observations, not a direct physical-disk latency or user-response measure |
| Planning/Execution Time | One instrumented measurement affected by caching, workload and overhead; not a capacity guarantee |

No test asserts an exact cost or fixed time threshold. The evidence JSON retains both complete plans: estimates, index names, discarded rows and buffers can be examined. This host's original plan removed 38,180 rows by filtering before reaching its results. The composite index located candidates directly. That number describes this dataset/run, not a timeless constant.

Sequential scanning can be cheaper for a small table or low-selectivity query. Indexes consume storage and increase write maintenance. Leading-column order should reflect query conditions; indexing every column is not a strategy. If another environment chooses a different plan, inspect distribution, statistics, predicates, ordering and costs instead of disabling alternatives to manufacture success.

The experimental index exists only in its dedicated test database. It is not part of D05's migration head. A later service adopting it needs a reviewed index migration and lock/write-cost assessment; its existence in a test does not upgrade production schema.

## 14. Evidence, pause record and unverified boundaries

The complete live suite reports **26 passed**: parameterized constraint failures, duplicates, atomic rollback/recovery, commit-time recovery, query scoping/pagination, RESTRICT, migrations/candidate review, two fixture-failure paths, actual server/role checks, the index experiment and independent aggregation. Repeating it creates fresh databases rather than reusing the previous data.

Evidence records server_version_num=180006. Wrapper exit should report stopped=true, status_after_stop=3 and removed=true; stop failure retains its exact path and log. Finally cannot handle SIGKILL/power loss, so normal cleanup does not prove automatic disaster recovery. Stop only the owned directory, never unrelated PostgreSQL services.

When pausing, record test names/parameters, the last command, current revision, data volume/distribution, plan-file location, unresolved questions and the first next step. Write plan evidence outside the disposable cluster, as the commands do. Save reproducible seeds rather than real user data.

Not verified: Windows/other hardware, production workloads/capacity, network partitions and unknown commit outcomes, production restoration, authorization, zero-downtime migrations, or xdist parallelism. Stating those limits prevents a local green suite from being mistaken for permission to launch.
