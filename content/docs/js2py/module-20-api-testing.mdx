## 2. Distinguish three kinds of client

TestClient sends requests to the ASGI application within the same Python process. Real routing, dependencies, Pydantic validation, and response handling run without a Uvicorn listening socket. **It does not mock every route into a fixed JSON result.** Network connections, process startup, and browser security enforcement are nevertheless outside that path.

An HTTPX Client sends to a real address, crossing the local TCP port and Uvicorn; connection refusal becomes observable. A real browser adds Origin and CORS enforcement: actual preflight and response readability need a browser check. These layers complement one another. Fast tests do not imply end-to-end production readiness.

| Entry point | Evidence it provides here | What it cannot establish alone |
| --- | --- | --- |
| Ordinary store/config tests | Concrete Python behavior and configuration parsing | Routes, HTTP, listening |
| TestClient without business overrides | In-process API input-to-output behavior | Uvicorn import entry, ports, browser enforcement |
| TestClient with a dependency double | Consumer behavior under the replacement scenario | The original provider and its children working |
| Real HTTPX/urllib | Actual process, socket, HTTP contract | Browser CORS enforcement, production networking, TLS |
| Real browser fetch | Readable responses and preflight for this page origin | Identity, object permissions, every browser environment |

## 5. Fixtures organize preparation and cleanup; they are not automatic mocks

Repeating create_app/with TestClient everywhere invites forgotten closure or a shortcut to one global app. A pytest fixture is a named preparation function registered with `@pytest.fixture`. A test parameter called client asks pytest to find that fixture, run it, and pass its product into the test. Python does not guess this from an ordinary function argument or same-named global variable.

Fixtures may request other fixtures. Client's app parameter asks pytest to construct app first. The default scope is function, preparing each test case afresh. When client and overrides both need app in one test, they receive the same app for that test, not separate applications. Each parameterized row gets its own preparation too.

<Code language="python">{getApiTestingExample('tests/conftest.py')}</Code>

Pytest discovers conftest.py within its directory scope; ordinary tests do not import client manually. App returns its value because it has no additional exit action. Client yields, then exits with to close the client after the test, including an assertion failure. Section 9 explains the overrides fixture. **Pytest fixture yield and FastAPI dependency yield have different framework drivers**, even though both build on L14's pause/resume mechanism.

A fixture that fails before reaching yield does not magically execute every line after yield. Arrange with or try/finally around resources actually acquired. Simply containing yield is not a safety guarantee. Here with owns the client and finally owns override restoration.

<details>
<summary>Explanation answer: is session scope better because it might be faster?</summary>

Not necessarily. Sharing a MemoryStore throughout a test session allows later tests to see earlier records and sequence changes, creating order dependence. These objects are cheap, and function scope expresses the intended isolation. Expensive resources later need an explicit isolation strategy, not merely broader scope. A fixture is not inherently a mock or a guarantee of clean state; cleanliness comes from this factory and its lifecycle design.

</details>

## 7. Error tests must prove correct rejection without corrupted state

Distinguish three failures: malformed JSON returns json_invalid; valid JSON with minutes=true/"3"/3.0 violates the model and returns a 422 body-field error; a valid but absent ID returns 404 and the stable business detail. Treating all three as merely “an error” loses useful contract evidence.

Parameterization expands field/value combinations for strict input rules without copying entire test functions. Check detail.loc to locate the expected body/query/path field, but do not freeze every Pydantic human-readable message, documentation URL, or version-specific error key. Our own 404 detail is a controlled interface contract and can be asserted exactly.

After rejected creation, total must still be zero. After a mixed invalid PATCH, GET again and compare the record to the original. A 422 alone does not exclude an implementation that mutates some fields before rejecting another. The current candidate-validation/replacement order protects these sequential paths, not concurrent database transactions.

The three note cases express no change, new text, and explicit clearing. Null for other fields is rejected. `if payload.note` cannot express those states because empty text and None are both falsey. We instead merge explicitly supplied fields through exclude_unset. Tests should assert the behavior, not a memorized internal framework algorithm.

<details>
<summary>Guided answer: how do you catch a partially applied invalid PATCH?</summary>

Create title="Keep", minutes=5, note="keep" and save the complete response. PATCH a valid new title, invalid minutes=true, and note=null together. After asserting 422, GET again and compare the entire record with the original. Testing only one invalid field may miss premature changes to other fields. The independent task asks you to implement this evidence, not merely describe it.

</details>

## 8. Application exceptions and HTTP errors are observed differently

An unhandled RuntimeError is an application defect, not an intentional HTTPException. By default, TestClient reraises server exceptions into the test so the original traceback is visible. A test expecting a Response can therefore stop inside client.get before reaching a status assertion.

To inspect the external 500 response, locally create `TestClient(app, raise_server_exceptions=False)` and assert status and text. A default non-debug app responds with Internal Server Error, not JSON; unconditional response.json() is wrong. This does not mean ignoring the bug: one test observes exception propagation and another observes the external failure surface.

<Code language="python">{getApiTestingExample('tests/test_dependencies.py')}</Code>

Test_unhandled_errors_raise_by_default deliberately supplies a broken provider and observes both client modes. It proves that controlled failure path, not production incident handling. Capsys is pytest's built-in output-capture fixture. Test_real_trace_cached_and_closed reads stdout to check one acquisition, two uses, and one release. It does not replace trace, so the real temporary-file code runs.

Even reading a release line after the client call returns does not establish whether release preceded response send. H05's versioned lifecycle explanation and maintainer ASGI probe provide that finer evidence. This chapter does not smuggle in asynchronous-test prerequisites.

## 9. dependency_overrides: what is replaced, and which evidence disappears?

App.dependency_overrides is a dictionary whose key is the **original function object** used by the route declaration, and whose value is a replacement provider. `overrides[get_store] = replacement_store` is correct. The string "get_store", the result of calling get_store(), or another same-named function is not the same key. The framework consults this mapping during dependency resolution; it does not rewrite every Python function call in the module.

Test_override_store returns a separate MemoryStore with a known record. It also asserts that app.state.store remains empty, explicitly documenting the bypass. The original get_store has request_trace as a child dependency. Overriding get_store in this list test skips both that original function and its trace child. Its passing result therefore says nothing about real resource acquisition or cleanup.

Test_dependency_rejection makes a substitute raise 503, proving the consumer receives the intended status and body. It does not unplug a network, induce a disk failure, or verify recovery from either. A simple function supplies the stub; we do not need unittest.mock yet. If “mock” is used broadly, name the replaced boundary rather than treating any mocked test as complete integration evidence.

Overrides only affect dependency resolution. Real configuration has already been loaded during create_app. Later overriding get_settings cannot repair a factory that already failed. This is why tests using explicit Settings still need a separate real-process environment check.

## 10. Restore overrides even when a test fails

Do not write request, assertion, and clear as three ordinary statements: an assertion failure skips clear. Our fixture copies the previous mapping and uses try/yield/finally to clear current changes and restore that snapshot regardless of the test outcome. Restoring prior contents is safer than always assigning an empty dictionary, because a caller might already have controlled overrides.

Even though this suite creates a new app per test, keep the cleanup discipline. Diagnostics sharing an app, multiple phases within one test, or future scope changes can otherwise produce misleading leftovers. ## 13. Explain CORS participants before adding middleware

The page at http://127.0.0.1:5506 and API at http://127.0.0.1:8006 have different ports, so they are different origins. Origin consists of scheme, host, and port. Localhost and 127.0.0.1 also differ as origins. CORS governs whether a browser permits page JavaScript to read cross-origin responses; it is not login or server-side object authorization.

Before a cross-origin POST with Content-Type: application/json, the browser normally sends an OPTIONS preflight with Origin, Access-Control-Request-Method, and Access-Control-Request-Headers. CORSMiddleware handles that preflight outside the routes and adds allowed headers to eligible responses. You do not manually add OPTIONS to every endpoint. Middleware is an outer request/response processing layer; here we use this one concrete behavior, not a generic middleware architecture lesson.

<Code language="python">{getApiTestingExample('task_api/main.py')}</Code>

Only http://127.0.0.1:5506 is allowed, with the chapter's methods and Content-Type, and no credentials. There is no wildcard expansion, token, or cookie authentication. The ordinary create_app factory remains the composition entry point; asynchronous lifespan is unnecessary.

<Code language="python">{getApiTestingExample('tests/test_cors.py')}</Code>

Allowed preflight receives 200 and the exact allowed-origin header. Origin 5507 receives 400 without that header. The third test is essential: a direct GET with a disallowed Origin may still receive 200, just without permission for browser JavaScript to read it. A non-browser client without Origin can also access the API. **CORS is not authentication that keeps unauthorized callers out of the service.**

TestClient inspects emitted headers/statuses; it does not enforce a browser's response-reading restriction. Frontend integration is not complete yet.

## 15. Diagnose failures and record recoverable evidence

| Symptom | Distinguish the cause | Recover and recheck |
| --- | --- | --- |
| fixture 'client' not found | File is outside the relevant conftest scope | Put it in tests or declare a local fixture as the independent solution does |
| A test passes alone but the suite fails | Shared app, mutable inputs, or unrecovered overrides | Restore function scope/factories; run the case, full suite, and full suite again |
| client.get raises RuntimeError | Default server-exception propagation | Fix the implementation; locally disable propagation only when testing external 500 behavior |
| JSONDecodeError | Parsing a text 500 or empty 204 as JSON | Check status/Content-Type first; assert empty bytes for 204 |
| TestClient passes, HTTPX is refused | Service absent, factory failed, or mismatched port | Read service logs, start the correct entry point, replay |
| HTTPX passes, browser fetch fails | Origin/preflight or frontend request error | Inspect Network without weakening the boundary |
| A mock test passes without trace logs | Replacement skipped the real provider and children | Keep the substitute case and add non-overridden evidence |

When pausing, record the directory and lock versions, actual ordinary and independent counts, whether the cleanup experiment yielded 1 failed, 1 passed, which app was overridden and whether restored, real startup command/PID/port, both browser-origin results, task cleanup and stopped processes, unverified behavior, and the next action. Do not record only “everything passed.”

Acceptance means explaining each evidence layer, independently adding tests, detecting and recovering from a controlled defect, and completing real-browser integration. Download allowlists exclude environments, caches, .env, logs, and secrets. The 48+3 cases and real-process/browser exercises do not prove database behavior, authentication/authorization, production concurrency, deployment, TLS, performance, or all-browser compatibility. Later stages establish those separately.
