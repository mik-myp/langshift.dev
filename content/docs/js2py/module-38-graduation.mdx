## 1. An independent delivery, not a final implementation answer

Understanding a backend tutorial does not establish that you can make maintainable choices without its reference implementation. This chapter supplies no physical schema, route design, migration commands, transaction algorithm or complete backend. Extend your own collaborative task API and explain why you chose a design, how you discovered mistakes, and how you recover.

The prerequisite is **O06 capability and evidence**, not an accessible lesson page. Your existing project needs isolated restoration, access control and controlled-release foundations. If a preceding chapter lacks an environment, restoration or mainline acceptance, you may prepare G01 requirements, but G01 cannot mark that prerequisite verified. Mainline review controls chapter status.

Task comments are an equivalent controlled alternative to the capstone's label extension: you do not need both, and delivery gates are not relaxed. New complexity comes from distinct author/owner permissions, concurrent revisions, redaction and repeated requests, all of which must survive upgrade, release rollback and restoration. Adding another CRUD table is not sufficient.

Download the [G01 requirements and evidence package](/learning-assets/js2py/g01-graduation.zip) and enter `g01-graduation`. It contains a product contract, synthetic scenario data, evidence/reviewer templates, a rubric and a **material-format checker**, not a deployable reference backend. Every student scenario starts as `not_run`; no pilot data is fabricated.

## 3. The new requirement: task comments with immutable authorship

Logically a comment has identity, owning task/project, server-derived author, plain text, creation time, a revision after successful modification, and redaction state. Text contains 1–1000 Unicode code points, is not whitespace-only and cannot be NULL. Rich text, attachments, nested replies and real-time notifications are excluded. These are logical facts, not a prescribed physical table. Storage, interface representation and conflict responses are decisions you must defend.

Current active project members can read/list/create and edit or redact their own visible comments. A project owner can redact any comment in that project, but **cannot rewrite another author's text**. A removed member cannot read or operate on that project's comments, even with an unexpired old credential or historical authorship. Current members still see the historical author attribution. Anonymous and disabled users receive no access merely because a membership row remains.

Normal reads of a redacted comment expose tombstone metadata, not the original text. Lists, detail, history, exports and logs must not become bypasses. Editing after redaction fails; delayed requests cannot resurrect text. Choose and explain internal retention or deletion and its backup consequences. Do not claim retroactive erasure from every existing backup.

## 5. Concurrency, repeated requests and uncertain outcomes differ

Two edits based on the same old revision must not silently overwrite one another successfully. Declare conflict behavior and prove actual interleaving using independent requests. A committed redaction cannot be undone by a delayed edit. Requests beginning after membership removal commits must be denied; define and test a consistent policy for already in-flight work rather than selecting whichever run looks favorable afterward.

The repeated-create contract is a retention window of at least 24 hours: the same authenticated actor, task, request identity and content represent one logical comment and return the same identity. Different text with the same scoped request identity conflicts without changing the original. Different actors or tasks must not receive each other's cached result. Choose a bounded, documented, tested expiry policy rather than promising exactly-once behavior forever.

A replay must still satisfy current permission. Revocation cannot be bypassed by “this request previously succeeded.” A lost response also does not mean the database failed to commit. S16 specifically requires an accepted request whose response was not received to be retried without creating a duplicate. This is a product requirement, not an instruction to copy a particular idempotency middleware.

Failure evidence identifies the stage, what should remain, what must not exist, and how a subsequent valid operation recovers. “Caught an exception” does not describe the database afterward. Final row counts alone can miss a success promised externally without a corresponding record. External outcomes and persistent state must explain each other.

## 7. Upgrade, rollback and restoration must include existing data

Starting on an empty database does not prove upgrade safety. Existing users, projects, members and tasks retain their identities and permitted behavior; old tasks begin with zero comments, without invented default authors. A task with any comment, including a tombstone, cannot be physically deleted. Deletion of uncommented tasks retains its previous behavior. Project deletion must not bypass this rule; document and test a consistent project policy.

Rollback evidence must identify which application revision is compatible with which schema revision. If an old application cannot understand new state, a declared safe freeze or controlled rollback condition is acceptable, but blindly downgrading and losing accepted comments is not successful recovery. Test compatibility and preservation against meaningful data, not an empty demonstration database.

Restoration requires actually restoring a backup into a different, explicitly isolated target. Check relationships, revisions, redaction privacy and repeated-request behavior, and record recovery duration and acceptable/observed loss windows. Table counts can miss resurrected redacted text or missing replay state. An older backup can contain old content; explain retention and the restored data window rather than treating backups as merely a performance concern.

Without an approved target, account, budget and O06 evidence, pilot use remains blocked. Once those conditions are met, limit it to 2–5 invited testers with nonsensitive data and at least one traceable anonymized feedback item followed by a verified adjustment. Never invent participants or describe a localhost URL as public HTTPS.

Also defend a real problem you encountered: initial hypothesis, counterevidence, diagnostic material, repair result and remaining limits. Reciting someone else's conclusion is insufficient.

## 9. The format checker deliberately cannot graduate you

The package has no external Python dependencies and needs no pytest, database, Docker or frontend build. Its optional checker uses the standard library and was tested with Python **3.13.15**. Reading JSON/Markdown does not require installing Python at all. Execute these commands inside the package, first checking the active interpreter.

```bash
python3 --version
python3 check_evidence.py templates/evidence.json
python3 -m unittest discover -s tests -v

A unit test deliberately constructs an in-memory fictional report that passes format checks while backend_verified stays false. That limitation test is not fabricated deployment evidence.

## 10. Pause around evidence, without prescribing implementation order

You can pause at requirements understanding, design review, behavior observation, delivery/recovery evidence or independent defense. These are evidence-maturity states, not an instruction to create one table before a particular endpoint. Choose your development order, provided every commitment is eventually reviewable.

At each pause record code/schema revisions, the owned target, last actual command, last established fact, unresolved questions, next evidence to collect and stopped resources. On resumption, confirm that reality still matches the record. “It probably passed last time” is not a checkpoint. Missing environments remain blocked with an owner; unexecuted scenarios remain not_run rather than receiving expected success values.

Relative artifact paths and digests help reviewers locate evidence, but redact first. Do not share full environment dumps, tokens, connection passwords, real private comment text or private keys. Correlation IDs should help reconstruct incidents, not create another disclosure channel. The format checker is not a confidentiality audit; the submitter still reviews shared material manually.
