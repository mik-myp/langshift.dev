## 1. “測試通過”離發佈還差哪些證據？

H06 能檢查 API，D05/D06 能檢查遷移和真實數據庫，O01—O03 建立進程、容器、網絡入口的邊界。把這些命令放進一個 YAML 還不等於安全發佈：測試可能連錯庫，多個 worker 可能同時改表，舊程序可能讀不了新結構，回退代碼也不會自動撤銷新版本寫入的數據。

本章用一個小而真實的發佈序列把責任分開：檢查候選代碼 → 在獨佔測試庫驗證遷移和接口 → 審查兼容矩陣 → 單獨執行遷移 → 啟動候選版本並做就緒驗收 → 才允許切換流量。任何一步失敗，後面的動作都不應假裝繼續成功。

## 2. 保留 D/S 契約，但不偽裝整套產品

## 3. 環境分離先落實到連接與所有權

“測試數據庫”不只是把名字改成 test。測試必須擁有創建和清理權限，不能接受一個誤指生產的默認 DATABASE_URL。本實驗不讀取環境裡的業務 DSN，只允許自建 `/tmp/ls-ops-*` 目錄下的私有 Unix socket，數據庫名字也採用固定 allowlist。

mkdtemp 給每次運行獨佔目錄；0700 限制目錄訪問，標記記錄 UID 和隨機所有權值；停止前重新核對路徑、所有者、模式與標記，不允許 symlink 把清理指向別處。PG 不監聽 TCP，API 只監聽 127.0.0.1 臨時端口。private socket 下的 trust 是本機短命教學政策，**不是生產認證配置**；同一操作系統賬戶仍是信任邊界。

開發、自動測試、預發佈、生產應使用不同數據庫、賬戶和秘密，部署賬戶與應用賬戶也分開。這裡真實驗證的是隔離測試環境，不把它叫成已經部署好的預發佈環境。若工具版本不符或路徑檢查失敗，就停下來定位，不能改腳本去連接已有用戶庫“先跑通”。

傳入私有 socket 的 host 還不夠：libpq 仍可能從 `PGHOSTADDR`、`PGSERVICE`、`PGSERVICEFILE` 等環境變量取得另一個連接默認值。`reject_connection_environment` 在創建臨時目錄之前，以及每次直接連接、遷移和服務啟動之前，拒絕繼承的全部 `PG*` 變量，唯一例外是隻定位可執行文件的 `PG_BIN`。錯誤只列變量名，不打印值，也不修改調用者環境。Python 連接、SQLAlchemy 的連接創建器和 PG 子命令都使用自有目錄內的空白 0600 `empty.pgpass`，不讀取用戶的默認密碼文件。直接運行 `demo.py` 或 `ci.py` 也執行這些防護，不依賴倉庫總 runner 先替它清理。

啟動 API 不再先探測空閒端口、關閉探測 socket，再要求另一個進程搶佔同一號碼。Uvicorn 自己用 `--port 0` 完成綁定；控制器從**該子進程自己的私有啟動日誌**讀取實際端口，再請求 readiness。`--no-access-log` 不關閉 info 級啟動 banner；控制器固定無顏色日誌和單 worker。兩個同版本服務也使用不同日誌文件。測試實際同時啟動兩個服務，核對兩個不同端口、各自 banner、真實請求和退出清理。這消除了選端口後釋放再綁定的窗口，不是對任意併發故障的保證；未來 Uvicorn 改變 banner 格式時會超時拒絕，不猜測端口。

## 6. 用矩陣描述兼容，不靠“應該沒問題”

| 應用 / 數據結構 | 006，無 description | 007，description 可空 |
| --- | --- | --- |
| v1，按 id/name 讀寫 | 可用 | 可用，新列省略為 null |
| v2，需要 description | 拒絕啟動 | 可用 |

向前兼容在本次回退語境裡，是舊應用能繼續面對已經擴展的新結構。新增可空列只解決這個例子，並不意味著所有 ADD COLUMN 都安全：新約束、默認值、枚舉、新請求格式或數據含義都可能讓舊程序失敗。

切換 v2 後如果客戶端已強制依賴 description，退回 v1 的響應就可能不滿足客戶端。因此回退計劃還需要前後端兼容窗口、功能開關或協調停止新功能寫入；不能只驗證數據庫列存在。本實驗明確由控制客戶端分別使用對應版本的契約，不冒稱真實用戶切換零影響。

## 8. 失敗不是重建數據庫的理由

NOT NULL 失敗的根因是歷史記錄沒有值，不是 Alembic “壞了”。修復順序是審查需求：先增加可空列；部署兼容代碼；按業務規則回填；驗證無空值；另一個受控版本才加約束。不能把用戶數據刪除重建來讓 migration 變綠。

其他故障要分階段定位：版本不符在環境門禁失敗；錯誤 revision 在遷移/兼容檢查失敗；角色不足在數據庫授權失敗；就緒超時在應用啟動或 DB 路徑失敗；公網連不通則屬於當前實驗沒有覆蓋的入口層。打印整個環境、SQL 參數或 Bearer token 都不是合理診斷手段。

<details>
<summary>帶提示修復答案：如何證明失敗沒有留下半遷移？</summary>

不要只檢查異常類型。重新連接，確認項目仍為原來的三條、alembic_version 仍為 006，再執行經過審查的 007。事務內的失敗 DDL 會回滾，但不能由此推斷所有外部副作用或所有遷移操作都可回滾。需要逐變更確認；例如併發索引創建、外部調用和長時回填有另外的約束。

</details>

## 10. 發佈記錄與暫停恢復

記錄候選代碼標識、鎖文件哈希、應用版本、目標環境身份、遷移前後 revision、檢查命令及結果、誰批准遷移、就緒結果、回退版本與兼容條件。實驗沒有執行 Git 提交、推送或正式製品發佈，不能編造提交 SHA 或發佈地址。

暫停記錄最後成功階段、是否仍有自己的進程、數據庫是否已清理、故障是否刻意、下次從哪個乾淨狀態重放。這裡 demo/ci 退出會停止自己的 API/PG 並刪除臨時目錄，因此恢復時重新運行，不去找一個已經刪除的 socket。下載清單隻包含源碼/SQL/鎖/文檔；環境、日誌、數據庫目錄、備份和秘密全排除。

真實發布仍需 O03 的受控 HTTPS 入口、生產秘密與權限、已運行的 CI、監控、備份恢復演練和回退演習。當前完成的是本地可重複的數據庫與應用交付機制，不是 V4 已向用戶上線。
