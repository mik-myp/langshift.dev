## 1. 想復用一個函數，不想順便運行整個程序

L05 把解析、報告和演示數據放在一個文件里。現在另一個程序只想復用解析函數：複製代碼會產生兩份需要同步維護的實現；直接導入整個文件，又可能連演示一起執行。下一步不是規劃龐大的後端目錄，而是理解：**一個文件怎樣取得另一個文件的能力，這個過程中究竟會執行哪些代碼。**

Python 模塊是一個擁有自己命名空間的對象：名稱在這個空間中指向對象。最初的例子由一個 `.py` 文件提供模塊代碼。模塊可以包含函數定義、常量，也可以包含立即執行的語句。因此，導入不只是把聲明粘貼過來，更不是安裝依賴。

## 2. 內置能力、標準庫、本地模塊和第三方包不是一回事

你已經直接使用過 `print`、`len`、`int` 和 `sum`：它們是內置能力，不需要先導入。Python 還自帶標準庫，其中很多能力放在模塊里，必須先導入，相關名稱才在當前代碼中可用。自己寫的本地文件也可以是模塊；第三方發行包則必須先存在於所選環境中。**`import` 負責尋找和加載，不負責聯網下載與安裝。** 安裝和隔離放在 L08。

`report.py`：

<Code language="python">{getModuleExample('first_import/report.py')}</Code>

從實驗根目錄運行：

```bash
uv run --no-project --python 3.13 python first_import/report.py
```

```text
task_rules initialized
Default: 20
Buffered: 25
```

按順序追蹤，而不是只記住兩種語法：

1. Python 開始執行 `report.py`，遇到 `import task_rules`。
2. 在這個新進程里，它找到相鄰的 `task_rules.py`，創建模塊對象並執行頂層代碼：先打印標記，再綁定常量，再由 `def` 創建函數。此時沒有調用函數體。
3. 導入語句在調用方綁定名稱 `task_rules`，讓它指向那個模塊對象。
4. `task_rules.DEFAULT_MINUTES` 在模塊的命名空間中查找屬性；`task_rules.add_buffer(20)` 先取得函數，再調用它。

兩個模塊不會把全局名稱合併在一起。`task_rules.py` 的全局名稱屬於這個模塊，不屬於進程中的所有文件。這裡的“獨立”指組織方式，不是保密機制：調用方仍然能通過模塊對象訪問公開屬性。命名空間不是權限控制邊界。

`task_rules.py` 對應的導入名稱是 `task_rules`，不帶 `.py`。採用清晰、符合標識符習慣的文件名，不要寫成 `task-rules.py`，也不要與打算使用的模塊重名。第 10 節會實際定位一次重名問題。

## 4. 幾種導入形式：到底在當前文件中建立了哪個名稱？

文件：`first_import/import_styles.py`。

<Code language="python">{getModuleExample('first_import/import_styles.py')}</Code>

```bash
uv run --no-project --python 3.13 python first_import/import_styles.py
```

```text
task_rules initialized
Alias: 20
Direct names: 20 25
```

| 語句 | 調用方得到的名稱 | 使用方式 |
| --- | --- | --- |
| `import task_rules` | `task_rules`，指向模塊 | `task_rules.add_buffer(20)` |
| `import task_rules as rules` | `rules`，同樣指向模塊 | `rules.add_buffer(20)` |
| `from task_rules import DEFAULT_MINUTES` | `DEFAULT_MINUTES`，指向取出的對象 | `DEFAULT_MINUTES` |
| `from task_rules import add_buffer as buffered` | `buffered`，指向取出的函數 | `buffered(20)` |

`from` 不會跳過模塊加載，也不是挑選幾行源碼執行。它改變的是最後建立的名稱綁定。別名改變調用方的叫法，不會重命名源文件或改寫原函數。多個模塊都有類似名稱時，保留來源通常更容易閱讀；不要用通配符導入把名稱來源隱藏起來。

現在故意運行 `first_import/missing_name.py`：

<Code language="python">{getModuleExample('first_import/missing_name.py')}</Code>

```bash
uv run --no-project --python 3.13 python first_import/missing_name.py
```

程序先打印初始化標記和 25，再在 `task_rules.DEFAULT_MINUTES` 處拋出 `NameError`。模塊已經加載，但**調用方只綁定了 `add_buffer`，沒有綁定名稱 `task_rules`**。修復實際需要的綁定：用 `import task_rules` 配合限定訪問，或者明確導入那個常量。安裝任何依賴都不能修復這個名稱錯誤。

## 5. 同進程內復用，以及為什麼 from 不是 ESM 的實時綁定

文件：`first_import/import_twice.py`。

<Code language="python">{getModuleExample('first_import/import_twice.py')}</Code>

```bash
uv run --no-project --python 3.13 python first_import/import_twice.py
```

```text
task_rules initialized
Same module: True
Buffered: 25
```

在這個解釋器里按普通方式導入同一個模塊名稱，會復用內存中的緩存（`sys.modules`）。兩個別名指向同一個模塊對象，初始化標記只出現一次。再次運行終端命令會啓動新進程，標記也會重新出現。修改源碼不會讓已運行進程中的模塊自動重新執行；本章的處理方式是結束舊進程，再重新啓動。

這**不是**“一個物理文件永遠只會執行一次”的保證。作為 `__main__` 執行，和之後換一個導入名稱加載，是不同身份；重新加載與手動操作緩存也是另一些情況，本章暫不展開。不要把“導入永遠只發生一次”當成業務可靠性的依據。

### 重綁定與修改仍然遵循 L01、L02

`bindings/settings.py`：

<Code language="python">{getModuleExample('bindings/settings.py')}</Code>

`bindings/observe.py`：

<Code language="python">{getModuleExample('bindings/observe.py')}</Code>

```bash
uv run --no-project --python 3.13 python bindings/observe.py
```

```text
Initial: 20 20
Rebound: 20 40 40
Shared: ['python', 'modules'] ['python', 'modules']
Local tags: ['local'] ['python', 'modules']
```

畫出兩個命名空間：最初調用方的 `BUDGET` 與 `settings.BUDGET` 都指向 20。`settings.BUDGET = 40` 改變模塊內部的綁定，不會把調用方的獨立名稱也改為 40。`current_budget()` 讀取的是函數**定義所在模塊**的全局名稱，所以即使這個函數被直接導入，調用結果仍然是 40。

大寫 `BUDGET` 是命名約定，不會強制對象或名稱不可修改。

兩個 `tags` 最初指向同一個列表。通過其中一個引用追加內容，會修改那個列表，所以另一方也看得到；把調用方的 `tags` 重新綁定到新列表，則把兩個綁定分開了。**`from` 既不是深複製，也不是對未來重綁定的實時連接。**

JavaScript 的 **ES 模塊**使用實時導入綁定：導出方改變綁定，導入方可以觀察到；導入方不能直接對那個導入綁定重新賦值。Python 的直接導入名稱可以在本地重新綁定。這個對照只討論 ESM，不把所有 CommonJS 或打包器轉換都一概而論。應遷移你對引用的理解，而不是假設同樣叫 `import` 就一定有同樣語義。

### 兩種緩存，解決兩個不同問題

此時目錄里可能出現 `__pycache__/` 和 `.pyc` 文件。CPython 可以把編譯後的代碼緩存到磁盤，減少重復編譯；它們不是你維護的源碼，不需要複製進作業或下載包。它們不會保存上一個進程的變量，也不會讓新進程跳過模塊初始化。內存中的模塊復用與磁盤字節碼緩存解釋的是不同現象。

**暫停點 A：** 關掉終端，再預測初始化標記和綁定結果，最後運行驗證。如果你還把“共享同一個模塊對象”理解成“所有文件共用一個全局命名空間”，先重復這些實驗，不急著進入包。

## 7. 三個經常被混淆的位置

學習包之前，先讓運行上下文可見。文件：`locations/show_context.py`。

<Code language="python">{getModuleExample('locations/show_context.py')}</Code>

- `os.getcwd()` 返回進程的**當前工作目錄**；本實驗從啓動它的終端繼承這個目錄。
- `__file__` 在這些普通文件示例里標識當前源碼文件。
- `sys.path` 是 Python 搜索模塊的目錄列表；`[0]` 取下面普通命令中的第一項。它不是 Shell 的 `PATH`，後者用來尋找可執行命令。
- `__name__` 標識當前執行的模塊，不是目錄。

在沒有隔離/安全路徑選項或自定義路徑配置時，直接運行文件會把腳本所在目錄放到搜索路徑開頭；`-m` 從當前目錄開始尋找指定模塊。其他搜索位置還包括 Python 的庫目錄；內置模塊也有自己的導入處理。因此，不要把所有導入規則簡化成“永遠在寫 import 的那個文件旁邊找”。

從實驗根目錄執行：

```bash
uv run --no-project --python 3.13 python locations/show_context.py
```

這裡的路徑輸出用 `<LAB>` 代表你實際解壓目錄的絕對路徑；它**不是要輸入的文本**：

```text
Name: __main__
Cwd: <LAB>
File: <LAB>/locations/show_context.py
First search: <LAB>/locations
```

現在明確改變終端目錄：

```bash
cd locations
uv run --no-project --python 3.13 python show_context.py
uv run --no-project --python 3.13 python -m show_context
cd ..
```

兩條 Python 命令都輸出：

```text
Name: __main__
Cwd: <LAB>/locations
File: <LAB>/locations/show_context.py
First search: <LAB>/locations
```

`-m` 的意思是“按名稱找到模塊，再把它作為入口運行”。參數是 `show_context`，**不是** `show_context.py` 或文件系統路徑。上方用 `/` 展示路徑，不同操作系統的格式可能不同。運行腳本本身不會自動把當前目錄切換到腳本所在目錄；L07 讀取相對文件路徑時，這個區別還會再次出現。

不要用向 `sys.path` 追加路徑或設置 `PYTHONPATH` 來掩蓋當前的混淆。先記錄實際目錄與完整命令。這些實驗刻意使用正常的本地導入行為；隔離運行的 `python -I` 會去掉本地搜索位置，不能隨意替換進去。

沒有出現 `Package total: 65`。`import task_tools.app` 在調用方綁定 `task_tools`，可以通過它訪問子模塊，並不會綁定一個單獨的 `app` 名稱。探針隨後明確地使用自己的輸入調用可復用函數。包可以提供能力，而不強迫導入者運行它的演示。

**暫停點 B：** 重跑這兩個命令，畫出 `buffered_total` 與 `main` 分別屬於哪個命名空間。不要為了讓它運行就引入安裝文件或依賴管理器：它能被找到，是因為包含包的目錄位於搜索位置中。

## 9. 故意選錯一次入口命令

仍在 `package_demo` 中，執行下面這個**預期失敗**：

```bash
uv run --no-project --python 3.13 python task_tools/app.py
```

最後的錯誤指出 `ImportError: attempted relative import with no known parent package`。直接執行磁盤文件路徑，並不會建立 `.report` 所需的 `task_tools` 包上下文。入口保護條件也救不了它：導入在到達條件之前就失敗了。僅僅增加 `__init__.py` 不能改變一個文件被直接啓動的方式。

應在包外層目錄使用支持的 `python -m task_tools.app`，而不是刪除點號或者修補 `sys.path`。再回到實驗根目錄，觀察另一個**預期失敗**：

```bash
cd ..
uv run --no-project --python 3.13 python -m task_tools.app
```

在實驗的正常環境中，Python 從這裡找不到 `task_tools`，因為它放在 `package_demo` 內部；錯誤包含 `ModuleNotFoundError`。修復的是命令要求的工作目錄，不是安裝一個恰好同名的其他包。一條可復現說明必須包含**文件佈局 + 工作目錄 + 解釋器 + 命令**，不能只留最後一個文件名。

### 本地文件可能把你真正想要的模塊遮住

<Code language="python">{getModuleExample('shadowing/statistics.py')}</Code>

<Code language="python">{getModuleExample('shadowing/show_source.py')}</Code>

| 現象 | 首先檢查什麼 |
| --- | --- |
| ModuleNotFoundError | 到底缺少哪個模塊？從哪個運行上下文尋找？ |
| 具名導入的 ImportError | 模塊是否已經建立那個名稱？是否與初始化順序有關？ |
| 調用方的 NameError | 這種導入形式是否綁定了正在使用的名稱？ |
| 模塊屬性的 AttributeError | 實際加載的是哪個模塊對象？它是否有該屬性？ |
| 導入時意外出現業務輸出 | 哪個頂層業務調用被執行了？ |

### C. 獨立完成多文件任務計劃器

在**下載實驗之外**新建一個真正的空目錄，然後自己建立下面的佈局。不要先複製參考包；不需要項目元數據或第三方依賴。

```text

  check_import.py
  study_plan/
    __init__.py
    rules.py
    summary.py
    app.py
```

先確定責任，再寫 import：

- `rules.py`：實現 `parse_minutes(raw)`，沿用 L05 的嚴格文本契約。非字符串拋出 TypeError；無法轉換的整數文本拋出 ValueError，並保留原轉換異常為原因；負整數拋出 ValueError；兩側空白和零有效。錯誤消息與下面的預期輸出一致。
- `summary.py`：實現 `build_plan(rows, budget=20)`。budget 必須是普通的非負整數：bool 與非整數拋出 TypeError，負整數拋出 ValueError。即使 rows 為空也要校驗。
- 合法任務的分鐘數不超過 budget 時，**逐項獨立**選入。這是每個任務的閾值，不是會被消耗的總預算。合法但超出閾值的任務只是被過濾，不記為壞輸入。
- 在可恢復的轉換處理之外讀取必需的 `title`、`minutes`。把已知壞文本與負分鐘數記錄為拒絕項，保留原輸入的一基行號；缺字段、minutes 類型錯誤和未知故障必須繼續暴露。本練習假設 title 為字符串，不在這裡引入通用 schema 校驗器。恢復策略識別約定解析邊界產生的 ValueError，不能自動判明所有同類異常的來源；替換解析器內部的缺陷也可能破壞這個約定。
- 返回 `accepted`、`rejected`、`total_minutes`；不修改源行，不在模塊全局持續累加。每次調用創建自己的結果列表和條目字典，保持來源順序。
- `app.py`：演示數據、調用、展示都放在 `main` 內，並有明確保護條件。`__init__.py` 不運行演示。依賴方向從 app 到 summary 再到 rules，不反向依賴。
- `check_import.py`：導入 app 與 summary，然後只打印 `Imported: study_plan.app study_plan.summary`；前面不能夾帶演示輸出。

採用 L05 的五行輸入：Read / `" 20 "`、Typo / `"twenty"`、Zero / `"0"`、Negative / `"-5"`、Practice / `"35"`。在**你自己的 `my_plan` 目錄中**執行：

```bash
uv run --no-project --python 3.13 python check_import.py
uv run --no-project --python 3.13 python -m study_plan.app
```

探針輸出：

```text
Imported: study_plan.app study_plan.summary
```

默認入口輸出：

```text
Accepted: [{'title': 'Read', 'minutes': 20}, {'title': 'Zero', 'minutes': 0}]
Rejected: [{'row': 2, 'title': 'Typo', 'reason': 'minutes must be an integer'}, {'row': 4, 'title': 'Negative', 'reason': 'minutes must be non-negative'}]
Total: 20
Source first: {'title': 'Read', 'minutes': ' 20 '}
```

不要只核對默認運行。在自己的探針中用 `from study_plan.summary import build_plan` 添加臨時調用，打印並比較結果；需要的循環、調用和異常處理你都已經學過。自動化測試是後面的章節，不是這裡突然出現的前置要求。

| 變式 | 驗收要求 |
| --- | --- |
| budget 為 40 | 選入 Read、Zero、Practice，總計 55，不是 20 或 40；仍有兩行壞輸入被拒絕 |
| budget 為 0 | 只選 Zero，總計零；合法正數任務不變成拒絕項 |
| budget 為 20，Read 改為 `"21"` | 只選 Zero，總計零，不增加壞輸入拒絕項 |
| 空輸入 / 全部壞輸入 | 保留完整返回結構，總計零，不偽造有效任務 |

| 缺 title/minutes；minutes 為 None 或整數 | 傳播 KeyError/TypeError，不返回偽成功計劃 |
| budget 為 True、`20.0`、`"20"`、None / -1 | TypeError / ValueError，即使 rows 為空也一樣 |
