## 1. From two records to data whose size can change

L02 used two study plans, so accessing `plans[0]` and `plans[1]` directly was manageable. Now imagine three changes: there are no plans today, five tomorrow, and some are finished while others have no time estimate. Hard-coded indexes do more than repeat work: a change in data size can become a program failure.

This chapter answers two questions: **which statements should run, and for which data should the same operations repeat?** This is control flow. Your JavaScript experience helps, but Python has its own rules for indentation, container truth values, traversal, and name binding. Replacing braces with colons is not enough.

## 2. Branches: colons and indentation determine which statements belong together

### 2.1 Read the execution path before memorizing syntax

Start by classifying one task by estimated minutes. The input here is an integer; arbitrary external text is outside this section's contract.

File: `branches.py`.

<Code language="python">{getControlFlowExample('branches.py')}</Code>

Expected:

```text
Short session
Checked
```

Read it in execution order:

1. Bind 25 to `minutes`.
2. `if` checks the first condition. If it is False, move to `elif`, meaning “otherwise, if.”
3. At the first true condition, execute that indented block only. Later conditions in the same chain are not checked.
4. Enter `else` only if no earlier condition matched. There is no condition after else.
5. `print("Checked")` returns to the outer indentation level, so normal execution reaches it regardless of the selected branch.

The `if`, `elif`, and `else` headers end with a colon. Unlike JavaScript, conditions do not require surrounding parentheses, though parentheses remain useful for grouping. Use four spaces per indentation level. Four spaces are a convention; **consistent indentation within a block** is a syntax requirement. Do not mix tabs and spaces.

This is not merely visual layout. Indenting the last line inside else changes its meaning to “print Checked only for a long task.” The program may still run, but its behavior has changed.

Predict first, then change only the initial input:

| minutes | Classification output | Reason |
| --- | --- | --- |
| -1 | Invalid estimate | Reject a negative value before considering later branches |
| 0 | No time required | Handle zero separately rather than absorbing it into the short category |
| 1, 25 | Short session | The upper boundary includes 25 |
| 26 | Long session | None of the first three conditions matched |

Every case should also print `Checked`. If `minutes <= 25` appeared before the negative and zero checks, those values would match it first. Branch order expresses business priority, not an arbitrary arrangement of labels.

### 2.2 Separate if statements are not an if/elif chain

This is a complete, independent comparison:

```python case=separate_if
minutes = 0
if minutes == 0:
    print("Zero")
if minutes <= 25:
    print("Short")
else:
    print("Long")
```

Expected:

```text
Zero
Short
```

Both if statements perform their own checks. The else belongs to the immediately preceding second if at the same indentation level, not the first. Use one chain for mutually exclusive categories. Separate if statements may be exactly right when multiple conditions can apply. Do not delete a branch mechanically just because you see an extra line of output.

### 2.3 First failure: missing indentation does not print a partial result

This is an **expected syntax failure**, not a finished script. Save it separately as `missing_indent.py` if you want to reproduce it:

```python expected-error=SyntaxError case=missing_indent
if True:
print("Inside")
print("After")
```

Before executing any statement, Python reports `IndentationError`, a kind of syntax error. It points to the second line that needs indentation; there is no standard output. Add four spaces to the second line and leave the third at the outer level: execution then prints `Inside` followed by `After`.

A missing colon typically produces SyntaxError; inconsistent tabs and spaces can produce TabError. Check the colon, the block's start, and where indentation returns before debugging the business condition. **Successful parsing does not prove correct logic.** Input variations remain necessary.

## 3. Truth values and logical operations: an empty container is not a JS empty object

### 3.1 A condition does not have to contain a bool value

Python tests the truth value of an object in a condition. `bool(value)` displays that result explicitly as True or False. It is a conversion, not a parser for English words stored in strings.

The false values relevant here include `None`, `False`, numeric zero, empty strings, and empty lists, tuples, dictionaries and sets. A nonempty container is true even if its only entry is False. The nonempty strings `"False"` and `"0"` are also true.

File: `truthiness.py`.

<Code language="python">{getControlFlowExample('truthiness.py')}</Code>

Expected:

```text

False
False
False
False
False
True
True
No tasks
```

Here, `if tasks` means “does this list contain any entries?”, not “is every task valid?” The true value of `bool([False])` makes the distinction visible: container nonemptiness and the truth of its entries are different questions.

This is a static syntax comparison. Acceptance uses local scripts rather than the browser runner:

Do not transfer the meaning of frontend `if (items)` unchanged. With a JS array you would usually need to check `.length`; a Python empty list itself is false. See [Python truth value testing](https://docs.python.org/3.13/library/stdtypes.html#truth-value-testing) and [MDN Truthy](https://developer.mozilla.org/en-US/docs/Glossary/Truthy).

### 3.2 and/or short-circuit and may return non-bool values

| Operation | Evaluation | Result |
| --- | --- | --- |
| `x and y` | Test x first; if x is false, do not evaluate y | The false x, or the evaluated y |
| `x or y` | Test x first; if x is true, do not evaluate y | The true x, or the evaluated y |
| `not x` | Test x and negate its truth value | Always a bool |

These resemble JavaScript's `&&`, `||`, and `!`, but use Python's truth rules. Short-circuiting means the right side **might never execute**, not merely that the final result is unchanged.

File: `logical.py`.

<Code language="python">{getControlFlowExample('logical.py')}</Code>

Expected:

```text
False
Untitled
Ready
True
25
0
```

- An empty list stops `titles and ...` on the left, so `titles[0]` is never evaluated and no IndexError occurs. The outer bool converts the returned empty list to False. Reversing the operands removes that protection.
- `"" or "Untitled"` returns a string, not True; `"Read" and "Ready"` also returns an operand.
- `minutes or 25` replaces a valid zero with 25. If the policy is “default only for None,” write `if minutes is None` explicitly. This is not another spelling of JS `??`.
- A missing field and an existing None still differ. Use L02's key membership check when that difference matters, rather than guessing from truthiness.

`not` binds more tightly than `and`, which binds more tightly than `or`; comparisons normally bind before all three. Make your intention explicit while learning, for example `(minutes >= 0) and (minutes <= 25)`. This chapter does not use dense operator combinations as a memory test.

## 4. Ordinary for: bind one entry, then execute the same block

### 4.1 A loop does not first copy all its statements many times

For a variable number of tasks, prepare accumulators before processing, handle one entry per round, and print the combined result afterward.

File: `for_tasks.py`.

<Code language="python">{getControlFlowExample('for_tasks.py')}</Code>

Expected:

```text
Tasks: 3; total: 55 minutes
Pending: 2
```

`for task in tasks:` obtains entries from the list in order. Each time, it binds `task` to the current dictionary and executes the entire indented block. The nested if adds one indentation level. Both final print calls return to the outer level and execute only once.

`total = total + task["minutes"]` calculates a value using the old total, then rebinds the name. It is not a mathematical equation. We use full assignment here to keep the state change visible instead of introducing shorthand.

| Point | Current minutes / done | total | pending |
| --- | --- | --- | --- |
| Before the loop | No current entry yet | 0 | 0 |
| After round one | 20 / True | 20 | 0 |
| After round two | 35 / False | 55 | 1 |
| After round three | 0 / False | 55 | 2 |

Replace tasks with an empty list. The loop body executes zero times; total minutes and the pending count both remain zero. Initialization happened before the loop, so a valid result still exists. Move total's initialization inside the loop and it resets every round; with empty input the assignment never executes at all.

For now, every record must contain these three fields, minutes must be a nonnegative integer, and done must be a bool. A for loop does not validate record structure automatically. Missing keys can still cause KeyError. This is not an arbitrary external-input validator.

### 4.2 The current entry is a binding, not an automatic copy

File: `loop_binding.py`.

<Code language="python">{getControlFlowExample('loop_binding.py')}</Code>

Expected:

```text
Read
Practice
Practice
['Read', 'Practice']
True
```

Three details are easy to misread through JavaScript habits:

1. Ordinary for and if statements do not create a JS `let`-style block scope. This loop runs at least once, so title remains bound to the last string afterward.
2. `title = "Changed"` only rebinds a name; it does not replace slots in titles, so the original list is unchanged.
3. `task["done"] = True` mutates the shared dictionary obtained by the loop, so the task in the list changes too. This follows L02's reference relationships; for does not add a copying mechanism.

The first point does not mean “a loop variable always exists afterward.” File: `errors/empty_loop.py`.

Initialize meaningful accumulators in advance, and do not confuse “the last entry” with “the processing result.”

## 5. range: make the start, stop and step explicit

Use range when you need a certain number of repetitions or a sequence of integer positions. There is no need to turn every list traversal into index manipulation. The simplest `range(stop)` starts at zero with a step of one and **excludes stop**.

The three-argument form is `range(start, stop, step)`. A negative step moves downward; a zero step is invalid. The `list(...)` call introduced here collects successive items into a list for inspection. You do not have to perform this conversion before every loop.

File: `ranges.py`.

<Code language="python">{getControlFlowExample('ranges.py')}</Code>

Expected:

```text
range(0, 3)
[0, 1, 2]
[1, 3, 5]
[3, 2, 1]
[]
[]
1
2
3
```

The final `range(1, 4)` produces 1, 2 and 3. `range(3, 0)` uses the default positive step, but its start is already past its stop, so it is empty. Counting downward requires an explicit negative step.

A range is a repeatably iterable integer sequence object, not an expanded list and not a generator. For now, “iterable” means that for can obtain successive items until there are none left. A range does not store the whole integer list in advance. Only our display-oriented list conversion collects those entries. Do not expand an enormous range just to print it.

### 6.2 enumerate provides a count alongside each entry

When you need “which item number + the current item,” use enumerate instead of maintaining a separate counter that can drift. It provides pairs of count and entry. The two for targets unpack a pair each round.

File: `numbered_tasks.py`.

<Code language="python">{getControlFlowExample('numbered_tasks.py')}</Code>


In `enumerate(titles, start=1)`, start=1 is a **keyword argument**: it sets this call's start parameter to 1 rather than creating a variable called start outside the call. If omitted, counting starts at zero. L04 covers parameters fully; for now, understand this particular call.

## 7. Dictionary traversal: keys by default, not key-value pairs

File: `dict_iteration.py`.

<Code language="python">{getControlFlowExample('dict_iteration.py')}</Code>

Expected:

```text
title
minutes
title: Read
minutes: 20
```

`for key in task` retrieves a key each round. `task.items()` returns a view of the dictionary's entries, from which `(key, value)` pairs can be obtained. The second loop therefore uses two unpacking targets. This view is neither a frozen snapshot nor a list. We do not modify the dictionary while reading it here.

`for key, value in task` is not a shortcut for that second loop. It tries to unpack each key itself instead of looking up its value. A string key of exactly two characters might even unpack without an error, silently yielding two characters. Choosing items explicitly states that both keys and values are needed.

Dictionaries iterate in insertion order, not automatic key-sorted order. Sets do not offer that ordering guarantee. Adding or removing dictionary keys during iteration may raise RuntimeError or fail to visit entries; this chapter does not depend on such behavior. Different containers expose different items: changing a variable name does not make their traversal semantics identical.

## 8. while: explain progress toward termination, not just the condition

For fits “perform these operations for each entry.” While fits “perform another round as long as this condition holds.” A while condition is checked before each round, so an initially false condition executes no body statements.

Split a nonnegative integer duration into blocks of at most 20 minutes. This uses existing integers only: no user-input waiting and no server access.

File: `while_budget.py`.

<Code language="python">{getControlFlowExample('while_budget.py')}</Code>

Expected:

```text
Block: 20 minutes
Block: 20 minutes
Block: 10 minutes
Blocks: 3; remaining: 0
```

| Round | Initial remaining | used | Updated remaining |
| --- | --- | --- | --- |
| 1 | 50 | 20 | 30 |
| 2 | 30 | 20 | 10 |
| 3 | 10 | 10 | 0 |
| Next check | 0 | Do not enter | Finished |

At each round's start, remaining is positive. Used is either 20 or the smaller positive remainder, so remaining decreases without becoming negative. **Explain both progress per round and the stopping condition.** Writing `while remaining > 0` alone does not guarantee termination.

Test inputs 0, 1, 20 and 21. They should produce 0, 1, 1 and 2 blocks respectively, always ending with remaining zero. Negative numbers are outside this example's contract: they skip the loop but remain negative. That is not validation or automatic data repair.

Deleting the update to remaining would make the current positive input print forever. Do not deliberately leave it running. If your terminal repeats continuously, interrupt with Ctrl+C, then check the update's position and numerical direction. You may see KeyboardInterrupt; interruption does not fix the loop. Exception handling is not required yet.

## 9. continue and break: skipping one round is not ending all processing

After ordinary traversal is clear, introduce two concrete needs: skip completed tasks, and stop searching once the first pending task that fits the budget is found.

File: `loop_controls.py`.

<Code language="python">{getControlFlowExample('loop_controls.py')}</Code>

Expected:

```text
Check: Finished
Check: Long practice
Check: Zero estimate
First match: Zero estimate
```

- Continue skips **the rest of the current round** and proceeds to the next. Finished therefore does not participate in the budget comparison.
- Long practice fails to match and naturally proceeds to the next round. You do not need continue at the end of every iteration.
- Break exits **the nearest enclosing loop**, then execution resumes outside it. It does not end the script or automatically exit every surrounding loop.
- `found = None` records “nothing found yet” before the loop. A match makes found refer to the current dictionary without copying it. An explicit is None check distinguishes the two cases afterward.
- The Check lines are diagnostic output showing which entries were actually visited. Read is never visited, demonstrating the early exit.

Here, fields exist, minutes are nonnegative, and budget is also a nonnegative integer. A zero-minute task is a valid candidate; `if task["minutes"]` would wrongly exclude it. Inside an f-string, `task['title']` remains an ordinary dictionary lookup. Different inner and outer quote styles make it easier to read.

Empty input or all-completed input should produce No match. With budget zero, Zero estimate should still match. When using continue inside while, make sure it does not bypass the progress update and leave the loop stuck in the same state. We defer loop else clauses and nested searches so that basic flow remains visible.

## 10. A logic failure: why deleting during traversal skips an entry

File: `pitfalls/mutation_skip.py`. This is an executable **wrong approach**: lack of an exception does not imply a correct result.

<Code language="python">{getControlFlowExample('pitfalls/mutation_skip.py')}</Code>

Actual output:

```text
[{'title': 'Second', 'done': True}, {'title': 'Third', 'done': False}]
```

The intention is to remove every completed task, but Second remains:

1. The first round reads First at position zero and removes it.
2. Second shifts left to position zero; Third shifts to position one.
3. List traversal moves to the next position, one, and reads Third. Second is never checked.

Enumerate supplies a counter; it does not freeze the list. Distinguish mutating a field in the current dictionary from changing the length of the list being traversed. The former changes a record; the latter shifts positions that traversal will read later.

Read the original list while building a new list instead. File: `safe_filter.py`.

<Code language="python">{getControlFlowExample('safe_filter.py')}</Code>

Expected:

```text
False
```

The source still contains three tasks, while the new list contains only the pending one. False shows that the outer lists are different objects; filtering has not removed source data.

However, **a new result list is not a deep copy**. Inspect inner sharing with this separate one-item experiment, rather than hard-coding an index at the end of the general filtering script:

## 11. List comprehensions come last: shorten a loop you already understand

A list comprehension suits “traverse → optionally filter → compute one result → collect.” It is not an advanced replacement required for every for loop.

File: `comprehensions.py`.

<Code language="python">{getControlFlowExample('comprehensions.py')}</Code>

Expected:

```text
['Practice', 'Review']
['Practice', 'Review']
True
False
```

Read it as follows: obtain each task from tasks; keep entries for which `not task["done"]` holds; put task's title into a new list. The syntax places the collected expression first, but understanding can start with the for in the middle.

Without filtering, omit the final if clause. The result preserves relative traversal order; empty input produces an empty list. These two lists have equal contents but different identities. Here we collect strings; collecting task instead would share dictionaries again. Comprehensions do not automatically copy task objects.

One important difference from ordinary for remains: a comprehension's target name does not leak outside it.

```python case=comprehension_binding
title = "Outside"
labels = [title for title in ["Read", "Practice"]]
print(title)
print(labels)
```

Expected:

```text
Outside
['Read', 'Practice']
```

The claim is therefore “equivalent generated list contents,” not “identical effects on every surrounding name.” L04 expands the scope model. Avoid multiple for clauses, print side effects, assignment tricks and dense conditions just to fit one line. Keep ordinary loops when accumulating several states, breaking early, or making error categories explicit.

## 12. Put it together: a task summary without a hard-coded size

Combine branches, accumulation, empty input and numbering rather than adding another API list. Input contract: tasks is a list; each entry contains a string title, a bool done and a nonnegative integer minutes.

File: `task_summary.py`.

<Code language="python">{getControlFlowExample('task_summary.py')}</Code>

Expected:

```text
Tasks: 3
Done: 1; pending: 2
Remaining: 35 minutes
Pending average: 17.5 minutes
1. Practice loops
2. Check boundaries
```

Why organize it this way?

- Counters, accumulated time and result lists are initialized before the loop, making zero rounds a complete execution path.
- Each entry goes into either the completed or pending branch, never both. Completed and pending counts should add up to the input count.
- Only pending durations contribute to remaining. A zero-minute task is still pending and participates in the average's denominator.
- Divide only after checking that pending_count is positive. No pending tasks means no average; n/a expresses that absence instead of inventing a meaningful numeric zero.
- The `:.1f` format displays one decimal place without changing average's internal value. Finally, enumerate numbers the collected titles.

Change input only, keeping the summary logic unchanged:

| Input variation | Required observation |
| --- | --- |
| Empty tasks list | Tasks: 0; done, pending and remaining are zero; average n/a; no numbered lines |
| Every done becomes True | Pending zero and average n/a; no division by zero |
| Only one zero-minute pending task | Pending one, average 0.0, and one numbered title |
| Add one five-minute pending task | Original pending count becomes three, remaining 40, and displayed average 13.3 |

A missing minutes field may still fail: exception handling has not disguised the field contract. The independent exercise adds an explicit “unknown estimate” policy rather than pretending input is always perfect.
