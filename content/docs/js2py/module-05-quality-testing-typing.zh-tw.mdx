## 1. 從“看到報錯”走到“知道誰該處理”

L04 已經讓你遇到 NameError、TypeError 和 UnboundLocalError。此前我們故意讓程序停止，是為了看到機制；現在任務時長不再總是可信的整數，而是一些類似表單內容的字符串。`"20"` 可以轉換，`"twenty"` 不行，`"-5"` 雖然能轉換，卻不符合業務規則。

如果一個錯誤就讓整批已知格式的任務無法處理，體驗不好；但如果把所有失敗都變成 0，程序會把“沒有得到合法時長”謊報為“合法的零分鐘”。更危險的是，代碼本身寫錯也會被偽裝成用戶填錯。

**本章的目標不是讓紅色文字消失，而是建立可解釋的失敗路徑：知道哪裡失敗、哪裡有能力恢復、哪裡必須繼續傳播。** 調試用於找出原因；異常處理用於實現明確的恢復政策，二者不能互相代替。

| 項目 | 約定 |

## 2. 三種問題，不要都交給 except

| 問題 | 發生階段 | 本章的處理方向 |
| --- | --- | --- |
| 語法不成立 | 當前文件還沒有開始執行 | 修正冒號、縮進或結構；不是吞掉運行異常 |
| 運行中操作失敗 | 執行到某個表達式或調用時 | 查具體異常與調用鏈，決定恢復還是傳播 |
| 正常結束但結果錯誤 | 所有語句都可能合法 | 對照需求和邊界輸入，跟蹤狀態與控制流 |

下面是**有意語法錯誤**，單獨保存為 `syntax_error.py`：

```python expected-error=SyntaxError case=syntax-error
print("Before")
if True
    print("Inside")
```

解析階段在第 2 行發現缺少冒號。即使第一行看起來正常，也不會輸出 Before。不能在同一個尚未解析成功的文件外面加 try 來讓裡面的非法語法變合法。以後動態編譯或導入涉及的 SyntaxError 是另一個場景，不在這裡混講。

對照 L04 的運行異常：函數調用前的打印可能已經發生，未處理異常後的語句則不會執行。**沒有異常也不代表業務結果正確**，第 4 節會復現一個過早 return 的問題。

## 3. 讀 traceback：先定位失敗點，再沿調用鏈找輸入

文件：`errors/traceback_chain.py`。

<Code language="python">{getExceptionExample('errors/traceback_chain.py')}</Code>

標準輸出只有：

```text
Starting report
```

錯誤流的核心結構如下。這裡只歸一化了絕對路徑，並省略重復源碼行和位置指示符；你本機的完整輸出會更長：

```text
Traceback (most recent call last):
  File ".../errors/traceback_chain.py", line 17, in <module>
  File ".../errors/traceback_chain.py", line 12, in build_total
  File ".../errors/traceback_chain.py", line 6, in task_minutes
  File ".../errors/traceback_chain.py", line 2, in parse_minutes
ValueError: invalid literal for int() with base 10: '25m'
```

按兩次閱讀完成定位，而不是把整段 traceback 當作一條不透明字符串：

1. **先看最後一行**：ValueError 是異常種類；後面的消息說明 int 收到了不能按該規則解析的 `'25m'`。類別用於選擇處理方式，消息用於定位細節；不要依靠匹配英文報錯文案來設計恢復邏輯。
2. **再看最後一個相關文件位置**：第 2 行的 `int(raw)` 是失敗表達式，不是 print 或 for 自己出了問題。
3. **向上追溯調用者**：task_minutes 傳入字典的 minutes，build_total 正在遍歷，頂層傳入的是一份含 `"25m"` 的任務列表。每一層對應一次尚未完成的函數調用。
4. **區分原因與觸發位置**：問題在輸入不符合轉換合同；不應看到第 2 行就把 int 換成一個無條件返回 0 的函數。

“most recent call last”表示最近的調用靠後。異常從失敗處向外尋找匹配處理器：parse_minutes → task_minutes → build_total → 頂層；本例沒有處理器，因此進程異常結束。函數沒有成功返回本次結果，後面的 Done 不會輸出。

終端常把標準輸出和錯誤流放在同一個窗口。兩種流的緩衝可能影響肉眼看到的排列，所以這裡分開給出，不要求跨環境逐字比對路徑、箭頭或交錯順序。

## 4. 調試是一套實驗，不是到處加 try

### 4.1 先把實際輸入觀察清楚

文件：`errors/debug_observation.py`。

<Code language="python">{getExceptionExample('errors/debug_observation.py')}</Code>

異常前輸出：

```text
raw: '25m'
type: <class 'str'>
```

`repr(raw)` 返回適合診斷的表示形式，這裡能看見引號和字符串里的空白；`print(raw)` 只顯示內容，容易漏看細節。repr 不會修改 raw，也不自動保護秘密，因此不要把真實口令、令牌或用戶敏感數據當作診斷樣本。

觀察得到“它確實是字符串，但帶有 m”，而不是憑熟悉前端表單就假定“數字輸入框產出的必然是數字”。`type(raw)` 負責看類型，`repr(raw)` 負責看值，兩個問題分開。

文件：`debug_fixed.py`。

<Code language="python">{getExceptionExample('debug_fixed.py')}</Code>

預期：

```text
raw: ' 25 '
type: <class 'str'>
minutes: 25
```

這裡按當前輸入合同把測試數據改成 `" 25 "`，驗證 int 可以處理首尾空白。**這不是聲稱所有非法輸入都能由開發者手工改掉**：真實壞文本如何拒絕，後面用明確規則實現。如果產品真的允許 `25m`，應先定義單位語法，再實現和測試；盲目截掉最後一個字符可能損壞原本合法的 `25`。

### 4.2 沒有 traceback 時，仍要追蹤執行路徑

文件：`debug_logic.py`，有意把 return 放錯位置。

<Code language="python">{getExceptionExample('debug_logic.py')}</Code>

實際輸出：

```text
10
0
```

兩項 10、20 應得 30，卻只得 10。按 L04 的模型追蹤：第一次循環累計成 10 → return 結束整個調用 → 第二項根本沒執行。不是列表數據丟了，也不是 Python 的加法規則不同。

修復時去掉循環體內的 return，保留循環結束後的 return。分別重跑 `[]`、`[0]`、`[10, 20]`、`[5, 7, 9]`，應得到 0、0、30、21。只修到原始輸入得到 30，還沒有證明空輸入正常。

### 4.3 一次可復用的排錯記錄

| 步驟 | 本例應該寫下什麼 |
| --- | --- |
| 復現 | 完整文件名、運行命令、輸入，以及“預期 30，實際 10” |
| 縮小 | 去掉無關任務字段，只保留能復現的兩個數字 |
| 假設 | return 在第一次循環內提前結束調用 |

| 回歸 | 原例、空輸入、單項零值和多項都重跑 |

以後可以用斷點調試器暫停和查看同樣的狀態；本章先把思考過程建立起來，不把 IDE 插件、pdb 命令或框架日誌當作先修。

**停靠點 A**：保留修復前後文件，寫下最後成功命令。能解釋 traceback 的四層調用，也能解釋“沒有報錯但過早返回”，再繼續。

## 5. try/except：只恢復你能說明白的失敗

文件：`recover_value.py`。

<Code language="python">{getExceptionExample('recover_value.py')}</Code>

預期：

```text
Input: '25'
Converted: 25
Next item
Input: 'bad'
Rejected: invalid literal for int() with base 10: 'bad'
Next item
Input: '0'
Converted: 0
Next item
```

`try:` 不是“提前測試這段代碼有沒有錯誤”，而是照常執行其中語句，並為**執行期間傳播出來的異常**設置處理邊界。流程分為兩條：

- 正常：int 返回整數 → Converted 打印 → 跳過 except → 打印 Next item。
- 已知失敗：int 拋出 ValueError → 跳過本次 try 中剩餘語句 → 執行匹配的 except → 打印 Next item → for 開始下一項。

處理完異常**不會回到失敗的 int 那一行自動重試**。本例也沒有使用失敗之前某次循環留下的 minutes；不能在 try 後無條件打印它，因為本次賦值可能根本沒完成。

`except ValueError as error:` 把本次異常對象臨時綁定為 error。`print(error)` 顯示它的說明；`str(error)` 可以得到說明字符串。這個名稱在處理塊結束後會被清除，不要把它當作長期保存的結果；需要長期結果時，明確保存消息或結構化拒絕記錄。

### 5.1 不是所有異常都匹配 ValueError

文件：`errors/unexpected_type.py`。

<Code language="python">{getExceptionExample('errors/unexpected_type.py')}</Code>

第 3 行得到 TypeError，既不打印 Rejected text，也不打印 After conversion。`None` 不是本例支持的數字文本。一個處理器只匹配其聲明的異常種類及其子類，不會因為放在旁邊就接住任何錯誤。

當前政策是“字符串格式錯誤可報告並繼續”；如果上游突然給了 None，就應暴露接口合同錯誤。這不是說所有項目都必須拒絕 None，而是**本章沒有約定把它當作空白或零值**。

## 6. raise：主動表達“操作不能按合同完成”

`int("-5")` 能成功，但任務時長不能為負。沒有解釋器自動替你知道這個業務規則。

文件：`validate_minutes.py`。

<Code language="python">{getExceptionExample('validate_minutes.py')}</Code>

預期：

```text
Accepted: 25
Accepted: 0
Rejected: minutes must be non-negative
```

`raise ValueError("minutes must be non-negative")` 先創建帶消息的異常對象，再使當前正常執行路徑中斷。它不是返回一個 ValueError，也不是打印一條錯誤後繼續運行。外層調用者可以針對 ValueError 恢復；沒有匹配處理器時，錯誤繼續向外傳播。

`type(raw) is not str` 檢查輸入是不是這裡約定的普通內置字符串。str 既可用於 L01 學過的轉換，也表示該內置類型；is not 是 is 的否定。本例有意採用窄合同，不接受數字對象後再偷偷用 int 截斷小數，也沒有聲稱支持自定義字符串子類或任意對象。

| 輸入或問題 | 本章的約定 |
| --- | --- |
| `"20"`、`" 20 "`、`"0"` | 接受並返回整數，0 不是缺失 |
| `"bad"`、`""`、`"2.5"` | 文本不能轉換成整數，ValueError |
| `"-5"` | 能轉換，但違反非負規則，ValueError |
| None、20、2.5 | 不滿足普通字符串合同，TypeError，不能冒充已知壞文本 |

轉換語法以 int 的規則為準，**不是我們已經實現了“只能輸入 ASCII 數字”的表單校驗器**；例如符號及某些其他整數寫法也可能有效。更嚴格的產品限制需要另行定義，不能從這個例子推斷出來。

### 與 JavaScript 的類比到哪裡為止？

兩邊都可以主動中斷當前路徑，交給調用方決定怎麼處理。下面是獨立的靜態對照；本章在本地驗證 Python 的異常行為，不依賴瀏覽器運行按鈕。

<PythonEditor title="主動拒絕不合法的時長" compare={true} canRun={false} height={430}>
```javascript !! js case=raise-comparison
try {
  throw new RangeError("minutes must be non-negative");
} catch (error) {
  console.log(error.message);
}
```

```python !! python case=raise-comparison
try:
    raise ValueError("minutes must be non-negative")
except ValueError as error:
    print(error)
```
</PythonEditor>

兩邊預期：

```text
minutes must be non-negative
```

JavaScript 的 catch 通常先接到被拋出的值，再在塊內判斷；Python 可以直接在 except 後指定異常類型。JS 允許拋出普通值，Python 的 raise 需要異常類或異常實例；不要照搬 `throw "bad"` 寫成 `raise "bad"`。這裡只使用內置異常，不要求你先學類繼承。

## 7. 匹配順序：具體錯誤在前，不代表應該什麼都捕獲

文件：`handler_order.py`，前半故意寫出遮蔽關係，後半交換順序。

<Code language="python">{getExceptionExample('handler_order.py')}</Code>

預期：

```text
Broad handler ran
Specific handler ran
```

處理器按書寫順序尋找**第一個匹配項**，一次異常不會把所有匹配塊都執行一遍。ValueError 屬於 Exception 大類，因此放在前面的 `except Exception` 已經把它接走。

認識當前需要的關係即可，不要求現在定義自己的異常類：

```text
BaseException
├── Exception
│   ├── ValueError
│   ├── TypeError
│   └── LookupError
│       └── KeyError
├── KeyboardInterrupt
└── SystemExit
```

這是節選，不是完整異常樹。KeyboardInterrupt 常來自 Ctrl+C，SystemExit 表達退出；它們不屬於 Exception。裸 `except:` 的捕獲範圍比 `except Exception` 更大，會把這些退出意圖也包進去，本章不這樣寫。

如果多種已知失敗確實需要相同恢復政策，可以寫 `except (ValueError, TypeError):`，括號里是 L02 學過的元組；但**能合併語法不代表業務上該合併**。本章導入報告故意不把類型錯誤與文本格式錯誤合併。

不要把後半代碼當成每個函數都要加 Exception 兜底的模板。大多數函數只需拋出或自然傳播；只有真正擁有恢復職責的邊界才處理。

## 8. 縮小 try，並用 else 把成功後的工作分開

僅僅把 `except Exception` 改成 `except ValueError` 仍然可能吞掉 bug：其他代碼也可能拋出同一種異常。

<Code language="python">{getExceptionExample('pitfalls/wide_try.py')}</Code>

實際輸出：

```text

```

輸入明明是合法的 `"25"`，卻被報告成 Bad input。try 包住了轉換與顯示，處理器分不清同為 ValueError 的來源；錯誤類型不是業務來源標籤。

文件：`errors/narrow_try.py`。

<Code language="python">{getExceptionExample('errors/narrow_try.py')}</Code>

這裡 int 成功後執行 else，display_minutes 拋出的 ValueError **不由同一條 try 的 except 捕獲**。程序在第 2 行失敗，消息保留 `display rule is broken`，沒有 Bad input 或 After display。

else 的條件是 try 正常走完；如果 try 內已經通過 return、break 或 continue 轉移控制，也不會再跑這個 else。它不是 except 的兜底分支，更不是所有分支之後必跑的代碼。

這個結構把責任說清楚了：只把 int 的格式失敗解釋為輸入錯誤；顯示階段失敗繼續暴露。也可以把成功後的工作放在其他明確位置，但不能讓未知錯誤悄悄變成一個看似成功的返回值。

## 9. 保留錯誤：不處理、重新拋出、補充原因

### 9.1 沒有恢復責任時，最簡單的是不捕獲

parse_minutes 不知道整批任務應當停止還是跳過一項，所以它只返回合法分鐘數，或拋出明確異常。報告構造函數才知道逐行政策。不要在底層函數里隨便 print 然後返回 None，讓所有調用者猜測這個 None 究竟表示什麼。

### 9.2 必須補充觀察後，用裸 raise 繼續傳播

文件：`errors/reraise.py`。

<Code language="python">{getExceptionExample('errors/reraise.py')}</Code>

標準輸出：

```text
Context: parsing Read
```

隨後仍以 ValueError 異常結束，原始 int 的第 3 行仍在 traceback 中。except 內不帶對象的 `raise` 重新拋出當前正在處理的異常；它不是另一次轉換，也不是成功恢復。不能脫離正在處理的異常隨意寫裸 raise。

這裡打印的上下文是固定教學文本。以後服務端會有結構化日誌及敏感信息處理；本章不是推薦把所有輸入或 traceback 原樣發給最終用戶。僅為了“捕獲一下”而又重新拋出沒有收益，不需要給每層函數都套這一結構。

### 9.3 更換消息時，把原始原因留下

文件：`errors/chained_error.py`。

<Code language="python">{getExceptionExample('errors/chained_error.py')}</Code>

`except ValueError as error` 只圍住 int；隨後 `raise ... from error` 給出穩定的領域消息，並明確原始異常是其原因。traceback 會先顯示轉換失敗，再顯示類似以下連接說明及新錯誤：

```text
The above exception was the direct cause of the following exception:
...
ValueError: minutes must be an integer
```

這裡的 `...` 是**traceback 摘錄的省略記號**，不是讓你寫進 Python 文件的實現。兩個 ValueError 對象不是同一個對象，因果關係仍保留；原因鏈和第 3 節單個異常的多層調用棧也不是一回事。

沒有使用 `from None` 隱藏原因，也沒有把 NameError、TypeError 等所有問題都翻譯成 ValueError。未知錯誤仍按原來的種類傳播。

**停靠點 B**：分別運行寬 try、窄 try、重新拋出和原因鏈的文件。記錄“哪裡捕獲、哪裡繼續失敗、原始位置有沒有保留”，不要以退出碼為零作為唯一正確標準。

## 10. finally：離開保護區之前執行，不是恢復成功

文件：`finally_paths.py`。

<Code language="python">{getExceptionExample('finally_paths.py')}</Code>

預期：

```text
else
finally
Result: 0
except
finally
Result: None
```

兩條路徑都先執行 finally，再把之前準備返回的值交給調用者。finally 沒有把 None 改成 0，也沒有決定這次轉換是否成功。

| 離開方式 | except | else | finally 後的去向 |
| --- | --- | --- | --- |
| try 正常走完 | 不執行 | 執行 | 繼續後續語句，或完成 else 中的 return |
| 匹配且被恢復的異常 | 執行對應塊 | 不執行 | 繼續後續語句，或完成 except 中的 return |
| 沒有匹配的異常 | 不執行 | 不執行 | 清理後繼續向外傳播 |
| try 內 return | 不執行 | 不執行 | 完成已準備的返回；finally 仍先執行 |

文件：`errors/finally_unhandled.py`。

<Code language="python">{getExceptionExample('errors/finally_unhandled.py')}</Code>

標準輸出：

```text
finally before propagation
```

然後仍然出現第 2 行 TypeError；不會打印 After。這說明“清理代碼執行過”不等於“異常已經被處理”。except、else 或 finally 自己也可能失敗；finally 里新的失敗還可能取代當前傳播的異常，不能把清理區當成不會出錯的安全地帶。

### 10.1 不在 finally 里偷偷 return

### 13.2 帶提示修復：不要把“缺字段”和“壞文本”都變成 0
