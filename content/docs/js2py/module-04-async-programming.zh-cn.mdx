## 1. 为什么现在才把代码装进函数？

L03 已经能处理任意数量的任务，并说明空输入、未知时长和零预算怎样经过控制流。现在出现一个新需求：同一套规则既要用于 20 分钟的学习安排，也要用于 40 分钟的安排，还要在修改输入后重新计算。

复制整段脚本虽然能暂时得到结果，却会把规则复制出多个版本。修改一处、忘记另一处，就可能让两个地方对“0 分钟是否有效”给出不同答案。我们希望给一段已有逻辑命名，明确它需要什么、返回什么、是否修改输入，再从不同地方调用它。

**函数不是让代码看起来更工程化的盒子，而是带着输入、输出和副作用约定的可调用对象。** 本章先把执行机制讲清，再把它用于任务规则；不会为了学习 def 就提前引入类、装饰器、模块拆分或 FastAPI。

## 2. 定义不等于调用：先建立执行顺序

文件：`definition_and_call.py`。

<Code language="python">{getFunctionExample('definition_and_call.py')}</Code>

预期：

```text
Before definition
After definition
Inside call
25
```

这几行中有两种不同的动作：

- 执行 `def add_buffer(minutes):`，创建函数对象，把名称 add_buffer 绑定到它。**此时不执行函数体。** 括号中的 minutes 是形参，表示这段逻辑需要接收一个值。
- 执行 `add_buffer(20)` 才是调用：20 是实参，本次调用把局部名称 minutes 绑定到这个整数，然后开始执行缩进的函数体。

`return minutes + 5` 先计算结果，再结束**当前这次函数调用**，把值交还给调用表达式。于是 `result = add_buffer(20)` 等待这次同步调用完成，将返回的 25 绑定给 result，然后继续执行下一行。

可以把执行路径写成：顶层语句 → 执行 def → 顶层语句 → 进入调用 → 执行函数体 → return 回到调用处 → 后续顶层语句。示例里的 Inside call 只是帮助观察进入时机；计算规则不需要永远夹带这些诊断打印。

注意三个细节：

1. 函数体像 if/for 一样通过冒号和缩进组织，但函数还建立了自己的局部名称空间，后面会逐步解释。
2. 空行用于阅读分隔，不负责开始或结束函数；退回外层缩进才回到顶层代码。
3. 普通函数没有强制的 self 参数。实例方法属于后续的类知识，不应把它当作所有 Python 函数的固定模板。

文件：`errors/before_definition.py`。

<Code language="python">{getFunctionExample('errors/before_definition.py')}</Code>

第一行就产生 NameError，没有标准输出，因为执行尚未到达 def。Python 会先解析整个文件，但**解析成功不等于所有定义语句都已经执行**。修复时让 def 在真正调用之前执行，再确认结果为 25。

## 3. return 与 print：一个传递结果，一个产生输出

### 3.1 调用表达式必须有一个结果，即使结果是 None

print 把文字写到标准输出；return 把一个对象交给调用方。终端看见某个数字，并不意味着调用方拿到了那个数字。

文件：`return_paths.py`。

<Code language="python">{getFunctionExample('return_paths.py')}</Code>

预期：

```text
done
unknown
pending
Ready: Read
None
None
```

逐个区分这三个函数：

- status_label 在第一个匹配的 return 处立刻结束当前调用。已完成任务返回 done，不再检查它的时长；0 分钟待办返回 pending。这里返回的是字符串，不是自动打印它。
- announce 的函数体执行一次 print，但没有写 return，走到函数末尾后隐式返回 None。所以 Ready: Read 是函数的输出，下一行 None 才是调用方随后打印的返回值。
- maybe_announce 在空标题时执行不带表达式的 return，直接返回 None，不打印标题；非空时走到函数末尾，也返回 None，但会产生输出。这两个路径的副作用不同，返回值却都为 None。

return 不只退出 if 或循环，而是退出当前函数；它也不会直接退出整个脚本。需要得到业务结果的函数，应逐条检查返回路径，不能只在一个分支 return 而让其他分支意外落到 None。

### 3.2 复现“看见数字，却不能继续计算”

文件：`errors/printed_result.py`。

<Code language="python">{getFunctionExample('errors/printed_result.py')}</Code>

错误发生前的标准输出：

```text

```

第六行产生 TypeError：result 是 None，不能与 10 做数值加法。问题不在这次加法的写法，而在上游函数把“打印结果”误当成“返回结果”。把函数体中的 print 改为 return，再运行，应只打印最终的 35。

不要用 `result or 0` 把这个错误隐藏掉；那会把违反函数合同的情况伪装成合法结果。也不要为了让终端出现 35 而在函数里硬编码打印它。

### 3.3 返回两个信息时，仍然是返回一个对象

L03 学过元组解包；它可以接收函数返回的元组：

```python case=tuple_result
def split_minutes(total):
    hours = total // 60
    minutes = total % 60
    return hours, minutes


hours, minutes = split_minutes(135)
print(hours)
print(minutes)
```

预期：

```text
2
15
```

`return hours, minutes` 打包成一个二元组，再由调用方解包。不是函数有两次 return，也不是两个独立异步结果。当前输入约定为非负整数；接口字段更多时，命名字典可能比不断增加元组位置更易读。

**暂停点 A**：预测定义与调用的打印顺序；修复一次“只打印、不返回”；解释一次提前 return。记录调用时传入的值、返回值和副作用，恢复时分别核对这三项。

## 4. 参数与实参：调用时到底给哪个名称什么值？

形参是 def 中的名称，实参是一次调用提供的对象或表达式。它们不是同一个层次：函数只定义一次，可以接收很多次不同的调用。

文件：`arguments.py`。

<Code language="python">{getFunctionExample('arguments.py')}</Code>

预期：

```text
25
45
20
40
```

| 调用 | 本次 minutes / repeats / extra | 解释 |
| --- | --- | --- |
| `estimate(20)` | 20 / 1 / 5 | minutes 必需；其他使用默认值 |
| `estimate(20, 2)` | 20 / 2 / 5 | 位置实参依照形参顺序分配 |
| `estimate(20, extra=0)` | 20 / 1 / 0 | 用名称指定 extra，不必先填 repeats |
| `estimate(repeats=2, minutes=20, extra=0)` | 20 / 2 / 0 | 关键字实参按名称匹配，不按这里的书写顺序匹配 |

在这个普通签名里，必需的位置参数写在带默认值的参数之前。`extra=0` 在调用位置是关键字实参，不是给调用方创建变量；这是 L03 的 `enumerate(..., start=1)` 所使用的同一种机制。

Python 会在进入这个函数体前完成参数绑定。参数数量或名称不合适会失败，但**绑定成功不会替你验证业务类型或取值范围**。当前例子约定输入为合适的数字，不会自动解析 `"20"` 或拒绝负数。

## 5. 参数绑定不自动复制：把 L02 的引用模型带进函数

调用时，形参这个局部名称绑定到实参对象。**没有自动深复制，也不能通过重新绑定形参，让调用方的名称自动改指向另一个对象。** 与其争论“按值／按引用”两个过于简短的标签，不如直接看具体对象和绑定。

文件：`argument_binding.py`。

<Code language="python">{getFunctionExample('argument_binding.py')}</Code>

预期：

```text
Read
Local
False
None
['python', 'functions']
```

| 操作 | 改变了什么 | 调用方会看到什么 |
| --- | --- | --- |
| 刚进入 replace_local | 局部 task 与 original 指向同一个字典 | 还没有修改 |
| `task = {...}` | 仅把局部 task 改绑到新字典 | original 仍是原对象 |
| `return task` | 把新字典交给调用方保存为 replacement | replacement 与 original 不同 |
| `task["tags"].append(topic)` | 通过共享字典取得内部列表并修改它 | original 的 tags 内容改变 |

add_topic 以修改传入对象为目的，这里返回 None 是明确的设计，而不是忘写 return。相反，如果函数承诺返回一份可继续计算的数据，意外返回 None 就是错误。不要用“所有函数都必须无副作用”或“返回 None 都是坏写法”代替具体合同。

一个函数即使使用了局部参数，也不代表与外部完全隔离。返回一个新列表也不保证其中的字典是新的；复制到哪一层，仍按 L02 的数据形状分析。稍后创建任务时，我们会明确选择隔离传入的标签列表。

## 6. 默认值何时建立？为什么第二次调用会影响第一次？

### 6.1 默认表达式在执行 def 时求值

文件：`default_values.py`。

<Code language="python">{getFunctionExample('default_values.py')}</Code>

预期：

```text
20
0
None
35
```

每次**执行这条 def 语句**时，默认表达式各求值一次，并把得到的对象保留为这个函数的默认值；不是每次调用时重新读取表达式。这里执行 def 时 default_minutes 是 20，后面重新绑定为 35，并没有替换函数已经保存的默认对象。

省略 minutes 才使用默认值。显式传 0 就得到 0，显式传 None 就得到 None；Python 不会把 None 自动当成“没传参数”。最后一次调用明确读取当前 default_minutes，所以传入 35。

不要把这个规则理解成“默认值永远在整个进程中只计算一次”：如果以后在另一个函数里反复执行 def，会创建不同的函数对象，各自建立默认值。当前先理解每个函数定义与其后多次调用的区别。

### 6.2 默认列表会被多次调用共享

文件：`pitfalls/shared_default.py`。这是可运行但有意展示风险的写法。

<Code language="python">{getFunctionExample('pitfalls/shared_default.py')}</Code>

实际输出：

```text
['python']
['python', 'functions']
['python', 'functions']
True
```

`tags=[]` 在定义时创建一份列表。两次调用都省略 tags，所以都把局部 tags 绑定到这同一份默认列表。第二次 append 修改它，first 仍指向它，因此 first 观察到的内容也改变了。

把输出画成时间线：第一次调用追加 python → 返回同一列表给 first → 第二次调用追加 functions → first 与 second 都指向已经有两项的列表。问题既涉及默认值的建立时机，也涉及返回对象的共享，不能只背“不要用 []”。字典和其他可变默认对象同样需要分析。

### 6.3 用 None 表达省略，再决定是否复制输入

文件：`fresh_defaults.py`。

<Code language="python">{getFunctionExample('fresh_defaults.py')}</Code>

预期：

```text
['python']
[]
False
['python']
['python', 'copy']

```

这里有两个不同的设计决定：

1. tags 为 None 时，在函数体内创建空列表。这段代码每次调用都会重新执行，因此两个省略 tags 的任务有各自的列表。
2. 显式传入标签列表时，先浅复制。因为函数承诺返回可独立编辑的任务，不应让之后的任务编辑污染调用方的标签列表。

第一点只解决默认对象共享；不加第二点，调用方显式传来的列表仍会被共享。当前标签都是不可变字符串，因此复制一层列表足够；如果标签里还有可变字典，这不等于通用深复制。

本函数把显式 None 和省略参数同样解释为“没有标签输入”，这是主动选择的政策。需要区分这两种含义时，None 就不能同时充当两者的标记；本章不引入自定义哨兵对象。也不使用 `if not tags` 混淆 None 与调用方明确传来的空列表。

**暂停点 B**：分别测试省略参数、传 None、传 0、传空列表和传共享列表时的适用函数。写明哪些调用合法、默认值何时用到、哪些对象被共享或复制；不要把不属于某个函数合同的输入当作它必须支持的情况。

## 7. 作用域：名称从哪里来，为什么“外面明明有”仍然报错？

### 7.1 每次调用有自己的局部绑定

文件：`local_scope.py`。

<Code language="python">{getFunctionExample('local_scope.py')}</Code>

预期：

```text
local: Read
module
20
35
```

format_label 的形参 label 是本次调用的局部名称，遮住了文件顶层的同名 label；prefix 也是局部名称。调用后顶层 label 仍是 module。两次函数调用各有自己的局部绑定，不因为名称相同就自动变成全局状态。

current_limit 没有把 limit 定义为局部名称，因此读取本文件顶层的 limit。两次调用之间，顶层把它从 20 改绑成 35，下一次调用就读到 35。这与上一节**已经求值保存的默认值**不同：这里在函数体运行时查找名称。

对本章的普通函数，可以先用下面的查找路线建立模型：

| 层次 | 在哪里找 | 本章例子 |
| --- | --- | --- |
| Local | 当前函数调用的局部绑定，包括形参 | label、prefix |
| Enclosing | 外层函数的绑定，若函数嵌套定义 | 后面闭包中的预算 |
| Global | 本文件顶层的名称，以后会称模块级名称 | limit |
| Built-in | Python 提供的内置名称 | len、print |

这常被缩写为 LEGB，但背缩写不是验收。它不是“局部没值就永远自动去外层找”的无条件兜底规则；下一小节会验证例外。这个简图也不试图提前覆盖类体、注解等后续机制。

局部名称不会因为调用结束就变成顶层变量。下面是独立的预期失败实验：

```python case=local_unavailable

    prefix = "Task"
    return f"{prefix}: {title}"


print(make_label("Read"))
print(prefix)
```

失败前输出：

```text
Task: Read
```

第七行 NameError：返回的是格式化后的字符串，不是把 prefix 这个名称导出给调用方。对象可以通过 return 继续被使用，不表示原来的所有局部名称都对外可见。

### 7.2 局部赋值会影响整个函数体中该名称的含义

文件：`errors/local_before_binding.py`。

<Code language="python">{getFunctionExample('errors/local_before_binding.py')}</Code>

调用进入函数后，第五行产生 `UnboundLocalError`，没有输出。它是 NameError 的一种更具体情况：Python 已经把 budget 判定为此函数的局部名称，却在给它绑定值之前先读了它。

原因在赋值左侧：函数体中对 budget 的名称赋值使它成为局部名称。执行右边的 `budget + 5` 时，不能再用文件顶层的 20 作为兜底。不是顶层变量突然消失，也不是整数不能相加。

当前更清楚的修复方式是把依赖作为参数，把结果返回：

```python case=scope_repair
def increased_budget(budget, extra=5):
    return budget + extra


budget = 20
new_budget = increased_budget(budget)
print(budget)
print(new_budget)
```

预期：

```text
20
25
```

调用方明确决定是否再把 new_budget 绑定给 budget。Python 也提供 global/nonlocal 来声明对其他层级绑定的操作，但本章不把修改共享外层状态当作修复的默认方案，也不要求掌握有状态闭包。先能通过参数与返回解释数据流。

还记得 L03 吗？if/for 没有 JS let 式块级作用域；def 建立函数局部范围。不要用“所有缩进都产生新作用域”来替换这两个不同规则。

## 9. 简单闭包：让返回的规则记住一次配置

### 9.1 先区分两次调用做了什么

我们想得到一个 20 分钟规则和一个 40 分钟规则，而不是每次判断都再传预算。可以让一个函数接收配置，返回另一个函数。

文件：`closure_factory.py`。

<Code language="python">{getFunctionExample('closure_factory.py')}</Code>

预期：

```text
False
True
True
False
```

按生命周期拆开理解：

1. 调用 `make_budget_rule(20)`，为这次外层调用建立 limit 的局部绑定。
2. 执行内部 def，创建 fits 函数；它会用到外层的 limit，但此时不执行 fits 的函数体。
3. `return fits` 把函数对象交给调用方。不是 `return fits(...)`，所以此处没有提前判断某个分钟数。
4. 外层调用已经结束；之后 `small_rule(25)` 才执行返回的函数，并读取它所关联的外层 limit。
5. 第二次工厂调用另建一套绑定，产生另一个函数对象，所以 20 与 40 的规则能同时存在，彼此不串台。

这种函数连同它使用的外层函数绑定，形成这里所说的**闭包**。不必把外层整个运行过程想成一直在后台执行，也不是把所有局部名称导出到全局；需要的绑定仍可被返回函数访问。

工厂、内部函数、闭包不是三个额外框架 API：这里仍只有 def、调用、返回与名称查找。完整机制来自之前各节的组合。

### 9.2 闭包不是定义那一刻的值快照

文件：`closure_binding.py`。

<Code language="python">{getFunctionExample('closure_binding.py')}</Code>

预期：


fits 创建时 limit 是 10，但同一次外层调用在返回前把 limit 改绑为 30。之后执行 rule 时读取这个外层绑定，所以 20 能通过。不要把闭包查找与默认表达式在定义时求值混为一谈。

上个工厂里没有再次改绑自己的 limit，因此每个规则保持各自的预算；如果调用方后来把它自己的预算变量重新绑定为别的整数，不会自动改写工厂这次调用已经建立的参数绑定。若捕获可变对象，则仍要分析共享修改，闭包并不自动深复制。

现在不要求在循环里批量嵌套定义函数，也不要求用 nonlocal 实现计数器；不能照搬 JS let 的逐轮绑定假设。先能独立写一个返回判断函数的工厂，并解释“创建规则”与“应用规则”的两个调用时刻。

## 10. 抽函数之前，先写清合同

不是每几行都值得包一个函数，也不是每个函数都要接收整个系统的数据。先回答四个问题，再选择函数边界：

| 问题 | 分类规则的示例答案 |
| --- | --- |
| 输入是什么？ | 一个 None 或整数时长；bool 和字符串不在合同内 |
| 返回什么？ | unknown、invalid、known 三个字符串之一 |
| 修改谁或打印什么？ | 不修改调用方对象，也不打印 |
| 未覆盖什么？ | 不负责解析外部文本、捕获异常或保存数据 |

把分类函数与汇总函数分开，是因为前者决定一项数据的含义，后者负责遍历和累计。显示结果则交给调用方。以后同一份返回数据可以被其他代码使用，不必先从打印文字里再解析出来。

下一份文件使用**文档字符串**：函数体第一条语句是三引号字符串，简要写下用途和合同。它不是运行时校验，也不是 return；函数继续执行后面的语句。三引号可以容纳多行文本，这里只写短说明。我们不要求现在使用文档生成器或学习类型注解。

这样的分工提高可验证性，但不是“所有函数都必须纯函数”的教条；例如前面的 add_topic 明确负责修改。重要的是调用方能看见合同、预测副作用，而不是被隐藏状态影响。
