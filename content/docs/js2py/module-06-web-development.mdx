## 1. Reuse a function without accidentally running a program

In L05, parsing, reporting and demonstration data lived in one file. A second program now wants only the parser. Copying it gives two implementations to maintain; importing the whole file can unexpectedly run its demonstration. The next step is not a large directory architecture. It is understanding **how one file obtains another file's capabilities, and which code runs along the way**.

A Python module is an object with its own namespace: a place where names refer to objects. In our first examples, a `.py` file supplies its code. A module can contain function definitions, constants and executable statements. Importing is therefore not simply pasting declarations or installing a dependency.

## 2. Builtins, standard-library modules, local modules and third-party packages

You already call `print`, `len`, `int` and `sum` without imports: they are builtins. Python also ships a standard library. Many of its capabilities live in modules that must be imported before their names are available. A local file you write is another possible module; a third-party distribution must first exist in the selected environment. **`import` locates and loads; it does not download or install.** Installation and isolation belong to L08.

This comparison is static (`canRun={false}`); the local command below is the verification path:

<PythonEditor title="A builtin namespace versus an imported module" compare={true} canRun={false}>
```javascript case=ceil-comparison

```

```python case=ceil-comparison

```
</PythonEditor>

Both print 3. JavaScript's `Math` is a builtin object; Python's `math` is a standard-library module. The dot selects an attribute after the left-hand name has been resolved. It does not mean that `math` is a class, or that every JavaScript builtin has the same Python packaging.

<Code language="python">{getModuleExample('first_import/task_rules.py')}</Code>

`report.py`:

<Code language="python">{getModuleExample('first_import/report.py')}</Code>

Run from the lab root:

```bash
uv run --no-project --python 3.13 python first_import/report.py
```

```text
task_rules initialized
Default: 20
Buffered: 25
```

Trace this in order:

1. Python begins executing `report.py`. It encounters `import task_rules`.
2. For this fresh process, it finds the neighboring `task_rules.py`, creates a module object and executes its top-level code. The marker prints; the constant is bound; `def` creates the function. The function body has not been called.
3. The import binds the name `task_rules` in the caller to that module object.
4. `task_rules.DEFAULT_MINUTES` looks up an attribute in the module's namespace. `task_rules.add_buffer(20)` retrieves and then calls its function.

The modules do not merge their globals. A global in `task_rules.py` belongs to that module, not to every file in the process. This is organization rather than secrecy: public attributes can still be accessed through the module object. The namespace is not an access-control boundary.

A filename such as `task_rules.py` becomes the import name `task_rules`, without `.py`. Use clear identifier-like names, not `task-rules.py`, and avoid names of modules you intend to use. We will diagnose collisions in section 10.

## 4. Import forms: exactly which name is introduced?

File: `first_import/import_styles.py`.

<Code language="python">{getModuleExample('first_import/import_styles.py')}</Code>

```bash
uv run --no-project --python 3.13 python first_import/import_styles.py
```

```text
task_rules initialized
Alias: 20
Direct names: 20 25
```

| Statement | Name bound in this caller | How to use it |
| --- | --- | --- |
| `import task_rules` | `task_rules`, a module | `task_rules.add_buffer(20)` |
| `import task_rules as rules` | `rules`, the same kind of module reference | `rules.add_buffer(20)` |
| `from task_rules import DEFAULT_MINUTES` | `DEFAULT_MINUTES`, the retrieved object | `DEFAULT_MINUTES` |
| `from task_rules import add_buffer as buffered` | `buffered`, the retrieved function | `buffered(20)` |

`from` does not avoid loading the module or select only a few source lines to execute. It changes the final name binding. An alias changes the caller's spelling, not the module file or original function's implementation. Keep the origin visible when several modules have similar names; avoid wildcard imports that make origins hard to trace.

## 5. Reuse within a process, and why from is not an ESM live binding

File: `first_import/import_twice.py`.

<Code language="python">{getModuleExample('first_import/import_twice.py')}</Code>

```bash
uv run --no-project --python 3.13 python first_import/import_twice.py
```

```text
task_rules initialized
Same module: True
Buffered: 25
```

Under ordinary importing in this one interpreter, the same module name is reused from an in-memory cache (`sys.modules`). Both aliases refer to the same object and initialization occurs once. Run the command again and a new process prints the marker again. Editing a source file does not automatically re-execute an already imported module in an existing process; for these lessons, end that process and start another.

This is **not** a guarantee that a physical file can never run twice. Executing code as `__main__` and later importing it under another name are different identities; reload and manual cache manipulation are additional cases outside this lesson. Do not construct business guarantees around “imports always happen only once.”

### Rebinding and mutation still follow L01 and L02

`bindings/settings.py`:

<Code language="python">{getModuleExample('bindings/settings.py')}</Code>

`bindings/observe.py`:

<Code language="python">{getModuleExample('bindings/observe.py')}</Code>

```bash
uv run --no-project --python 3.13 python bindings/observe.py
```

```text
Initial: 20 20
Rebound: 20 40 40
Shared: ['python', 'modules'] ['python', 'modules']
Local tags: ['local'] ['python', 'modules']
```

Draw two namespaces. Initially the caller's `BUDGET` and `settings.BUDGET` both refer to 20. Assigning `settings.BUDGET = 40` changes the module's binding; the caller's independent name still refers to 20. `current_budget()` reads the globals of the module where the function was **defined**, so it sees 40, even though the function was imported directly.

Uppercase `BUDGET` is a naming convention, not enforced immutability.

The two `tags` bindings initially point to the same list. Appending through either reference mutates that list, so both observe it. Reassigning the caller's `tags` to a new list separates the bindings. **`from` does not deep-copy an object, and it does not create a live link to future rebindings.**

JavaScript **ES modules** have live imported bindings: a change to an exported binding can be seen through its import, and the importer cannot assign to that imported binding. Python's directly imported name can be rebound locally. This comparison concerns ESM, not every CommonJS or bundler transformation. Transfer your understanding of references, not an assumption that similar `import` spellings have identical semantics.

### Two caches, two different jobs

You may now see `__pycache__/` and `.pyc` files. CPython can cache compiled code on disk to avoid repeating compilation work. Those files are not your source and need not be copied into the exercise or download. They do not preserve the previous process's variables or bypass module initialization in a new process. In-memory module reuse and disk bytecode caching explain different observations.

## 7. Three locations that are easy to confuse

Before packages, make execution context visible. File: `locations/show_context.py`.

<Code language="python">{getModuleExample('locations/show_context.py')}</Code>

- `os.getcwd()` reports the process's **current working directory**. It is inherited from the launching terminal here.
- `__file__` identifies this source file in these normal file-based examples.
- `sys.path` is Python's list of module-search locations. `[0]` selects its first entry in the ordinary commands below. It is not the shell's `PATH`, which helps find executable commands.
- `__name__` identifies the executing module; it is not a directory.

With no isolated/safe-path flags or custom path configuration, direct file execution puts the script's directory at the beginning of the search path. `-m` starts from the current directory to find the requested module. Other search locations include Python's library locations; built-in modules also have their own import handling. Do not reduce all import resolution to “always look beside the file containing the import.”

From the lab root:

```bash
uv run --no-project --python 3.13 python locations/show_context.py
```

Here and only in the path displays, `<LAB>` means your real absolute extracted directory; it is **not text to type**:

```text
Name: __main__
Cwd: <LAB>
File: <LAB>/locations/show_context.py
First search: <LAB>/locations
```

Now explicitly change the terminal directory:

```bash
cd locations
uv run --no-project --python 3.13 python show_context.py
uv run --no-project --python 3.13 python -m show_context
cd ..
```

Both Python commands print:

```text
Name: __main__
Cwd: <LAB>/locations
File: <LAB>/locations/show_context.py
First search: <LAB>/locations
```

`-m` means “find this module by name, then run it as the entry point.” It takes `show_context`, **not** `show_context.py` or a filesystem path. Paths above use `/` for display; your operating system may format them differently. Running a script does not itself change the working directory to that script's directory. This will matter when L07 reads relative file paths.

Do not “repair” confusion by appending paths to `sys.path` or setting `PYTHONPATH`. First record the actual current directory and exact command. These examples deliberately use normal local import behavior; an isolated `python -I` command removes the local search locations and is not interchangeable.

### C. Independent multi-file task planner

Choose responsibilities before writing imports:

- `rules.py`: `parse_minutes(raw)`. Reuse L05's strict text contract: non-string input raises TypeError; invalid integer text raises ValueError with the original conversion exception as its cause; negative integers raise ValueError; whitespace and zero are valid. Use the messages in the expected output below.
- `summary.py`: `build_plan(rows, budget=20)`. Budget must be an ordinary nonnegative integer: reject bool and nonintegers with TypeError, negative integers with ValueError. Validate it even for empty rows.

Keep missing fields, wrong minutes types and unknown failures visible. This exercise assumes titles are strings; it does not introduce a general schema validator. Recovery recognizes ValueError from the agreed parser boundary, not the origin of every possible ValueError: a defect inside a replacement parser can violate that assumption.
- Return `accepted`, `rejected` and `total_minutes`. Do not mutate source rows or accumulate data in module globals. Each call owns fresh result lists and item dictionaries; preserve source order.
- `app.py`: put demo data, the call and display inside `main`, with the explicit guard. `__init__.py` must not run the demo. Dependencies point from app to summary to rules, never backwards.
- `check_import.py`: import app and summary, then print only `Imported: study_plan.app study_plan.summary`. No demonstration output should precede it.
