## 1. A user_id in the database does not identify the caller

The D labs accepted an owner_id to demonstrate relationships and transactions. That was an explicitly limited teaching input, not authentication. Any client can change JSON; TypeScript types, hidden buttons and CORS cannot prove identity. This chapter moves “who is calling?” out of the request body and into a credential verified by the service. The next chapter decides which objects that person may operate on.

Download the [complete S01 lab](/learning-assets/js2py/s01-identity.zip). It includes three-language READMEs, sources, migrations, tests and an explicit packaging allowlist. It retains D's schema but **does not continue exposing D's self-reported-identity endpoints**. Each security lab is independent: no imports from another chapter and no connection to your existing database.

The capstone mentions JWT as one possible design. Here we deliberately choose the user-approved alternative: an **opaque random session token**, not a partial JWT implementation. There are no client-readable identity claims; every request checks the database, making revocation easier to explain. The trade-off is dependence on session storage and its availability, with no offline verification. There is no refresh flow: log in again after expiry.

## 2. Separate four things before following a login

```text
password -> Argon2id verify -> active user
                                  |
                     random bearer returned once
                                  |
DB: token digest + user_id + auth_version + expiry
                                  |
next request: Bearer -> digest lookup -> user/version/expiry checks
                                  |
                         authenticated actor
```

A **user record** represents an account, not a request. A **password** is a long-lived secret known to its user. A **password hash** lets the server verify a candidate without storing plaintext; it is not encrypted text that can be decrypted to recover the password. A **session token** is a temporary Bearer credential issued after login. Whoever possesses it may act through that session, so it is not an ordinary debugging string.

A browser's loggedIn=true is only UI state. The service must independently verify each protected request. Hiding a logout button or forgetting to clear a client token must not change server-side revocation. A single login 200 does not establish permanent identity, much less permission to access someone else's project.

## 4. Argon2id is not about turning passwords into strings quickly

<Code language="python">{getIdentityExample('security.py')}</Code>

Read hasher, password_matches and login first; do not memorize the whole module at once. PasswordHasher comes from the established argon2-cffi library and explicitly selects Argon2id. Each hash call lets the library generate a random salt. The encoded string contains the salt, algorithm version, memory/iteration parameters and result. Give that encoded value and a candidate password to verify; do not split the format, compare a homemade password digest or design your own encryption.

The fixed settings are m=65536 KiB, t=3 and p=4, matching the scale of the documented low-memory profile. Memory and computation raise the cost of offline guessing, but also consume server resources. Bigger parameters are not automatically better, and they are not a throughput promise. Measure on the deployment machine and pair the result with concurrency budgets and throttling. Two users choosing the same password should get different hashes; the lab actually tests this.

After successful verification, check_needs_rehash determines whether to hash again with current parameters. Only then is the plaintext password available: the old hash cannot produce an “upgraded password.” Updating the hash encoding is not the same as a user password change; an actual password change increments auth_version.

Unknown accounts also verify a startup-generated dummy hash, avoiding the obvious “no account, return immediately” branch. This **does not promise constant end-to-end timing**. A well-formed unknown-account login, wrong password and disabled account receive the same 401. Malformed input can still produce a sanitized 422; do not misclassify every failure as a database exception.

<details>
<summary>Explanation answer: why SHA-256 for token digests, but not passwords?</summary>

Human-chosen passwords may be guessable. A fast hash makes offline guessing cheap; passwords need an established salted, adjustable-cost password hasher. A session token is generated by secrets.token_urlsafe(32), containing 32 random bytes, not a short password or user_id. SHA-256 supports lookup without storing that original token; it is not a homegrown password scheme. The stored digest itself is not accepted as a Bearer token, and the entry point validates the original token format. A database leak is nevertheless a security incident: digest-only storage does not remove access-control and backup-protection requirements.

</details>

## 5. Reestablish identity on every request

Inside a transaction, login locks the user, verifies the password and active state, generates a random token, and stores its digest with the current auth_version. Only after commit does the endpoint return access_token. The default lifetime is 900 seconds, configurable within 60–3600. This example uses the application's UTC clock; production instances still need clock synchronization. UTC cannot repair an incorrect machine clock.

authenticate parses Bearer syntax, hashes the original token, locates the session, locks the user, rereads the session, then checks active state, revoked_at, expiry and version equality. Every failure produces a generic 401 with WWW-Authenticate: Bearer. Finding a digest is not the final check: an expired or revoked database row must still be rejected.

Why document lock ordering in code? Ordinary requests take a shared user lock; password changes and all-session revocation take an exclusive lock. Further locks follow user, credential, project, task order. Revocation waits for already-started operations holding the relevant lock, and requests after its commit see the new version. It cannot pull an already-sent response back, and it is not a free concurrency optimization. The initial session lookup only locates the user; the session is reread after the user lock so stale discovery data is not the final decision.

<Code language="python">{getIdentityExample('db.py')}</Code>

Each request owns its Session and transaction; never share one Session between threads. The engine is a connection-pool entry point, not a logged-in user session. auth_sessions is a business table. READ COMMITTED is explicit; echo is false and SQL parameters are hidden. These are three distinct meanings of “session.”

## 6. Inputs, responses and logs are separate leakage paths

<Code language="python">{getIdentityExample('schemas.py')}</Code>

SecretStr masks common string representations, but login must still unwrap it with get_secret_value for verification. It does not encrypt HTTP, sanitize every exception automatically or manage shell history. New passwords must contain 15–128 characters, without trimming or implicit normalization. Length alone does not make a password safe; compromised-password screening and a complete account-recovery design remain release gates.

<Code language="python">{getIdentityExample('app.py')}</Code>

Observe three output boundaries. UserPublic returns only id/login/is_active. TokenResponse returns the original Bearer only on successful login, with no-store/no-cache response headers. Validation errors retain only allowed loc components and type, never input, ctx, msg or the original body. Unknown field names are replaced too: a secret can appear as a JSON key, not just a value.

Access logging is off; audit events contain fixed event names and server actor IDs, never submitted passwords, Bearers or Authorization. Integrity failures become generic 409 responses. Other SQLAlchemy failures become generic 503 responses without exception repr or traceback; hiding SQL parameters alone cannot make driver error text safe. Do not undo these boundaries with middleware that logs every request “for debugging.” Tests inspect both responses and real application/PostgreSQL logs. That is not automatic protection against future logging code or every unknown exception.

## 8. Exercise the lifecycle with a client that does not print tokens

Open another terminal in the same lab directory. The client sends only loopback requests, explicitly disables environment proxies with `ProxyHandler({})`, refuses redirects, prompts for passwords with getpass and stores tokens in a local mode-0600 session file without printing them. **Do not cat, commit or archive that file.** This is terminal-lab infrastructure, not advice to persist browser credentials in localStorage. A 127.0.0.1 URL alone is insufficient: urllib normally reads http_proxy, which could receive a local login password first. The regression sets proxy variables, removes no_proxy and uses owned loopback proxy/target listeners to prove the target receives requests while proxy and redirect-target counts remain zero. Do not assume OS defaults bypass the proxy.

<Code language="python">{getIdentityExample('client.py')}</Code>

```bash
uv run --locked python client.py --port 8061 --session .session-alice.json login Alice
uv run --locked python client.py --port 8061 --session .session-alice.json request GET /users/me
cp -p .session-alice.json .session-before-change.json
uv run --locked python client.py --port 8061 --session .session-alice.json change-password
uv run --locked python client.py --port 8061 --session .session-before-change.json request GET /users/me
```

Expect login 200, public user retrieval 200, password change 204 with an empty body, and 401 when using the old copy. After a successful change the client deletes its current token file, but the server's auth_version increment is what invalidates all old tokens. Log in with the new password before testing revocation:

```bash
uv run --locked python client.py --port 8061 --session .session-alice.json login Alice
uv run --locked python client.py --port 8061 --session .session-alice.json request POST /auth/logout-all
uv run --locked python client.py --port 8061 --session .session-alice.json request GET /users/me
```

The last request must be 401. /auth/logout revokes only the current session by setting revoked_at; another valid session remains usable. /auth/logout-all increments the account version and invalidates even the calling token. Passwords and tokens are not interchangeable; changing a password does not turn the old token into a new credential.

<details>
<summary>Lifecycle answer: does reenabling an account revive old tokens?</summary>

No. The operator's disable sets is_active=false and increments auth_version; enable increments it again. An old session fails the version check even if it has not expired and revoked_at is still empty. A newly enabled user must log in to obtain a session at the current version. Deleting a browser token cannot replace server revocation, and changing only the password hash cannot invalidate previously issued sessions without a check such as this one.

</details>
