Calling a JS async function executes its body up to suspension and returns a Promise. Python's `async def` defines a coroutine function; calling it produces a **coroutine object without starting its body**. That object represents one resumable execution. It is not an already-started request or an automatically queued background job. Discarding it normally produces `RuntimeWarning: coroutine was never awaited`, not completed work.

`await pending` advances that coroutine as part of the current execution. `asyncio.create_task(pending)` wraps it in a Task and schedules it on the running loop. The Task tracks execution, a result or exception, and cancellation state. Its owner must keep a reference and ultimately observe the outcome. This lab uses Python 3.13's **default task factory**, not the optional eager task factory; observations about not-yet-started Tasks are not universal claims about custom factories.

## 4. Four roles, not four threads

Consider one event-loop thread in a service process. The loop tracks ready callbacks and pending I/O and resumes eligible work. A Task drives its coroutine until completion, failure or a wait for something not yet ready. `await` expresses a dependency on an awaitable's result. It neither creates a thread nor guarantees suspension.

An already-ready awaitable can return immediately. One test waits on an Event that is already set and confirms that a queued callback still has not run. An unset Event instead suspends its waiter, allowing the loop to advance other work. Putting an already-completed await in a CPU loop therefore does not guarantee responsiveness.

`asyncio.run(main())` owns loop creation, execution and closure at a standalone program boundary. Inside an async framework, use the existing await chain rather than nesting run. Similarly, do not create loop-bound clients in one loop and store them in module globals for unrelated loops to reuse.

Read `creation`, `sequential`, then `scheduled` in this complete file. The last two demonstrations belong to the blocking section below.

An Event here is a same-loop, in-process gate. `set()` makes waiters eligible to continue; `wait()` suspends while it is unset. It does not carry a result or persist a message. Gates let us express “the child has entered” and “this child may finish” without guessing ordering from machine speed.

## 5. Direct awaits are sequential; scheduling permits overlap

`sequential` fully awaits A before calling and awaiting B. A's `sleep(0)` gives the loop a scheduling opportunity, but B does not yet exist. It cannot magically overlap. This resembles consecutive `await fetch(...)` calls in JS; the important difference is that merely calling two Python coroutine functions early still does not start either one.

`scheduled` creates two Tasks first. The owner waits for both entered gates, releases B and observes B's completion, then releases A. Ownership and the required completion order are explicit. A/B start order in the transcript reflects this default-loop run. The meaningful test requires **both starts before both-entered and both ends after it**; unrelated ready-queue ordering is not a business contract.

The owner's finally calls `drain`: cancel every unfinished child, then await all terminal outcomes with `gather(..., return_exceptions=True)`. This use of gather is for cleanup. Returned positions correspond to inputs, and exceptions/cancellations become result items so that one cancellation does not prevent observing the other child. It does not give arbitrary programs a “cancel siblings immediately on failure” policy. The normal path already observes its intended results; this small cleanup helper does not re-raise secondary failures. Production supervision that must retain those failures needs explicit reporting rather than silently discarding that list.

<details>
<summary>Explanation check: do two coroutine calls followed by two awaits overlap automatically?</summary>

No. Constructing a coroutine object does not add ready work to the loop. The first object starts when awaited; the second starts after the first finishes. Explicitly schedule both Tasks, or use a combinator with known scheduling semantics, and own both lifetimes. A separate trap is that await need not suspend: an already-set Event may return immediately.

## 6. Blocking means occupying the loop thread, not merely waiting a long time

`blocking` schedules a ready callback with `loop.call_soon`, then executes synchronous `time.sleep(0.02)` on the loop thread. The CPU may be idle during sleep, but the thread has not returned control to the loop. Consequently the callback has still not run when the synchronous region ends. It runs only after the deliberate `await asyncio.sleep(0)` checkpoint.

The assertion concerns callback order, not a fragile “should finish in 20 ms” threshold. This demonstrates the inability to interleave work; it is not a throughput benchmark, nor does every delayed callback identify the exact source of a blockage.

`offloaded` bridges a necessarily synchronous blocking library using `asyncio.to_thread`. The worker announces entry with `call_soon_threadsafe` and waits on a thread-specific `threading.Event`. Meanwhile the loop records progress, releases the thread, and explicitly awaits its completion. Do not call asyncio.Event.set directly from a worker thread. The two Event types belong to different concurrency models.

Keep pure title validation and small dictionary operations synchronous. Await genuinely async I/O clients. Consider a thread bridge for unavoidable synchronous I/O; putting CPU-heavy computation inside async does not create parallelism. Cancelling the Task awaiting to_thread **cannot forcibly stop the underlying thread**. The library needs its own timeout/stop protocol. Our example releases and joins its worker instead of leaving a background thread to chance.

## 7. Cancellation is a request, not an immediate interrupt or a successful result

The next file uses a real temporary file, not merely a “closed” log. `hold_file` acquires the file only when its body starts, enters try, announces entry, and waits for release. The owner waits for entry before cancelling, ensuring that acquisition has happened.

<Code language="python">{getAsyncModelExample('ownership.py')}</Code>

`task.cancel()` requests injection of `asyncio.CancelledError`; it does not synchronously stop a thread at an arbitrary instruction. The coroutine generally receives the request at a cancellable wait and passes through finally. The owner must still await the Task to observe its actual end. CancelledError inherits BaseException rather than ordinary Exception. A bare except or broad BaseException handler can accidentally turn shutdown into an ordinary network failure.

If you catch cancellation to record it, clean up and re-raise. Our worker does not intercept it at all: finally closes the file. The owner's except is a boundary observation of the cancellation it requested, not a conversion of business work into success. Cleanup can itself fail and obscure the original cancellation; a log line cannot establish an unconditional cleanup guarantee.

One important edge case: with the default factory, cancelling before a Task starts runs neither its body nor its finally. Since acquisition also lives in the body, there is nothing to release. If an outer function acquires a resource before handing it to a not-yet-started Task, the outer owner remains responsible for that resource.

## 8. A timeout is a cooperative budget, not forced termination

`timed_out` uses `asyncio.timeout(0)` to expire on the next loop turn. The current Task still acquires the file; its wait on an unset Event makes cancellation observable. Finally closes the file, and TimeoutError is caught outside the timeout context. Zero is a deterministic mechanism demonstration, not a recommended network budget.

The timeout context translates the cancellation it initiated into TimeoutError. Independent external cancellation should still propagate as CancelledError. Catch timeout outside the context so that the boundary between budget expiry and internal business exceptions remains clear. A real overall budget should include queuing, multiple attempts and backoff, not silently restart at each step.

This is cooperative: a blocked loop cannot run its timer promptly, and cleanup can take additional time. Do not promise that everything has stopped at exactly N seconds or conclude that an external write could not have happened. A02 distinguishes HTTP phase timeouts from the complete operation's deadline.

## 9. A concurrency limit does not make unlimited input free

<Code language="python">{getAsyncModelExample('capacity.py')}</Code>

A Semaphore counts permits. Entering `async with slots` acquires one or waits; exiting returns it. Meter counts admitted work, not Tasks waiting outside. With four Tasks and two permits, only two entered gates are set. Releasing one admitted job allows a replacement to enter. Both normal completion and cancellation decrement active in finally and return the permit through the context manager.

A semaphore created inside every request gives each request its own limit; it does not limit total pressure on a shared dependency. A02 creates one during the application lifetime. This demo creates at most four Tasks, and the independent variation permits eight. **A semaphore of two still leaves a million pre-created Tasks consuming memory.** Unbounded input needs bounded admission, backpressure and additional design.

Guided change: switch limit from 2 to 1 and then 3. Do not assert that execution time doubles or shrinks. Verify the new peak and zero active work at exit. Explain why cancelling a permit waiter must not return an extra permit it never acquired.
