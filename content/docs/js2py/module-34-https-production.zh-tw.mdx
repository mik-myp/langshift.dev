## 1. 發佈入口不是把 host 改成 0.0.0.0

在本地看到 JSON，只證明某條本地請求鏈路工作。讓受邀用戶可靠、安全地訪問，還要回答：域名解析到哪裡？誰證明這臺服務器的身份？加密在哪一跳終止？應用從哪個代理接收真實客戶端信息？錯誤與日誌會不會帶出 token？這些問題不能通過打開全部網卡和關閉證書驗證來解決。

本章前置 O02；HTTP 與身份概念來自前面的 H/S 階段。新能力是解釋 DNS→連接→TLS→代理→應用的責任分工，驗證證書失敗、轉發信任、生產錯誤和瀏覽器來源策略。獨立驗收是按實際認證方案寫可測試的入口約束。本章不購買域名、不申請公簽證書、不創建外部可見資源、不替用戶部署完整產品。

## 2. 先把名字、地址、端口、路徑分開

`https://lab.test:8443/probe` 中，https 選擇加密的 HTTP 連接，lab.test 是主機名，8443 是 TCP 目的端口，/probe 是連接後由 HTTP 應用處理的路徑。DNS 常用 A/AAAA 把名字關聯到 IPv4/IPv6 地址，不替應用選擇 /probe，也不存儲你的登錄會話。CNAME 是名字之間的別名關係，並不會自動給別名申請證書。

遞歸解析器和客戶端會緩存 DNS 結果；TTL 是緩存壽命的一部分，不是“改完記錄所有設備立即更新”的按鈕。若發佈只檢查 A，卻留下指向舊主機的 AAAA，部分客戶端可能走到不同服務。域名所有權、DNS配置和某臺機器的進程都需要分別記錄。

本例使用保留的 `.test` 名字，不改系統 hosts/DNS。curl 的 `--resolve` 只給這一次客戶端請求提供名字→地址映射，同時保留 URL 主機名用於 TLS SNI、證書主機名校驗和 HTTP Host。因此本地成功不證明任何公網 DNS 記錄已配置。生產模板用 `.invalid` 佔位，不能拿它去真實上線。

## 3. TLS 到底驗證什麼，不驗證什麼

TLS 在連接上協商加密與完整性保護，並讓客戶端校驗證書鏈、有效期、主機名等。服務端持有葉證書對應的私鑰；證書中的 subjectAltName 聲明它適用的名字。客戶端信任某個 CA 並不代表任何名字都能通過：用可信 CA 給 lab.test 籤的證書，不能冒充 wrong.test。

TLS 保護的是連接，不負責判斷 Bearer token 是否過期、Alice 是否屬於項目，也不修復應用越權。HTTPS 的鎖標識不是“這個業務可信”的通用認證。代理終止 TLS 後若用 HTTP 連接應用，明文存在於後一跳；本例把這一跳嚴格留在同主機 loopback。跨主機或不可信網絡必須重新設計傳輸保護，不能照抄這個本地上游地址。

本地臨時 CA 只是讓實驗擁有可控信任鏈。`--cacert` 對本次 curl 明確指定它；不安裝到系統信任庫。CA/葉私鑰只在自己的 /tmp 臨時目錄生成，目錄 0700、文件 0600，結束後刪除；證書有效期一天，每次重建而不打包舊密鑰。`-k` 會跳過關鍵驗證，不能當成證書驗收。

## 5. 雙終端請求：curl 是客戶端，不是服務器

終端 A 在實驗根目錄啟動；`--serve` 讓程序保持前臺，`--port 0` 讓系統挑空閒端口。程序打印公開 CA 路徑以及可複製的 `export CA=...`、`export PORT=...` 兩行。這裡的省略號是說明運行時值，不是要你輸入的路徑。把實際打印的兩行復制到終端 B，目錄仍保持實驗根目錄。變量是公開信任材料路徑和端口，不是私鑰或會話 token。

```bash
uv run --locked python tls_lab.py --serve --port 0
```

終端 B 先粘貼實際 export 行，再執行以下命令。curl 發起一次請求然後退出，不會創建監聽服務。`--noproxy '*'` 避免本機代理環境把教學請求送走；`--resolve` 為指定名字和端口映射 loopback；`--cacert` 選擇本地信任 CA；`--max-time` 限制總等待；`--include` 顯示 HTTP 響應頭；`-H` 添加請求頭。Bearer 內容是固定的虛構標記，不是可登錄憑證。

```bash
curl --silent --show-error --include --max-time 5 --noproxy '*'   --resolve "lab.test:$PORT:127.0.0.1" --cacert "$CA"   -H 'Authorization: Bearer demo-not-a-valid-session'   "https://lab.test:$PORT/probe"
```

預期 HTTP 200，scheme=https、host=lab.test、client=127.0.0.1、authorization_present=true。最後一個字段只證明某個頭被轉發，**絕不證明已認證**。想觀察失敗，分別省略 --cacert、把 resolve 和 URL 都改為 wrong.test；本輪 curl 均返回 60，尚未進入業務處理。不要把 60 當 HTTP 狀態碼。

完成後在終端 A 按 Ctrl+C，程序停止自己的邊緣服務與後端進程，刪除臨時密鑰。不要 killall、不要停止機器上所有 uvicorn。終端 B 的 CA 變量此時指向已刪除文件，複用它會報本地文件/信任錯誤；重新啟動必須複製新的運行時行。

## 6. 反向代理：沿每一跳追蹤請求和憑證

客戶端選擇一個服務器入口；**反向代理**代表後面的應用接收請求，再發起到上游的連接。對應用來說，直接 TCP 對端通常變成代理，而不是原始瀏覽器。代理可以終止 TLS、統一入口和限制請求，但不因此自動擁有用戶身份。Authorization 必須在需要的路由上原樣轉交認證層，不得寫訪問日誌或當普通調試字段回顯。

本地鏈路是 curl → loopback TLS 教學邊緣 → loopback HTTP Uvicorn → FastAPI。邊緣只轉發明確允許的頭，限制 body 為 4096 字節、超時和響應大小，拒絕不支持的傳輸形式，覆蓋 Forwarded 類信息。這個很小的實現用於觀察信任邊界，沒有 HTTP/2、WebSocket、流式轉發、完整抗走私解析或生產限流。**不要把它部署到公網。**

413 只是本教學邊緣的已測行為，不能反向宣稱 H04 或 S03 已有相同大小限制。生產必須在實際入口獨立實現並測試大小限制與登錄節流，包括越過正常代理直接打上游時的邊界。

## 7. 可信代理：一個頭不是網絡事實

任何客戶端都能發送 `X-Forwarded-For: 203.0.113.9` 或 `X-Forwarded-Proto: https`。若應用無條件相信，就可能把偽造 IP 寫進限流/審計，生成錯誤重定向，或者把 HTTP 當 HTTPS。`--proxy-headers` 只是啟用解釋，`--forwarded-allow-ips` 才約束允許哪個直接對端提供信息；`*` 意味著信任所有可達對端，不能為了“URL對了”隨手開啟。

實驗分三步：關閉代理信任時，偽造頭被忽略，scheme=http、client=127.0.0.1；通過可信邊緣時，邊緣覆蓋客戶的偽造值，應用看到 https 和真實的 loopback；直接由本機另一個客戶端連接受信 loopback 上游時，偽造 client **能被接受**。第三步揭示關鍵限制：信任 127.0.0.1 等於信任有能力訪問該上游的本機進程，不等於只信任那一個代理。

生產要把可信代理列表與真實網絡隔離、socket權限、進程賬戶、容器網絡一起審核。多層代理/託管CDN不能簡單套用一跳配置；要明確每跳是否清洗、追加、解釋哪個頭。來源 IP 即使可信，也不是用戶身份，不替代 Bearer 驗證和對象授權。

## 8. 生產錯誤：少返回不等於不記錄

debug 頁面、traceback、異常 repr、驗證錯誤中的 input/ctx 都可能把路徑、SQL參數、密碼或 token 送回客戶端。生產不應把“方便調試”視為默認公開接口。本地診斷 app 為每次請求生成自己的隨機 request id，500 只返回通用 detail，日誌只記錄安全事件名和關聯 id；請求體校驗只返回 loc/type，不回顯原值。

不要吞掉所有錯誤然後返回 200。客戶端仍看到 500/422，維護者仍能關聯事件，只是不把秘密搬進響應。真實運維需要受訪問控制的錯誤觀測、必要的安全上下文與告警；這個小型安全日誌演示不是完整可觀測性方案。本地 /fail 是為了觸發失敗，真實業務入口不該保留任意人可調用的故障按鈕。

## 9. 與 S01–S03 對齊：不透明 Bearer，不是 JWT 或 Cookie

後續整合使用 S 階段已經約定的身份方案：服務生成高熵不透明隨機會話 token；原值只在登錄成功時返回，數據庫保存 SHA-256 摘要、過期/撤銷狀態和會話 auth_version。每次請求查會話、有效期、用戶啟用狀態以及當前版本，再檢查項目成員與動作權限。HTTPS 保護運輸，代理轉發 Authorization，但**不替應用查數據庫**。

這不是 JWT 本地驗籤方案，沒有本章要配置的 JWT 公私鑰。退出、改密、停用或退出全部會話如何撤銷，由 S 階段的服務邏輯負責，不能因為代理緩存了成功響應就繞過重新檢查。S03 創建任務的 UUIDv4 Idempotency-Key 與 Idempotency-Replayed 也需要跨入口保留；冪等回執不是永久訪問權限。

本下載只驗證 `authorization_present`，沒有真實 token 數據庫；不能拿它的 200 當 S03 的登錄成功。完整上線必須接回 S03 的 DB-backed readiness、授權/撤銷/冪等測試，關閉訪問日誌中的憑證，配置並壓測登錄節流和請求體邊界。不要把“運維切片”替換成後門式簡化認證。

## 10. CORS：約束瀏覽器讀響應，不授權調用者

瀏覽器 origin 是 scheme、host、port 的組合；`https://frontend.lab.test:8444` 與 HTTP、不同端口或不同子域都不相同。前端顯式設置 Authorization 或特定內容類型時，瀏覽器可能先發 OPTIONS 預檢，詢問這個來源、方法和頭是否允許。預檢允許之後才發送相應實際請求；CORS 不是給請求體簽名，也不阻止非瀏覽器客戶直接調用。

本地 app 只允許精確的演示來源、GET/POST，以及 Authorization/Content-Type/Idempotency-Key 請求頭；通過 expose_headers 讓前端讀到關聯 id 與冪等重放頭。它不使用 Cookie，allow_credentials=False，也不使用 `*` 放行一切。完整 S API 還包括 PATCH/DELETE 等，整合時必須按真實路由補充方法並測試，不能假裝這個診斷 app 的兩種方法就是生產策略。

實驗分別驗證：允許來源預檢 200；其他來源預檢 400；但直接普通 GET 仍可得到 200，只是沒有 Access-Control-Allow-Origin。curl 不執行瀏覽器的讀取限制，因此**CORS 不能替代認證/授權**。實測 HTTP 頭也不是所有真實瀏覽器行為的驗收，實際前端聯調仍列為待驗證。

## 11. CSRF：按實際憑證機制判斷，不背“前後端分離就安全”

傳統 CSRF 利用瀏覽器在跨站請求上自動攜帶環境憑證，例如 Cookie，使惡意頁面代替已登錄用戶發請求。當前不透明 Bearer 由前端顯式放進 Authorization，服務不把 Cookie 當會話，因此不直接具有同樣的自動 Cookie 附帶路徑。但這不是“所有 CSRF/XSS 風險消失”：token 若被腳本竊取、來源錯誤放行、危險跳轉或調用邏輯把憑證送到錯誤地址，仍會失敗。

若以後改成 Cookie 會話，必須重新評估 SameSite、Secure、HttpOnly、來源/Referer 校驗、反 CSRF token、允許的安全方法和跨站業務流程，不能只把 CORS 的 allow_credentials 改為 true 就上線。HttpOnly 限制腳本讀 Cookie，不能阻止瀏覽器自動發送；Secure 限制 HTTPS 傳輸，也不證明請求由用戶有意發起。

S 階段演示前端可用短期內存 token，刷新後重新登錄；這降低某些持久存儲暴露，卻不抵禦當前頁面的 XSS。不要將長期 token 放 localStorage 當作默認萬金油，也不要在教學截圖、錯誤報告、代理日誌中複製真實 token。本章只使用虛構標記。

## 13. 分層排錯：不要用 -k 掩蓋不同故障

| 觀察 | 所在層 | 下一步 |
| --- | --- | --- |
| 域名解析失敗 | DNS/客戶端解析 | 檢查記錄或本地 --resolve；未到 TLS |
| Connection refused | 地址/端口/監聽 | 檢查自己進程和實際端口；不是證書錯誤 |
| curl 60 未知 CA | 信任鏈 | 用本輪公開 CA，檢查有效期，不用 -k |
| curl 60 名字不符 | URL 主機名 vs SAN | 脩名字/證書，不改認證代碼 |
| 502 | 代理到上游 | 看上游是否運行、地址/命名空間/超時 |
| 500/422 | 應用處理/輸入 | 對照脫敏 request id、loc/type，不回顯秘密 |
| 瀏覽器報 CORS，但 curl 有響應 | 瀏覽器讀取策略 | 檢查精確 origin、預檢頭、實際響應頭；仍單獨查認證 |
| scheme 錯誤或來源 IP 可偽造 | 轉發信任 | 查直接對端、頭清洗和可達性，別把 allow-ips 改成 * |

TLS 握手失敗與 HTTP 401/403 是不同階段。當前診斷 app 沒有 401/403 認證邏輯；這些必須在 S03 完整服務裡驗收。日誌只保留可以共享的分類與關聯 id，不復制 Authorization、Cookie、數據庫 URL 或私鑰。
