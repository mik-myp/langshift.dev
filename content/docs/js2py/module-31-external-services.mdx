## 1. A hint may fail; saving a task must not fail with it

Suppose tasks can display an optional priority hint. Putting a remote request inside the task-creation transaction can keep requests, connections and transactions occupied when that service slows down. Worse, a timeout does not establish that a remote effect never happened. Blind retries can duplicate notifications or bills.

We start with ownership: **core CRUD completes independently; hints have a separate endpoint; one application lifetime owns one outbound client; requests borrow it**. We contact no third party, transmit no user task text, and need no credentials.

## 3. Follow one request and identify each owner

Caller → local FastAPI → hint service → shared HTTPX client and pool → local fault service. On the return path, validate the dependency's data again and expose only approved states and enum values.

- The application owns the client, pool and dependency-wide semaphore. Requests borrow them.
- Each attempt owns a response stream and closes it on every exit. Closing a response is not closing the client; a connection may return to the pool for reuse.
- One hint operation owns the budget for queuing, attempts and backoff. Core CRUD never enters this call chain.
- Application shutdown closes the application client. One request must not close an object other requests are still borrowing.

This resembles sharing an API client in frontend code, but the server must handle concurrent borrowers, pool shutdown and cancellation. Creating the client at module import obscures ownership, loop affinity and test isolation. Creating a new AsyncClient in every request instead repeatedly rebuilds its pool and prevents reuse across requests.

## 4. From L14's with to async with: protocol before decorator

In L14, `@contextmanager` adapts an ordinary generator to with's entry/exit protocol. The necessary change here is that acquisition or release may await, so entry and exit await `__aenter__` and `__aexit__`. Merely writing async with does not make an arbitrary synchronous close nonblocking; the implementation must provide suitable asynchronous behavior.

Because managed_client is an async def containing yield, it is an **async generator function**, not the ordinary result-producing coroutine function from A01. `@asynccontextmanager` adapts it into an async context-manager factory. Use that manager with async with, rather than trying to await it directly.

<Code language="python">{getExternalServiceExample('lifecycle.py')}</Code>

Trace one lifetime:

1. validate_origin checks configuration before acquisition. On failure there is no client and no entered block to clean up later.
2. Constructing AsyncClient configures a pool; it normally does not establish a network connection yet. Connections are opened as requests need them.
3. The single yield lends the client to the async with body. The manager is suspended but retains ownership.
4. Normal block completion resumes after yield; an exception or cancellation resumes the exceptional path at that suspension point. Finally handles release in either case.
5. Exiting waits for client.aclose. Cleanup is not business rollback; effects that reached the remote system are not undone.

The adapter requires exactly one yield. Zero or multiple yields violate its protocol. When acquiring multiple resources, establish their cleanup boundaries progressively instead of acquiring everything first and hoping one final finally covers every partial failure. Async changes the ability to wait during entry/exit, not L14's ownership principles.

## 5. Cleanup can await too: why finally has a small shield

FastAPI/Starlette's concurrency foundations use AnyIO. We need only its cancellation-scope concept here, not another task-management API. Within an already-cancelled AnyIO scope, cancellation can be delivered again at each waiting checkpoint. Reaching finally therefore does not automatically make an awaited close safe.

`with anyio.move_on_after(2, shield=True)` creates a **bounded, synchronous context-manager cancellation scope**, so the syntax is with, not async with. The shield temporarily blocks cancellation from outer AnyIO scopes while aclose runs. Its own two-second cleanup budget remains effective. If that budget fires, cancel_called is true and we raise an explicit cleanup failure instead of claiming a successful close.

This does not make the whole request uncancellable. Only release is shielded; request cancellation still propagates. Nor does an AnyIO shield defend against arbitrary repeated raw Task.cancel calls, process termination or machine failure. Tests cover the asyncio backend, one Task cancellation and an already-cancelled AnyIO scope, not other backends or forced shutdown.

`client.is_closed` is useful but insufficient: an implementation may set its flag before finishing underlying cleanup. Later tests also require a real TCP peer to observe EOF and a closed client to reject reuse. A property or log message alone is not proof of connection release.

<details>
<summary>Explanation check: which object should a failed request close?</summary>

Close that request's response stream, return its permit, and propagate cancellation or return the defined fallback. Do not close the shared AsyncClient. The application closes that client on exit. Normal, exceptional and cancelled owner scopes all need cleanup. The manager's yield lends a resource; it does not permanently transfer ownership. Closing a connection also does not reverse a remote effect.

## 7. Four timeout phases versus one operation deadline

HTTPX connect concerns establishing a connection; read concerns waiting for the next response-data chunk; write concerns sending data; pool concerns waiting to acquire a pool connection. The values are neither a summed overall duration nor a promise that `Timeout(0.2)` ends the entire operation within 0.2 seconds. A peer that keeps sending small chunks inside the read-idle window can sustain a response for much longer.

The lifecycle spells out all four values. Connection limits constrain transport connections; HintService's semaphore limits whole logical operations, which can include two attempts and a backoff. These are related but distinct controls.

The outer `asyncio.timeout(self.deadline)` covers **semaphore wait → pool acquisition → network → bounded retries → backoff**. A timeout placed only inside _once leaves queuing and backoff outside the user-facing budget. One test occupies all permits and verifies that expiry occurs without sending a request. Another makes backoff exceed the remaining budget and verifies that no second attempt starts. These assert budget scope, not unstable millisecond performance thresholds.

The tiny values are teaching parameters. Cancellation remains cooperative: blocked loop code or slow cleanup may delay actual exit. A real system derives budgets from dependency SLOs, load, remaining request budget and failure policy rather than copying 0.2 or 0.7.

## 8. The complete adapter: narrow retries, untrusted responses, propagated cancellation

**First understand the async for that reads the body below.** `response.aiter_raw()` provides an asynchronous iterator of byte chunks, not an already-downloaded list. `async for` requests the next chunk and awaits that retrieval: it runs the loop body only after obtaining a chunk, then requests the next one after processing it. Waiting for unavailable data can yield to the event loop; already-ready data means an await need not switch tasks. This neither creates a Task per chunk nor downloads chunks in parallel.

An ordinary `for` uses the synchronous iteration protocol and cannot directly traverse this asynchronous-only object. Adding await inside an ordinary for body does not make its next-item retrieval asynchronous. The iterator signals exhaustion with `StopAsyncIteration`; async for handles that end signal and continues after the loop. Exhaustion is not invalid JSON or a network error to retry. Cancellation and other exceptions are not normal exhaustion.

The `_once` implementation below accumulates bytes in a `bytearray`. For each chunk it checks the retained length plus the new chunk's length against 1024 before calling `extend`. Suppose chunks contain 700 and then 400 bytes: the first leaves 700 retained bytes; the second is rejected before appending, so the buffer never reaches 1100. The limit counts bytes, not characters. A chunk is not a complete JSON message, and characters or JSON fragments may span chunks, so normal completion precedes validating `bytes(body)` with the model. This limit bounds the body retained here, not every larger allocation the underlying network stack might make.

Cancellation while awaiting the next chunk propagates out of the loop; async for itself does not close the response or shared client. The enclosing `async with client.stream(...)` exits this response's scope, then the outer permit scope returns the semaphore permit. The application lifespan still owns the shared client and closes the entire pool only at application exit. Do not convert cancellation into `StopAsyncIteration` or successful fallback, and do not mistake asynchronous cleanup for protection against forced termination.

Read from hint's outer scope into _once. Within the overall budget, hint takes a shared permit and tracks admitted work using active/peak. Finally decrements active; async with returns the permit. _once owns a response stream while checking status and body; success, invalid data and transient failure all leave that response scope.

This lab permits at most two attempts, and only for a read-only GET with 502/503/504 or specified ConnectError/ConnectTimeout/ReadTimeout failures. The first failure yields during a short backoff; a second returns unavailable. A 401 is an authentication/authorization problem, not permission to hammer retries. A 429 requires a rate-limit/Retry-After policy; we do not automatically retry it. Pool timeout indicates local capacity pressure rather than an invitation to amplify traffic. Production policies may also need jitter, rate limiting and shared retry budgets.

An external 200 is still untrusted. Require JSON, refuse redirects and encoded bodies, retain at most 1024 raw body bytes, and use a strict Pydantic model allowing only low/normal/high with no extra fields. This bounds **the body retained by our adapter**, not every peak allocation inside the network stack. Invalid JSON, wrong enums, HTML and oversized bodies become the same small fallback. Do not send the original body, URL or exception message to the caller.

InvalidHint represents non-retryable boundary data failure. TransientFailure names the narrow retry set; neither is a bucket for all exceptions. TimeoutError and HTTPX RequestError can become unavailable at this business boundary, but CancelledError is deliberately outside that catch set. Owner cancellation must stop the work, not silently retry or masquerade as a successful fallback.

## 14. Background execution is not reliable delivery

FastAPI BackgroundTasks can run work after a response has been sent, but that work remains in-process. Shutdown, failure or restart can lose it. An asyncio.Queue in memory does not become durable because its name includes “queue.” Neither is a persistent task system with acknowledgements, retry, deduplication and recovery semantics.

Consequently, this lab does not quietly send a must-deliver notification after saving a task, nor launch an unobserved create_task. If notification delivery becomes a requirement, separately design consistency between database commit and task recording, durable delivery and recoverable consumers. One background-call line appended to this adapter cannot provide those guarantees.
