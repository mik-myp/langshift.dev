## 1. Real requests need a runtime boundary, not just annotations

A TypeScript interface cannot stop an external client from sending arbitrary JSON. An ordinary Python function annotation does not automatically reject an invalid value either. H03 rejected parameters because FastAPI actively read declarations and performed validation, not because Python's int annotation became a runtime checker. We now extend that boundary to an entire request body and add an equally important boundary on the way out: data known to the server is not necessarily data it should return.

Use only loopback, disposable data, and sequential operations. H06 will teach API test automation. For now, explainable curl requests are the acceptance method; successfully constructing a model is not a substitute for a network request.

This is a limited capstone V1 contract, not the final multi-user project model. We retain title, minutes, and done from the language work and add note and a server id. Later project_id, creator identity, and status enums require explicit evolution; none are secretly assumed to exist already.

## 2. Decide fields and routes before choosing an implementation

| Field | Creating a task | PATCH meaning | Public response |
| --- | --- | --- | --- |
| title | Required str, 1–120 characters, not entirely whitespace; preserve original spelling and surrounding spaces | Omitted: preserve; valid string: replace; null: reject | Original string |
| minutes | Required nonnegative ordinary int; reject bool, text, and float | Omitted: preserve; valid integer including 0: replace; null: reject | Integer |
| done | Strict bool; omitted defaults to False | Omitted: preserve; apply both true and false; reject null | Boolean |
| note | str or None, at most 1000 characters; omission defaults to None; empty string allowed | Omitted: preserve; string: replace; null: clear | String or null |
| id | Client may not supply it; generated as a process-local increasing positive integer | Cannot change | Positive integer |
| internal_tag | Client may not supply it; server sets h04-memory-only | Cannot change | Never returned |

Lengths use Python string length, not UTF-8 bytes or visual grapheme counts. We do not strip the stored title: checking for non-whitespace and normalizing input are different business decisions. Supplying id, user_id, or any unknown key produces 422. **Rejecting user_id is not authentication**; this service has no trusted user identity at all.

| Route | Success | Important failure or meaning |
| --- | --- | --- |
| GET /health | 200 | Only indicates that this process can answer |
| POST /tasks | 201, full public task | Missing body fields, types, unknown keys, or constraints: 422 |
| GET /tasks | 200, items/limit/offset/total | limit defaults to 20, range 1–100; offset defaults to 0, nonnegative; invalid values: 422 |
| GET `/tasks/{task_id}` | 200, public task | Valid but missing id: 404; invalid path argument: 422 |
| PATCH `/tasks/{task_id}` | 200, complete updated public task | Empty object: no change; invalid fields: 422; missing record: 404 |
| DELETE `/tasks/{task_id}` | 204, no body | Missing record: 404, including a repeated delete |

Lists are ordered by increasing id; total counts the whole collection. There is no PUT, user isolation, status filtering, or write-idempotency key. We make assertions about individually constructed failure cases. Do not assume that a request with both an invalid body and a nonexistent id must always report 404 first.

## 3. Three shapes represent three different kinds of trust

```text
untrusted JSON -> TaskCreate / TaskPatch -> handler
                                               |
                           TaskStored -> in-memory tasks
                                               |
                           TaskPublic / TaskPage -> JSON response
```

An input model allows only decisions assigned to the client. A storage model adds server-owned data. A public model lists permitted output fields. These are not three names for the same dictionary. Even when their fields overlap today, adding an internal field tomorrow should not silently expand the public API.

<Code language="python">{getValidationExample('models.py')}</Code>

BaseModel is Pydantic's model base class. Inheriting it makes the library execute field declarations during construction or model_validate. Field adds length and numeric constraints; it is not a database column. ConfigDict declares policy: strict=True chooses strict typing, extra="forbid" rejects unknown input fields, and validate_default=True checks the model author's defaults too, instead of trusting a mistaken default automatically.

min_length=1 cannot enforce a nonblank title: a single space has length one. By default, field_validator("title") runs after ordinary type and Field checks, so value is already a string. classmethod supplies the model class as cls, not a request instance; the outer decorator registers the check with Pydantic. Raising ValueError becomes part of a ValidationError, which FastAPI turns into 422. On success, return value. Returning value.strip() instead would silently violate our spelling-preservation contract.

TaskPatch and TaskStored inherit TaskCreate's rules and validator, then override or add fields. TaskPublic is deliberately separate and uses extra="ignore" to discard surplus internal keys. This is a different policy from forbidding extra input. TaskPage declares items as list[TaskPublic], so each nested record crosses the public boundary, not merely the top-level response object.

## 4. Coercion is a policy, and strictness has a defined scope

Before starting the service, run this self-contained model experiment:

<Code language="python">{getValidationExample('probe_models.py')}</Code>

```bash
uv sync --locked
uv run --locked python probe_models.py
```

```text
loose: 25
True int_type
'25' int_type
25.0 int_type
-1 greater_than_equal
strict: {'title': '  Read HTTP  ', 'minutes': 0, 'done': False, 'note': None}
nullable but missing: missing
nullable and present: {'note': None}
```

LooseMinutes has no strict configuration and converts text "25" into integer 25. That can fit some form boundaries, but it does not fit our task JSON contract. TaskCreate's strict=True rejects the shown cross-type conversions. Although Python bool is a subclass of int, true is not a valid minutes value here. Likewise 25.0 is numerically equal to 25 but is still a float. ge=0 is a separate constraint: -1 has the right type but the wrong value. done accepts neither the string "false" nor integer 0/1 as a boolean substitute.

The probe's show_error simply calls the operation passed to it, catches ValidationError, and prints its first error type. Each lambda is a no-argument function called immediately by show_error, not a queued or background task. The last two lines isolate nullable versus optional behavior, explained next.

Strictness applies to the body models. A URL's limit=20 begins as text, so Query and Path still parse numeric text. Mechanically adding strict=True to URL parameters would reject the very representation the transport provides. Pydantic's strict rules also differ for some types and for Python versus direct JSON input. These basic-field experiments do not establish “no coercion anywhere in the library.”

## 5. Required, defaulted, and nullable are separate questions

For every field, ask: may the key be omitted? May its value be null? What value results if it is omitted?

| Declaration's meaning | Omitted | Explicit null |
| --- | --- | --- |
| note: str | Missing required field | Type error |
| note: str or None, no default | Still missing a required field | Valid None |
| note: str or None, default None | Gets None | Valid None |
| done: bool, default False | Gets False | Type error |

JSON null becomes Python None, but not sending a key is not the same as sending None. During creation, omitting note and explicitly sending null both produce None. During an update, the intentions differ, so we must retain information about which keys the client supplied. A truthiness check cannot answer that question: it would discard legitimate False, 0, and empty-string values too.

<details>
<summary>Explanation checkpoint: why can a required nullable field report missing?</summary>

A union enlarges the allowed set of values; it does not provide a default. RequiredNullable() supplies no note and therefore fails. RequiredNullable(note=None) supplies a permitted empty value. When drawing a TypeScript analogy, distinguish an optional property from a property whose value can be null. In TaskPublic, note must appear but may be null, so the public response includes the key consistently rather than only when it has text.

</details>

The POST parameter payload: TaskCreate tells FastAPI to construct that model from the JSON body. It is neither a path parameter nor dependency injection. Only successful validation reaches the handler. payload.model_dump() converts validated fields to an ordinary Python dictionary. The `**` operator expands that dictionary into keyword arguments, while TaskStored adds the server id and internal default. Only after construction succeeds do we write tasks and increment next_id. Invalid creations therefore do not consume ids in our sequential experiment.

global next_id makes assignment update the module-level counter rather than create a local variable. It is not a thread lock. The store maps ids to TaskStored instances and exists only in this process's memory. require_task is an ordinary helper called by handlers; it is neither Depends nor an authorization check.

PATCH first retrieves the old record, merges supplied fields in a temporary dictionary, and validates the complete candidate before replacing the stored record. This avoids a partially applied invalid update in one sequential request. It is not a database transaction and does not prevent two requests from reading the same old state and overwriting each other.

DELETE checks existence, removes the record, and explicitly returns Response(status_code=204), because 204 has no JSON body. Returning None is not a reason to send JSON null. Task-returning routes instead return dictionaries and let response_model validate/filter them; they do not build a Response that bypasses the ordinary model path.

## 7. PATCH depends on what was supplied, not what looks nonempty

Every TaskPatch field can be omitted, but title, minutes, and done do not become nullable. To construct a model when keys are absent, title has the valid placeholder Untitled, minutes has 0, done inherits False, and note inherits None. These are internal model defaults, **not replacement values to write into storage**. Documentation may display those defaults; the PATCH contract remains “omitted means unchanged.” Creation still requires title and minutes.

model_dump(exclude_unset=True) selects fields by whether input explicitly set them, not by whether their values differ from defaults. An empty body produces empty changes. Explicit done=false is retained even though it equals the default; explicit note=null is retained too. Sending title="Untitled" is also a legitimate update and must not disappear merely because it equals the placeholder.

<Code language="python">{getValidationExample('probe_patch.py')}</Code>

```bash
uv run --locked python probe_patch.py
```

Each iteration begins with the same original. Read sent, changes, and merged in order. The final three deliberately wrong results are:

```text
WRONG dump of empty patch: {'title': 'Untitled', 'minutes': 0, 'done': False, 'note': None}
WRONG exclude_none: {}
WRONG exclude_defaults: {}
```

Merging the first would replace every old field with a placeholder. The second loses an explicit instruction to clear note. The third loses an instruction to turn done from True back to False. exclude_unset, exclude_none, and exclude_defaults answer different questions; similar names do not make them interchangeable.

We validate the merged dictionary with TaskStored.model_validate rather than treating model_copy(update=...) as revalidation. Pydantic's copy updates do not automatically validate the provided update data. Likewise, directly assigning current.minutes is not a promise of complete model checking. Revalidating the whole candidate becomes especially important with future cross-field rules, but advanced validators are not introduced as a hidden prerequisite here.

## 8. First real creation and rejection: keep status and body together

In terminal B, with terminal A running a freshly started empty service:

```bash
curl -sS -i http://127.0.0.1:8004/tasks
curl -sS -i -X POST http://127.0.0.1:8004/tasks \
  -H 'Content-Type: application/json' \
  --data-binary '{"title":"  Read HTTP  ","minutes":25,"note":"keep me"}'
```

-X selects the method, -H declares JSON, and --data-binary sends the supplied body. Single quotes protect JSON's double quotes. true and null are JSON literals, not Python True and None. -i exposes the status line; the body alone cannot tell you whether the response was 200 or 201.

The actual creation response, omitting dynamic headers, is:

```http
HTTP/1.1 201 Created
content-type: application/json

{"id":1,"title":"  Read HTTP  ","minutes":25,"done":false,"note":"keep me"}
```

Now send minutes as true:

```bash
curl -sS -i -X POST http://127.0.0.1:8004/tasks \
  -H 'Content-Type: application/json' \
  --data-binary '{"title":"Bad","minutes":true}'
```

The observed status is 422 and the body is:

```json
{"detail":[{"type":"int_type","loc":["body","minutes"],"msg":"Input should be a valid integer","input":true}]}
```

loc identifies body/minutes, not path/task_id. Correct the client's value and retry; removing strict=True to accommodate this request changes the contract instead of fixing the client. Validation never reached create_task, so no record was created. Error responses can echo invalid input. We use fictional data only; production still needs deliberate redaction and error policies rather than assuming a model automatically protects secrets.

## 9. Stored data and public data are different boundaries

The created record really contains internal_tag. To make filtering observable, each task handler deliberately returns the entire storage dictionary, including that key. response_model=TaskPublic is the final HTTP output allowlist. The list route applies the same boundary through TaskPage.items. Inspect POST, single GET, PATCH, and the list rather than proving filtering for only one route.

Why not use TaskCreate as the output model? It lacks id. Why not use TaskStored? It would expose internal fields. Why not silently ignore all unknown input? Client typos could appear to succeed, and attempted identity fields would no longer receive a clear rejection. Input forbid and output ignore are deliberate, different responsibilities.

If the handler omits a required public field or returns a wrong type, output validation is a server error, not a client 422. The producer of that invalid data is your service code. Repair it instead of removing response_model to hide the problem. Manually returned Response objects can bypass ordinary model processing; only the bodyless 204 uses that path here.

The internal field is not an example of storing secrets. Filtering constrains response shape, not whether a caller is entitled to read a task. Even perfect removal of internal_tag does not make an API without authentication and object-level authorization safe for real users.

<details>
<summary>Boundary checkpoint: does hiding user_id create user isolation?</summary>

No. Models check shape and the declared rules; they do not establish who called or who owns a task. This service rejects user_id and never uses it as an authorization claim. All local callers share one dictionary. Filtering keeps surplus fields out of responses, but every caller who can reach this service can still operate on all tasks. Authentication and membership checks require later implementation and separate acceptance.

</details>

## 12. Honest memory limits and a resumable checkpoint

Ordinary def handlers run in a thread pool; workers=1 does not eliminate concurrency. Reading next_id, writing a dictionary entry, and incrementing the counter are not a single business-level atomic operation. Two PATCH requests can both read an old record and lose each other's changes. Multiple worker processes would also hold separate, divergent dictionaries. Without a deliberate database, transaction, constraint, or locking design, we claim no concurrent correctness. L11–L14's types, model helpers, and resource cleanup functions do not supply those guarantees.

We verified **input/output behavior under sequential requests**. Unverified boundaries include concurrent load, cross-process consistency, persistence, identity and object authorization, idempotent retry, browser CORS, proxies, HTTPS, production redaction, capacity, and memory limits. Replacing a record only after candidate validation avoids writes during this request's validation failure; it is not a transaction system.

A useful pause record is:

```text
checkpoint: H04 PATCH and output boundary
cwd: <my extracted h04-validation directory>

```
