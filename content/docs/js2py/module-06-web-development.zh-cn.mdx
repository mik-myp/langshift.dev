## 1. 想复用一个函数，不想顺便运行整个程序

## 2. 内置能力、标准库、本地模块和第三方包不是一回事

`task_rules.py` 故意打印一条初始化标记。它是观察执行过程的实验工具，不是在推荐可复用模块都应该在导入时打印。

<Code language="python">{getModuleExample('first_import/task_rules.py')}</Code>

`report.py`：

<Code language="python">{getModuleExample('first_import/report.py')}</Code>

从实验根目录运行：

```bash
uv run --no-project --python 3.13 python first_import/report.py
```

```text
task_rules initialized
Default: 20
Buffered: 25
```

按顺序追踪，而不是只记住两种语法：

1. Python 开始执行 `report.py`，遇到 `import task_rules`。
2. 在这个新进程里，它找到相邻的 `task_rules.py`，创建模块对象并执行顶层代码：先打印标记，再绑定常量，再由 `def` 创建函数。此时没有调用函数体。
3. 导入语句在调用方绑定名称 `task_rules`，让它指向那个模块对象。
4. `task_rules.DEFAULT_MINUTES` 在模块的命名空间中查找属性；`task_rules.add_buffer(20)` 先取得函数，再调用它。

两个模块不会把全局名称合并在一起。`task_rules.py` 的全局名称属于这个模块，不属于进程中的所有文件。这里的“独立”指组织方式，不是保密机制：调用方仍然能通过模块对象访问公开属性。命名空间不是权限控制边界。

`task_rules.py` 对应的导入名称是 `task_rules`，不带 `.py`。采用清晰、符合标识符习惯的文件名，不要写成 `task-rules.py`，也不要与打算使用的模块重名。第 10 节会实际定位一次重名问题。

## 4. 几种导入形式：到底在当前文件中建立了哪个名称？

文件：`first_import/import_styles.py`。

<Code language="python">{getModuleExample('first_import/import_styles.py')}</Code>

```bash
uv run --no-project --python 3.13 python first_import/import_styles.py
```

```text
task_rules initialized
Alias: 20
Direct names: 20 25
```

| 语句 | 调用方得到的名称 | 使用方式 |
| --- | --- | --- |
| `import task_rules` | `task_rules`，指向模块 | `task_rules.add_buffer(20)` |
| `import task_rules as rules` | `rules`，同样指向模块 | `rules.add_buffer(20)` |
| `from task_rules import DEFAULT_MINUTES` | `DEFAULT_MINUTES`，指向取出的对象 | `DEFAULT_MINUTES` |
| `from task_rules import add_buffer as buffered` | `buffered`，指向取出的函数 | `buffered(20)` |

`from` 不会跳过模块加载，也不是挑选几行源码执行。它改变的是最后建立的名称绑定。别名改变调用方的叫法，不会重命名源文件或改写原函数。多个模块都有类似名称时，保留来源通常更容易阅读；不要用通配符导入把名称来源隐藏起来。

现在故意运行 `first_import/missing_name.py`：

<Code language="python">{getModuleExample('first_import/missing_name.py')}</Code>

```bash
uv run --no-project --python 3.13 python first_import/missing_name.py
```

程序先打印初始化标记和 25，再在 `task_rules.DEFAULT_MINUTES` 处抛出 `NameError`。模块已经加载，但**调用方只绑定了 `add_buffer`，没有绑定名称 `task_rules`**。修复实际需要的绑定：用 `import task_rules` 配合限定访问，或者明确导入那个常量。安装任何依赖都不能修复这个名称错误。

## 5. 同进程内复用，以及为什么 from 不是 ESM 的实时绑定

文件：`first_import/import_twice.py`。

<Code language="python">{getModuleExample('first_import/import_twice.py')}</Code>

```bash
uv run --no-project --python 3.13 python first_import/import_twice.py
```

```text
task_rules initialized
Same module: True
Buffered: 25
```

在这个解释器里按普通方式导入同一个模块名称，会复用内存中的缓存（`sys.modules`）。两个别名指向同一个模块对象，初始化标记只出现一次。再次运行终端命令会启动新进程，标记也会重新出现。修改源码不会让已运行进程中的模块自动重新执行；本章的处理方式是结束旧进程，再重新启动。

这**不是**“一个物理文件永远只会执行一次”的保证。作为 `__main__` 执行，和之后换一个导入名称加载，是不同身份；重新加载与手动操作缓存也是另一些情况，本章暂不展开。不要把“导入永远只发生一次”当成业务可靠性的依据。

### 重绑定与修改仍然遵循 L01、L02

`bindings/settings.py`：

<Code language="python">{getModuleExample('bindings/settings.py')}</Code>

`bindings/observe.py`：

<Code language="python">{getModuleExample('bindings/observe.py')}</Code>

```bash
uv run --no-project --python 3.13 python bindings/observe.py
```

```text
Initial: 20 20
Rebound: 20 40 40
Shared: ['python', 'modules'] ['python', 'modules']
Local tags: ['local'] ['python', 'modules']
```

画出两个命名空间：最初调用方的 `BUDGET` 与 `settings.BUDGET` 都指向 20。`settings.BUDGET = 40` 改变模块内部的绑定，不会把调用方的独立名称也改为 40。`current_budget()` 读取的是函数**定义所在模块**的全局名称，所以即使这个函数被直接导入，调用结果仍然是 40。

大写 `BUDGET` 是命名约定，不会强制对象或名称不可修改。

两个 `tags` 最初指向同一个列表。通过其中一个引用追加内容，会修改那个列表，所以另一方也看得到；把调用方的 `tags` 重新绑定到新列表，则把两个绑定分开了。**`from` 既不是深复制，也不是对未来重绑定的实时连接。**

JavaScript 的 **ES 模块**使用实时导入绑定：导出方改变绑定，导入方可以观察到；导入方不能直接对那个导入绑定重新赋值。Python 的直接导入名称可以在本地重新绑定。这个对照只讨论 ESM，不把所有 CommonJS 或打包器转换都一概而论。应迁移你对引用的理解，而不是假设同样叫 `import` 就一定有同样语义。

### 两种缓存，解决两个不同问题

此时目录里可能出现 `__pycache__/` 和 `.pyc` 文件。CPython 可以把编译后的代码缓存到磁盘，减少重复编译；它们不是你维护的源码，不需要复制进作业或下载包。它们不会保存上一个进程的变量，也不会让新进程跳过模块初始化。内存中的模块复用与磁盘字节码缓存解释的是不同现象。

## 7. 三个经常被混淆的位置

学习包之前，先让运行上下文可见。文件：`locations/show_context.py`。

<Code language="python">{getModuleExample('locations/show_context.py')}</Code>

- `os.getcwd()` 返回进程的**当前工作目录**；本实验从启动它的终端继承这个目录。
- `__file__` 在这些普通文件示例里标识当前源码文件。
- `sys.path` 是 Python 搜索模块的目录列表；`[0]` 取下面普通命令中的第一项。它不是 Shell 的 `PATH`，后者用来寻找可执行命令。
- `__name__` 标识当前执行的模块，不是目录。

在没有隔离/安全路径选项或自定义路径配置时，直接运行文件会把脚本所在目录放到搜索路径开头；`-m` 从当前目录开始寻找指定模块。其他搜索位置还包括 Python 的库目录；内置模块也有自己的导入处理。因此，不要把所有导入规则简化成“永远在写 import 的那个文件旁边找”。

从实验根目录执行：

```bash
uv run --no-project --python 3.13 python locations/show_context.py
```

这里的路径输出用 `<LAB>` 代表你实际解压目录的绝对路径；它**不是要输入的文本**：

```text
Name: __main__
Cwd: <LAB>
File: <LAB>/locations/show_context.py
First search: <LAB>/locations
```

现在明确改变终端目录：

```bash
cd locations
uv run --no-project --python 3.13 python show_context.py
uv run --no-project --python 3.13 python -m show_context
cd ..
```

两条 Python 命令都输出：

```text
Name: __main__
Cwd: <LAB>/locations
File: <LAB>/locations/show_context.py
First search: <LAB>/locations
```

`-m` 的意思是“按名称找到模块，再把它作为入口运行”。参数是 `show_context`，**不是** `show_context.py` 或文件系统路径。上方用 `/` 展示路径，不同操作系统的格式可能不同。运行脚本本身不会自动把当前目录切换到脚本所在目录；L07 读取相对文件路径时，这个区别还会再次出现。

不要用向 `sys.path` 追加路径或设置 `PYTHONPATH` 来掩盖当前的混淆。先记录实际目录与完整命令。这些实验刻意使用正常的本地导入行为；隔离运行的 `python -I` 会去掉本地搜索位置，不能随意替换进去。

## 9. 故意选错一次入口命令

仍在 `package_demo` 中，执行下面这个**预期失败**：

```bash
uv run --no-project --python 3.13 python task_tools/app.py
```

最后的错误指出 `ImportError: attempted relative import with no known parent package`。直接执行磁盘文件路径，并不会建立 `.report` 所需的 `task_tools` 包上下文。入口保护条件也救不了它：导入在到达条件之前就失败了。仅仅增加 `__init__.py` 不能改变一个文件被直接启动的方式。

应在包外层目录使用支持的 `python -m task_tools.app`，而不是删除点号或者修补 `sys.path`。再回到实验根目录，观察另一个**预期失败**：

```bash

uv run --no-project --python 3.13 python -m task_tools.app
```

在实验的正常环境中，Python 从这里找不到 `task_tools`，因为它放在 `package_demo` 内部；错误包含 `ModuleNotFoundError`。修复的是命令要求的工作目录，不是安装一个恰好同名的其他包。一条可复现说明必须包含**文件布局 + 工作目录 + 解释器 + 命令**，不能只留最后一个文件名。

## 10. 区分模块缺失、名称缺失与同名遮蔽

现在已回到实验根目录。文件 `missing_module.py` 故意包含运行时错误：

<Code language="python">{getModuleExample('missing_module.py')}</Code>

```bash
uv run --no-project --python 3.13 python missing_module.py
```

它因刻意不存在的模块抛出 `ModuleNotFoundError`。先问：这个名称应该来自本地文件、标准库还是已经安装的依赖？再检查拼写、位置、所用解释器和实际失败的导入。traceback 也可能指向被导入模块**内部的依赖**，不一定就是你写的最外层 import。不要把所有导入错误都当成需要安装软件。

`first_import/missing_export.py` 找得到模块，却要求一个模块没有定义的名称：

<Code language="python">{getModuleExample('first_import/missing_export.py')}</Code>

```bash

```

它先打印初始化标记，再因 `remove_buffer` 抛出 `ImportError`。对比前面的 `NameError`：模块是否加载、模块是否拥有某个属性、调用方是否绑定某个名称，是三件分别检查的事情。

### 本地文件可能把你真正想要的模块遮住

`shadowing/statistics.py` 故意采用了不合适的名称：

<Code language="python">{getModuleExample('shadowing/statistics.py')}</Code>

`shadowing/show_source.py`：

<Code language="python">{getModuleExample('shadowing/show_source.py')}</Code>

```bash
uv run --no-project --python 3.13 python shadowing/show_source.py
```

在缺少 `mean` 的 `AttributeError` 之前，标准输出揭示了真正加载的文件：

```text
Loaded: <LAB>/shadowing/statistics.py
```

这条命令先找到本地同名文件，没有加载你希望使用的标准库 `statistics`。在该实验的一个**副本**中，用编辑器将本地文件重命名为 `practice_statistics.py`，再用新进程运行 `show_source.py`。此时 `Loaded:` 指向 Python 标准库，下一行变为 `Average: 25`。

重命名文件不会更换运行中解释器已经缓存的模块。应检查来源路径并重启进程，而不是反复安装包或删除无关文件。`__file__` 对这些文件型模块很有用，但并非所有模块都有它，例如某些内置模块就没有。

| 现象 | 首先检查什么 |
| --- | --- |
| ModuleNotFoundError | 到底缺少哪个模块？从哪个运行上下文寻找？ |
| 具名导入的 ImportError | 模块是否已经建立那个名称？是否与初始化顺序有关？ |
| 调用方的 NameError | 这种导入形式是否绑定了正在使用的名称？ |
| 模块属性的 AttributeError | 实际加载的是哪个模块对象？它是否有该属性？ |
| 导入时意外出现业务输出 | 哪个顶层业务调用被执行了？ |
