## 2. Calling a generator function does not execute its body immediately

An ordinary call typically executes until returning or raising. With yield in its body, calling a generator function creates a generator object; execution starts when a consumer first requests an item. yield supplies a value and suspends, retaining locals and the execution position. The next request resumes after that suspension rather than restarting the body.

The consumer may be next, for, or list. for handles normal exhaustion; manual next raises StopIteration when exhausted. An exhausted generator is not a replayable array. Call the generator function again to establish a new iteration.

tracked_minutes records events to expose mechanics; it does not hold a real system resource. It validates each value only when about to yield it, so earlier items may have been consumed before a later failure. Lazy validation differs from L11's requirement to validate everything before returning a match. Saving memory alone does not justify replacing one policy with the other.

`Generator[int]` and `Generator[str]` describe the actual generator objects, including iteration and close. The single yielded-type parameter form fits the Python 3.13 baseline. These are not lists. Later, `Iterator[TextIO]` describes an iteration yielding a text file for contextmanager to adapt; bidirectional generator type parameters are not required here.

## 3. Draw suspension and cleanup on a timeline

```python
from collections.abc import Generator


def numbers() -> Generator[int]:
    print("start")
    try:
        yield 30
        print("resume")
        yield 0
    finally:
        print("finish")


values = numbers()
print("created")
print(next(values))
print(list(values))
print(list(values))
```

```text
created
start
30
resume
finish
[0]
[]
```

created precedes start because construction did not enter the body. list(values) consumes the remaining process: resume is printed, normal completion runs finally, then the collected [0] reaches print. The second list is empty; it does not restart the generator.

finally participates in normal completion, exception propagation, and closing a generator suspended within that try block. **Closing a never-started generator does not first execute its body or finally.** Acquiring a resource inside the body therefore means it has not been acquired before starting. Acquiring outside and returning another generator needs a separate ownership design.

## 4. break ends a loop, not an ownership protocol

<Code language="python">{getResourceExample('break_demo.py')}</Code>

```bash

uv run --locked python break_demo.py
```

```text
30
['started', 'yield 30']
['started', 'yield 30', 'finished']
```

After break, values still references the suspended generator and finally has not run. Explicit close triggers cleanup here. Do not depend on an interpreter immediately reclaiming an incidental temporary object or on process-exit cleanup as a stable resource policy.

close finishes the suspended generator; later iteration produces no values. Closing before start produces no acquisition/release events, and closing an already closed generator does not repeat cleanup. Ordinary business code need not inject exceptions manually. It does need an explicit consumer and owner responsible for closure.

## 5. A file generator must release even when you read less

lines_from opens the file when iteration actually starts and yields lines with the trailing newline removed, preserving blank lines. While suspended at yield, execution is still inside the file's with block and the handle remains open. Exhaustion exits that block; early stopping requires a reliable consumer-side exit boundary.

`contextlib.closing` accepts an object with close and calls that method when its with block exits, including through break or an exception. It does not turn arbitrary objects into generators or undo business effects. Having yield does not by itself make a raw generator a with-compatible context manager.

The app below includes the complete first-line-only use. There are two ownership layers: closing closes the generator; generator termination exits its internal with and closes the file. Proving that printing stopped is not proof of underlying release.

## 6. Expand with: the manager and the supplied value can differ

The class version implements two special methods. __enter__ acquires the resource and returns the value supplied to the body; __exit__ defines the exit policy. In `with TextFile(...) as handle`, handle is the actual file returned by __enter__, not the TextFile manager itself.

<Code language="python">{getResourceExample('resources.py')}</Code>

Read TextFile first. Entry records acquire-attempt and, after successful open, acquired. Normal body completion supplies three None values to __exit__. A body exception supplies its type, instance, and traceback. The unused traceback parameter carries diagnostic information; its internal structure and advanced annotations are not prerequisites here.

Returning False declines to suppress the body exception. Returning True suppresses it and requires a deliberate policy. If __enter__ fails while opening, the body never runs and __exit__ is not called for that unentered context. When acquiring multiple resources, establish a release boundary for each instead of assuming the final with manages all prior failures.

This simple TextFile is not promised to support nested reuse of the same instance. Construct a fresh manager for each with to avoid overwriting a previous handle. If close itself fails during error handling, another exception can result; this chapter does not claim exhaustive coverage of disk and operating-system failures.

## 7. contextmanager adapts an exactly-one-yield protocol

Now read opened_text. @contextmanager accepts a generator function and produces a factory for with-compatible managers. Entry runs to yield and supplies the file to the body. Exit resumes that suspension: normal exit continues, while exceptional exit throws the body's exception at the suspended yield, allowing finally to close the handle.

This is neither background execution nor coroutine scheduling. Before yield is acquisition, the yielded value is for use, and finally handles release. Successful entry must yield exactly once; yielding zero or twice violates the protocol. An open failure may raise immediately rather than supplying a fake resource to satisfy a yield count.

A manager instance is not a general reentrant object; call opened_text(...) afresh for each use. Logging and reraising an exception can aid diagnosis. Catching without reraising can instead turn failure into success, as the next experiment demonstrates.

## 11. Independent variation: a new report, not a pretend transaction

Implement new_report(path, events). It may only create a new file; an existing target must be refused without altering its bytes. Yield a writable text handle, close it after normal or exceptional body exit, and propagate body exceptions. Use the same acquire-attempt/acquired/released events. The caller prepares the parent directory; do not silently create or overwrite unrelated directories.

Mode x provides exclusive creation and raises FileExistsError for an existing path, unlike w, which truncates. “Exclusive” describes creation, not a transaction lock covering every subsequent file operation. If the body writes part of a report and fails, partial content may remain. Document and test that policy rather than claiming close provides rollback or atomic replacement.

Independently test normal writes, existing targets, partial-write failure, and real handle closure in temporary directories. Retained effects are part of the requirement; do not silently delete files to make tests green.

## 12. Acceptance and a lifecycle-based checkpoint

Independently draw creation, first next, suspension, resumption, and exhaustion/close. Prove break does not guarantee release, distinguish unstarted and suspended closure, implement a manager that does not swallow exceptions, make tests catch suppression, and complete the new-report requirement.

Before pausing, record who acquires and closes the resource, whether iteration has started, the last successful/failing commands, retained partial files, the failure stage, and the next step. Resume with temporary data rather than experimenting with overwriting or deleting important files.

Only after these foundations does H01 introduce a continuously running service: why one call ending does not end the process, who listens on a port, and why client input is untrusted. A file demonstration is not suddenly a deployable backend.
