## 1. 从“看起来正确”到可以重复检查的证据

前面你已经亲手观察程序输出，但每次改一个分支，都靠记忆重试所有输入很容易漏掉边界。自动化测试不是让计算机替你决定需求，而是把**你已经写明的预期**变成可以重复执行、失败时可定位的检查。

一次漂亮输出不能证明空数组、零、错误类型和第二次调用也正确。另一方面，测试全部通过也只证明已执行的断言：如果测试没被发现、根本没调用业务函数，或者预期本身错误，绿色没有你想象的含义。

| 契约 | 本章范围 |
| --- | --- |
| 前置 | 函数、异常、模块、L07 的 with 使用、L08 的环境 |
| 新能力 | 普通测试函数、断言、发现与收集、错误断言、输入隔离、失败诊断 |
| 独立验收 | 根据需求写出正常、空、边界、非法输入与重复调用测试，并证明测试能抓到故意缺陷 |
| 暂不要求 | 装饰器、参数化、fixture 参数、mock、异步和数据库测试 |

## 2. 测试先是一段普通 Python

本章业务契约很小：输入是 list，每项是恰好有 minutes 和 done 的 dict；minutes 为普通非负 int，done 为 bool；只汇总未完成项。空列表结果为零，不修改输入。先读业务函数，再读一段不用测试框架的检查：

<Code language="python">{getTestingExample('study.py')}</Code>

<Code language="python">{getTestingExample('first_check.py')}</Code>

```bash
uv sync --locked
uv run --locked python first_check.py
```

```text
Observed: 20
Checked
```

print 只让人看见结果；assert 把“应该等于 20”变成了可执行判断。条件为真就继续，为假则抛出 AssertionError；第二行成功提示不代表打印本身进行了检查。

文件顶部导入仍遵守 L06：调用发生在检查脚本，不在业务模块。测试有权给函数传入数据，不能偷偷依赖上一段终端里留下的变量。

## 3. 先认识一次真正的失败

<Code language="python">{getTestingExample('wrong_check.py')}</Code>

```bash
uv run --locked python wrong_check.py
```

预期 AssertionError、非零退出，最后的 Not reached 不会打印。函数算出了 20，故意错误的预期要求 99。这里应该修复测试预期，而不是把正确业务改成永远返回 99；判定依据必须回到需求。

测试断言不是生产输入校验。普通 Python 使用优化选项可能移除 assert，且 assert 的语义是检查程序假设，而不是约定的用户错误响应。业务契约仍用 if/raise ValueError 明确拒绝非法值。不要用 `python -O` 做本章验收，也不要在 assert 表达式里塞入必需业务副作用。

## 4. pytest 帮忙发现和报告，不替你设计预期

逐个手写调用很快会难以维护。pytest 发现符合规则的测试，执行它们，捕获失败，汇总结果，并提供非零退出供后续自动化使用。它不知道“完成项是否应计入时间”，那仍是你的契约。

<Code language="toml">{getTestingExample('pyproject.toml')}</Code>

```bash
uv sync --locked
uv run --locked python -m pytest --version
```

新配置 `[dependency-groups]` 的 dev 组保存开发时使用的依赖。pytest 不属于业务运行依赖，所以 project.dependencies 仍为空。uv 默认安装 dev 组；以后省略开发依赖的环境没有 pytest 是有意选择，不代表业务库坏了。

`[tool.pytest.ini_options]` 的 testpaths 指定默认从 tests 目录找测试，故意错误的 errors/exercises 不混入正常验收。`python -m pytest` 使用当前项目 Python 运行已安装模块；从项目根目录启动也让普通本地模块可导入。不要靠全局 pytest、修改 sys.path 或编辑器的偶然工作目录解决导入问题。版本命令应报告 pytest 8.4.2。

如果你用过 Jest 或 Vitest，约定式发现是相似的：`test_*.py` 之于 pytest，就像 `*.test.js` 之于 Jest。更大的差异在断言：pytest 直接使用普通 `assert`，失败时由断言重写显示每个子表达式的实际值；Jest 和 Vitest 则要求 `expect(...).toBe(...)` 这样的匹配器调用。因此 Python 测试模块不需要 `test()` 或 `describe()` 包装——一组普通函数就是完整测试套件。

## 5. 一份完整的基础测试文件

<Code language="python">{getTestingExample('tests/test_study.py')}</Code>

```bash
uv run --locked python -m pytest -q
uv run --locked python -m pytest --collect-only -q
uv run --locked python -m pytest -q tests/test_study.py::test_empty_input_is_zero
```

文件名 test_study.py 和函数名 test_... 满足发现约定。普通 def 定义函数，不要在文件末尾手动调用；pytest 在收集之后调用它们。第一个命令应是 **6 passed**，第三个只运行空输入测试，应是 **1 passed**；耗时、路径和终端装饰不是固定文本。

`-q` 减少输出，不改变正确性要求。`--collect-only` 只列出收集项而不执行业务检查：列出了六项不等于六项都通过。`文件::函数` 用于定位一个测试；修复后仍要回到完整套件，避免只验证局部。

每项测试可以按“准备输入 → 调用 → 验证”阅读。第一项同时含完成与未完成任务，能区分 if done 与 if not done；只用空数组则无法检查这个分支。测试数据应让错误有机会显现。

## 6. 预期抛错也能是成功测试

第五项的 `with pytest.raises(ValueError) as caught` 声明：块内必须抛出 ValueError 或其子类。没有抛错，pytest 会判失败；抛出其他类别，测试也不会假装成功。正常完成检查后，caught.value 是捕获的异常对象，块外再验证约定的消息。

这是在使用库提供的上下文行为，语法沿用 L07 的 with；不是文件资源，也不要求现在实现自定义上下文协议。将真正应抛错的那一次调用放在块内，不要把许多无关操作包进去，让其他 ValueError 冒名顶替。

`pytest.raises(Exception)` 通常过宽：拼写错误导致的异常也可能让测试变绿。只有当具体文本是稳定业务契约时才逐字检查消息；解释器诊断措辞可能随版本变化。这里自己定义的 minutes 消息是稳定契约，不匹配整段 traceback。正则 match 属于后续可选工具，本章不靠它完成验收。

## 7. 为什么输入要在每项测试里新建？

若把可变列表放在模块顶部，一个测试修改它，后一个测试就可能依赖执行顺序。单独跑时绿、一起跑时红，常常暴露这种污染，而不是 pytest 随机做错了事情。

本章每项测试自己构造小输入，不依赖“前一项已经创建过任务”。第四项不只检查返回值，还连续调用两次并检查原输入，区分纯计算与隐藏的累加/修改。

测试里多个 assert 可以围绕同一个可解释行为；不要把毫无关系的几十种情况塞进一个函数，一旦第一个失败后面的都不会执行。独立测试的目的不是追求固定行数，而是让失败名称能指向违反的契约。网络、真实用户文件和环境时钟都不是本章函数的输入，因此不应偷偷混进这些单元测试。

## 8. 绿色也可能没有证据

下面是**刻意错误的测试设计**：

<Code language="python">{getTestingExample('errors/test_false_green.py')}</Code>

```bash
uv run --locked python -m pytest -q errors/test_false_green.py
```

它会显示 1 passed，但只检查了函数对象的真值，从未调用业务函数。把业务返回值改成荒谬结果，它仍可能通过。这不是框架漏洞，是断言没有关联需求。

验证测试质量的最小实验：在副本中把正确实现的 if not done 改为 if done，保留测试不变。混合任务用例应失败；恢复实现后再跑绿。还可以去掉 minutes 的类型检查，bool 拒绝用例应失败。不要把这种临时缺陷留在规范源码，也不要通过更改预期把缺陷“认证”为正确。

这叫检查测试是否有能力发现具体缺陷，不意味着通过几个变异就证明覆盖所有错误。代码覆盖率也只是执行范围线索，不会替你验证正确的业务预期。

## 9. 区分测试失败、收集错误和没有测试

<Code language="python">{getTestingExample('errors/test_wrong_expectation.py')}</Code>

<Code language="python">{getTestingExample('errors/not_discovered/check_totals.py')}</Code>

<Code language="python">{getTestingExample('errors/test_import_failure.py')}</Code>

```bash
uv run --locked python -m pytest -q errors/test_wrong_expectation.py
uv run --locked python -m pytest -q errors/not_discovered
uv run --locked python -m pytest -q errors/test_import_failure.py
```

这三条命令刻意非零退出，分别观察，不要用最后一条的成功与否推断前两条。第一条执行断言后失败，退出码 1；第二条默认模式找不到 check_totals.py，退出码 5；第三条在收集导入阶段就报错，本轮实测退出码 2。

最后一个错误发生在测试函数运行前，所以不能通过修改期望数字来修复。第二个文件内的函数虽叫 test_empty，文件名仍不符合目录发现约定；在副本改为 test_totals.py，再用 collect-only 和真正执行分别验证。

从失败名称和具体 assert 开始阅读，比较实际值与预期值，回到输入与需求，然后才看实现。红色也可能是测试有误；没有收集到内容则不是“所有测试通过”。自动化不能把所有非零退出都改成绿色继续。

## 10. 三层练习

### A. 解释观察

不运行先说明：为何六个测试收集成功还不等于通过？为什么 AssertionError 与缺模块应该走不同排查路径？为何 bool 不能被普通 int 的业务约定接受？

<details>
<summary>解释核对——不以背命令代替机制</summary>

收集只找出待调用函数；执行才进行断言。缺模块可能阻止收集或启动，与已执行但值错误不同。Python 的 bool 与 int 有继承关系，但本章要求普通整数，所以契约显式使用 type(... ) is int。业务要求与语言可执行性不是同一层。

</details>

### B. 用红色定位修复

<Code language="python">{getTestingExample('exercises/broken_study.py')}</Code>

<Code language="python">{getTestingExample('exercises/test_broken_study.py')}</Code>

```bash
uv run --locked python -m pytest -q exercises/test_broken_study.py
```

两项应失败。先按需求修复分支，不改变测试预期；再为不完整校验增加失败用例，完善实现。保留红→绿证据，而不是把 wrong implementation 整段替换后只看绿。

<details>
<summary>修复核对——最小修复与完整契约不同</summary>

将条件改为 not done 可修复这两项观察，但仍缺少根、字段、类型与非负校验。新增非法输入测试后，参考 study.py 的验证责任逐步补齐。两个绿只说明这两项，不代表契约完整；不要把 bool、字符串和缺失字段都转换成成功数据。

</details>

### C. 独立实现剩余预算

从空目录建立独立项目，声明 pytest 为开发依赖，创建 budget.py 与 tests/test_budget.py。`remaining_budget(budget, spent)` 要求：budget 是普通非负 int；spent 是普通 list，每项也是普通非负 int；返回 budget 减总支出，负结果截为 0；不修改输入。

自己实现并写测试，至少覆盖 20/[5,8]→7、空列表、恰好耗尽、超支、零预算、非法预算、非法根与条目、连续调用和输入不变。禁止为了测试而调用参考实现。完成后临时改成“总是返回 0”，你的正常/空预算用例应抓住它；恢复后完整跑绿。

## 11. 退出条件、中断记录与下一步

你应该能独立写测试，区分生产校验和测试断言，解释收集/执行/退出码，定位一项红色，证明一次故意缺陷被捕获，并从自己的声明恢复测试环境。

暂停时记录项目目录、最后完整测试命令、收集与通过数量、是否还有刻意变异、最后一个失败的名称及原因。回来先确认临时缺陷是否恢复，再运行完整套件，不能把“上次有绿色截图”当成当前状态。

下一章 L10 把模块、文件、环境和这些普通测试组合成第一个独立可复现项目。不是立即跳入 Web，也不把本章的绿色结果当成整个后端已经可靠。
