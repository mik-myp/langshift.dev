## 1. 现在才建立工程环境，解决的是哪个问题？

L00—L07 已经让你独立运行、拆分、排错和保存一个 Python 程序。直到这里，我们才引入完整的环境声明：你现在能够区分“业务程序写错了”和“运行程序的解释器缺少依赖”，也知道配置文件本身不会替你执行代码。

## 2. 先区分四个参与者

**Python 解释器**读取并执行 Python 代码。**uv** 是管理解释器、解析依赖和运行项目命令的工具，本身不是 Python 解释器。**虚拟环境**是某个项目使用的解释器入口与安装目录。**项目源码**才定义业务行为。四者不能因为终端里都出现一个命令而混为一谈。

你在前端熟悉的“源码 + package.json + 锁文件 + node_modules”可以帮助建立类比：声明和安装结果不是同一种文件。但不要直接把 `.venv` 当成纯粹换名的 `node_modules`：Python 环境还有自己的解释器入口、前缀和包搜索路径；运行哪一个 Python，决定了它能够导入哪些安装内容。

在未激活环境的终端里，裸写 `python` 或 `python3`，Shell 会按自己的 PATH 找程序。编辑器运行按钮也可能选另一个解释器。不能凭“我刚装过 humanize”推断当前进程一定能导入它。

先检查工具，而不是先安装一堆东西：

```bash
uv --version
```

如果连这个命令都找不到，Python 源码尚未运行。回到 L00 的安装与终端 PATH 检查；重新打开终端或核对工具位置，不要把业务文件改成能够绕过工具缺失的样子。

## 3. 一个目录里，哪些是输入，哪些是结果？

实验根目录的重要部分如下；练习和答案目录各自另有声明，先不要进入它们：

```text
u08-environments/
  .python-version
  pyproject.toml
  uv.lock
  app.py
  probe.py
  .venv/              # created locally; not in the download
```

| 文件或目录 | 谁负责 | 它解决什么问题 | 它不保证什么 |
| --- | --- | --- | --- |
| `.python-version` | 作者选择，uv 读取 | 本项目请求哪一个 Python 版本 | 不安装第三方依赖，也不替代兼容范围 |
| `pyproject.toml` | 作者维护 | 项目元数据、Python 兼容范围与直接依赖 | 一个允许范围不等于已经选定的整棵依赖图 |
| `uv.lock` | uv 解析生成，作者审查 | 记录选定版本、来源、文件哈希和相关解析信息 | 不携带包内容、不证明包安全、不锁住全部操作系统条件 |
| `.venv/` | uv 创建/同步 | 本机实际安装结果 | 不适合复制到不同目录/机器，不是应提交的项目源码 |
| 应用与测试源码 | 作者维护 | 业务逻辑及其验收 | 不能单独说明解释器和外部包条件 |

提交到版本控制的是源码、声明、版本选择与锁文件；不要提交 `.venv`、缓存或真实秘密。共享项目也不能依赖你已经激活的某个环境。这里的示例没有私有包源、密钥或 `.env`。

`pyproject.toml`：

<Code language="toml">{getEnvironmentExample('pyproject.toml')}</Code>

这不是 Python 或 JSON，而是 TOML。`[project]` 打开一个配置表，后面的 `key = value` 属于该表；双引号是字符串，方括号中的逗号分隔项是数组。`[tool.uv]` 是 uv 专属配置。你需要读懂本例用到的几种形式，不需要先背完整 TOML 规范。

- `name` 是项目元数据的名称，不是让 Python 自动生成一个同名模块。`version` 是这个项目自身的版本，不是解释器版本。
- `requires-python = ">=3.13,<3.14"` 说明接受 3.13 系列。它是范围；具体选择由版本文件和工具共同确定。两者互相矛盾时应修复声明，而不是忽略错误。
- `dependencies` 是程序运行时需要的**发行包**。`humanize==4.13.0` 在本次课程中精确选择版本；它不是在执行 `import`。
- `package = false` 明确本例是无需安装自身的本地应用。我们从项目目录运行文件；暂时不制作可发布发行包，不需要提前引入构建系统。

发行包名是安装工具识别的名称，导入名是 Python 寻找模块的名称，两者不保证相同。本例恰好都叫 humanize；不要看到一个陌生 import 就去网络上猜同名包安装。先查该库的官方安装说明，也不要把标准库 `json`、`pathlib` 当成缺失的第三方依赖。

## 6. 声明、解析、锁定、同步不是同一个动作

创建一个没有锁文件的新项目时，`uv lock` 根据声明解析出具体版本并生成锁文件；`uv sync` 再使环境满足选定依赖。日常 `uv run` 也会检查项目，并按需要锁定和同步后再运行命令。

关键不是背命令数量，而是理解**谁会改变哪个状态**：

| 命令 | 主要用途 | 本章需要观察的变化 |
| --- | --- | --- |
| `uv add "humanize==4.13.0"` | 有意增加直接运行依赖 | 声明、锁文件与环境通常一起更新 |
| `uv lock` | 从声明解析或更新锁 | 不等于安装，也不等于强制升级所有包 |
| `uv sync --locked` | 按相容锁文件恢复环境 | 不允许悄悄修改锁；默认精确同步会移除多余安装包 |
| `uv run --locked python app.py` | 检查锁并在项目环境运行 | uv run 默认非精确同步，不能据此证明多余包不存在 |
| `uv remove humanize` | 有意移除直接依赖 | 更新声明/锁/环境，但不会替你删除源码里的 import |

**`--locked` 不是 `--frozen`。** 前者要求锁与声明相容，否则失败；后者使用已有锁而不检查它是否仍符合声明。这里用 `--locked` 是为了暴露陈旧锁，不建议遇到错误就换 `--frozen` 隐藏矛盾。`--no-sync` 也不是修复命令，它会跳过你本来需要检查的环境同步。

对于验证“只有声明过的依赖也能运行”，先执行 `uv sync --locked`，再运行程序，比单独看到一次 `uv run` 成功更有证据。不要把工具默认保留的额外安装误当作程序已经可复现。

## 7. 锁文件为什么需要保留，又为什么不能神化？

实验的完整 `uv.lock`：

<Code language="toml">{getEnvironmentExample('uv.lock')}</Code>

先找到两个 package 条目：一个是 humanize 发行包，一个是本地虚拟项目。前者包含版本、公共来源、可用发行文件及其哈希；后者连接本项目的依赖要求。当前依赖很小，所以图很简单。后续一个直接依赖可能再依赖多个包，锁文件会记录解析结果，不能只抄顶层版本就称作完整恢复。

你无需手写这些长 URL 或哈希。**声明表达意图，解析器生成锁，作者审查变化。** 不要为了让检查变绿手改锁中的版本号，因为来源、文件哈希和依赖关系可能已经不相符。

锁文件不能代替 Python 选择、操作系统说明、数据库版本、秘密配置、数据备份或测试。哈希帮助核对取得的发行文件，不证明其中的代码没有漏洞。跨平台的锁信息也不保证所有本地扩展和系统库都能在每台机器上编译。

本例只使用公共 PyPI，选择纯 Python 依赖减少第一轮环境实践中的系统构建噪声。这是教学边界，不是以后只会遇到纯 Python 包的承诺。

## 8. 亲手制造陈旧锁，而不是只读“应该提交锁文件”

先复制整个下载到一个**新的实验目录，但不要复制 `.venv` 和缓存**。在副本中，把根声明的 humanize 版本从 4.13.0 改为 4.12.0，保留旧锁文件：

```bash
uv run --locked python app.py
```

预期是 **uv 在启动 Python 之前拒绝陈旧锁**。4.13.0 已经不满足新的精确要求；这不是业务 traceback，也不是 app 的求和错误。不要改业务文件来修环境。

若目的是回到教材原样，恢复原来的声明，再执行同步与运行。若你确实打算变更依赖，则有意更新声明与锁，检查变更，恢复环境，再验证程序行为。二者都是合理动作，但表达了不同意图。

仅改变一个仍然允许当前锁定版本的范围，不一定导致锁失效，因此本实验用**排除旧版本的精确要求**。我们验证的是相容关系，不是“文件有改动就必须报错”的错误模型。

## 9. 三种“包的问题”，不能用同一个重装命令解决

### 缺少声明

进入独立练习目录。它自己的声明没有 humanize：

<Code language="toml">{getEnvironmentExample('exercises/missing-declaration/pyproject.toml')}</Code>

<Code language="python">{getEnvironmentExample('exercises/missing-declaration/app.py')}</Code>

```bash
cd exercises/missing-declaration
uv sync --locked
uv run --locked python app.py
```

这里应出现 **ModuleNotFoundError**。先确认 cwd 与本项目环境，再把实际运行依赖加入声明：

```bash
uv add "humanize==4.13.0"
uv run --locked python app.py
cd ../..
```

修复后输出 `2.0 KiB`。检查两个文件：声明新增了依赖，锁中也出现了对应解析。只在某个环境里临时安装成功、却不修改声明，不算修好独立重建能力。

### 安装成功，但导入了本地同名文件

根目录的已安装包不缺失，下面仍然会失败：

<Code language="python">{getEnvironmentExample('errors/humanize.py')}</Code>

<Code language="python">{getEnvironmentExample('errors/show_shadow.py')}</Code>

```bash
uv run --locked python errors/show_shadow.py
```

先打印的是 `errors/humanize.py` 的实际路径，再出现 **AttributeError**：这个本地模块没有 `naturalsize`。L06 的模块搜索规则没有因为建立 `.venv` 就失效。重装发行包不会改变本地命名冲突。在副本中将这个本地文件改名，再启动一个新进程观察实际来源；不要修改 site-packages。

### 下载失败，还没轮到 import

DNS、网络、包源认证、TLS 或没有对应发行文件，都可能让同步失败。离线且冷缓存的机器不能凭 `uv.lock` 生成包内容。此时应阅读 uv 的下载/解析诊断，不要给 app 添加 except，也不要关闭证书校验或把真实私有源凭据粘贴进教材和日志。

按顺序问：**工具能否启动 → 项目与解释器选对了吗 → 声明和锁相容吗 → 安装完成了吗 → 实际导入来源是什么 → 业务运行是否正确？**

## 10. 激活不是必须，也不是在复制一个环境

激活主要改变当前 Shell 的命令搜索与环境，使你直接写 `python` 更容易选中 `.venv`。它没有把依赖装进源码，也不会永久修改所有终端。不同 Shell 的激活命令不同，所以本书的主路径统一使用 `uv run`，减少隐藏会话状态。

不要把其他项目已激活的环境带入本项目并假设工具一定按你的意图选择。若工具提示 VIRTUAL_ENV 与项目环境不一致，先确认你要操作的是哪个项目，不要随意加“使用当前活动环境”的开关。

恢复验证的方法不是复制 `.venv`，而是准备另一个干净目录，复制**源码、声明、版本文件与锁**，执行：

```bash
uv sync --locked
uv run --locked python app.py
```

这比删除唯一工作环境再祈祷能恢复更安全，也会暴露漏提交的依赖。原始数据、秘密与其他外部服务不在这份环境恢复证据里，未来要分别验收。

## 11. 三层练习：解释、修复、独立恢复

### A. 先预测，再运行

1. 锁文件存在，是否代表 `.venv` 已经安装？
2. `uv run --locked` 成功，是否代表没有额外包？
3. ModuleNotFoundError、陈旧锁拒绝、同名遮蔽 AttributeError 分别发生在哪一层？
4. 安装了某个发行包，为什么仍要查看 `__file__`？

<details>
<summary>解释核对——先写自己的依据</summary>

锁只是解析信息，不是安装目录。uv run 默认非精确同步，不能证明没有额外包；需要受控的精确同步或干净恢复。陈旧锁在启动业务前由工具拒绝；缺少模块在 Python 导入时失败；本地同名文件则可能成功导入错误模块，再访问不存在的属性。发行元数据与实际模块来源需要分别观察。

</details>

### B. 修复但不掩盖

在下载副本中完成缺声明和同名遮蔽两个实验。保留失败命令、退出是否非零、报错层次、修改了哪些文件，以及新进程的成功输出。不要把原本应失败的命令包装成忽略错误，也不要删掉 import 让“功能不再存在”充当修复。

<summary>修复核对——为什么这些改动才解决根因？</summary>
