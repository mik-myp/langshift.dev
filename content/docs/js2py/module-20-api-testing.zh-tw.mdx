## 1. 業務函數通過，接口仍可能壞在哪裡？

L09 已能寫普通測試函數、斷言與 pytest.raises；L13 已知道參數化如何把多組數據變成獨立用例。H05 的 store 測試可以證明 PATCH 合併規則，卻沒有證明 /tasks 已被註冊、請求 JSON 被解析、錯誤狀態正確，或輸出模型真的過濾內部字段。手動 curl 能看到這些，但每次修改都靠記憶重放容易遺漏。

## 2. 先分清三種“客戶端”

TestClient 把請求交給同一 Python 進程裡的 ASGI 應用，經過真實路由、依賴、Pydantic 驗證和響應處理；它不需要 Uvicorn 監聽端口。**它不是把每條路由都 mock 成一個固定 JSON。** 但網絡、進程啟動和瀏覽器安全策略不在這條路徑上。

HTTPX Client 向真正地址發請求，會經過本機 TCP 端口和 Uvicorn；連接拒絕是可觀察故障。真實瀏覽器又多了一層 Origin 與 CORS 執行：服務器允許頭是否足夠、預檢是否成功、前端能否讀取響應，要由瀏覽器實際證明。三者互補，不應拿“測試很快”推導“已經端到端上線”。

| 檢查入口 | 本章能夠證明 | 不能由它單獨證明 |
| --- | --- | --- |
| 普通 store/config 測試 | 具體 Python 行為、配置解析 | 路由/HTTP/監聽 |
| TestClient，未覆寫業務依賴 | 輸入到輸出的進程內 API 行為 | Uvicorn 導入入口、端口、瀏覽器 CORS |
| TestClient，加依賴替身 | 替身場景下的消費方行為 | 被替換的真實依賴及其子依賴正常 |
| 真實 HTTPX/urllib | 實際進程、端口和 HTTP 契約 | 瀏覽器執行 CORS、生產網絡、TLS |
| 真實瀏覽器 fetch | 本次頁面來源的可讀取響應與預檢 | 用戶身份、對象權限、所有瀏覽器環境 |

## 5. fixture 解決的是準備與清理，不是自動 mock

多個測試都寫 create_app/with TestClient 容易遺漏關閉，也容易偷懶把 app 變成模塊全局。pytest fixture 是帶名稱的準備函數：用 `@pytest.fixture` 登記；測試形參寫 client，pytest 找到名為 client 的 fixture，先運行它，再把產物傳給測試。不是靠 Python 自動猜參數，也不是寫個同名全局變量。

fixture 自己也可以要求其他 fixture：client 的形參 app 讓 pytest 先創建 app。默認 scope 是 function，每個測試用例重新準備；同一測試裡 client 和 overrides 都需要 app 時，拿到的是同一個本次 app，而不是兩個不相干的應用。參數化的每一行也各自得到這套準備。

<Code language="python">{getApiTestingExample('tests/conftest.py')}</Code>

conftest.py 是 pytest 會在目錄作用域發現的 fixture 文件；普通測試不需要手動 import client。這裡 app fixture 用 return，因為它沒有額外退出動作；client fixture 用 yield，測試執行完（包括斷言失敗）後繼續退出 with，關閉客戶端。overrides 的 finally 在第 9 節解釋。**fixture 的 yield 與 FastAPI 依賴的 yield 由不同框架驅動**，只是共同建立在 L14 的暫停/恢復機制上。

創建前就失敗、根本沒到 yield 的 fixture，不會神奇地執行寫在 yield 後的所有語句。需要為實際已經取得的資源安排 try/finally 或 with；不能寫“只要有 yield 就一定安全”。本例客戶端由 with 管理，覆寫由 finally 管理。

<details>
<summary>解釋題答案：把 fixture 改成 session scope 會更快，所以更好嗎？</summary>

不一定。共享整個測試會話裡的 MemoryStore 會讓後執行測試看到前面的任務和遞增編號，測試開始依賴順序。當前對象很輕，function scope 直接表達“每例一份狀態”。若將來資源昂貴，要另設計隔離策略，不是隻為縮短耗時擴大作用域。fixture 本身既不是 mock，也不保證它返回的對象是乾淨的；乾淨來自這裡的工廠和生命週期設計。

</details>

## 6. 狀態、正文與後續讀取要一起檢查

<Code language="python">{getApiTestingExample('tests/test_contract.py')}</Code>

參數化的 note 三態測試還分別為遺漏、替換和 null 構造完整預期任務：先核對 PATCH 響應，再 GET 同一個 ID，核對狀態 200 與整條預期記錄。只有響應斷言，可能放過“返回舊內容、存儲已經損壞”的實現。

先讀 test_crud，不要一口氣背所有方法。201 證明創建狀態符合契約，完整或關鍵字段斷言證明結果形狀，後續 GET 證明修改確實寫入當前存儲，204 的 `content == b""` 證明刪除沒有錯誤地返回 JSON，隨後 404 證明資源不再可讀。只斷言 status_code < 500，會把業務拒絕、錯誤路由和成功都混成一類。

`set(task)` 在字典上取得鍵集合，檢測內部字段是否洩漏；`type(id) is int` 避免把 Python bool 當整數。本例第一項測試對完整響應相等，也同時證明標題空格保留和默認值正確。不要為了測試方便把響應中的所有“多餘”字段先刪掉再比較，那會掩蓋輸出白名單失效。

test_each_case_starts_empty 用兩行參數各執行一次：每項先觀察 total=0，再創建自己的記錄並得到 id=1。若一個用例需要另一個用例先創建數據，它不是獨立測試。涉及多步業務的一個測試內部可以有順序；不同測試之間不該通過遺留數據互相喂輸入。

## 7. 錯誤測試要證明“正確地失敗，而且沒有寫壞數據”

這裡分三類故障：壞 JSON 文本返回 json_invalid；JSON 合法但 minutes=true/"3"/3.0 等不符合模型，返回 422 且定位 body 字段；合法 ID 查不到對象返回 404 和穩定的業務 detail。它們不應該被統一成一個模糊的“有錯誤”。

參數化按 field/value 展開嚴格校驗，不使用一堆 copy-paste 測試。檢查 detail 中的 loc，確認錯誤發生在 body/query/path 的預期位置；不過不硬編碼整段 Pydantic 人類可讀錯誤文案、文檔 URL 和所有版本相關字段。對自己擁有的 404 detail 則可以完整斷言，它屬於本章接口契約。

非法創建之後檢查 total 仍為 0；混合非法 PATCH 後重新 GET，確認任何字段都沒有偷偷改變。只檢查 422 不足以排除“先寫入部分值，再報錯”。注意當前代碼的候選記錄驗證與替換順序只保障這些順序執行路徑，不是在承諾併發事務。

PATCH note 的三行分別表達不改、賦新文本、顯式清空；非 note 字段的 null 被拒絕。`if payload.note` 無法表達三態，因為空字符串和 None 都是假值；本例使用顯式字段集合生成的 exclude_unset 結果。需要斷言行為，而不是要求學習者記住某段框架實現。

<details>
<summary>帶提示答案：如何設計一個能抓住“錯誤 PATCH 先改了一部分”的測試？</summary>

先創建 title="Keep"、minutes=5、note="keep"，保存完整響應；PATCH 同時提交合法的新 title、非法 minutes=true 和 note=null；確認 422 後重新 GET，與原響應完整相等。若只測試一個非法字段，未必暴露實現提前寫入其他字段的問題。獨立題會要求你自己寫出這個測試，而不是隻口頭描述。

</details>

## 8. 應用異常與 HTTP 錯誤不是同一個觀察方式

未處理 RuntimeError 是應用缺陷，不是你有意拋出的 HTTPException。TestClient 默認把這類服務端異常重新拋給測試，方便看到原始 traceback；因此一個期待 response.status_code 的測試可能在 client.get 處就停了。

要驗收對外 500 響應，局部創建 `TestClient(app, raise_server_exceptions=False)`；再檢查狀態和文本。默認非 debug 應用的 500 正文是 Internal Server Error，不是 JSON，不能無條件 response.json()。這不是讓測試忽略缺陷：一個測試檢查異常傳播，另一個檢查對外錯誤面，兩者目的不同。

<Code language="python">{getApiTestingExample('tests/test_dependencies.py')}</Code>

test_unhandled_errors_raise_by_default 使用故意拋錯的依賴，分別觀察兩種客戶端模式；這隻能證明這個受控失敗路徑，不代表生產故障觀測已做好。capsys 是 pytest 自帶的捕獲輸出 fixture，讀取本次 stdout；test_real_trace_cached_and_closed 檢查原依賴一次 acquire、兩次使用、一次 release。它沒有替換 trace，所以確實執行了真實臨時文件邏輯。

即使 capsys 在客戶端返回後讀到了 release，也不能據此確定 release 與響應發送的先後。H05 的版本化時序與維護用 ASGI 探針負責那項更細的證據；本章不偷加異步測試前置。

## 9. dependency_overrides：替換哪個函數，丟失哪部分證據

app.dependency_overrides 是字典：鍵為路由聲明時使用的**原函數對象**，值為替代提供者函數。`overrides[get_store] = replacement_store` 正確；字符串 "get_store"、get_store() 的結果或另寫一個同名函數都不是同一鍵。框架解析請求依賴時才查這張表，它不重寫 Python 模塊裡的全部函數調用。

test_override_store 返回預置記錄的另一份 MemoryStore，讓列表行為可控；同時斷言 app.state.store 仍為空，明確說明真實提供者被繞過。get_store 原本依賴 request_trace；覆寫 get_store 的列表測試不會執行原 get_store，也不會執行它原有的 trace 子依賴。不能拿這項綠色結果宣稱資源創建/清理正確。

test_dependency_rejection 用替身拋 503，證明消費方能得到預定狀態和正文；它沒有真的拔網線、製造磁盤故障或驗證恢復策略。這裡使用普通函數作為 stub（提供預設結果的替身），沒有必要先引入 unittest.mock。mock 是寬泛術語時，應說清替換邊界，而不是聲稱“有 mock 就是完整集成測試”。

覆寫僅作用於依賴解析。真實環境在 create_app 時已被讀取；事後覆寫 get_settings 不能倒流修復一個已經失敗的工廠。這個區別解釋了為什麼測試使用顯式 Settings 後，還要單獨啟動真實進程檢驗環境。

## 10. 覆寫必須恢復，而且要在失敗時也恢復

不要寫“請求、斷言、最後清空”三個普通語句：斷言一失敗，清空就不執行。conftest 中 overrides fixture 先複製原映射，再 try/yield/finally；無論測試是否通過都清除本次改動並恢復原映射。恢復快照比永遠賦空字典更穩妥，因為調用者可能原本有別的受控覆寫。

即使本章每測試新建 app，也保留這個清理習慣：共享 app 的診斷、一個測試裡的多個階段、以後改變 fixture scope，都可能讓殘留產生誤判。下面故意讓一項測試失敗，並保留同一個 app 的引用供下一項檢查；這是**有意按順序的清理探針**，不是普通測試互相依賴的推薦模式。

<details>
<summary>故障診斷答案：第二項也失敗，應該修哪一層？</summary>

先確認運行的是整個診斷文件，而不是隻挑第二項；這個特定探針需要前一項保留引用。再檢查 overrides fixture 是否把恢復放在 finally，是否誤覆寫另一個 app，或把快照本身當成同一個可變字典。恢復清理後應重新得到 1 failed, 1 passed，再跑正常套件。不要修改第二項為“允許覆寫殘留”，也不要將它當作日常測試順序依賴的模板。

</details>

## 11. 正常自動驗收與獨立變式

```bash
uv run --locked python -m pytest -q
```

```text
48 passed
```

這是 48 個實際收集的用例，不是 48 個函數或斷言。原來的 44 項涵蓋進程內 CRUD、嚴格輸入、PATCH 三態、錯誤定位、缺失資源、分頁、隔離、原依賴清理、替身錯誤、500 模式及 CORS 響應頭。新增 2 項用自有本地故障服務器驗證真實客戶端清理，另 2 項在可丟棄副本驗證驗收能抓住“舊響應掩蓋壞狀態”的 mutant。重複運行不應依賴上一次數據。故障服務器提供的是狹義真實端口證據，不代表健康服務完整流程或瀏覽器可讀。

## 13. CORS 先解釋參與者，再加中間件

瀏覽器頁面 http://127.0.0.1:5506 與 API http://127.0.0.1:8006 端口不同，因此不同源。Origin 由協議、主機、端口組成；localhost 和 127.0.0.1 也不是字符串相同的來源。CORS 是瀏覽器決定是否允許頁面腳本讀取跨源響應的協議，不是登錄或服務端對象權限。

瀏覽器發送 Content-Type: application/json 的跨源 POST 前，通常先發 OPTIONS 預檢，帶 Origin、Access-Control-Request-Method 和 Access-Control-Request-Headers。CORSMiddleware 在路由外處理這類預檢，併為符合配置的響應添加允許頭；不是要求每條路由自己寫 OPTIONS。中間件是包在應用請求/響應外的一層處理器，這裡只使用這個明確功能，不講任意中間件架構。

<Code language="python">{getApiTestingExample('task_api/main.py')}</Code>

允許來源只有 http://127.0.0.1:5506，允許本章方法與 Content-Type，不攜帶 credentials。沒有用星號擴大來源，也沒有 token/cookie 認證。已解釋的普通 create_app 工廠仍然是唯一組合入口；不用異步 lifespan。

<Code language="python">{getApiTestingExample('tests/test_cors.py')}</Code>

允許預檢得到 200 與精確來源頭；5507 的預檢得到 400 且沒有允許來源頭。更重要的第三項：直接 GET 即使帶一個不允許的 Origin，也可能得到 200，只是沒有允許瀏覽器讀取的頭；不帶 Origin 的非瀏覽器客戶端仍可訪問。因此 **CORS 不是把非允許調用者擋在服務之外的認證機制**。

TestClient 只檢查服務發出的頭與狀態，不會像瀏覽器一樣阻止腳本讀取響應。到這裡仍不算前後端聯調完成。

## 14. 真瀏覽器聯調：一個靜態頁面就足夠

無需安裝前端框架。繼續保持 API 在 8006 運行，第三個終端提供靜態頁面：

```bash
uv run --locked python -m http.server 5506 --bind 127.0.0.1 --directory browser
```

打開 http://127.0.0.1:5506，點擊 Run browser check。不是雙擊 file:// 文件，不是打開 localhost:5506；這些來源不在本章允許表裡。

<Code language="html">{getApiTestingExample('browser/index.html')}</Code>

```text
PASS: browser POST 201, GET 200, strict input 422
PASS: cleanup DELETE 204
```

瀏覽器按鈕禁用期間避免重複點擊；fetch 不會因為 HTTP 422 自動拋異常，所以頁面明確檢查狀態和 detail。CORS/網絡錯誤則可能讓 fetch 直接拒絕，根本拿不到可讀 Response。finally 刪除已成功創建的任務，並單獨顯示清理是否失敗；測試失敗不是留下垃圾數據的理由。

再開一個終端從不被允許的端口提供同一文件：

```bash
uv run --locked python -m http.server 5507 --bind 127.0.0.1 --directory browser
```

打開 http://127.0.0.1:5507，點擊按鈕，預期頁面以 FAIL 開頭，瀏覽器 Network 中 POST 的 OPTIONS 被拒絕，任務沒有被創建。不同瀏覽器錯誤文字可能不同，不固定 TypeError 的完整句子。回到 5506 再運行應恢復通過；同時真實 Python 客戶端依舊能請求 API，進一步證明 CORS 不是身份驗證。

若第一次就失敗，按順序檢查 API 是否在監聽、頁面的完整 Origin、OPTIONS 狀態與響應頭、POST 是否實際發出、服務器是否返回 422、前端是否錯誤讀取 JSON。不要用 mode:no-cors 修復：opaque 響應無法完成本章的狀態/JSON 驗收；也不要關閉瀏覽器安全性或改成任意來源。

完成後 Ctrl-C 停 API 與兩個靜態服務器，記錄清理後的任務數。若瀏覽器失敗在刪除環節，頁面會保留 task id；只刪除自己創建的教學記錄，再複驗。

## 15. 故障定位、恢復記錄與證據邊界

| 現象 | 區分原因 | 恢復與複驗 |
| --- | --- | --- |
| fixture 'client' not found | 文件不在對應 conftest 目錄作用域 | 放回 tests，或像獨立答案那樣聲明本地 fixture |
| 單測單獨過，整套失敗 | 共享 app、共享可變輸入、未恢復覆寫 | 回到 function scope 和工廠；重跑單項、整套、第二次整套 |
| client.get 直接拋 RuntimeError | 默認傳播服務異常 | 修實現；若故意驗收 500，局部關閉傳播並斷言正文 |
| JSONDecodeError | 500 文本或 204 空正文被當 JSON | 先檢查狀態/Content-Type；204 檢查空 bytes |
| TestClient 過，HTTPX 連接拒絕 | 服務未啟動、工廠失敗、端口不一致 | 看服務日誌，重啟正確入口後再驗收 |
| HTTPX 過，瀏覽器 fetch 失敗 | 來源或預檢，或頁面請求錯誤 | 查 Network；保持安全邊界，不擴大允許表掩蓋問題 |
| mock 測試過，真實 trace 無日誌 | 替換跳過真實依賴與子依賴 | 保留替身測試，再增加未覆寫的真實路徑證據 |

暫停記錄：當前目錄與鎖版本；基礎套件實際 count；獨立題實際 count；故障探針是否得到 1 failed, 1 passed；覆寫在哪個 app 上且是否已恢復；真實服務啟動命令/PID/端口；兩個瀏覽器 Origin 的結果；任務清理與進程停止情況；尚未驗證項與下次第一步。不要只寫“全部通過”。

畢業門檻是能解釋每層證據、獨立補測試、讓受控缺陷被抓住並恢復、完成真實瀏覽器聯調。下載 allowlist 排除環境、緩存、.env、日誌和秘密。當前的 48+3 項與真實進程/瀏覽器驗收不證明數據庫、認證授權、生產併發、部署、TLS、性能或所有瀏覽器兼容性；這些仍要在後續階段建立。
