## 1. A user says “it failed a moment ago.” Where do you start?

O04 can release and roll back, but a bare 503 does not tell you which request, route, or time window failed. Printing the entire Request, exception, or SQL parameters seems convenient while risking passwords, cookies, Bearer tokens, and bodies in long-lived logs. Observability must answer both what happened and what must never be collected.

We do not begin by installing a dashboard. We cause a real request to encounter a controlled database privilege fault, find its structured event using the response request ID, investigate the authorization change, repair it, and observe a healthy window. Synthetic secret scans then check that another output path did not leak the same data.

## 2. Logs, metrics, and traces are different evidence

A log records context for an event. A metric aggregates events over an interval into counts, ratios, or distributions. A trace describes spans across components for a request. They can be linked, but one JSON event does not implement distributed tracing, and a count of log lines is not service capacity.

For each request reaching the response-headers-ready point, our event contains only event, request_id, timestamp, method, route, status, ready_ms, and error_type. This supports individual lookup and aggregation of 5xx rates/p95. Consumed fields become a data contract; silently renaming them or replacing numeric values with prose breaks consumers.

Route uses the template `/projects/{project_id}`, not the concrete URL. Otherwise each ID or query could create another label, increase cardinality, and expose business identifiers or secrets. An unmatched route is the fixed label unmatched, and unknown methods become OTHER.

## 3. Generate correlation IDs; do not blindly trust caller headers

A browser or HTTPX client can report the response X-Request-ID to a maintainer. It is a correlation marker, not proof of identity or an authorization credential. This server generates a UUID for every request and does not log the caller's same-named header.

Why not merely validate the caller ID's length and characters? A valid random Bearer token can satisfy that exact character policy. Logging the header would still leak it. Valid format is not permission to record a value. Accepting an upstream proxy ID later requires a separately defined trusted-proxy boundary.

Production needs bounded buffering, collection/rotation, quotas, access controls, and a policy for failures of the logging system itself. Do not scale this finite exercise unchanged.

## 4. Where does latency start, and where does it end?

Timestamp uses wall-clock time to locate an event approximately. Ready_ms uses a perf_counter difference to measure duration without interpreting clock adjustments as latency. They serve different purposes even though both relate to time.

Ready_ms ends when call_next returns and response headers are ready. **It does not measure delivery of the final byte to the client**, slow streaming bodies, download time, or browser rendering. P95_ready_ms uses the same boundary. Define the measurement alongside the field; an attractive low number may simply measure a narrower interval.

Do not invent successful events for requests never observed. Readiness probes are real requests and are counted; the drill does not label them as business users. Multiple processes introduce separate logs, clock differences, sampling, and duplicate handling that need additional design. No distributed aggregation guarantee is made here.

## 5. Aggregate a window rather than hiding failures in an average

Summarize computes request count, 5xx count, error ratio, and nearest-rank p95 from a supplied finite collection. It sorts durations and takes the rounded-up 95% position. With twenty observations, tail statistics remain coarse. P95 is neither the maximum nor a measure that “95% of users are happy.” Averaging percentiles from different windows does not produce a global percentile.

The exercise requires at least twenty samples and a 5xx ratio of at least five percent to return page. Fewer samples produce insufficient_data, not an invented healthy result. A 422 is client-input rejection, so it is not in this server-failure numerator. A rise in 4xx may still deserve another rule for incompatible frontend versions or abuse.

Page is only a decision value: it sends no SMS, email, or on-call notification. Real alerting needs a time window, minimum volume, duration, suppression/recovery rules, an owner, and a runbook. These thresholds are an explainable teaching policy, not a universal production SLO.

Passing a private-socket host is not sufficient by itself: libpq can still obtain other connection defaults from `PGHOSTADDR`, `PGSERVICE`, `PGSERVICEFILE`, and related variables. `reject_connection_environment` rejects every inherited `PG*` name before temporary-directory creation and before each direct connection, migration, or server launch. ## 8. Scan every actual output path for secrets

The drill puts a random synthetic canary in an invalid password field, cookie, query parameter, and untrusted request ID, and sends real synthetic Bearer tokens. It scans event files, service stdout/stderr, and PostgreSQL logs for those original values. Validation responses must not echo the canary either.

This proves no disclosure of those markers on the executed paths. It does not prove every dependency, future route, proxy, browser console, or exception path is eternally safe. Rerun after changes to logging or error handling and review collection scope. Do not print the full token from test locals while debugging a failed privacy assertion; statuses, counts, and correlation IDs suffice.

Logs themselves require access policy, retention, and deletion rules. This drill deletes its entire temporary directory on exit, so no logged business data or secrets become artifacts. Production cannot evade maintenance by retaining nothing; it needs controlled retention and deletion, not a ZIP containing every .log file.

## 10. Capacity observations and a recovery checkpoint

Actual request counts, failures, response-ready times, and elapsed observation time can expose regressions, but do not constitute production capacity testing. This is one machine, one worker, sequential synthetic requests, tiny data, and warm local caches. There are no concurrent real users, remote databases, login-hash load, long connections, or durable log collectors. Dividing requests by this duration cannot establish supported production user count.

Before invited use, bound users, rates, and data sizes. Observe CPU, memory, connection pools, queues, disk, errors, and latency while gradually increasing representative load in isolation. Define overload rejection/degradation. Average latency or an installed dashboard cannot replace that work.

When pausing, record the last correlation ID—not the token—application version, observation interval, affected route/status, privilege change, verified repair, privacy scan, stopped processes/removed directories, and next action. Resume ordinary aggregate tests, then replay the fault in a new cluster. Never revoke privileges on a user database for this exercise.
