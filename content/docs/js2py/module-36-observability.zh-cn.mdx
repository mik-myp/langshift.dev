## 1. 用户说“刚才失败了”，你准备从哪里开始？

O04 能发布和回退，但如果只能看到一行 503，很难知道是哪个请求、哪条路由、哪个时间窗口开始异常。把整个 Request、异常对象、SQL 参数打印出来看似方便，却可能把密码、Cookie、Bearer token 和正文放进长期日志。可观测性要同时回答“发生什么”和“哪些内容不能收集”。

本章不先安装仪表盘。我们让一个真实请求遇到受控数据库权限故障，拿响应里的关联 ID 找到结构化记录，根据变化检查授权，再恢复权限并观察错误窗口下降。最后用合成秘密扫描实际日志，证明没有通过另一条输出路径泄露。

## 2. 日志、指标与追踪，不是同一种资料

日志记录一个事件的上下文；指标把一段时间的事件聚合成数量、比例或分布；追踪用多个跨度描述一次跨组件调用。三者可以相关联，但一份 JSON 日志并不自动建立完整分布式追踪，日志条数也不等于吞吐能力。

本实验每个完成到“响应头已准备好”阶段的请求写一个事件，字段只包括 event、request_id、timestamp、method、route、status、ready_ms、error_type。这样既能按 request_id 查一项，也能聚合 5xx 比例与 p95。字段一旦被消费，就成为需要维护的数据契约，不应随意换名或把数字变成自然语言段落。

route 记录模板 `/projects/{project_id}`，不是具体 URL；否则每个 ID、查询参数都可能变成新标签，既膨胀指标维度，又泄露业务标识或秘密。未匹配路由用固定 unmatched，未知方法归到 OTHER。

## 3. 关联 ID 由服务器生成，不盲信客户端

浏览器或 HTTPX 收到 X-Request-ID 后，可以把它交给维护者定位记录。它只是相关性标识，不证明用户身份，也不是授权凭证。服务端本例每次生成新 UUID；即使调用者提交同名请求头，也不写入日志。

为什么不只检查客户端 ID 的长度和字符？一个合法的随机 Bearer token 也可能正好符合安全字符规则；原样记录这个头，仍会把 token 写进日志。因此“格式合法”不等于“允许记录”。以后若接受受信任代理产生的上游 ID，要单独定义代理可信边界，而不是信任所有来源。

## 4. 耗时从哪里开始，到哪里结束？

timestamp 用墙上时钟定位大致时间；ready_ms 用 perf_counter 的差值计持续时间，避免把系统校时跳变当成请求耗时。两者有不同用途，不能只因为都用秒就互换。

这里 ready_ms 结束于 call_next 返回、响应头准备好时，**不是最后一个响应字节送达客户端的时间**，也不覆盖慢速流式响应、网络下载或浏览器渲染。p95_ready_ms 使用同一边界。请求 ID 与日志字段必须一起解释，否则一个漂亮的低延迟数字可能只是测量范围很窄。

对没有观察到的请求不能补写虚构成功日志。健康探测也是真实请求，会进入计数；演练报告说明包含 readiness 探测，不把它当业务用户数。跨多个进程时各自日志、时钟偏差、采样与重复都要另设计，本章没有做分布式合并保证。

## 5. 从事件计算窗口，而不是用平均值掩盖错误

summarize 对给定的有限事件集合计算请求数、5xx 数、错误比例和 nearest-rank p95。排序后取向上取整的 95% 位置；只有 20 项时，尾部统计仍很粗。p95 不是最大值，也不表示“95% 用户都满意”。不同窗口的 p95 不能简单平均成全局 p95。

本实验规则是至少 20 个样本，5xx 比例达到 5% 才进入 page 状态；不足样本是 insufficient_data，不是假装健康。422 是客户端输入拒绝，不计入这个服务端故障分子，但 4xx 突增仍可能提示前端版本不兼容或攻击，需要另一条规则观察。

这个 page 只是规则返回值，没有真实发送短信、邮件或值班通知。真实告警还要定义时间窗口、最小请求量、持续时间、抑制/恢复策略、责任人和操作手册。阈值是本实验的可解释选择，不是通用生产 SLO。

事件文件在独占 0700 临时目录内，以 0600 创建。Uvicorn access log 关闭，避免旁路记录完整查询 URL；验证错误只输出安全 loc/type，不返回 input/body/context。数据库也不记录语句和错误参数。这些配置与白名单共同建立边界；只修一份 logger，却任由代理或访问日志泄漏，仍然失败。

本实验验证的是管理／运行身份分离，以及已测试的 ALTER/DROP 被拒绝；**没有证明 DML 已按最小权限收敛**。共用的 `sql/grants.sql` 仍对 projects、project_members、tasks 授予 SELECT/INSERT/UPDATE/DELETE，并对 public 的全部序列授予 USAGE/SELECT；其中部分权限超过当前“读取／创建项目”路由的需要。真正部署前，须逐个列出路由和作业需要的表操作，收窄表／序列授权，再验证必要操作成功、未使用的 UPDATE/DELETE 等操作被拒绝。已有 DDL 拒绝测试不能代替这项审计。

传入私有 socket 的 host 还不够：libpq 仍可能从 `PGHOSTADDR`、`PGSERVICE`、`PGSERVICEFILE` 等环境变量取得另一个连接默认值。`reject_connection_environment` 在创建临时目录之前，以及每次直接连接、迁移和服务启动之前，拒绝继承的全部 `PG*` 变量，唯一例外是只定位可执行文件的 `PG_BIN`。错误只列变量名，不打印值，也不修改调用者环境。Python 连接、SQLAlchemy 的连接创建器和 PG 子命令都使用自有目录内的空白 0600 `empty.pgpass`，不读取用户的默认密码文件。直接运行 `demo.py` 或 `ci.py` 也执行这些防护，不依赖仓库总 runner 先替它清理。

启动 API 不再先探测空闲端口、关闭探测 socket，再要求另一个进程抢占同一号码。Uvicorn 自己用 `--port 0` 完成绑定；控制器从**该子进程自己的私有启动日志**读取实际端口，再请求 readiness。`--no-access-log` 不关闭 info 级启动 banner；控制器固定无颜色日志和单 worker。两个同版本服务也使用不同日志文件。测试实际同时启动两个服务，核对两个不同端口、各自 banner、真实请求和退出清理。这消除了选端口后释放再绑定的窗口，不是对任意并发故障的保证；未来 Uvicorn 改变 banner 格式时会超时拒绝，不猜测端口。

```text

```

过程中还输出 OBSERVATION JSON，其耗时和 p95 会变化，不应照抄某次机器数字当验收常量。实际步骤是先发一组健康请求；管理连接撤回 lab_app 对 projects 的 SELECT；再发五个项目请求，真实数据库拒绝查询，API 返回 503；用每个响应里的服务端 ID 精确找到对应 route/status；恢复 GRANT；最后二十个真实请求都回到 200。

对项目表的故障，SELECT 1 的 readiness 仍可能成功；这说明健康检查只证明它查询过的条件，不证明所有业务权限完整。日志中没有 SQL 参数，但变化时间、受影响路由和关联 ID 足以缩小范围，结合本次权限变更记录定位原因。不要靠重新授予 SUPERUSER 来“修复”。

## 8. 秘密扫描要检查所有实际输出

演练把随机合成 canary 放进非法 password 字段、Cookie、查询参数和不可信请求 ID，并发送真实 Bearer token。随后扫描事件文件、服务 stdout/stderr 日志和 PostgreSQL 日志，要求原始 canary 与 token 均未出现。校验失败正文也不能回显那个值。

这证明本次已执行路径没有泄漏这些标记，不是证明任意第三方库、未来路由、代理、浏览器控制台或异常路径都永远安全。新增日志字段/错误处理后要重跑，并审查收集范围。也不要为了调试一次失败把测试变量中的完整 token 打印出来；回执用状态、计数与关联 ID 足够。

日志文件本身也需要访问权限、保留期限与删除政策。当前脚本退出会删除整份临时目录，因此最终交付没有日志里的秘密或业务数据。真实系统不能靠“日志不留存”逃避维护，需要设计受控保存与删除，而不是把 .log 全打进发布 ZIP。

## 10. 容量观察与暂停恢复记录

演练记录实际请求数、错误数、响应准备时间与总观察耗时，可用来发现明显回归，却不是生产容量测试。这里是一台机器、一个 worker、顺序合成请求，小数据、热本地缓存；没有真实并发用户、远程数据库、哈希登录负载、长连接或持久日志采集器。不能把请求数除以这个时间就宣称“生产可服务多少用户”。

上线前先给受控试用限定用户数/速率/数据量，记录 CPU、内存、连接池、队列、磁盘与错误/延迟趋势，再在隔离环境逐步增加代表性负载；超限要有拒绝或降级策略。单看平均延迟或装好仪表盘不能替代这些验证。

暂停记录最后关联 ID（不是 token）、应用版本、观察窗口、受影响路由与状态、权限变更、已验证修复、日志私密性检查、子进程与临时目录是否清理、下次第一步。恢复先重跑正常聚合测试，再用新集群重放故障；不要连接用户数据库撤权。
