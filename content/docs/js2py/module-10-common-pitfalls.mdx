## 2. Specify the data and behavior before coding

The file contains one JSON array. Each item has exactly title, minutes and done. Title is non-whitespace str with spelling preserved; minutes is an ordinary nonnegative int, rejecting bool, float and numeric strings; done is bool only. Empty arrays, zero minutes and duplicate titles are valid. Preserve order and reject missing/extra fields.

Compared with frontend form validation, this boundary is stricter by design. JavaScript coerces the string "30" into the number 30 in arithmetic and loose comparisons; Python keeps str and int distinct, and this contract rejects numeric strings outright. Likewise, reading a missing key from a JS object yields undefined and the program continues, while `data["missing"]` on a Python dict raises KeyError — the language basis for treating damaged input as a visible failure instead of a silent default.

Only a **missing** destination initializes this data. An existing empty array is not absence:

<Code language="json">{getProjectExample('fixtures/initial.json')}</Code>

Every successful run marks all unfinished tasks whose title exactly equals Read as done. Already-complete items do not increase changed. Save once, then report changed count, total tasks and unfinished minutes. Titles are not unique IDs; matching duplicates are all processed rather than silently adopting a first-match rule.

A missing file and a damaged existing file are different events. Invalid encoding, malformed JSON or invalid business shape must produce a visible nonzero failure while preserving the original bytes. Do not initialize, save an empty array or merely warn and continue. Permission and unknown I/O errors cannot become “a new user with no tasks.”

## 3. Separate responsibilities along data flow

Draw the flow: **path → open file → parsed text → validated data → business change → summary → serialization → save → display**. At each boundary ask who guarantees input and who interprets or propagates failure.

- Validation returns a fresh list of fresh dictionaries. Mutating the result must not mutate the original input.
- Rules complete tasks and compute summaries without opening files, printing or creating directories. There is no global mutable task database.
- Storage reads/writes and validates. Load propagates absence instead of choosing initialization policy. Save validates/serializes before a destructive open.
- The app chooses its owned fixed path, creates its parent, decides when initialization is allowed, orders calls and stops after damaged input.

These are ordinary modules/functions, not an invitation to memorize enterprise architecture terms. Equivalent names are fine if responsibilities remain explainable. A small program still must not read or write user files merely on import; more directories do not automatically establish better boundaries.

Write your module sketch and each function's inputs, outputs and errors before opening the reference. Type annotations are not required until their dedicated L11 lesson.

## 5. Define acceptance before implementing

First and second process runs should respectively print:

```text
Source: new file
Changed: 1
Tasks: 3
Pending minutes: 35
```

```text
Source: existing file
Changed: 0
Tasks: 3
Pending minutes: 35
```

Use fresh Python processes. Retaining a list in one process does not demonstrate persistence. Changed becoming zero follows this particular completion operation's contract; it does not mean every repeated program run is universally side-effect free.

Also verify:

| Situation | Required observation |
| --- | --- |
| Import app/storage | Only the probe's output; no directory creation, data I/O or business entry |
| Existing empty array | Remains empty; counts and minutes are zero |
| Duplicate Read titles, some already done | All match, but count only newly completed items |
| Change Practice to 36 minutes | A new process reports 36 rather than hard-coded 35 |
| Malformed JSON, invalid encoding or shape | Visible failure, unchanged original bytes, no success report |
| Missing parent | App creates its owned parent; storage does not silently create arbitrary directories |
| Different cwd | Same anchored project data, no accidental second dataset under the caller |

Invalid values rejected before saving must preserve the old file. **A failure during writing can still damage it.** Retain L07's explicit limits instead of turning with, tests or one-document formatting into a database transaction claim.

## 6. Give file tests their own disposable directory

Tests must not damage your working task file, and fixture knowledge is not a prerequisite. Introduce one small standard-library utility: TemporaryDirectory creates an owned temporary directory; leaving its with scope cleans up that directory and contents on normal or exceptional exit.

<Code language="python">{getProjectExample('demo_resource.py')}</Code>

```bash
uv run --locked python demo_resource.py
```

```text
Inside: True
After: False
```

Directory is a string path; Path turns it into the familiar object. Create only test-owned files beneath that temporary directory, never supply a real user's location. After exit, the path name still exists but the location is cleaned up, extending L07's distinction between a name and an available resource.

Each file test creates its own directory. A reader need not know it is being tested: it accepts a Path. Similarly, main(path) can accept a test-owned location while the normal entry chooses its fixed default. This is an ordinary function parameter, not premature framework dependency injection or a security promise for arbitrary uploaded paths.

## 7. Work in observable stages rather than one large leap

Use small verifiable steps while deciding the implementation yourself:

1. Build pure validation/rules and plain tests for empty, zero, duplicates and non-mutation.
2. Add storage and round-trip in temporary directories; two saves still produce one document.
3. Add orchestration and the fixed path; verify first/repeated/existing-empty behavior.
4. Copy bad input into an owned disposable destination and compare bytes before/after failure; never repair fixtures in place.
5. Use an outer entry from another cwd and probe imports without business execution.
6. Recover in a second clean directory, rerun the whole acceptance table, then attempt the variation.

For a red step, identify its layer before changing Python, registries, JSON and assertions simultaneously. Run focused checks after each small change and the complete suite afterward, preserving explainable progress.

## 10. Diagnose damaged data instead of deleting the evidence

Two supplied bad inputs are:

<Code language="text">{getProjectExample('fixtures/broken.json')}</Code>

<Code language="json">{getProjectExample('fixtures/wrong-shape.json')}</Code>

In a disposable project copy, first create normal output and preserve a backup. Copy a bad fixture to that copy's _output/tasks.json. Run the same entry, observe nonzero failure, then compare the destination with the injected bytes using an editor or familiar read_bytes. Original fixtures remain unchanged.

The first is invalid JSON; the second parses but violates the array-root contract. Neither permits initialization. After observing failure, deliberately restore the good backup and rerun. Deleting damaged data until the app starts is not successful corruption handling. Data recovery, code repair and fresh initialization are different actions.

Likewise, do not reinterpret PermissionError as an empty list or broadly relax system permissions to make a demo work. Unknown failures should remain diagnosable instead of producing a misleading successful new file.

## 11. Independent variation: choose a plan within a budget

No line-by-line recipe: add a pure function over valid tasks and an ordinary nonnegative int budget. Consider unfinished tasks in original order. Skip an item that does not fit but keep considering later items. Exact fits and zero-minute items are valid. Return fresh selected records plus used minutes; preserve input and perform no file I/O.

This is not a globally optimal knapsack algorithm. Do not reorder tasks to maximize packing. First choose a signature and write tests that distinguish break/continue, equality, completed items, bool budgets and shared references. Then implement it, keeping the original 15 tests green.

## 12. Graduating from this stage is not deployment readiness

Exit this stage when you can explain your design from requirements, implement source/environment from an empty directory, detect a deliberate business defect, read data in a fresh process, preserve rejected input, recover in a second directory, complete the variation, and state the remaining concurrency, authorization, transaction and service-operation limits.

Your README must specify command working directories, versions, first/repeated outputs, intentional failures, owned output paths and recovery steps. A pause record includes source changes, last test command/count, whether data is currently damaged, backup location and the next behavior to prove—not merely the last page read.

L11 adds annotations to functions/containers whose behavior you already understand, separating static checking from runtime validation. Types, models, decorators and resource protocols then prepare HTTP and FastAPI; this integration assignment is not a shortcut past server foundations.
