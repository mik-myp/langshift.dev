## 2. 先固定不变的业务，再决定如何拆

## 4. APIRouter 登记路由，不负责启动服务

APIRouter 像一张可组装的路由登记表。`prefix="/tasks"` 与 `@router.get("")` 合成 /tasks；`@router.get("/{task_id}")` 合成 `/tasks/{task_id}`。不要在装饰器里再写一遍 /tasks，否则得到 /tasks/tasks。这里使用空字符串而不是末尾 /，避免实验无意依赖重定向。

模块导入时装饰器登记函数；main 调用 `app.include_router(router)` 时把路由加入应用。两步都不是在监听端口。Uvicorn 仍负责启动服务。忘记 include_router 时，Python 导入可能成功，/health 也可能正常，但 /tasks 是 404；这不是模型验证错误。

先认识接下来源码里尚未展开的记号：`Depends(get_store)` 是交给框架的声明，不是拿到 store 的普通函数调用。下一节先拆解机制，再阅读整个路由文件。

## 5. Depends：函数值、调用者与返回值

回忆 L13：写 get_store 是传函数对象，写 get_store(...) 才立即调用。`Depends(get_store)` 保存“处理请求时需要调用哪个提供者”的元数据。FastAPI 检查路由参数，找出依赖，准备依赖所需参数，调用依赖，再把结果当成路由参数传入。

一次列表请求的路径是：请求携带查询文本 → get_page 校验查询参数并获得 settings → get_store 获得当前 app 的 MemoryStore → list_tasks 使用两者 → 返回字典 → response_model 验证和过滤 → HTTP 响应。若提供者还有依赖，框架先满足它们；这形成一张小的调用关系图，不是一个读取全局魔法变量的黑箱。

`Request` 是 FastAPI 提供的当前请求对象，不是 JSON 请求体模型。`request.app.state` 是我们挂在**当前应用实例**上的状态容器。state 不会自动建立 store，也不会验证其类型；这些对象由工厂显式写进去。settings 是应用级配置，store 是应用级内存；它们不是每请求重建的对象。

在同一次请求中，相同依赖按默认策略复用解析结果。本例 create_task 直接请求 request_trace，get_store 也请求同一个 request_trace；两处使用相同 function scope，因此只获得一个跟踪资源。下一次请求会重新创建这个资源，不会复用已经关闭的文件。这个缓存不是跨请求数据缓存，也不让多个应用共享 store。

<details>
<summary>解释题答案：为何不能把 Depends(get_store) 改成 Depends(get_store())？</summary>

前者把函数交给框架，后者在模块导入时就尝试调用 get_store，而且没有本次 Request。它会在服务启动前失败，或把错误的调用结果当提供者。反过来，直接从普通 Python 调用一个带 Depends 默认参数的路由，也不会触发自动注入：默认参数仍是声明对象。调用普通业务函数进行单元测试，与走框架请求解析，是两个不同入口。

</details>

## 6. 同步 yield：取得一份临时资源，然后交还控制权

这次不用数据库冒充教学资源。每个依赖创建一个真实 TemporaryFile 文本句柄，路由写入动作名，finally 关闭它；只在终端输出不含请求体的 acquire/use/release 信息。临时文件不是长期审计记录，关掉后不再读取它。

<Code language="python">{getDependencyExample('task_api/dependencies.py')}</Code>

request_trace 是普通同步生成器函数。框架开始处理依赖时推进到 yield；yield 的 RequestTrace 对象交给使用者；退出时恢复生成器，让 finally 关闭文件。L14 的暂停/恢复没有改变，只是推进与退出的主人从手写 with 变成框架。不要再给这个提供者加 `@contextmanager`：FastAPI 需要这里的生成器函数，并负责管理它。

文件创建失败时尚未 yield，路由拿不到假资源；已经成功获取且进入 try 的资源，正常返回或异常传播时都会经过 finally。本例没有 except 吞掉 HTTPException，也没有“失败后返回空列表”伪装成功。如果强制杀进程、解释器崩溃或机器断电，不能承诺 Python finally 一定运行。

RequestTrace 的 mark 使用文件，close 负责释放。get_store 只是借用这个资源记录一次动作，不能自行 close。资源的所有者与使用者不同，正是需要依赖生命周期的原因。但释放不回滚任务修改，也不证明响应已送达客户端。

## 7. 版本和 scope 决定“清理在什么时候”

本实验固定 FastAPI 0.135.1。自 0.121.0 起支持这里使用的 `Depends(..., scope="function")`。本例明确选 function，因为响应已是普通 JSON 数据，不需要继续读临时文件：正常路由完成后、响应发往客户端之前清理。

对 yield 依赖，未指定 scope 的默认值是 request：**正常响应路径**会在响应发送之后清理。这不是“yield 总在发送前执行”的通则。历史版本变过行为，不能只引用一张旧时序图。若在依赖或路由抛出受处理的 HTTPException，异常展开会先清理，再由异常处理器发送错误响应；不要把正常成功时序机械套到所有错误。

```text
function, success: acquire -> use -> release -> response send
request, success:  acquire -> use -> response send -> release
handled HTTPException: acquire -> use -> release -> error response send
```

一个 request-scope 的 yield 依赖不能依赖更早关闭的 function-scope yield 子依赖，因为它自己的退出代码可能仍需要子依赖。function-scope 依赖则可以使用 function 或 request 子依赖。本例 get_store 本身不 yield；所有临时 trace 的声明显式使用相同 function scope，不制造混合寿命。

2026-09-28 维护验收不仅观察打印，还截取了实际 ASGI response.start/body 的发送位置，分别确认两种 scope 的成功和受处理错误，共四种时序。该探针涉及底层异步协议，只在维护脚本里，不把它变成读者的前置要求。**客户端已经收到响应后才查看“closed=True”，无法单独证明关闭发生在发送前还是发送后。**

<details>
<summary>预测题答案：一次 POST 会打开两份 trace 吗？失败的 GET 会漏清理吗？</summary>

不会因两处依赖声明打开两份：本次请求中它们共享同一个已解析依赖。正常 POST 的动作顺序是 acquire、get_store、create_task、release。合法但不存在的 ID 会先取得 store，再由 require_task 抛出 404；已经取得的 trace 仍经 finally 关闭。如果错误发生在取得资源之前，就没有那个资源需要关闭。不要要求所有 422 都必须执行相同依赖集合。

</details>

finally 不是“里面每条语句都会成功”的保证。客户端对本次创建的每个 ID 单独 try/except：记录该 ID 的清理失败，再尝试其他自有 ID，不清空整个服务。循环结束输出 CLEANUP FAILED、清理未确认的 ID 及各自诊断。“未确认”不声称超时删除到底有没有生效；重放前只检查这些自有 ID。主体已完成时，清理失败抛出 RuntimeError，进程非零退出；主体本来就失败时，body_succeeded 仍为 false，清理错误照样报告，但 finally 不再抛替代异常，也不 return，因此原 traceback 继续传播。逐项捕获清理错误不等于把整次运行伪装成功；一个简单标志即可保留两类诊断，不需要异常组框架。

这是通过 urllib 访问真正端口的独立客户端，没有调用 Python 路由函数。HTTPError 仍携带错误状态和正文，因此客户端把它当可检查的 HTTP 响应；连接拒绝则连 HTTP 响应都没有。断言失败时先看对应请求和服务端日志，不把“程序没抛异常”当唯一标准。它只在空的可丢弃服务运行，记录本次创建的 ID 并在 finally 删除；不会清空不属于它的全部记录。

## 11. 故意失败：定位阶段，而不是盲改代码

先停正在运行的服务，再逐条执行以下预期失败：

```text

ValueError: TASKS_MAX_PAGE_SIZE must be an integer from 20 to 100
```

这里列出 traceback 的最后诊断行，不承诺路径和完整栈完全相同。两次都应退出非零，发生在应用工厂阶段，而不是发出一个 422。恢复后用正确环境启动，/health 应再次 200；再用 TASKS_MAX_PAGE_SIZE=20 启动，/tasks?limit=20 为 200，/tasks?limit=21 为 422，正文 detail 为 limit exceeds TASKS_MAX_PAGE_SIZE。

| 观察 | 先定位哪里 | 恢复动作 |
| --- | --- | --- |
| No module named task_api | 工作目录、解压结构、当前环境 | 回到实验根目录，锁定同步后重新启动 |
| address already in use | 旧进程仍持有端口 | 停自己的进程或更换服务与客户端双方端口，不杀未知进程 |
| /health 200，/tasks 404 | 是否 include_router；实际前缀 | 恢复注册，重启，重新请求真实路径 |
| 输入 422 | body/query/path 的 detail.loc 或配置上限 | 修正调用方；别删除验证来换成功 |
| 未知 ID 404 但没有 release | 先确认依赖是否 acquire、finally 是否被破坏 | 恢复 finally；重放该请求，检查配对 |
| 第二次启动任务消失 | 内存生命周期，而非路由故障 | 承认边界；数据库持久化留到 D 阶段 |
