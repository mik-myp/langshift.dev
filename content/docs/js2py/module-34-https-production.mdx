## 1. A production entry point is not simply host=0.0.0.0

Seeing JSON locally proves one local request path works. Reliable, safe access for invited users requires more answers: where does DNS point, who authenticates the server, where does encryption end, which proxy may supply client information, and can errors or logs expose a token? Opening every interface and disabling certificate checks does not solve those problems.

This chapter follows O02, using HTTP and identity concepts established in H/S. You will explain responsibilities along DNS→connection→TLS→proxy→application and test certificate failures, forwarding trust, production errors, and browser-origin policy. Independent acceptance means testable entry constraints matched to the real authentication scheme. We buy no domain, request no public certificate, create no externally visible resource, and do not deploy a complete product for you.

[Download the complete O03 lab](/learning-assets/js2py/o03-https-production.zip). Python/web versions match O02; local tools tested were OpenSSL 3.6.4 and curl 8.7.1. The diagnostic API, failure endpoint, and standard-library forwarder are **local teaching tools**, not a production reverse proxy. They implement neither real login nor task authorization and must never receive real users or tokens.

## 2. Separate names, addresses, ports, and paths first

In `https://lab.test:8443/probe`, https selects encrypted HTTP, lab.test is the hostname, 8443 is the TCP destination port, and /probe is the HTTP application path after connection establishment. DNS commonly associates names with IPv4/IPv6 addresses through A/AAAA records. It does not select /probe or store login sessions. A CNAME aliases one name to another; it does not automatically issue a certificate for that alias.

Recursive resolvers and clients cache DNS results. TTL participates in cache lifetime; it is not a button that makes every device update immediately after a record changes. Checking A while leaving AAAA pointing at an old machine can send some clients to a different service. Domain control, DNS configuration, and the process running on a host are separate records.

This lab uses reserved `.test` names and does not modify system hosts or DNS. curl’s `--resolve` supplies a name→address mapping for that client invocation while preserving the URL hostname for TLS SNI, hostname verification, and HTTP Host. Local success therefore proves no public DNS configuration. The production template uses a reserved `.invalid` placeholder and is not a real deployment domain.

## 3. What TLS does—and does not—verify

TLS negotiates encryption and integrity for a connection while the client verifies such properties as the certificate chain, validity period, and hostname. The server possesses the private key corresponding to its leaf certificate; subjectAltName declares applicable names. Trusting a CA does not accept arbitrary hostnames: a certificate issued for lab.test cannot impersonate wrong.test.

TLS protects a connection. It does not decide whether a Bearer token expired, whether Alice belongs to a project, or whether the application leaks another user’s data. The HTTPS indicator is not general certification of business trustworthiness. If a proxy terminates TLS and connects to the application over HTTP, that later hop is plaintext. This lab confines it to same-host loopback. A cross-host or untrusted network requires a new transport-protection design, not copying this local upstream address.

A temporary local CA gives the experiment a controllable trust chain. `--cacert` selects it for this curl invocation without installing it into a system store. CA and leaf keys exist only in an owned /tmp directory with mode 0700 and files at 0600, removed afterward. Certificates last one day and are recreated rather than packaging old keys. `-k` skips essential checks and is not certificate acceptance.

## 5. Two-terminal requests: curl is the client, not the server

In terminal A, start from the lab root. `--serve` keeps the process in the foreground; `--port 0` lets the OS choose an available port. It prints the public CA path and two copyable lines, `export CA=...` and `export PORT=...`. The ellipses here describe runtime values, not paths to type. Copy the actual printed lines into terminal B and remain at the lab root. They contain a public trust-material path and port, not a private key or session token.

```bash
uv run --locked python tls_lab.py --serve --port 0
```

After pasting the actual export lines, run the following in terminal B. curl sends one request and exits; it does not create a listening service. `--noproxy '*'` prevents local proxy configuration from sending the teaching request elsewhere. `--resolve` maps this name/port to loopback, `--cacert` chooses the local trust CA, `--max-time` bounds total waiting, `--include` displays response headers, and `-H` adds a request header. The Bearer value is a fixed fictional marker, not a login credential.

```bash
curl --silent --show-error --include --max-time 5 --noproxy '*'   --resolve "lab.test:$PORT:127.0.0.1" --cacert "$CA"   -H 'Authorization: Bearer demo-not-a-valid-session'   "https://lab.test:$PORT/probe"
```

Expect HTTP 200 with scheme=https, host=lab.test, client=127.0.0.1, and authorization_present=true. The last field proves only that a header was forwarded, **never that authentication succeeded**. To observe failures, omit --cacert, then separately change both the resolve name and URL to wrong.test. Both returned curl exit 60 in this run, before business handling. 60 is not an HTTP status.

Finish with Ctrl+C in terminal A. The program stops its own edge and backend process and removes temporary keys. Do not use killall or stop every uvicorn on the machine. Terminal B’s CA variable now points to a deleted file; reusing it causes a local file/trust error. A fresh launch requires fresh printed export lines.

## 6. Reverse proxies: trace requests and credentials across every hop

A client selects a server entry point. A **reverse proxy** accepts requests on behalf of the application and opens an upstream connection. The application’s immediate TCP peer is usually the proxy, not the original browser. A proxy can terminate TLS, centralize entry, and constrain requests, but does not automatically establish user identity. Authorization must reach the authentication layer on routes that need it, without appearing in access logs or debug echoes.

The local chain is curl → loopback teaching TLS edge → loopback HTTP Uvicorn → FastAPI. The edge forwards an allowlist of headers, bounds bodies at 4096 bytes, applies timeouts/response bounds, rejects unsupported transfer forms, and overwrites forwarding information. This deliberately small implementation has no HTTP/2, WebSocket, streaming, complete request-smuggling-resistant parser, or production throttling. **Never deploy it publicly.**

413 is an observed policy of this teaching edge, not evidence that H04 or S03 already limits request sizes. Production must separately implement and test real entry-point bounds and login throttling, including the boundary when a caller bypasses the normal proxy and reaches upstream directly.

## 7. Trusted proxies: a header is not a network fact

Any client can send `X-Forwarded-For: 203.0.113.9` or `X-Forwarded-Proto: https`. Unconditional trust can poison rate-limit/audit identity, generate wrong redirects, or misclassify HTTP as HTTPS. `--proxy-headers` enables interpretation; `--forwarded-allow-ips` restricts which immediate peers may supply that information. `*` trusts every reachable peer and is not a quick fix for a wrong URL.

The experiment has three stages. With proxy trust disabled, forged headers are ignored and scheme=http/client=127.0.0.1. Through the trusted edge, caller values are overwritten and the application sees https and actual loopback. But another local client connecting directly to the trusted loopback upstream **can forge the client value**. This reveals the limit: trusting 127.0.0.1 trusts local processes able to reach that upstream, not exclusively one proxy process.

Production must review the proxy allowlist together with real network isolation, socket permissions, process accounts, and container networking. Multiple proxies or a hosted CDN require an explicit hop-by-hop design for sanitizing, appending, and interpreting headers. Even a reliable source IP is not a user identity and never replaces Bearer validation or object authorization.

## 8. Production errors: return less without losing diagnosis

Debug pages, tracebacks, exception repr, and validation input/ctx can disclose paths, SQL parameters, passwords, or tokens. Production must not expose convenient debugging as a default public interface. The diagnostic app creates its own random request ID, returns only generic detail for 500, logs a safe event name and correlation ID, and returns only loc/type for validation failures without echoing input.

Real operations need access-controlled error observation, appropriate safe context, and alerting; this small logging demonstration is not full observability. /fail exists to trigger a local experiment, not as a public failure button in the real application.

## 9. Align with S01–S03: opaque Bearer, not JWT or cookies

Integration follows the S-stage contract: the service generates a high-entropy opaque random session token. Its raw value is returned only on successful login; the database stores its SHA-256 digest, expiry/revocation state, and session auth_version. Every request checks the session, expiry, active user, and current version before project membership and action authorization. HTTPS protects transport and the proxy forwards Authorization; **neither performs the application’s database verification**.

This is not JWT signature verification and requires no JWT key pair from this chapter. Logout, password changes, disabling, and logout-all are enforced by S-stage revocation logic, not bypassed by a proxy-cached successful response. S03’s UUIDv4 Idempotency-Key and Idempotency-Replayed must also survive the entry path; an idempotency receipt is not permanent permission.

This download verifies only `authorization_present`, with no real session database. Its 200 is not an S03 login success. Production must reconnect S03’s DB-backed readiness, authorization/revocation/idempotency tests, credential-safe logging, and configured/tested login throttling and request bounds. Never replace the complete identity system with a simplified operations-demo bypass.

## 10. CORS constrains browser response access, not caller authority

A browser origin combines scheme, host, and port. `https://frontend.lab.test:8444` differs from HTTP, another port, or another subdomain. Explicit Authorization or certain content types can cause a browser to send an OPTIONS preflight asking whether the origin, method, and headers are allowed. It sends the corresponding actual request after permission. CORS does not sign request bodies or prevent non-browser clients from calling an API directly.

The local app permits one exact demonstration origin, GET/POST, and Authorization/Content-Type/Idempotency-Key headers. expose_headers lets the frontend read correlation and idempotency-replay headers. There are no cookies, allow_credentials is false, and no wildcard opens access to everything. The complete S API also uses methods such as PATCH/DELETE; integration must add and test the real method policy rather than treating this diagnostic app’s two methods as production configuration.

The experiment verifies approved-origin preflight=200 and another origin’s preflight=400, yet a direct ordinary GET still returns 200 without Access-Control-Allow-Origin. curl does not enforce browser response-access rules. **CORS cannot replace authentication or authorization.** HTTP-header tests also do not accept every real browser behavior; actual frontend integration remains pending.

## 11. CSRF follows credential mechanics, not frontend/backend separation

Traditional CSRF exploits automatically attached ambient credentials, such as cookies, so a malicious page can send requests as a logged-in user. Our opaque Bearer is explicitly placed in Authorization by frontend code; the service does not treat cookies as sessions, so it does not expose that same automatic-cookie path. This is not “all CSRF/XSS risk disappears.” Stolen tokens, incorrectly allowed origins, unsafe redirects, or caller logic sending credentials to the wrong address still create failures.

Switching to cookie sessions requires renewed evaluation of SameSite, Secure, HttpOnly, Origin/Referer checks, anti-CSRF tokens, safe-method semantics, and legitimate cross-site flows. Setting allow_credentials=true is not a release plan. HttpOnly limits script access to a cookie but does not stop automatic sending. Secure restricts transport to HTTPS but does not establish user intent.

The S-stage demonstration frontend can use a short-lived in-memory token and require login after reload. This reduces some persistent-storage exposure but cannot defeat XSS in the current page. Do not recommend long-lived localStorage tokens as a universal default or copy real tokens into screenshots, error reports, or proxy logs. This chapter uses fictional markers only.

## 13. Layered diagnosis: do not conceal distinct faults with -k

| Observation | Layer | Next step |
| --- | --- | --- |
| Name resolution fails | DNS/client resolution | Inspect records or local --resolve; TLS has not started |
| Connection refused | Address/port/listener | Inspect your own process and actual port, not certificates |
| curl 60, unknown CA | Trust chain | Use this run’s public CA and check validity, never -k |
| curl 60, wrong name | URL hostname versus SAN | Correct name/certificate, not authentication code |
| 502 | Proxy-to-upstream hop | Inspect upstream process, address/namespace, and timeout |
| 500/422 | Application/input | Use sanitized request ID or loc/type without echoing secrets |
| Browser CORS error while curl responds | Browser access policy | Check exact origin, preflight and actual headers; assess authentication separately |
| Wrong scheme or forgeable client IP | Forwarding trust | Inspect peer, sanitization and reachability, not allow-ips=* |

A TLS handshake failure occurs at a different stage from HTTP 401/403. The diagnostic app implements no 401/403 authentication behavior; verify that in the complete S03 service. Share only safe categories and correlation IDs, never Authorization, Cookie, database URLs, or private keys.
