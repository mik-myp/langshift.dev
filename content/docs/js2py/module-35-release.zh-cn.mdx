## 1. “测试通过”离发布还差哪些证据？

H06 能检查 API，D05/D06 能检查迁移和真实数据库，O01—O03 建立进程、容器、网络入口的边界。把这些命令放进一个 YAML 还不等于安全发布：测试可能连错库，多个 worker 可能同时改表，旧程序可能读不了新结构，回退代码也不会自动撤销新版本写入的数据。

本章用一个小而真实的发布序列把责任分开：检查候选代码 → 在独占测试库验证迁移和接口 → 审查兼容矩阵 → 单独执行迁移 → 启动候选版本并做就绪验收 → 才允许切换流量。任何一步失败，后面的动作都不应假装继续成功。

## 3. 环境分离先落实到连接与所有权

“测试数据库”不只是把名字改成 test。测试必须拥有创建和清理权限，不能接受一个误指生产的默认 DATABASE_URL。本实验不读取环境里的业务 DSN，只允许自建 `/tmp/ls-ops-*` 目录下的私有 Unix socket，数据库名字也采用固定 allowlist。

mkdtemp 给每次运行独占目录；0700 限制目录访问，标记记录 UID 和随机所有权值；停止前重新核对路径、所有者、模式与标记，不允许 symlink 把清理指向别处。PG 不监听 TCP，API 只监听 127.0.0.1 临时端口。private socket 下的 trust 是本机短命教学政策，**不是生产认证配置**；同一操作系统账户仍是信任边界。

开发、自动测试、预发布、生产应使用不同数据库、账户和秘密，部署账户与应用账户也分开。这里真实验证的是隔离测试环境，不把它叫成已经部署好的预发布环境。若工具版本不符或路径检查失败，就停下来定位，不能改脚本去连接已有用户库“先跑通”。

传入私有 socket 的 host 还不够：libpq 仍可能从 `PGHOSTADDR`、`PGSERVICE`、`PGSERVICEFILE` 等环境变量取得另一个连接默认值。`reject_connection_environment` 在创建临时目录之前，以及每次直接连接、迁移和服务启动之前，拒绝继承的全部 `PG*` 变量，唯一例外是只定位可执行文件的 `PG_BIN`。错误只列变量名，不打印值，也不修改调用者环境。Python 连接、SQLAlchemy 的连接创建器和 PG 子命令都使用自有目录内的空白 0600 `empty.pgpass`，不读取用户的默认密码文件。直接运行 `demo.py` 或 `ci.py` 也执行这些防护，不依赖仓库总 runner 先替它清理。

启动 API 不再先探测空闲端口、关闭探测 socket，再要求另一个进程抢占同一号码。Uvicorn 自己用 `--port 0` 完成绑定；控制器从**该子进程自己的私有启动日志**读取实际端口，再请求 readiness。`--no-access-log` 不关闭 info 级启动 banner；控制器固定无颜色日志和单 worker。两个同版本服务也使用不同日志文件。测试实际同时启动两个服务，核对两个不同端口、各自 banner、真实请求和退出清理。这消除了选端口后释放再绑定的窗口，不是对任意并发故障的保证；未来 Uvicorn 改变 banner 格式时会超时拒绝，不猜测端口。

迁移控制器用管理身份和事务执行，设置 lock_timeout，失败应回滚并停止发布；普通 worker 不在启动时争抢 DDL。我们的演练由一个操作员串行执行，**不宣称这个函数实现了跨部署系统的分布式迁移锁**。真实流水线还要保证只有一个发布协调者，并根据表大小、锁等待和兼容窗口决定执行时机。

downgrade 明确拒绝自动破坏性回退。删掉 description 列会丢失新版本已写的数据；即使技术上可以写 DROP COLUMN，也不能把它当作普通代码回退的一部分。备份与恢复也会丢失快照之后的数据，O06 恢复流程会单独计算这个窗口。

<details>
<summary>解释题答案：为什么“每个 worker 启动时 upgrade head”不是方便的默认？</summary>

多个 worker 可能并发读版本、等待或争抢锁；部分新进程已经对外服务，另一部分仍卡在迁移。应用账户还被迫持有 DDL 权限。把迁移作为受控发布步骤，可以先观察失败并停止后续动作，再启动通过兼容检查的进程。它不是保证迁移必定无锁、无停机；这些仍由具体变更与数据规模决定。

</details>

## 6. 用矩阵描述兼容，不靠“应该没问题”

| 应用 / 数据结构 | 006，无 description | 007，description 可空 |
| --- | --- | --- |
| v1，按 id/name 读写 | 可用 | 可用，新列省略为 null |
| v2，需要 description | 拒绝启动 | 可用 |

向前兼容在本次回退语境里，是旧应用能继续面对已经扩展的新结构。新增可空列只解决这个例子，并不意味着所有 ADD COLUMN 都安全：新约束、默认值、枚举、新请求格式或数据含义都可能让旧程序失败。

切换 v2 后如果客户端已强制依赖 description，退回 v1 的响应就可能不满足客户端。因此回退计划还需要前后端兼容窗口、功能开关或协调停止新功能写入；不能只验证数据库列存在。本实验明确由控制客户端分别使用对应版本的契约，不冒称真实用户切换零影响。

## 8. 失败不是重建数据库的理由

NOT NULL 失败的根因是历史记录没有值，不是 Alembic “坏了”。修复顺序是审查需求：先增加可空列；部署兼容代码；按业务规则回填；验证无空值；另一个受控版本才加约束。不能把用户数据删除重建来让 migration 变绿。

其他故障要分阶段定位：版本不符在环境门禁失败；错误 revision 在迁移/兼容检查失败；角色不足在数据库授权失败；就绪超时在应用启动或 DB 路径失败；公网连不通则属于当前实验没有覆盖的入口层。打印整个环境、SQL 参数或 Bearer token 都不是合理诊断手段。

<details>
<summary>带提示修复答案：如何证明失败没有留下半迁移？</summary>

不要只检查异常类型。重新连接，确认项目仍为原来的三条、alembic_version 仍为 006，再执行经过审查的 007。事务内的失败 DDL 会回滚，但不能由此推断所有外部副作用或所有迁移操作都可回滚。需要逐变更确认；例如并发索引创建、外部调用和长时回填有另外的约束。

</details>
