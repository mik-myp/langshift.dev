## 1. 函数返回的字典，不会自动留到下一次运行

L06 把规则、汇总和入口拆开了，但每次启动仍然重新建立输入。函数返回的字典存在于当前进程中；它有变量名、被打印到终端，都不等于已经保存。

持久化意味着把数据记录到进程结束之后仍能重新读取的地方。本章从**实验自己拥有的小型本地文件**开始，不引入数据库或服务器。目标是把 Python 值、文本、编码后的字节、文件系统路径和已经打开的资源之间的边界逐个解释清楚。

## 2. 路径描述位置，不等于已经打开文件

L06 中，当前目录与脚本目录可以不同。文件操作也一样：相对路径以进程的当前工作目录为基准，不会自动以写出这行代码的源文件为基准。

本章使用标准库的 `Path`。`Path("fixtures")` 创建路径对象，不会创建目录，也不会打开文件。你已经使用过列表和字典的方法；现在只是使用库提供的现成类型与方法，不要求自己编写类。

文件：`paths.py`。

<Code language="python">{getFileExample('paths.py')}</Code>

```bash
uv run --no-project --python 3.13 python paths.py
```

下面用 `<LAB>` 代表你实际解压目录的绝对路径。这是输出中的占位表示，不是要输入的命令：

```text
Cwd: <LAB>
Relative: fixtures/notes.txt
Absolute: True
Name: notes.txt
Parent name: fixtures
Target: <LAB>/fixtures/notes.txt
```

这些操作承担不同职责：

1. `Path.cwd()` 观察进程当前工作的目录。
2. 左边是 Path 时，`/` 拼接路径组成部分，这里不是数值除法；不用手动拼不同平台的分隔符。
3. `Path(__file__).resolve().parent` 从当前源文件出发，解析绝对位置，再取得所在目录。`resolve()` 还会解析符号链接；它不保证目标存在、可以读取或满足安全要求。
4. `.name` 是最后一段名称的字符串；`.parent` 是另一个路径对象。它们都没有包含文件内容。

如果右边的组成部分是绝对路径，它可能替换前面的路径，而不是继续留在前面的目录之下。本章只使用固定、可信的路径组成部分。**路径拼接不是任意用户输入路径的安全沙箱**；这类输入需要在后面的服务端安全边界中另行处理。

只改变当前目录，再执行同一个文件：

```bash
cd fixtures
uv run --no-project --python 3.13 python ../paths.py
cd ..
```

只有 `Cwd:` 变成 `<LAB>/fixtures`，固定到脚本位置的 `Target:` 不变。这里的 macOS 实测路径用 `/` 展示，你的系统可能显示其他分隔符。把数据放在脚本旁边适合这个可写的本地实验，不代表安装后的应用源码目录永远适合存放生产数据。

## 3. 完整读取一个文件，观察资源边界

UTF-8 输入 `fixtures/notes.txt` 有两行。第二行**开头和结尾各有两个空格**，两行都以换行符结束。我们用 `repr` 观察不可见字符，而不是不加判断地清理它们。

文件：`read_text.py`。

<Code language="python">{getFileExample('read_text.py')}</Code>

```bash
uv run --no-project --python 3.13 python read_text.py
```

```text
Inside closed: False
Text: 'Python 学习\n  keep spaces  \n'
After closed: True
```

把 `with path.open("r", encoding="utf-8") as stream:` 按执行顺序理解：

1. `path.open(...)` 请求操作系统以读取方式打开这个路径。如果失败，缩进块不会执行。
2. 成功进入后，`stream` 指向一个**文件对象**，它关联已打开的资源以及当前读取位置。它不是 Path，也不是文件中的文本。
3. `.read()` 通过这个资源取得文本；`encoding` 指定文本流怎样把存储的字节解码。
4. 离开这个文件的 with 块时关闭资源；后面会具体观察普通异常与 return 路径。`.closed` 用于查看关闭状态。

`text` 已经是读取到内存中的独立字符串。关闭流不会清空它，也不会删除文件。`stream` 名称在块外仍然存在，只是对应资源已经关闭；这不是 JavaScript 式的块级局部名称创建。

`Path.open(...)` 与内置的 `open(path, ...)` 承担类似的基本作用；本章统一使用前者，让路径操作始终可见。`with` 用于管理资源的使用范围，不是导入、循环，也不是把失败自动变成成功的异常处理器。

因为路径固定到脚本位置，这样也会读取同一份输入：

```bash
cd fixtures
uv run --no-project --python 3.13 python ../read_text.py
cd ..
```

## 4. 读取会移动位置，逐行遍历也不等于清理数据

文件：`read_cursor.py`。

<Code language="python">{getFileExample('read_cursor.py')}</Code>

```bash
uv run --no-project --python 3.13 python read_cursor.py
```

```text
First: 'Python'
Rest: ' 学习\n  keep spaces  \n'
At end: ''
Reopened: 'Python'
```

`read(6)` 在这个文本流中最多读取六个字符，并向前移动位置。随后的 `read()` 从那里继续，而不是重新开始；到文件末尾后，无限制读取会返回空字符串。重新打开一个读取流，才得到一个从开头开始的新位置。理解顺序读取，不需要先学随机定位。

不指定数量的 `.read()` 可能把整个文件读进内存。这适合这些小样本，不是处理任意大上传文件或日志的无限内存方案。对于顺序文本，可以直接遍历文件：

<Code language="python">{getFileExample('read_lines.py')}</Code>

```bash
uv run --no-project --python 3.13 python read_lines.py
```

```text
1 'Python 学习\n'
2 '  keep spaces  \n'
```

循环使用文件提供的迭代行为，每次取得一行。存在的行结束符通常也包含在结果中，最后一行则未必有换行；不能因为这个输入有，就假设所有文件都如此。

`.strip()` 会把第二行有意义的空格与换行一起删掉。它是数据变换，不是读取文件必须执行的动作。`print(line)` 还可能产生额外空行，因为原行已经带有 `\n`，print 又补了一个。使用 `repr`，可以在不修改输入的情况下观察这些机制。

## 5. 文本不是字节，编码也不是显示偏好

Python 的 `str` 表示 Unicode 文本，文件存储的是字节。编码把文本变成字节，解码把字节解释为文本；两者都不是 JSON 操作。本章明确约定 UTF-8，使文件含义不依赖机器上隐含的默认编码。

文件：`encoding_bytes.py`。

<Code language="python">{getFileExample('encoding_bytes.py')}</Code>

```bash
uv run --no-project --python 3.13 python encoding_bytes.py
```

```text
Text length: 2
Byte length: 6
Bytes: b'\xe5\xad\xa6\xe4\xb9\xa0'
Decoded: 学习
```

这两个汉字各占三个 UTF-8 字节。`b'...'` 表示 bytes 值，不是给普通字符串加一个装饰性前缀。`len(str)` 统计 Unicode 码点；复杂的可见符号可能由多个码点组成，所以它并非普遍意义上的“用户眼中的字数”。`len(bytes)` 统计字节数。

文本流替你完成解码，而二进制模式返回字节。文件：`read_binary.py`。

<Code language="python">{getFileExample('read_binary.py')}</Code>

```bash
uv run --no-project --python 3.13 python read_binary.py
```

```text
Is bytes: True
Decoded: 'Python 学习\n  keep spaces  \n'
```

`"rb"` 表示读取二进制数据。二进制打开时不传 `encoding`，确认格式后再明确解码。文本写入需要 str，二进制写入需要 bytes。这里用小对照建立边界，不扩展成二进制文件格式课程。

现在在 `error_wrong_encoding.py` 中故意选择错误的解码器：

<Code language="python">{getFileExample('error_wrong_encoding.py')}</Code>

```bash
uv run --no-project --python 3.13 python error_wrong_encoding.py
```

先打印 `After error closed: True`，随后以 **UnicodeDecodeError** 退出：ASCII 无法解码输入中的汉字字节。打开成功，读取时解码失败，离开 with 仍先关闭文件，外层处理器才运行。这里是在已知打开成功后的解码失败中引用 `stream`，不是宣称任意打开错误之后这个名称都已经绑定。

换一个编码声明，不会自动把损坏的字节恢复为正确文本。不要为了藏起异常就加 `errors="ignore"`：被丢弃的字节可能有实际意义。应先确定来源编码，或者拒绝输入。下载中还有 `invalid-utf8.bin`，只含单个字节 `0xff`，它不是有效的独立 UTF-8 序列，后面会用它定位错误发生的层次。

## 6. 写入模式是在做数据损失决策

写之前先确认目标。下面的程序用 `.mkdir(exist_ok=True)` 创建 `_output/`，而它的父目录已经存在。`exist_ok=True` 允许目录已经存在，不会把文件变成目录，也不会忽略权限。中间目录不存在时，需要明确决定是否创建，而不是假设 open 会自动补齐。

文件：`write_text.py`。

<Code language="python">{getFileExample('write_text.py')}</Code>

```bash
uv run --no-project --python 3.13 python write_text.py
```

```text
Characters written: 10
Read back: '学习 Python\n'
```

`write` 不会自动补换行，所以字符串自己包含一个。这里返回的 10 是文本字符数，**不是字节数**；生成的 UTF-8 文件有 14 字节。`newline="\n"` 避免写入的换行被按平台转换，使实验输出字节保持一致。文本读取采用默认换行行为时，会把常见行结束形式统一成 `\n`；二进制读取不会做这种转换。

| 本章使用的模式 | 目标不存在 | 目标已经存在 | 主要风险 |
| --- | --- | --- | --- |
| `r` | 失败 | 读取，不主动写入 | 路径/编码错误，或无限制读取 |
| `w` | 父目录存在则创建 | 打开时即截断，早于第一次 write | 后续操作失败也可能已经丢失旧内容 |
| `a` | 父目录存在则创建 | 从末尾追加写入 | 重复执行会增加数据，不是整份 JSON 的更新协议 |
| `x` | 创建新文件 | 抛出 FileExistsError | 调用方要明确决定如何处理已有文件 |

`write_modes.py` 只重置自己的 `_output/modes.txt`，对比追加和替换：

<Code language="python">{getFileExample('write_modes.py')}</Code>

```bash
uv run --no-project --python 3.13 python write_modes.py
```

```text
Appended: 'First\nNext\n'
Replaced: 'Reset\n'
```

接着由 `create_once.py` 使用独占创建：

<Code language="python">{getFileExample('create_once.py')}</Code>

在新解压、尚不存在 `_output/once.txt` 的实验中，**按顺序执行两条命令**：


第一次打印 `Created once`；第二次是**预期的 FileExistsError**，不会打印成功提示，也不会改变第一次留下的文件字节。如果之前做过这个实验，第一条命令就可能遇到已有文件。要重新开始，请使用新的解压副本，不要删除无关文件，也不要不理解后果就改成 `w`。

独占创建把“只允许新建”的决策表达在打开操作自身。先 `exists()`，再单独写入，不能保证这两个动作之间文件系统不发生变化。本章不实现多进程协调。

## 7. 关闭是明确的清理，不是回滚

文件对象关联操作系统资源和缓冲状态。不要依赖变量被丢弃或解释器“总有一天会清理”；应明确约束资源的取得与使用范围。

先运行 `closed_stream.py`，这是一个**预期失败**：

<Code language="python">{getFileExample('closed_stream.py')}</Code>

```bash
uv run --no-project --python 3.13 python closed_stream.py
```

程序先打印已经读出的字符串，再抛出 **ValueError: I/O operation on closed file**。字符串仍能使用，关闭的流却不能继续读。读取函数返回数据很合理；返回一个已经在函数内部关闭的资源，通常不是调用方想要的结果。

### 正常结束、return、块内异常和取得资源失败

`cleanup_paths.py` 把每条路径都变得可见。`stream = None` 记录尚未取得文件，避免观察代码本身在打开失败时又使用未绑定名称。

<Code language="python">{getFileExample('cleanup_paths.py')}</Code>

```bash
uv run --no-project --python 3.13 python cleanup_paths.py
```

```text
Mode: normal
Inside closed: False
After block closed: True
Finally closed: True
Result: normal
Mode: return
Inside closed: False
Finally closed: True
Result: early
Mode: error
Inside closed: False
Finally closed: True
Caught: ValueError
Mode: missing
No stream acquired
Caught: FileNotFoundError
```

正常路径会到达 with 后面的语句；return 路径不会，但离开 with 仍会先关闭文件，外层 finally 才执行。异常路径先关闭，再把 ValueError 传播给调用方。文件缺失时，既没有进入块体，也没有取得流。观察用的 finally 不负责再次关闭，只报告已经形成的状态。

这里教的是**使用内置文件资源**，不是实现自定义上下文管理协议。其他上下文管理器可能采取不同的异常处理策略；本章也不承诺进程被强行终止或断电之后一定清理。缓冲写出与关闭自身也可能失败，一次 write 调用成功不等于已经获得抗崩溃持久性保证。

### 文件关闭了，数据仍然可能错了

`pitfall_truncate.py` 故意准备并破坏**自己的临时实验文件**，不是修改输入样本：

<Code language="python">{getFileExample('error_missing_file.py')}</Code>

`error_missing_parent.py`：

`error_directory.py`：

```bash
uv run --no-project --python 3.13 python error_missing_parent.py

```

第一条抛出 FileNotFoundError，不打印 `Entered block`，因为 `fixtures/absent.txt` 刻意不存在。第二条同样是 FileNotFoundError：以 `w` 打开新文件，不会替它创建缺失的父目录 `absent-folder`。第三条把目录当成文件；实测 macOS 抛出 IsADirectoryError，某些平台可能对同一操作报告 PermissionError，所以还要检查路径和操作，不能只机械地看类别。

| 失败 | 应检查什么 | 不能直接推导什么 |
| --- | --- | --- |
| FileNotFoundError | 实际解析目标、缺少哪一段路径 | 不是所有缺失路径都代表“新的空用户数据” |
| FileExistsError | 独占创建政策和已有目标 | 不应静默切换到破坏性覆盖 |
| IsADirectoryError / NotADirectoryError | 路径各段究竟是文件还是目录 | 扩展名拼写不能决定文件系统类型 |
| PermissionError | 访问权限与预期可写位置 | 它不表示文件不存在 |
| UnicodeDecodeError | 字节内容与约定的文本编码 | 它不自动等于 JSON 语法损坏 |

对真正需要的资源执行操作，只处理你有能力恢复的失败。不要用一次 `exists()` 预检查替代异常处理，也不要为了让例子运行就给文件授予过大的权限。未知 OSError 应继续暴露。

## 9. JSON 把值转换成文本，保存是另一步

JSON 是数据交换格式，不是 Python 源码，也不是数据库。名为 `tasks.json` 的文件仍然存放字节，扩展名不会校验它们。语法正确的 JSON 文档，也可能包含程序不接受的值。

完整过程是：

```text
Python values -> JSON text (str) -> UTF-8 bytes in a file
file bytes -> decoded text -> parsed Python values -> business validation
```

`json_values.py` 只做值与文本之间的转换，不创建文件：

<Code language="python">{getFileExample('json_values.py')}</Code>

```bash
uv run --no-project --python 3.13 python json_values.py
```

```text
Is text: True
{
  "title": "学习",
  "minutes": 20,
  "done": false,
  "note": null
}
Equal value: True
Same object: False
Escaped: "\u5b66\u4e60"
```

`dumps` 返回 JSON 字符串，`loads` 把字符串解析为 Python 值。带 `s` 的版本处理字符串，而不是已经打开的文件。恢复得到的字典是新对象。`indent=2` 控制展示格式，不会让文档“更有效”。

`ensure_ascii=False` 让“学习”这样的字符直接出现在 JSON 文本里。默认的转义写法 `"\u5b66\u4e60"` 解析后表示同一个 JSON 字符串。**转义不是文件编码。** 两种文本表示都可以采用 UTF-8 写入。`allow_nan=False` 则拒绝输出非有限数，下一节会解释。

下面是静态浏览器语言对照，以本机验证为准，不借此操作浏览器文件：

<PythonEditor title="JSON 文本不等于已经保存的文件" compare={true} canRun={false}>

```javascript case=json-text-comparison
console.log(JSON.parse(text).title);
```


## 10. JSON 不是任意 Python 对象的通用复制品

| JSON 值 | 默认解码后常见的 Python 值 |
| --- | --- |
| 成员名称为字符串的 object | 键为 str 的 dict |
| array | list |
| string | str |
| 整数 / 带小数部分的数 | 默认解码下的 int / float |
| true / false | True / False |
| null | None |

JSON 不保留 Python 的元组身份，不直接表示集合、函数或任意对象。可互操作的 JSON 对象使用字符串成员名称；Python 编码器会把部分其他类型的键转换成字符串，这可能改变含义或产生冲突，所以我们的任务格式只使用固定字符串键。

文件：`json_limits.py`。

<Code language="python">{getFileExample('json_limits.py')}</Code>

```bash
uv run --no-project --python 3.13 python json_limits.py
```

```text
Restored: {'pair': [20, 35], 'labels': {'1': 'one'}}
Equal: False
Set is not JSON-serializable
Non-finite output rejected
Default decoder accepts NaN: True
Repeated key: {'minutes': 20}
Python repr is not JSON
```

逐项追踪，而不是假设所有对象来回转换后都完全相等：

- 元组变成列表，整数键变成字符串。
- 默认编码器不支持集合。不要在尚未约定格式时，通过随意转换来掩盖错误。
- 标准 JSON 不包含 NaN 或 Infinity。Python 默认 JSON 行为带有扩展；`allow_nan=False` 控制的是**编码**，不是 `loads`。默认解码器仍可能接受 NaN。JavaScript 的 `JSON.stringify(NaN)` 则得到 `null`，不能照搬失败行为。
- Python 默认解码器遇到重复成员名称会保留最后的值，并不是检测重复项。
- 字典的 `str`/`repr` 可能带单引号和 Python 的 False，不能充当 JSON 编码器。更不能用 `eval` 解析 JSON。

后面的任务校验把 minutes 限定为普通非负整数，因此会拒绝 bool 和 float，包括 NaN。但它**不会**检测原文中的重复键，不是通用严格 JSON 解码器，也没有实现大小/深度限制。本章是小型自有文件格式，不是任意不可信上传的处理政策；后者需要在后端边界明确制定限制和解析策略。

`dump(value, stream)` 把 JSON 文本写进文本流，返回 None，不返回生成的文本。`load(stream)` 读取并解析一份 JSON 文档。流负责 UTF-8，JSON 函数负责 JSON 语法和值。它们都不会替调用方自动关闭传入的流，生命周期由外面的 with 管理。dump 不会替我们补最后的换行，因此明确多写一次。

| dumps / loads | Python 值 ↔ 字符串 | 调用本身不打开文件 |
| dump / load | 值 → 可写流；可读流 → 值 | 调用方打开并关闭文件 |

## 12. 解析成功不是业务校验：按层定位失败

四段输入都可以被 JSON 解析。第二段根形状不对，第三段把格式要求的整数写成了字符串，第四段用了布尔值；不能让布尔值冒充整数混过去，`type(minutes) is int` 表达的就是这个严格边界。不同于 L05 的表单式文本输入，本章文件格式要求数字本身就是数字，自动调用 `int` 会掩盖契约不匹配。

接着在不修改输入文件的前提下检查六种情况。`inspect_documents.py` 导入刚刚解释过的函数：

<Code language="python">{getFileExample('inspect_documents.py')}</Code>

```text
wrong-types.json: invalid data: row 1 minutes must be a non-negative integer
```

沿边界追踪：

1. 打开可能在任何内容可用之前失败。
2. 把字节解码为文本可能失败，此时还没有有效文本。
3. 解析文本可能抛出 `json.JSONDecodeError`；`.lineno` 和 `.colno` 帮助定位语法位置，不负责校验业务含义。
4. 业务校验在读取的 with 块之后执行，此时文件已经关闭；它仍可能拒绝完全可解析的值。

JSONDecodeError 和 UnicodeDecodeError 都属于 ValueError 的子类。把一个宽泛 ValueError 处理器放在前面，会丢失这些区别。这里读取阶段使用具体处理器，校验阶段的 ValueError 则属于另外一次函数调用。PermissionError 与未知故障不会被重新解释成“没有数据”或“成功得到零”。

检查器报告坏文件后继续，是因为检查一组已知输入就是它的职责。任务保存程序承担的是另一种责任：**读取损坏输入后，必须在覆盖该输入之前停止。** 不要脱离用途照抄恢复政策。

- 找到失败发生的层次，说明哪个调用方有理由恢复，而不是把所有错误都当空数据。
- 从空目录重建任务存储，使用新进程运行，并验证拒绝输入时旧数据不变。

暂停时记录**当前目录、最后命令、目前已有的输出文件、这是首次还是重复运行、观察结果和下一个尚未验证的变式**。已有 `_output/once.txt` 或 `_output/tasks.json` 会改变下次运行的前提。回来先检查这些状态，再预测一个小实验，不要盲目清空，也不用重建整个环境。
