## 1. 数据库有一个 user_id，不代表请求来自这个人

D 系列为了演示关系和事务，曾让调用者填写 owner_id。那是明确的教学输入，不是认证。任意客户端都能改 JSON；TypeScript 类型、隐藏按钮和 CORS 都不能证明身份。本章把“谁在调用”从请求体移到服务验证过的凭证上。下一章才决定这个人有权操作哪些对象。

## 2. 先分清四样东西，再跟随一次登录

```text
password -> Argon2id verify -> active user
                                  |
                     random bearer returned once
                                  |
DB: token digest + user_id + auth_version + expiry
                                  |
next request: Bearer -> digest lookup -> user/version/expiry checks
                                  |
                         authenticated actor
```

**用户记录**表示账号，不是一次请求。**密码**是用户知道的长期秘密。**密码哈希**让服务器能验证密码而不保存明文；它不是可以解密回原密码的密文。**会话令牌**是登录后临时持有的 Bearer 凭证：谁拿到它，谁就可能代表该会话发请求，因此不能把它当成普通调试字符串。

浏览器路由状态中的 loggedIn=true 只是 UI 状态。服务必须独立验证每条受保护请求；前端不显示退出按钮、客户端忘记清掉令牌，都不应该改变服务端撤销结果。客户端收到一次登录 200，也不意味着它永久拥有身份，更不意味着可以访问别人的项目。

## 4. Argon2id 的工作不是“把密码快速变成一串字符”

<Code language="python">{getIdentityExample('security.py')}</Code>

阅读这个完整模块时先看 hasher、password_matches、login，不必一次记住每个函数。PasswordHasher 来自成熟的 argon2-cffi 库，明确选择 Argon2id；每次 hash 由库生成随机盐。盐、算法版本、内存/迭代参数和结果一起编码在保存的字符串中。验证时把这个编码结果和候选密码交给 verify，不自己拆字符串、比较自算密码哈希或设计加密算法。

这里固定 m=65536 KiB、t=3、p=4，采用该库文档中的低内存配置量级。内存与计算成本用于提高离线猜测成本，也会占用你的服务器资源：参数不是越大越好，更不是吞吐承诺。上线前必须在目标机器测量，并结合并发预算与限流。两个用户选择同一个密码应得到不同哈希；本章实际测试了这一点。

成功验证后检查 check_needs_rehash，必要时用当前参数重新哈希。此时才有明文密码可用，不能从旧哈希“升级计算出新密码”。这里只改变哈希编码策略，不把参数升级等同于用户改密；真正改密会提高 auth_version。

未知账号也验证一个启动时生成的 dummy hash，避免“没有用户就立即返回”的明显分支差异；**不承诺端到端恒定耗时**。正确结构下的未知账号、错误密码、停用账号都返回同样的 401。格式不合法仍可返回脱敏的 422；不能把所有失败都混成数据库异常。

<details>
<summary>解释性答案：为何密码不能用 SHA-256，而会话令牌摘要却可以？</summary>

人选的密码可能可猜，快速散列会让离线尝试便宜；需要成熟的带盐、可调成本密码哈希。会话令牌由 secrets.token_urlsafe(32) 生成，含 32 个随机字节，不是短密码或 user_id。对它做 SHA-256 用于数据库查找与避免保存原令牌，并没有自造密码哈希算法。数据库摘要也不是可直接提交的 Bearer，入口还检查原令牌格式。不过数据库泄露仍是安全事件，不能因只存摘要就取消数据库访问控制和备份保护。

</details>

## 5. 每次请求重新建立身份，不缓存“上次登录成功”

login 先在事务中锁定用户，验证密码与启用状态，产生随机令牌，保存摘要及当时的 auth_version，提交后才返回 access_token。默认寿命 900 秒，可配置范围 60–3600 秒。本例使用应用的 UTC 时钟，生产多实例仍需时间同步；使用 UTC 不会自动修复错误的机器时钟。

authenticate 按顺序执行：解析 Bearer 格式、对原令牌求摘要、查会话、锁用户、重新读取会话，然后检查启用状态、revoked_at、到期时间和版本一致性。任何失败都得到通用 401，并带 WWW-Authenticate: Bearer。查到摘要不是最后一步：数据库里保留着过期或已撤销记录也必须拒绝。

为什么锁顺序写进代码？普通请求取用户共享锁，改密/全部撤销取用户排他锁；再按用户、会话、项目、任务的顺序取得后续锁。这样撤销会等待已经开始并持锁的授权操作结束，提交后到来的请求看见新版本。它不是“让已经发出的响应倒流回来”，也不是无代价的并发优化。会话先做一次无锁定位，再在用户锁之后重新读取，避免把定位时的旧状态当最终判断。

<Code language="python">{getIdentityExample('db.py')}</Code>

每个请求使用自己的 Session 和事务，绝不在线程之间共享 Session。engine 是连接池入口，不是用户会话；auth_sessions 是业务表。READ COMMITTED 在引擎配置中明确写出，SQL 参数隐藏且 echo=false。不要混淆三种“会话”。

注意三个输出边界：UserPublic 只返回 id/login/is_active；TokenResponse 只在登录成功时将原 Bearer 交给客户端，并设置 no-store/no-cache 响应头；验证错误处理器只保留允许的 loc 和 type，不返回 input、ctx、msg 或原正文。连未知字段名也可能含敏感内容，所以错误位置中的未知名称被替换成 field。

## 8. 用不泄露令牌的真实客户端走完生命周期

另开终端，进入同一实验目录。客户端固定请求回环地址，通过 `ProxyHandler({})` 显式禁用环境代理，拒绝跟随重定向，用 getpass 读密码，将令牌写入模式 0600 的本地会话文件，不打印原令牌。**不要 cat 这个文件，也不要提交或打包它。** 它是终端实验设施，不是建议浏览器把令牌长期放进 localStorage。仅把 URL 写成 127.0.0.1 不够：urllib 默认会读取 http_proxy，原本发给本地的密码也可能先到代理。回归测试设有值的代理环境、去掉 no_proxy，用自建回环代理/目标证明目标收到请求而代理为 0，重定向目标也为 0；不能假定操作系统默认会绕过代理。

<Code language="python">{getIdentityExample('client.py')}</Code>

```bash
uv run --locked python client.py --port 8061 --session .session-alice.json login Alice
uv run --locked python client.py --port 8061 --session .session-alice.json request GET /users/me
cp -p .session-alice.json .session-before-change.json
uv run --locked python client.py --port 8061 --session .session-alice.json change-password
uv run --locked python client.py --port 8061 --session .session-before-change.json request GET /users/me
```

登录成功为 200，公开用户读取为 200，改密为 204 且正文为空，旧副本再请求为 401。客户端改密成功会删除当前本地令牌文件；服务端提高 auth_version 才是真正让所有旧令牌失效的原因。用新密码重新登录后再试两种撤销：

```bash
uv run --locked python client.py --port 8061 --session .session-alice.json login Alice
uv run --locked python client.py --port 8061 --session .session-alice.json request POST /auth/logout-all
uv run --locked python client.py --port 8061 --session .session-alice.json request GET /users/me
```

最后一步应为 401。单会话撤销路径是 /auth/logout，只设置当前会话 revoked_at，不影响另一个有效会话；/auth/logout-all 提升账号版本，连发起操作的令牌也失效。密码不是令牌，改密后不能继续把原令牌当新密码使用。

<details>
<summary>生命周期推演答案：停用后再启用，会不会复活旧令牌？</summary>

不会。管理员 disable 把 is_active 置 false 并提升 auth_version；enable 再提升版本。旧会话即使没有过期、revoked_at 仍为空，也因版本不匹配而失败。启用后必须重新登录获得新版本会话。仅删除浏览器里的令牌不能替代服务端撤销；仅改密码哈希而不检查版本也不能自动撤销已经签发的令牌。

</details>

记录状态，不记录秘密。此次验收不证明 TLS、登录限流、请求大小限制、哈希容量、泄露密码筛查、账号找回、MFA、生产日志管线、时钟同步或对象权限已经完成。HTTP 只允许 loopback；真实上线必须补齐并实测相关门槛。数据库和备份包含敏感哈希及会话元数据，需要受控访问。若改成 Cookie，还要另教 CSRF、SameSite、Secure、HttpOnly，不能借用本章 Bearer 流程的假设。
