<Code language="sql">{getSqlExample('sql/queries.sql')}</Code>

用逻辑阶段理解 A：FROM 找到 tasks → WHERE 保留 todo 且估时至少 20 的行 → SELECT 取 id/title → ORDER BY 按 id 排。结果是 `(1, 'Design API')` 和 `(4, 'Read SQL')`。这是理解模型，不保证执行器物理上照此扫描；优化器可以重排等价操作。

WHERE 的 `AND` 比 `OR` 结合得紧。例如“Launch 项目中 todo 或 doing”必须把两个状态用括号组合，否则 `OR status='doing'` 可能把别的项目也放进来。`=` 比较值，`<>` 表示不等，`IN` 表示属于集合。不要写 `==`，也不要用 SQL 条件的结果猜 Python truthiness。

筛选条件为 unknown 的行同样不返回：F 的 `NULL = NULL` 输出 `(null)`，`NULL IS NULL` 输出 true。`description IS NULL` 得 id 1、4；`description = ''` 只有 id 2；`description = NULL` 一行也没有。`COALESCE` 选择第一个非 NULL 值，可用于显示缺省值，但不能据此说缺失与零是同一种事实。

## 4. 排序与分页：稳定，不代表冻结

数据库表没有默认显示顺序。B 用 `ORDER BY minutes DESC, id ASC`：分钟多的在前，同分钟时用唯一 id 打破平局；`LIMIT 2 OFFSET 1` 跳过一行再取两行，得到 id 5、1。仅按非唯一字段排序，翻页时同分记录可换位；给查询加 LIMIT 本身不能保证顺序。

分页参数也属于业务输入：本实验 limit 必须是 1–100 的整数，offset 必须是非负整数，并拒绝 Python 的 bool 伪装整数。限制页大小是资源边界，不是认证。稳定排序只能在当前结果上确定顺序：第一页取 1、2 后，另一请求删除 1，再用 OFFSET 2 会得到 4、5，id 3 被跳过。测试真的执行这次删除，并不只讲“可能”。跨请求一致快照、游标分页和索引性能另行设计，本章不承诺大 offset 高效。

<details>
<summary>解释题答案：前端给列表加了 key，为什么后端还需要 ORDER BY id？</summary>

React key 帮助前端识别已收到的元素，不能决定服务器从数据库挑了哪几行。ORDER BY 决定结果顺序，唯一的第二排序键解决同分歧义；但两次请求之间的插入/删除仍会改变 offset 位置。三者分别是 UI 身份、查询顺序和跨请求一致性，不能互相替代。

</details>

## 5. JOIN：按匹配关系生成结果，不是把对象自动嵌套

C 把 tasks 与 projects 按项目 ID 相等组合，再按 created_by 找 users。别名 t/p/u 让同名 id 的来源明确。INNER JOIN 对每一对满足条件的行生成一行，找不到匹配就没有该结果；由于外键存在，每项种子任务能找到父项目和创建者。输出仍是扁平行 `(task_id, title, project, creator)`，不是自动嵌套的 JSON。

D 使用 LEFT JOIN，以 projects 为保留方，即使没有任务也产生一行，右侧列都是 NULL。这解释了两种易错计数：`count(*)` 数结果行，Empty 是 1；`count(t.id)` 只数非 NULL 的任务 ID，Empty 是 0。`sum` 在没有非空输入时是 NULL，报告明确选择 `coalesce(..., 0)` 表达“没有任务，总估时为零”。这不是把未知任务估时也定义成零。

G 把 `t.status='todo'` 放在 ON 中，先决定哪些子记录可以匹配，再保留所有项目；结果 Launch/Docs/Empty 的待办数为 1/1/0。若把该条件放到 WHERE，LEFT JOIN 补出的 NULL 行也会被过滤，Empty 就消失。选 ON 还是 WHERE 不是风格问题，而是需求不同。

再加 project_members 时要预测基数：Launch 三项任务乘以两名成员，得到六行。此时 `sum(t.minutes)` 会错误翻倍。只统计任务数可以 `count(DISTINCT t.id)`；求估时不能简单用 `sum(DISTINCT minutes)`，因为不同任务可能恰好同分钟。正确方向是先按任务或项目聚合，再组合成员信息，或者根本不做不需要的 JOIN。

## 6. GROUP BY 与 HAVING：行与组是两层过滤

D 把每个项目的匹配行收集成一组；SELECT 中输出项目键/名及聚合值。E 先用 WHERE 排除 done，再按 project_id 分组求 minutes 总和，最后 HAVING 只保留至少 30 分钟的组。结果只有 `(1, 75)`；Docs 的 20 没到门槛。不要把 `sum(minutes)` 塞进 WHERE：该阶段还没有组的总和。

写查询前，先用一句话定义“一行结果代表什么”。若答案是“一个项目”，SELECT 出任意一个任务标题就没有明确含义；要么改变分组粒度，要么选择合适聚合，而不是随机包一层 min 让语法通过。SQL 没报错只能证明语句可执行，不能证明分组符合业务。

<details>
<summary>带提示修改答案：把 G 改成每个项目的未完成估时，保留 Empty</summary>

把 ON 中的状态条件改为 `t.status <> 'done'`，SELECT 用 `coalesce(sum(t.minutes), 0)`，仍按项目分组。预期 Launch=75、Docs=20、Empty=0。若改到 WHERE，Empty 消失；若去掉 coalesce，Empty 是 NULL。三种结果都能解释，却只有第一种符合本题报告的契约。

</details>

## 7. CRUD：影响的是匹配集合，不是当前屏幕那一行

CRUD 对应 INSERT、SELECT、UPDATE、DELETE。INSERT 明确列清单，省略 identity 主键；`RETURNING` 让同一条写入返回数据库实际生成的 id，不要用“SELECT 最大 ID”猜刚写的记录——别的连接也会写。UPDATE/DELETE 的 WHERE 是数据安全边界：没有 WHERE 可能操作整张表；前端只选中一行不能改变它的含义。

下面的完整模块同时展示安全的查询和单条写入。先看 CRUD 函数：插入返回 id/title/status；更新显式维护 updated_at；删除返回被删 ID。WHERE 没匹配行通常不是 SQL 错误：fetchone 返回 None，由调用者决定映射成什么业务响应。错误父项目则触发外键异常，不能伪装成“没查到”。

## 8. 驱动、连接、游标和参数分别做什么

psycopg 是把 Python 调用转换成 PostgreSQL 通信的驱动，不是数据库，也不是 ORM。`connect` 与指定地址的服务器建立会话，返回连接对象；`cursor` 在该连接上执行命令并持有本次结果的读取位置。`fetchone` 取下一行，没行是 None；`fetchall` 取剩余行，本实验返回 tuple 列表。关闭游标释放结果资源，不等于提交事务或关闭连接；同连接的两个游标也不是两个独立事务。

从 list_tasks 追踪数据：Python 验证参数 → 选择固定 SQL 结构 → execute 发送结构与参数 → 服务端解析、执行与约束检查 → 驱动把结果转成 Python 值 → fetchall 返回。SQL 不会在 Python 里执行；数据库连接失败与输入 ValueError、SQL 约束错误发生在不同层。

`%s` 是 psycopg 的值占位符，不是字符串格式化操作。所有类型都用它，不按整数换成 `%d`；不要给占位符加 SQL 引号；不要用 `%` 运算符、f-string 或字符串加法把值拼进 SQL。单参数的 `(title,)` 是单元素 tuple，逗号不能省。None 被适配成 SQL NULL，SQL 类型错误仍可能由服务器拒绝。

参数**不能替代列名、表名、ASC/DESC 等语法**。`SELECT %s ...` 传入 `title` 只会返回字符串 title，不会读取 title 列；测试实际证明这点。list_tasks 的 ORDERINGS 仅选择作者写死的两个片段，再拼接片段，不拼用户输入。将来确实需要动态标识符时可用驱动的 Identifier 组合接口，但仍要限定用户允许选择的对象；引用安全不等于对象访问授权。

## 9. 注入实验与防护边界

SQL 注入发生在“不可信数据被解析成 SQL 结构”这一边界。错误反例是把 title 插进引号包裹的 SQL 文本；攻击者可以关闭引号，再改变 WHERE 或添加命令。不要靠替换单引号列表与攻击样本比赛，正确做法是把值交给驱动参数通道。

```bash

uv run --locked python demo.py
uv run --locked pytest -q
```

```text
todo [(1, 'Design API', 'todo', 30), (4, 'Read SQL', 'todo', 20)]
page [(3, 'Ship demo', 'done', 15), (4, 'Read SQL', 'todo', 20)]
totals [('Launch', 3, 90), ('Docs', 2, 60), ('Empty', 0, 0)]
unmatched payload []
literal stored [(6, "x' OR TRUE --")]
updated (6, 'doing')
deleted (6,)
tasks remaining 5
```

这是 reset 后的确定输出；重复执行 demo 而不 reset 时，identity 会继续增长。测试还存入 `'; DROP TABLE tasks; --`，精确查回原字符串，再确认 tasks 表仍有数据。证明的是这个驱动调用中的值未变成 SQL，不是证明整套系统永远没有注入。LIKE 参数中的 `%`/`_` 仍是模式通配符；参数化不会把模式自动变成字面搜索，也不会完成 XSS 防护、权限判断或分页成本控制。

故意把 sort 改成带分号的字符串，预期 Python `ValueError`，尚未发出 SQL；把 project_id 改成 9999，预期 PostgreSQL `ForeignKeyViolation / 23503`；直接把 description 与 NULL 用等号比较，查询成功但结果错。能把这三类失败分开，是排错能力的一部分。
