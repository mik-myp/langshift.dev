## 1. 从“看到报错”走到“知道谁该处理”

L04 已经让你遇到 NameError、TypeError 和 UnboundLocalError。此前我们故意让程序停止，是为了看到机制；现在任务时长不再总是可信的整数，而是一些类似表单内容的字符串。`"20"` 可以转换，`"twenty"` 不行，`"-5"` 虽然能转换，却不符合业务规则。

如果一个错误就让整批已知格式的任务无法处理，体验不好；但如果把所有失败都变成 0，程序会把“没有得到合法时长”谎报为“合法的零分钟”。更危险的是，代码本身写错也会被伪装成用户填错。

**本章的目标不是让红色文字消失，而是建立可解释的失败路径：知道哪里失败、哪里有能力恢复、哪里必须继续传播。** 调试用于找出原因；异常处理用于实现明确的恢复政策，二者不能互相代替。

### 本章契约

| 项目 | 约定 |
| --- | --- |
| 前置 | L00—L04：独立脚本、值与类型、容器和共享、控制流、函数调用与返回 |
| 新学 | traceback、复现与缩小问题、具体异常、raise、重新抛出与原因链、try/except/else/finally、assert 的边界 |
| 独立验收 | 将已知坏输入记入拒绝报告并继续；缺字段、类型错或未知内部错误仍可见；解释各条执行路径 |
| 暂不要求 | 类与自定义异常、导入、文件读写、pytest、调试器命令、日志框架、HTTP 异常或服务端架构 |

这里的“任务导入”只是**内存中的列表处理**，不是 CSV 文件导入、数据库写入或 HTTP 接口。名称描述业务动作，不偷偷增加运行前提。

## 2. 三种问题，不要都交给 except

| 问题 | 发生阶段 | 本章的处理方向 |
| --- | --- | --- |
| 语法不成立 | 当前文件还没有开始执行 | 修正冒号、缩进或结构；不是吞掉运行异常 |
| 运行中操作失败 | 执行到某个表达式或调用时 | 查具体异常与调用链，决定恢复还是传播 |
| 正常结束但结果错误 | 所有语句都可能合法 | 对照需求和边界输入，跟踪状态与控制流 |

下面是**有意语法错误**，单独保存为 `syntax_error.py`：

```python expected-error=SyntaxError case=syntax-error
print("Before")
if True
    print("Inside")
```

解析阶段在第 2 行发现缺少冒号。即使第一行看起来正常，也不会输出 Before。不能在同一个尚未解析成功的文件外面加 try 来让里面的非法语法变合法。以后动态编译或导入涉及的 SyntaxError 是另一个场景，不在这里混讲。

对照 L04 的运行异常：函数调用前的打印可能已经发生，未处理异常后的语句则不会执行。**没有异常也不代表业务结果正确**，第 4 节会复现一个过早 return 的问题。

## 3. 读 traceback：先定位失败点，再沿调用链找输入

文件：`errors/traceback_chain.py`。

<Code language="python">{getExceptionExample('errors/traceback_chain.py')}</Code>

标准输出只有：

```text
Starting report
```

错误流的核心结构如下。这里只归一化了绝对路径，并省略重复源码行和位置指示符；你本机的完整输出会更长：

```text
Traceback (most recent call last):
  File ".../errors/traceback_chain.py", line 17, in <module>
  File ".../errors/traceback_chain.py", line 12, in build_total
  File ".../errors/traceback_chain.py", line 6, in task_minutes
  File ".../errors/traceback_chain.py", line 2, in parse_minutes
ValueError: invalid literal for int() with base 10: '25m'
```

按两次阅读完成定位，而不是把整段 traceback 当作一条不透明字符串：

1. **先看最后一行**：ValueError 是异常种类；后面的消息说明 int 收到了不能按该规则解析的 `'25m'`。类别用于选择处理方式，消息用于定位细节；不要依靠匹配英文报错文案来设计恢复逻辑。
2. **再看最后一个相关文件位置**：第 2 行的 `int(raw)` 是失败表达式，不是 print 或 for 自己出了问题。
3. **向上追溯调用者**：task_minutes 传入字典的 minutes，build_total 正在遍历，顶层传入的是一份含 `"25m"` 的任务列表。每一层对应一次尚未完成的函数调用。
4. **区分原因与触发位置**：问题在输入不符合转换合同；不应看到第 2 行就把 int 换成一个无条件返回 0 的函数。

“most recent call last”表示最近的调用靠后。异常从失败处向外寻找匹配处理器：parse_minutes → task_minutes → build_total → 顶层；本例没有处理器，因此进程异常结束。函数没有成功返回本次结果，后面的 Done 不会输出。

终端常把标准输出和错误流放在同一个窗口。两种流的缓冲可能影响肉眼看到的排列，所以这里分开给出，不要求跨环境逐字比对路径、箭头或交错顺序。

### 4.1 先把实际输入观察清楚

文件：`errors/debug_observation.py`。

<Code language="python">{getExceptionExample('errors/debug_observation.py')}</Code>

异常前输出：

```text

```

观察得到“它确实是字符串，但带有 m”，而不是凭熟悉前端表单就假定“数字输入框产出的必然是数字”。`type(raw)` 负责看类型，`repr(raw)` 负责看值，两个问题分开。

文件：`debug_fixed.py`。

<Code language="python">{getExceptionExample('debug_fixed.py')}</Code>

预期：

```text

type: <class 'str'>

```

这里按当前输入合同把测试数据改成 `" 25 "`，验证 int 可以处理首尾空白。**这不是声称所有非法输入都能由开发者手工改掉**：真实坏文本如何拒绝，后面用明确规则实现。如果产品真的允许 `25m`，应先定义单位语法，再实现和测试；盲目截掉最后一个字符可能损坏原本合法的 `25`。

### 4.2 没有 traceback 时，仍要追踪执行路径

文件：`debug_logic.py`，有意把 return 放错位置。

<Code language="python">{getExceptionExample('debug_logic.py')}</Code>

实际输出：

```text

```

两项 10、20 应得 30，却只得 10。按 L04 的模型追踪：第一次循环累计成 10 → return 结束整个调用 → 第二项根本没执行。不是列表数据丢了，也不是 Python 的加法规则不同。

## 5. try/except：只恢复你能说明白的失败

文件：`recover_value.py`。

<Code language="python">{getExceptionExample('recover_value.py')}</Code>

预期：

```text
Input: '25'
Converted: 25
Next item
Input: 'bad'
Rejected: invalid literal for int() with base 10: 'bad'
Next item
Input: '0'
Converted: 0
Next item
```

`try:` 不是“提前测试这段代码有没有错误”，而是照常执行其中语句，并为**执行期间传播出来的异常**设置处理边界。流程分为两条：

- 正常：int 返回整数 → Converted 打印 → 跳过 except → 打印 Next item。
- 已知失败：int 抛出 ValueError → 跳过本次 try 中剩余语句 → 执行匹配的 except → 打印 Next item → for 开始下一项。

处理完异常**不会回到失败的 int 那一行自动重试**。本例也没有使用失败之前某次循环留下的 minutes；不能在 try 后无条件打印它，因为本次赋值可能根本没完成。

`except ValueError as error:` 把本次异常对象临时绑定为 error。`print(error)` 显示它的说明；`str(error)` 可以得到说明字符串。这个名称在处理块结束后会被清除，不要把它当作长期保存的结果；需要长期结果时，明确保存消息或结构化拒绝记录。

### 5.1 不是所有异常都匹配 ValueError

文件：`errors/unexpected_type.py`。

<Code language="python">{getExceptionExample('errors/unexpected_type.py')}</Code>

第 3 行得到 TypeError，既不打印 Rejected text，也不打印 After conversion。`None` 不是本例支持的数字文本。一个处理器只匹配其声明的异常种类及其子类，不会因为放在旁边就接住任何错误。

## 6. raise：主动表达“操作不能按合同完成”

`int("-5")` 能成功，但任务时长不能为负。没有解释器自动替你知道这个业务规则。

文件：`validate_minutes.py`。

<Code language="python">{getExceptionExample('validate_minutes.py')}</Code>

预期：

```text
Accepted: 25
Accepted: 0
Rejected: minutes must be non-negative
```

`raise ValueError("minutes must be non-negative")` 先创建带消息的异常对象，再使当前正常执行路径中断。它不是返回一个 ValueError，也不是打印一条错误后继续运行。外层调用者可以针对 ValueError 恢复；没有匹配处理器时，错误继续向外传播。

`type(raw) is not str` 检查输入是不是这里约定的普通内置字符串。str 既可用于 L01 学过的转换，也表示该内置类型；is not 是 is 的否定。本例有意采用窄合同，不接受数字对象后再偷偷用 int 截断小数，也没有声称支持自定义字符串子类或任意对象。

| 输入或问题 | 本章的约定 |
| --- | --- |
| `"20"`、`" 20 "`、`"0"` | 接受并返回整数，0 不是缺失 |
| `"bad"`、`""`、`"2.5"` | 文本不能转换成整数，ValueError |
| `"-5"` | 能转换，但违反非负规则，ValueError |
| None、20、2.5 | 不满足普通字符串合同，TypeError，不能冒充已知坏文本 |

转换语法以 int 的规则为准，**不是我们已经实现了“只能输入 ASCII 数字”的表单校验器**；例如符号及某些其他整数写法也可能有效。更严格的产品限制需要另行定义，不能从这个例子推断出来。

文件：`errors/negative_minutes.py`，没有外层恢复：

<Code language="python">{getExceptionExample('errors/negative_minutes.py')}</Code>

第 6 行产生 ValueError，消息为 `minutes must be non-negative`，没有标准输出。这条真实失败也会在第 12 节用优化模式再次运行。

### 与 JavaScript 的类比到哪里为止？

两边都可以主动中断当前路径，交给调用方决定怎么处理。下面是独立的静态对照；本章在本地验证 Python 的异常行为，不依赖浏览器运行按钮。

<PythonEditor title="主动拒绝不合法的时长" compare={true} canRun={false} height={430}>
```javascript !! js case=raise-comparison
try {
  throw new RangeError("minutes must be non-negative");
} catch (error) {
  console.log(error.message);
}
```

```python !! python case=raise-comparison
try:
    raise ValueError("minutes must be non-negative")
except ValueError as error:
    print(error)
```
</PythonEditor>

两边预期：

```text
minutes must be non-negative
```

JavaScript 的 catch 通常先接到被抛出的值，再在块内判断；Python 可以直接在 except 后指定异常类型。JS 允许抛出普通值，Python 的 raise 需要异常类或异常实例；不要照搬 `throw "bad"` 写成 `raise "bad"`。这里只使用内置异常，不要求你先学类继承。

## 7. 匹配顺序：具体错误在前，不代表应该什么都捕获

文件：`handler_order.py`，前半故意写出遮蔽关系，后半交换顺序。

<Code language="python">{getExceptionExample('handler_order.py')}</Code>

预期：

```text
Broad handler ran
Specific handler ran
```

处理器按书写顺序寻找**第一个匹配项**，一次异常不会把所有匹配块都执行一遍。ValueError 属于 Exception 大类，因此放在前面的 `except Exception` 已经把它接走。

认识当前需要的关系即可，不要求现在定义自己的异常类：

```text
BaseException
├── Exception
│   ├── ValueError
│   ├── TypeError
│   └── LookupError
│       └── KeyError
├── KeyboardInterrupt
└── SystemExit
```

这是节选，不是完整异常树。KeyboardInterrupt 常来自 Ctrl+C，SystemExit 表达退出；它们不属于 Exception。裸 `except:` 的捕获范围比 `except Exception` 更大，会把这些退出意图也包进去，本章不这样写。

如果多种已知失败确实需要相同恢复政策，可以写 `except (ValueError, TypeError):`，括号里是 L02 学过的元组；但**能合并语法不代表业务上该合并**。本章导入报告故意不把类型错误与文本格式错误合并。

不要把后半代码当成每个函数都要加 Exception 兜底的模板。大多数函数只需抛出或自然传播；只有真正拥有恢复职责的边界才处理。

## 8. 缩小 try，并用 else 把成功后的工作分开

仅仅把 `except Exception` 改成 `except ValueError` 仍然可能吞掉 bug：其他代码也可能抛出同一种异常。

文件：`pitfalls/wide_try.py`。display_minutes 里的 raise 是**故障注入**：我们用一个明确的失败替代未来可能写错的显示规则，观察边界，不是完整显示实现。

<Code language="python">{getExceptionExample('pitfalls/wide_try.py')}</Code>

实际输出：

```text
Bad input
```

输入明明是合法的 `"25"`，却被报告成 Bad input。try 包住了转换与显示，处理器分不清同为 ValueError 的来源；错误类型不是业务来源标签。

文件：`errors/narrow_try.py`。

<Code language="python">{getExceptionExample('errors/narrow_try.py')}</Code>

这里 int 成功后执行 else，display_minutes 抛出的 ValueError **不由同一条 try 的 except 捕获**。程序在第 2 行失败，消息保留 `display rule is broken`，没有 Bad input 或 After display。

else 的条件是 try 正常走完；如果 try 内已经通过 return、break 或 continue 转移控制，也不会再跑这个 else。它不是 except 的兜底分支，更不是所有分支之后必跑的代码。

这个结构把责任说清楚了：只把 int 的格式失败解释为输入错误；显示阶段失败继续暴露。也可以把成功后的工作放在其他明确位置，但不能让未知错误悄悄变成一个看似成功的返回值。

## 9. 保留错误：不处理、重新抛出、补充原因

### 9.1 没有恢复责任时，最简单的是不捕获

parse_minutes 不知道整批任务应当停止还是跳过一项，所以它只返回合法分钟数，或抛出明确异常。报告构造函数才知道逐行政策。不要在底层函数里随便 print 然后返回 None，让所有调用者猜测这个 None 究竟表示什么。

### 9.2 必须补充观察后，用裸 raise 继续传播

文件：`errors/reraise.py`。

<Code language="python">{getExceptionExample('errors/reraise.py')}</Code>

标准输出：

```text
Context: parsing Read
```

随后仍以 ValueError 异常结束，原始 int 的第 3 行仍在 traceback 中。except 内不带对象的 `raise` 重新抛出当前正在处理的异常；它不是另一次转换，也不是成功恢复。不能脱离正在处理的异常随意写裸 raise。

这里打印的上下文是固定教学文本。以后服务端会有结构化日志及敏感信息处理；本章不是推荐把所有输入或 traceback 原样发给最终用户。仅为了“捕获一下”而又重新抛出没有收益，不需要给每层函数都套这一结构。

### 9.3 更换消息时，把原始原因留下

文件：`errors/chained_error.py`。

<Code language="python">{getExceptionExample('errors/chained_error.py')}</Code>

`except ValueError as error` 只围住 int；随后 `raise ... from error` 给出稳定的领域消息，并明确原始异常是其原因。traceback 会先显示转换失败，再显示类似以下连接说明及新错误：

```text
The above exception was the direct cause of the following exception:
...
ValueError: minutes must be an integer
```

这里的 `...` 是**traceback 摘录的省略记号**，不是让你写进 Python 文件的实现。两个 ValueError 对象不是同一个对象，因果关系仍保留；原因链和第 3 节单个异常的多层调用栈也不是一回事。

没有使用 `from None` 隐藏原因，也没有把 NameError、TypeError 等所有问题都翻译成 ValueError。未知错误仍按原来的种类传播。

**停靠点 B**：分别运行宽 try、窄 try、重新抛出和原因链的文件。记录“哪里捕获、哪里继续失败、原始位置有没有保留”，不要以退出码为零作为唯一正确标准。

```text
Result: None
```

两条路径都先执行 finally，再把之前准备返回的值交给调用者。finally 没有把 None 改成 0，也没有决定这次转换是否成功。

| 离开方式 | except | else | finally 后的去向 |
| --- | --- | --- | --- |
| try 正常走完 | 不执行 | 执行 | 继续后续语句，或完成 else 中的 return |
| 匹配且被恢复的异常 | 执行对应块 | 不执行 | 继续后续语句，或完成 except 中的 return |
| 没有匹配的异常 | 不执行 | 不执行 | 清理后继续向外传播 |
| try 内 return | 不执行 | 不执行 | 完成已准备的返回；finally 仍先执行 |

文件：`errors/finally_unhandled.py`。

<Code language="python">{getExceptionExample('errors/finally_unhandled.py')}</Code>

标准输出：

```text
finally before propagation
```

然后仍然出现第 2 行 TypeError；不会打印 After。这说明“清理代码执行过”不等于“异常已经被处理”。except、else 或 finally 自己也可能失败；finally 里新的失败还可能取代当前传播的异常，不能把清理区当成不会出错的安全地带。

### 10.1 不在 finally 里偷偷 return

文件：`pitfalls/finally_return.py`，是明确反例：

<Code language="python">{getExceptionExample('pitfalls/finally_return.py')}</Code>

### 13.3 从空文件实现任务导入报告
