## 1. When should data and behavior live together?

Using dictionaries for tasks and functions for operations was not wrong, and does not become obsolete when class syntax appears. When several functions depend on the same fields and rules, an object can make relevant operations easier to find. It does not automatically provide a database, authorization, or unbreakable constraints.

We will build a small, traceable model of task completion. Understand what each object contains, which names refer to the same instance, and who can modify state. Do not convert every dictionary into a class merely because the syntax is available.

## 2. Compare an existing dictionary design before learning labels

A task has title, minutes, and done. The dictionary version can call mark_done(task), inspect done, update it if necessary, and return whether anything changed. The object version calls task.mark_done(). The benefit is not prettier punctuation but a clearer connection between state and relevant behavior. Whether it prevents mistakes depends on rules and tests.

A class describes how to construct and operate on a kind of object; an instance is a particular constructed object. Creating Task("Read", 30) twice creates distinct instances. Binding another name to an existing task does not copy it. Equal field contents and identical object identity are separate questions.

A Python class is not a TypeScript interface: classes and instances exist at runtime. Nor should you simply equate a Python class with a JavaScript prototype object. Start with observable construction, attributes, and methods, without assuming any backend framework experience.

## 3. self receives the instance; it is not hidden global state

This is a complete, independent example:

```python
class Counter:
    def __init__(self, start: int = 0) -> None:
        self.value = start

    def increase(self) -> int:
        self.value += 1
        return self.value


first = Counter()
second = Counter(10)
print(first.increase(), second.value)
print(Counter.increase(first))
```

```text
1 10
2
```

Ordinary instance-method access binds the instance as the first argument. Here first.increase() and Counter.increase(first) perform the same operation. self is a conventional name, not a keyword. Unlike relying on JavaScript this binding, you explicitly declare the receiving parameter but omit it when calling through an instance.

`self.value = start` sets an attribute on this instance; a local variable named value is a different storage location. __init__ initializes a newly created instance and should not return a business object. Implementing low-level allocation is outside this chapter.

<details>
<summary>Explanation answer: what changes after second = first?</summary>

Both names refer to one instance. Calling increase through either changes the same value. Constructing Counter(first.value) creates a different counter instead. Equal initial numbers do not make these operations equivalent copies.

</details>

## 4. Constructor checks establish a starting point, not a permanent seal

Task initialization checks a non-blank title, ordinary non-negative integer minutes, and strictly boolean done. Validated values are stored on the instance. If construction fails, the caller does not receive a normally initialized Task. Silently substituting zero would conceal the failure.

mark_done reports whether a transition occurred, so repeated completion is not counted twice. remaining_minutes derives its result from current done instead of storing another total that might become stale. Many state errors come from redundant information, not from insufficient inheritance layers.

Task attributes are still publicly writable. After valid construction, assigning -1 to task.minutes does not automatically rerun validation. Using the methods is a convention, not a security sandbox. Service inputs, database constraints, and business operations will each have responsibilities later; naming something a model does not remove those obligations.

## 5. Composition starts with ownership and sharing

Plan contains a task list: it has Tasks rather than being a Task. It copies the outer input list, so a caller clearing its own list does not empty the plan. The contained Task instances are intentionally shared: completing read changes the remaining minutes observed by the plan.

This is not a deep copy or a frozen snapshot. Draw the references: the original list points to task; Plan.tasks points to the same task; the two lists themselves differ. An independent snapshot needs an explicit policy about copied state and later updates, not merely list(...).

The implementation uses an ordinary for loop to avoid requiring generator expressions before L14. Plan is also not a public converter for arbitrary input: it expects a list of Tasks and does not validate every possible foreign object.

## 7. Explain the @ line before using dataclass

`@dataclass` above a class passes the created class through dataclass and binds the result back to the class name. For this simple use, think of writing the class and then `Estimate = dataclass(Estimate)`. It is not magic rerun whenever a field is read. L13 fully explains decorator evaluation, wrapping, and registration; this local explanation is enough to use the library now.

A dataclass derives common methods, including initialization, representation, and field comparison, from declared fields. RawEstimate deliberately has no validation: text can enter minutes despite its int annotation. Estimate explicitly checks values in __post_init__, called by its generated initializer. Those rules come from our code, not from annotations.

`field(default_factory=list)` supplies a function for creating defaults. When tags is omitted, each instance calls list separately and gets its own empty list. Pass list, not list(). If the caller explicitly supplies a list, the factory does not copy it; __post_init__ therefore validates text elements and copies the outer list itself.

Do not use a shared tags = [] as an instance default. This dataclass rejects that common mutable default declaration, while an ordinary class attribute can silently share state, as we will observe next. __post_init__ also protects only initialization; later appending a non-text value can still violate the convention.
