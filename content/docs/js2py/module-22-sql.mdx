## 1. Describe the result before writing SQL

## 3. Logical SELECT stages differ from written clause order

The file groups queries A–G. Read A and B first, then return to the joins and aggregates. SQL keyword case is insignificant. Strings use single quotes; double quotes primarily quote identifiers. JavaScript quote habits do not transfer directly.

Follow A logically: FROM identifies tasks; WHERE retains todo tasks estimated at least 20 minutes; SELECT projects id/title; ORDER BY sorts IDs. Expect `(1, 'Design API')` and `(4, 'Read SQL')`. This is a reasoning model, not a promise about physical scan order: the optimizer may rearrange equivalent operations.

AND binds more tightly than OR. To request “todo or doing tasks in Launch,” group the statuses in parentheses; otherwise an ungrouped `OR status='doing'` can admit another project's tasks. `=` compares values, `<>` means not equal, and IN tests membership in a set. Do not use `==` or infer SQL truth from Python truthiness.

Unknown conditions are also discarded. F prints `(null)` for `NULL = NULL` and true for `NULL IS NULL`. `description IS NULL` selects 1 and 4; `description = ''` selects only 2; `description = NULL` selects nothing. COALESCE chooses the first non-NULL value, useful for a presentation default but not evidence that missing and zero mean the same thing.

## 4. Ordering and pagination: stable does not mean frozen

A table has no default display order. B orders by `minutes DESC, id ASC`: largest estimates first, with unique ID breaking ties. `LIMIT 2 OFFSET 1` skips one row and takes two, giving IDs 5 and 1. Sorting only by a nonunique field leaves ties ambiguous; adding LIMIT does not create an order.

Pagination parameters are business input. The lab requires integer limit 1–100 and nonnegative integer offset, rejecting Python bool despite its integer relationship. A page-size cap limits resource use; it is not authentication. Stable ordering orders the current result only. After the first request returns 1 and 2, deleting 1 before OFFSET 2 makes the next request return 4 and 5, skipping 3. A test performs that deletion for real. Cross-request snapshots, keyset pagination and indexing need separate design; large offsets are not promised to be efficient here.

<details>
<summary>Explanation answer: why does the backend need ORDER BY when the frontend has list keys?</summary>

React keys identify elements already received; they cannot determine which records the server selected. ORDER BY determines result order, and a unique tie-breaker removes ambiguity within equal values. Inserts and deletes between requests still change offset positions. UI identity, query order and cross-request consistency are separate responsibilities.

</details>

## 5. JOIN creates matching pairs, not automatically nested objects

C matches tasks to projects by project ID and then to users by created_by. Aliases t/p/u identify the source of overlapping names such as id. INNER JOIN emits one row per matching pair and emits none for an unmatched record. Because foreign keys hold, each seed task finds its parent and creator. The result is still a flat `(task_id, title, project, creator)` row, not nested JSON.

D uses LEFT JOIN with projects as the preserved side. Even an empty project produces a row, with NULL task columns. This explains a counting trap: `count(*)` counts result rows, so Empty produces 1; `count(t.id)` counts non-NULL task IDs, so it produces 0. SUM without non-NULL inputs is NULL. The report deliberately coalesces that to zero to mean no tasks and therefore zero total estimate. This is not a policy that an unknown task estimate equals zero.

G places `t.status='todo'` in ON: choose eligible matches, then preserve every project. Expect todo counts 1/1/0 for Launch/Docs/Empty. Moving the condition to WHERE removes the NULL-extended Empty row. ON versus WHERE changes meaning, not just style.

Predict cardinality before adding memberships. Launch's three tasks joined to two members produce six rows. Summing minutes now doubles the total. `count(DISTINCT t.id)` can fix task counting, but `sum(DISTINCT minutes)` is not the corresponding fix: different tasks can share an estimate. Aggregate tasks at the desired project grain before combining membership data, or avoid an unnecessary join.

## 6. GROUP BY and HAVING filter at a different level

D groups matched records by project and selects project identity/name plus aggregates. E first removes done tasks with WHERE, groups the rest by project_id and sums minutes, then uses HAVING to keep totals at least 30. Only `(1, 75)` remains; Docs has only 20. Do not put `sum(minutes)` in WHERE, whose logical stage does not yet have the group total.

Before writing a query, finish the sentence “one output row represents…”. If the answer is a project, selecting an arbitrary task title has no clear meaning. Change the grouping grain or choose a meaningful aggregate instead of adding min merely to satisfy syntax. Successful execution proves the statement is executable, not that it answers the business question.

## 7. CRUD affects the matching set, not the row selected on screen

CRUD maps to INSERT, SELECT, UPDATE and DELETE. INSERT specifies columns and omits the identity primary key. RETURNING returns the ID actually generated by that write; “SELECT the largest ID” is unsafe because another connection can write too. UPDATE/DELETE's WHERE controls affected records. Without it the entire table may change; selecting one row in a frontend cannot constrain the SQL.

## 8. Separate driver, connection, cursor and parameters

psycopg translates Python calls into PostgreSQL communication. It is neither a database nor an ORM. Connect establishes a server session at a particular address and returns a connection. A cursor executes commands on that connection and tracks retrieval of the current result. Fetchone gets the next row or None; fetchall gets the remaining rows, represented here as tuples. Closing a cursor releases result resources, not the transaction or connection. Two cursors on one connection are not two independent transactions.

Trace list_tasks: Python validates options, chooses fixed SQL structure, execute sends structure and parameters, the server parses/executes/checks constraints, the driver converts returned values, and fetchall returns them. SQL does not run inside Python. Connection failures, Python ValueError and SQL constraint errors originate in different layers.

`%s` is a psycopg value placeholder, not string formatting. Use it for every value type, rather than `%d` for integers. Do not put SQL quotes around it, and do not use the `%` operator, f-strings or concatenation to insert values. `(title,)` is a one-element tuple; its comma matters. None adapts to SQL NULL, while the server can still reject an incompatible type.

Parameters **cannot replace column names, table names, ASC/DESC or other grammar**. Supplying title to `SELECT %s ...` returns the string title, not the title column; a real test demonstrates this. ORDERINGS selects between two author-written fragments and concatenates that selected constant, never the raw user value. When dynamic identifiers are genuinely needed, the driver's Identifier composition interface can quote them; you must still restrict which objects a caller may select. Quoting safety does not grant access permission.

## 9. Injection experiment and the boundary of protection

Injection happens when untrusted data becomes parsed SQL structure. Interpolating title into quoted SQL text lets an attacker close a quote and change a condition or add a command. Do not race an ever-growing list of attacks by replacing quote characters. Pass values through the driver's parameter channel.

This proves those calls keep values out of SQL grammar, not that the whole application can never have injection. `%` and `_` in a LIKE value remain pattern wildcards; parameterization does not automatically make patterns literal. Nor does it implement XSS protection, authorization or pagination cost limits.

Deliberately change sort to a semicolon-bearing string: expect Python ValueError before SQL execution. Use project_id 9999: expect PostgreSQL `ForeignKeyViolation / 23503`. Compare description to NULL with `=`: execution succeeds but the result is wrong. Distinguishing these three failure classes is part of diagnosis.
