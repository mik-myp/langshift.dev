## 1. HTTP 測試通過，不等於數據庫承諾成立

H06 可以用依賴替換驗證路由怎麼處理成功/錯誤，D05 驗證了版本變化。但字典替身不會執行外鍵，SQLite 也不是 PostgreSQL 的事務、類型、默認值與規劃器。用它們測某些純應用規則有價值，不能據此聲稱真實 PostgreSQL 的提交失敗、遷移或索引行為已經通過。

本章不追求一個好看的覆蓋率數字，而要為每個承諾安排能把它推翻的實驗：第二次寫入失敗後還能找到第一行嗎？提交失敗的 Session 能不恢復就繼續用嗎？fixture 建立到一半異常會留下連接嗎？已有文字在自動候選遷移中會消失嗎？索引是否真的減少了無關數據的訪問，而不是查詢碰巧跑得快？

## 3. 隔離不是一句“測試前清空數據”

<Code language="python">{getDatabaseTestingExample('safety.py')}</Code>

wrapper 在 mkdtemp 創建獨佔集群目錄和 0700 私有 Unix socket，不監聽 TCP。它移除繼承的 PG 設置與常見數據庫 URL，創建非超級用戶 lab_owner，再把隨機 LAB_DATABASE_URL 和 marker 僅傳給子命令。護欄檢查目錄、標記、驅動、用戶名、socket、端口、庫名格式和進程標記，不允許手工給任意開發 URL 換個變量名就繞過。

local trust 只適用於這份同一 OS 用戶掌控的短命集群；它不是生產認證。marker 防誤操作而不防同一 OS 用戶惡意進程。lab_owner 的 CREATEDB 也只用於此集群建立隔離數據庫，不建議把生產 API 賬號授予建庫權限。

每項測試得到一個新數據庫，名稱含隨機 UUID；DROP 只接收內部生成的標識符，並通過 psycopg Identifier 正確引用。不是用外部請求字符串拼表名。使用結束先關閉 Session/Connection，再 dispose，最後 DROP DATABASE；不加 FORCE，避免洩漏被強制踢連接掩蓋。

驗收還查詢真實服務版本、current_database、當前角色不是 superuser、inet_server_addr 為 NULL（Unix socket）。SQLite、共享開發庫或 mock 不會通過這些條件。安全護欄屬於實驗工具，不是為任意 URL 提供破壞性清理的通用管理腳本。

pytest 的 yield fixture 很像 H05 的請求依賴：前半獲取，後半清理。但如果獲取到連接之後、執行到 yield 之前遷移失敗，僅在 yield 後面寫清理未必會執行。migrated_engine 把 prepare/upgrade 也放進 try/finally，先建立退出邊界，再開始可能失敗的準備工作。

## 5. 為什麼本章不把每個測試包進一個永不提交的大事務

外層事務 + SAVEPOINT 可讓某些數據庫測試更快，但如果被測 API 的 commit 實際只結束保存點，數據庫真正的 COMMIT 延遲約束、連接釋放和跨連接可見性就未必被測試到。它不是錯誤技術，只是不適合替代本章的關鍵驗收。

這裡為每個測試建立獨立數據庫，允許被測代碼真的 commit/rollback，再在新連接中觀察結果。代價是建庫與遷移更慢，優點是提交語義不被測試工具改寫。跨測試不共享已修改的數據，不依賴某個測試先創建 alice；每項自己 seed。當前 runner 串行重複執行；沒有把未跑過的 xdist 並行或任意隨機順序稱為已驗證。

## 7. 事務驗收必須離開原來的失敗工作單元

項目+負責人測試在第二次 flush 注入非法 role；新的 Session 必須看見兩表都是 0，隨後新事務能正常建立項目。不能只檢查失敗函數沒有返回，或者 Python list 為空。

<Code language="python">{getDatabaseTestingExample('commit_failure.py')}</Code>

```bash
uv run --locked python pg_sandbox.py -- python commit_failure.py
```

```text
two INSERT values accepted; deferred check awaits COMMIT
COMMIT failed
Session refuses reuse before rollback
rollback restored Session; next transaction committed one row
checked out: 0
```

deferred UNIQUE 把錯誤推遲到真實 COMMIT，不是把 flush 失敗換個名字。rollback 前繼續查詢必須失敗，恢復後新事務寫 8 並提交，新連接只看到 8。新借出的 Connection 可能複用池內同一物理連接；這裡證明的是離開失效 Session 後的新事務狀態，不是每次必須建立新 socket。清理、回滾與成功持久化是三項不同事實，測試要分別觀察。網絡中斷導致的未知提交結果未在此驗收，不能據此承諾所有錯誤都可盲目重試。

## 9. 查詢的正確性先於查詢速度

先檢驗任務列表只包含指定項目、status 篩選正確、按 id 排序分頁、空結果與不篩選情況正確。把另一個項目的任務混進去，即使只有 1 毫秒也不是優化成功。offset 分頁在靜態數據集穩定，不承諾併發寫入時每頁永遠不漂移。

接著問數據庫如何得到這些結果。數據庫並不是看到 WHERE 就天然只讀匹配行：缺少合適索引時，可能掃描很多行再篩掉。主鍵已經是索引，也不代表所有列表查詢都有適用索引。讀 EXPLAIN 要看實際使用哪個索引、何處篩選，而不只是搜到 Index Scan 三個字。

本次 18.6 觀察到的輸出如下；它是觀察樣本，不是所有機器/版本必須固定的計劃樹：

```text
plan before: [('Limit', None), ('Index Scan', 'tasks_pkey')]
plan after: [('Limit', None), ('Index Scan', 'ix_tasks_project_status_id')]
same result rows: 20
```

兩次都有 Index Scan，卻不是同樣工作：之前按主鍵順序掃描並過濾大量無關項目/狀態；之後複合索引先縮小到一個項目和狀態，再沿 id 順序取得結果。只看節點名稱會錯過真正變化。索引前並不保證總是 Seq Scan。

## 11. 逐個讀 EXPLAIN 字段，不背成本數字

EXPLAIN 顯示規劃器的估計；EXPLAIN ANALYZE 真正執行 SQL 並加入實際觀測。因此對寫語句加 ANALYZE 會真的寫，不應隨手用於生產破壞性語句。本實驗只解釋 SELECT，且在專用測試庫中。

| 觀察項 | 怎樣解釋，怎樣避免誤讀 |
| --- | --- |
| Startup Cost / Total Cost | 規劃器內部相對單位，不是毫秒或賬單；父節點成本包含子節點，不逐層相加 |
| Plan Rows 與 Actual Rows | 估計與實際可不同；循環節點還要結合 Actual Loops，不只看一個 rows 數 |
| Index Cond 與 Filter | 前者用索引縮小候選，後者還需篩選；Rows Removed by Filter 揭示丟棄的工作 |
| Buffers 的 shared hit/read | 數據塊已在緩存或需要讀取的觀測，不直接等於物理磁盤時延或用戶耗時 |
| Planning/Execution Time | 本次儀器測量，會受緩存、機器負載與測量開銷影響，不能據一次運行做容量承諾 |

測試不比較某個精確 cost 或固定毫秒閾值。證據 JSON 保存兩份完整計劃，可查看不同環境的估計、索引名、過濾行和 buffers。本機觀測原計劃過濾了 38,180 行，新計劃通過複合索引直接定位；這屬於本次樣本，正文不把它當作永恆常數。

小表、低選擇性過濾或取大部分行時，順序掃描可能更便宜。索引佔空間，並增加 INSERT/UPDATE/DELETE 的維護工作；前導列順序和查詢條件有關，不是把所有列都加索引就好。若新環境不選擇索引，先檢查數據分佈、統計、條件、排序和代價，再解釋差異，不關閉規劃器路徑偽造成功。

此索引僅在獨立實驗數據庫創建，不是 D05 默認 migration head 的一部分。後續服務若採用它，應提交受審查的 index migration，並評估鎖/寫入成本；不能以測試裡存在過索引為由聲稱生產結構已經升級。

## 12. 三層練習：解釋、修改、獨立查詢

**解釋題。** 為什麼“所有測試最後 rollback”可能掩蓋提交失敗？為什麼 fixture 只把清理寫在 yield 後不夠？

<details>
<summary>答案：測試工具不能改掉要驗證的邊界</summary>

如果被測 commit 只結束保存點，真正 COMMIT 的 deferred 約束可能直到外層事務結束才執行；最後測試又只 rollback，就錯過了故障。fixture 若在獲取資源後、yield 前拋錯，尚未建立的後半清理不能被假設執行。把獲取後的全部準備放進 try/finally，並允許獨立庫裡的真實提交。

</details>

**帶提示修改。** 在完整實驗的臨時副本中把計劃實驗改成 **3 個項目、12 個任務**，觀察小表計劃，再回到未修改的 60,000 行基線。仍透過 pg_sandbox 執行；不換成現有資料庫，也不修改正式範例來遷就這次練習。這裡不是只把一個 60000 改成 12：

1. 項目生成範圍由 `generate_series(1, 200)` 改為 `generate_series(1, 3)`；任務範圍由 `generate_series(1, 60000)` 改為 `generate_series(1, 12)`。分配項目的 `(g-1) % 200` 同步改成 `(g-1) % 3`；否則陣列下標與項目集合不匹配。
2. 狀態條件由 `((g-1)/200) % 10 = 0` 改成 `((g-1)/3) % 2 = 0`。每個項目由此有 4 個任務，其中 2 個 doing、2 個 todo。繼續以實際傳回的 `projects[-1]` 為目標，不猜資料庫 ID 從 1 開始；該項目的 doing 標題應為 `Task 3` 和 `Task 9`，其他項目/狀態不能混入。
3. 保留查詢的 `ORDER BY id LIMIT 20`。20 是上限，不是必須湊滿的數量；本樣本只能傳回 2 行。在仍開啟的 connection 區塊裡，把總行數斷言由 60000 改為 12；兩次查詢後，用下面的斷言替換原先固定傳回 20 行的組合斷言。相等、預期內容、順序和無重複仍須通過，不能刪除所有 assert 來獲得綠燈。

```python
assert before_rows == after_rows
assert len(after_rows) == 2
assert [row.title for row in after_rows] == ["Task 3", "Task 9"]
ids = [row.id for row in after_rows]
assert ids == sorted(ids) and len(ids) == len(set(ids))
```

4. 保留「建索引前沒有使用實驗索引」的檢查；僅把「建索引後必須採用實驗索引」的斷言改為觀察並記錄兩份計劃。兩次 ANALYZE、實際建索引、結果正確性檢查都保留。不設定 `enable_seqscan=off`，也不強求小表必須出現 Seq Scan。
