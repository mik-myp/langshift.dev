## 1. From seeing an error to knowing who should handle it

L04 deliberately exposed NameError, TypeError and UnboundLocalError so you could observe the mechanisms. Now task estimates arrive as strings resembling form values: `"20"` converts, `"twenty"` does not, and `"-5"` converts successfully but violates the business rule.

Stopping an entire batch at the first known malformed value can be unhelpful. Replacing every failure with zero is not a solution either: it misreports “no valid estimate obtained” as “a valid zero-minute task.” Worse, a programming defect may be disguised as a user mistake.

**The goal is not to remove red text. It is to establish explainable failure paths: where an operation failed, who can recover, and what must propagate.** Debugging finds causes; exception handling implements an explicit recovery policy. Neither replaces the other.

## 2. Three kinds of problem: except is not the answer to all of them

| Problem | When it occurs | Direction of repair |
| --- | --- | --- |
| Invalid syntax | Before the current file starts executing | Repair the colon, indentation or structure; do not swallow a runtime exception |
| An operation fails | While evaluating an expression or call | Inspect the exception and call chain, then choose recovery or propagation |
| Normal termination, wrong result | Every statement may be valid | Compare requirements and boundary inputs; trace state and control flow |

This is an **intentional syntax error**. Save it separately as `syntax_error.py`:

```python expected-error=SyntaxError case=syntax-error
print("Before")
if True
    print("Inside")
```

Parsing detects the missing colon on line 2. Even though the first line looks valid, Before is not printed. Wrapping invalid syntax in a try in that same, unparseable file cannot make it executable. SyntaxError produced by later dynamic compilation or importing is a different scenario, not combined with this one.

Compare L04's runtime errors: earlier prints may already have happened, but statements after an unhandled exception do not execute. **No exception does not prove a correct business result.** Section 4 reproduces an early-return defect.

## 3. Reading a traceback: locate the failure, then trace its input

File: `errors/traceback_chain.py`.

<Code language="python">{getExceptionExample('errors/traceback_chain.py')}</Code>

Standard output contains only:

```text
Starting report
```

The essential error-stream structure is shown below. Absolute paths are normalized, and repeated source lines and position markers are omitted; the full output on your machine is longer:

```text
Traceback (most recent call last):
  File ".../errors/traceback_chain.py", line 17, in <module>
  File ".../errors/traceback_chain.py", line 12, in build_total
  File ".../errors/traceback_chain.py", line 6, in task_minutes
  File ".../errors/traceback_chain.py", line 2, in parse_minutes
ValueError: invalid literal for int() with base 10: '25m'
```

Read it in two passes rather than treating the whole traceback as an opaque string:

1. **Start with the last line.** ValueError is the exception category; its message identifies `'25m'` as invalid input for this int conversion. Categories select handlers; messages help diagnosis. Do not implement recovery by matching English error wording.
2. **Find the final relevant source location.** `int(raw)` on line 2 failed; print and for are not themselves the defective operations.
3. **Work back through callers.** task_minutes supplies the minutes field; build_total is traversing tasks; the top-level call supplies a list containing `"25m"`. Each frame represents a function call that has not completed.
4. **Separate a triggering location from its cause.** The input violates the conversion contract. Seeing line 2 does not justify replacing int with a function that always returns zero.

“Most recent call last” places the most recent call near the bottom. The exception looks outward for a matching handler: parse_minutes → task_minutes → build_total → top level. There is none, so the process ends with an error. These calls do not successfully return their pending results, and Done is not printed.

A terminal often displays standard output and the error stream together. Buffering can affect their visible interleaving, so they are presented separately here. Absolute paths, arrows and combined ordering are not required to match byte for byte across environments.

## 5. try/except: recover only from failures you can explain

File: `recover_value.py`.

<Code language="python">{getExceptionExample('recover_value.py')}</Code>

Expected:

```text
Input: '25'
Converted: 25
Next item
Input: 'bad'
Rejected: invalid literal for int() with base 10: 'bad'
Next item
Input: '0'
Converted: 0
Next item
```

`try:` does not inspect code in advance to see whether it is erroneous. It executes the statements normally and sets a handling boundary for **exceptions propagating during that execution**. There are two paths:

- Success: int returns an integer → Converted prints → except is skipped → Next item prints.
- Known failure: int raises ValueError → the remaining try statements are skipped → the matching except runs → Next item prints → for starts the next item.

Handling the exception **does not automatically retry the failed int line**. This example also avoids using minutes left over from a previous iteration. An unconditional print after try would be unsafe: the current assignment may never have completed.

`except ValueError as error:` temporarily binds the exception object to error. `print(error)` displays its explanation, and `str(error)` produces a message string. That binding is cleared when the handler ends; it is not long-term result storage. Explicitly save a message or structured rejection record when needed.

### 5.1 ValueError does not match every exception

File: `errors/unexpected_type.py`.

<Code language="python">{getExceptionExample('errors/unexpected_type.py')}</Code>

## 6. raise: explicitly report that an operation cannot fulfill its contract

`int("-5")` succeeds, but a task estimate must not be negative. The interpreter cannot infer that business rule for you.

File: `validate_minutes.py`.

<Code language="python">{getExceptionExample('validate_minutes.py')}</Code>

Expected:

```text
Accepted: 25
Accepted: 0
Rejected: minutes must be non-negative
```

`raise ValueError("minutes must be non-negative")` creates an exception object with a message, then interrupts normal execution. It neither returns a ValueError nor merely prints an error and continues. An outer caller can recover from ValueError; without a matching handler, the exception propagates.

`type(raw) is not str` checks for the ordinary built-in string required by this contract. Besides the conversion learned in L01, str names that built-in type; is not negates is. This deliberately narrow contract avoids accepting numeric objects and silently truncating floating-point values through int. It does not claim support for custom string subclasses or arbitrary objects.

| Input or issue | This chapter's agreement |
| --- | --- |
| `"20"`, `" 20 "`, `"0"` | Return integers; zero is not missing |
| `"bad"`, `""`, `"2.5"` | Text cannot convert to an integer: ValueError |
| `"-5"` | Conversion succeeds but violates the nonnegative rule: ValueError |
| None, 20, 2.5 | Violates the ordinary-string contract: TypeError, not known malformed text |

The conversion grammar is int's grammar. **We have not implemented an “ASCII digits only” form validator.** Signs and some other integer spellings may also be valid. Stricter product rules must be defined separately rather than inferred from this example.

### Where does the JavaScript analogy stop?

Both languages can interrupt a path and let the caller decide how to respond. This independent comparison is display-only; Python behavior is verified locally rather than relying on a browser run button.

<PythonEditor title="Explicitly reject an invalid estimate" compare={true} canRun={false} height={430}>
```javascript !! js case=raise-comparison
try {
  throw new RangeError("minutes must be non-negative");
} catch (error) {
  console.log(error.message);
}
```

```python !! python case=raise-comparison
try:
    raise ValueError("minutes must be non-negative")
except ValueError as error:
    print(error)
```
</PythonEditor>

Both produce:

```text
minutes must be non-negative
```

A JavaScript catch normally receives the thrown value before your code inspects it; Python can specify a category directly after except. JavaScript allows ordinary thrown values, while Python raise requires an exception class or instance. Do not translate `throw "bad"` into `raise "bad"`. We use built-in exceptions without requiring you to define class inheritance first.

## 7. Matching order: specific first does not mean catch everything

File: `handler_order.py`. The first half intentionally demonstrates shadowing; the second reverses the order.

<Code language="python">{getExceptionExample('handler_order.py')}</Code>

Expected:

```text
Broad handler ran
Specific handler ran
```

Handlers are inspected in order, and **the first matching one** runs. A single exception does not execute every matching handler. ValueError belongs to the larger Exception category, so a preceding `except Exception` receives it first.

Learn only the relationships currently needed, not how to define exception classes:

```text
BaseException
├── Exception
│   ├── ValueError
│   ├── TypeError
│   └── LookupError
│       └── KeyError
├── KeyboardInterrupt
└── SystemExit
```

This is an excerpt, not the whole hierarchy. KeyboardInterrupt often comes from Ctrl+C; SystemExit represents exiting. Neither belongs to Exception. Bare `except:` has a broader reach than `except Exception` and can catch those exit intentions too. We do not use it here.

Several known failures with the same recovery policy can be grouped as `except (ValueError, TypeError):`; the parentheses form the tuple learned in L02. **Syntactic grouping does not justify grouping their business meaning.** Our import report deliberately distinguishes wrong types from malformed strings.

The second half is not a template requiring an Exception fallback in every function. Most functions can raise or naturally propagate. Only a boundary that owns a real recovery responsibility should handle the failure.

File: `errors/narrow_try.py`.

<Code language="python">{getExceptionExample('errors/narrow_try.py')}</Code>

After int succeeds, else runs. ValueError from display_minutes **is not caught by the except attached to this same try**. The program fails on line 2, retaining `display rule is broken`, without Bad input or After display.

## 9. Preserve failures: propagate, re-raise, or attach a cause

### 9.1 With no recovery responsibility, do not catch

parse_minutes cannot decide whether a batch should stop or skip an item. It returns legal minutes or raises a defined exception. The report builder owns the per-row policy. Printing and returning None arbitrarily in a lower-level function leaves every caller guessing what None means.

### 9.2 If you need an observation before propagation, use bare raise

File: `errors/reraise.py`.

<Code language="python">{getExceptionExample('errors/reraise.py')}</Code>

Standard output:

```text

```

The process still ends with ValueError, with the original int on line 3 present in the traceback. `raise` without an object in the handler re-raises the active exception. It is neither another conversion nor successful recovery. Bare raise cannot be placed arbitrarily outside an active exception-handling context.

The printed context here is fixed teaching text. Later server chapters cover structured logs and sensitive information; this is not permission to send every input or traceback to end users. Catching merely to re-raise adds nothing by itself, so do not wrap every function layer this way.

### 9.3 When replacing a message, retain its original cause

File: `errors/chained_error.py`.

<Code language="python">{getExceptionExample('errors/chained_error.py')}</Code>

`except ValueError as error` protects only int. `raise ... from error` then supplies a stable domain message and explicitly identifies the original exception as its cause. The traceback shows the failed conversion, followed by a connection and the new failure:

```text
The above exception was the direct cause of the following exception:
...
ValueError: minutes must be an integer
```

The `...` here is **an omission marker in a traceback excerpt**, not Python implementation for you to copy. These are two distinct ValueError objects linked by causation. That chain is also different from the multiple call frames for one exception in section 3.

We do not hide the cause with `from None` or translate every NameError, TypeError and other defect into ValueError. Unknown failures retain their original categories.

## 10. finally: run before leaving the protected statement, not proof of recovery

File: `finally_paths.py`.

<Code language="python">{getExceptionExample('finally_paths.py')}</Code>

Expected:

```text
else
finally
Result: 0
except
finally
Result: None
```

Both paths execute finally before delivering the previously prepared return value. finally neither changes None into zero nor decides whether conversion succeeded.

| Way of leaving | except | else | Destination after finally |
| --- | --- | --- | --- |
| try completes normally | Skipped | Runs | Continue afterward, or complete a return in else |
| Matching, recovered exception | Matching handler runs | Skipped | Continue afterward, or complete a return in except |
| Unmatched exception | Skipped | Skipped | Continue propagating after cleanup |
| return inside try | Skipped | Skipped | Complete the prepared return; finally runs first |

## 11. Catching an exception does not undo earlier mutations

File: `pitfalls/partial_mutation.py`.

<Code language="python">{getExceptionExample('pitfalls/partial_mutation.py')}</Code>

Actual output:

```text
Rejected
{'title': 'Read', 'minutes': 20, 'changes': ['estimate changed']}
```

append has already changed changes when int fails. Assignment to minutes never happens because its right-hand side does not finish evaluating. except changes subsequent control flow; it does not replay the program backward to undo previous mutations.

File: `apply_estimate.py`, which computes and validates before mutation:

<Code language="python">{getExceptionExample('apply_estimate.py')}</Code>

Expected:

```text
Rejected: minutes must be non-negative
{'title': 'Read', 'minutes': 20, 'changes': []}
```

Invalid minutes fail before touching the task, preserving both minutes and changes.
