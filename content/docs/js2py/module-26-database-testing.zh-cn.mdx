## 1. HTTP 测试通过，不等于数据库承诺成立

H06 可以用依赖替换验证路由怎么处理成功/错误，D05 验证了版本变化。但字典替身不会执行外键，SQLite 也不是 PostgreSQL 的事务、类型、默认值与规划器。用它们测某些纯应用规则有价值，不能据此声称真实 PostgreSQL 的提交失败、迁移或索引行为已经通过。

本章不追求一个好看的覆盖率数字，而要为每个承诺安排能把它推翻的实验：第二次写入失败后还能找到第一行吗？提交失败的 Session 能不恢复就继续用吗？fixture 建立到一半异常会留下连接吗？已有文字在自动候选迁移中会消失吗？索引是否真的减少了无关数据的访问，而不是查询碰巧跑得快？

## 3. 隔离不是一句“测试前清空数据”

<Code language="python">{getDatabaseTestingExample('safety.py')}</Code>

wrapper 在 mkdtemp 创建独占集群目录和 0700 私有 Unix socket，不监听 TCP。它移除继承的 PG 设置与常见数据库 URL，创建非超级用户 lab_owner，再把随机 LAB_DATABASE_URL 和 marker 仅传给子命令。护栏检查目录、标记、驱动、用户名、socket、端口、库名格式和进程标记，不允许手工给任意开发 URL 换个变量名就绕过。

local trust 只适用于这份同一 OS 用户掌控的短命集群；它不是生产认证。marker 防误操作而不防同一 OS 用户恶意进程。lab_owner 的 CREATEDB 也只用于此集群建立隔离数据库，不建议把生产 API 账号授予建库权限。

每项测试得到一个新数据库，名称含随机 UUID；DROP 只接收内部生成的标识符，并通过 psycopg Identifier 正确引用。不是用外部请求字符串拼表名。使用结束先关闭 Session/Connection，再 dispose，最后 DROP DATABASE；不加 FORCE，避免泄漏被强制踢连接掩盖。

验收还查询真实服务版本、current_database、当前角色不是 superuser、inet_server_addr 为 NULL（Unix socket）。SQLite、共享开发库或 mock 不会通过这些条件。安全护栏属于实验工具，不是为任意 URL 提供破坏性清理的通用管理脚本。

pytest 的 yield fixture 很像 H05 的请求依赖：前半获取，后半清理。但如果获取到连接之后、执行到 yield 之前迁移失败，仅在 yield 后面写清理未必会执行。migrated_engine 把 prepare/upgrade 也放进 try/finally，先建立退出边界，再开始可能失败的准备工作。

## 5. 为什么本章不把每个测试包进一个永不提交的大事务

外层事务 + SAVEPOINT 可让某些数据库测试更快，但如果被测 API 的 commit 实际只结束保存点，数据库真正的 COMMIT 延迟约束、连接释放和跨连接可见性就未必被测试到。它不是错误技术，只是不适合替代本章的关键验收。

这里为每个测试建立独立数据库，允许被测代码真的 commit/rollback，再在新连接中观察结果。代价是建库与迁移更慢，优点是提交语义不被测试工具改写。跨测试不共享已修改的数据，不依赖某个测试先创建 alice；每项自己 seed。当前 runner 串行重复执行；没有把未跑过的 xdist 并行或任意随机顺序称为已验证。

## 6. 约束测试绕过 API，才知道最后一道防线还在

API 可以先拒绝空标题和非法状态，但导入脚本、旧版本服务或另一个连接仍可能绕过它。参数化测试直接 UPDATE 真实任务：bogus 状态、负分钟、空白标题、不存在的用户/项目、越界或 NULL 的 priority 都必须触发 IntegrityError；用新连接确认原行仍正确。

## 7. 事务验收必须离开原来的失败工作单元

项目+负责人测试在第二次 flush 注入非法 role；新的 Session 必须看见两表都是 0，随后新事务能正常建立项目。不能只检查失败函数没有返回，或者 Python list 为空。

<Code language="python">{getDatabaseTestingExample('commit_failure.py')}</Code>

```bash
uv run --locked python pg_sandbox.py -- python commit_failure.py
```

```text
two INSERT values accepted; deferred check awaits COMMIT
COMMIT failed
Session refuses reuse before rollback
rollback restored Session; next transaction committed one row
checked out: 0
```

deferred UNIQUE 把错误推迟到真实 COMMIT，不是把 flush 失败换个名字。rollback 前继续查询必须失败，恢复后新事务写 8 并提交，新连接只看到 8。新借出的 Connection 可能复用池内同一物理连接；这里证明的是离开失效 Session 后的新事务状态，不是每次必须建立新 socket。清理、回滚与成功持久化是三项不同事实，测试要分别观察。网络中断导致的未知提交结果未在此验收，不能据此承诺所有错误都可盲目重试。

## 9. 查询的正确性先于查询速度

先检验任务列表只包含指定项目、status 筛选正确、按 id 排序分页、空结果与不筛选情况正确。把另一个项目的任务混进去，即使只有 1 毫秒也不是优化成功。offset 分页在静态数据集稳定，不承诺并发写入时每页永远不漂移。

接着问数据库如何得到这些结果。数据库并不是看到 WHERE 就天然只读匹配行：缺少合适索引时，可能扫描很多行再筛掉。主键已经是索引，也不代表所有列表查询都有适用索引。读 EXPLAIN 要看实际使用哪个索引、何处筛选，而不只是搜到 Index Scan 三个字。

本次 18.6 观察到的输出如下；它是观察样本，不是所有机器/版本必须固定的计划树：

```text
plan before: [('Limit', None), ('Index Scan', 'tasks_pkey')]
plan after: [('Limit', None), ('Index Scan', 'ix_tasks_project_status_id')]
same result rows: 20
```

两次都有 Index Scan，却不是同样工作：之前按主键顺序扫描并过滤大量无关项目/状态；之后复合索引先缩小到一个项目和状态，再沿 id 顺序取得结果。只看节点名称会错过真正变化。索引前并不保证总是 Seq Scan。

## 11. 逐个读 EXPLAIN 字段，不背成本数字

EXPLAIN 显示规划器的估计；EXPLAIN ANALYZE 真正执行 SQL 并加入实际观测。因此对写语句加 ANALYZE 会真的写，不应随手用于生产破坏性语句。本实验只解释 SELECT，且在专用测试库中。

| 观察项 | 怎样解释，怎样避免误读 |
| --- | --- |
| Startup Cost / Total Cost | 规划器内部相对单位，不是毫秒或账单；父节点成本包含子节点，不逐层相加 |
| Plan Rows 与 Actual Rows | 估计与实际可不同；循环节点还要结合 Actual Loops，不只看一个 rows 数 |
| Index Cond 与 Filter | 前者用索引缩小候选，后者还需筛选；Rows Removed by Filter 揭示丢弃的工作 |
| Buffers 的 shared hit/read | 数据块已在缓存或需要读取的观测，不直接等于物理磁盘时延或用户耗时 |
| Planning/Execution Time | 本次仪器测量，会受缓存、机器负载与测量开销影响，不能据一次运行做容量承诺 |

测试不比较某个精确 cost 或固定毫秒阈值。证据 JSON 保存两份完整计划，可查看不同环境的估计、索引名、过滤行和 buffers。本机观测原计划过滤了 38,180 行，新计划通过复合索引直接定位；这属于本次样本，正文不把它当作永恒常数。

小表、低选择性过滤或取大部分行时，顺序扫描可能更便宜。索引占空间，并增加 INSERT/UPDATE/DELETE 的维护工作；前导列顺序和查询条件有关，不是把所有列都加索引就好。若新环境不选择索引，先检查数据分布、统计、条件、排序和代价，再解释差异，不关闭规划器路径伪造成功。

此索引仅在独立实验数据库创建，不是 D05 默认 migration head 的一部分。后续服务若采用它，应提交受审查的 index migration，并评估锁/写入成本；不能以测试里存在过索引为由声称生产结构已经升级。

## 12. 三层练习：解释、修改、独立查询

**解释题。** 为什么“所有测试最后 rollback”可能掩盖提交失败？为什么 fixture 只把清理写在 yield 后不够？

<details>
<summary>答案：测试工具不能改掉要验证的边界</summary>

如果被测 commit 只结束保存点，真正 COMMIT 的 deferred 约束可能直到外层事务结束才执行；最后测试又只 rollback，就错过了故障。fixture 若在获取资源后、yield 前抛错，尚未建立的后半清理不能被假设执行。把获取后的全部准备放进 try/finally，并允许独立库里的真实提交。

</details>

**带提示修改。** 在完整实验的临时副本中把计划实验改成 **3 个项目、12 个任务**，观察小表计划，再回到未修改的 60,000 行基线。仍通过 pg_sandbox 运行；不换成现有数据库，也不修改正式样例来迁就这次练习。这里不是只把一个 60000 改成 12：
