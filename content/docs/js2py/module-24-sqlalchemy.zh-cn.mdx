## 4. Engine、池、连接与 Session：四层不能混成一个变量

从请求向下看：路由借 Session → Session 需要执行 SQL 时向 Engine 借 Connection → 连接池提供 psycopg 的数据库连接 → PostgreSQL 中的后端进程执行事务。Session 对 Python 对象的管理与数据库连接的生命周期相关，但不是同一个东西。

| 对象 | 保管什么 | 谁拥有，何时结束 |
| --- | --- | --- |
| Engine | 驱动/SQL 方言配置与连接池入口 | 一个应用进程通常建一次，进程退出时 dispose |
| Pool | 可重用的物理客户端连接 | Engine 管理；不是启动时立刻开满所有连接 |
| Connection | 一段时间内借出的数据库连接及事务访问 | Session 内部或显式 with 块借用；close 通常归还池 |
| Session | identity map、待写对象、当前工作单元/事务状态 | 一个请求一次使用，不在并发请求间共享；结束 close |

可以把 Session 的 identity map 类比组件树内按 key 保留同一对象，但它不是 React 状态库，更不是自动订阅全数据库变化的全局缓存。两个请求有两个 Session，它们可能读到不同时间的数据；数据库隔离级别仍然决定可见性。

池可减少反复建立连接的开销，不能让一条连接同时执行两个互不相干的业务事务。示例 pool_size=2、max_overflow=0 是为了让泄漏容易观察，不是生产配置建议；多个 worker 各有自己的池，总连接预算不能只看一处的 2。pool_pre_ping 可在借出时检查失效连接，但无法自动挽救事务中途断线，也不能安全地替你重试未知是否提交成功的操作。

## 5. Session 的工作单元：排队、发送、提交不是同一件事

构造 User 或 Project 只是建立 Python 对象。add 把它纳入 Session 管理；flush 把待写变化转成 SQL 发往数据库，可能取得 identity，也可能立刻碰到 CHECK/FK 错误。flush 成功不等于其他事务已经看见，更不等于持久化成功；随后 rollback 仍可撤销这些插入。

commit 通常先 flush，再要求数据库结束事务。某些约束可延期到提交，磁盘/网络也可能在这一阶段失败，所以“函数正常走到 return 前”不能代替“commit 已成功”。查询前还可能 autoflush，不能假定只有手写 flush 那一行才会触发写入错误。

Session 默认 autobegin：第一次需要数据库的读/写就进入事务。GET 的 SELECT 也可能借连接并开启事务；不关闭它就可能长期 idle in transaction。`with Session(...)` 负责关闭，不负责成功时自动提交；`with session.begin()` 才负责成功提交、异常回滚。显式 begin 应包在首次读写外面，不能先 SELECT 开了事务再盲目 begin。

默认 expire_on_commit=True 会使持久对象的属性过期，后续访问可能再查数据库；关闭后的对象也不应被响应序列化器拿来偷偷加载。这里在事务内复制纯 dict，并在提交成功之后才返回它，不把懒加载和关闭顺序交给运气。dict 在提交前构造不代表提前对外发送，commit 若失败，返回路径根本不会执行。

## 8. HTTP 边界：提交先完成，响应才宣称成功

<Code language="python">{getOrmExample('api.py')}</Code>

依赖 get_session 只负责创建和 finally 关闭；写路由的 begin 负责提交/回滚。退出 begin 后才 return，因此 deferred constraint 在 commit 失败时仍能变成错误响应，而不是先发 201 再发现失败。IntegrityError 在 begin 外捕获，此时事务管理器已处理回滚；本教学接口把数据库完整性冲突归为脱敏的 409，不把 SQL、表细节或输入回显给用户。

并非所有异常都应翻译为 409。连接不可达、代码错误等不在这个捕获范围内，应交给服务层的错误观测和失败政策。请求结构错误由 Pydantic 返回 422，父项目不存在为 404。正式产品应进一步按约束名细分业务错误，而不是吞掉所有数据库异常。

路由用普通 def，数据库调用都是同步的。lifespan 的 asynccontextmanager 只是 ASGI 的启动/关闭协议包装，不是异步 ORM；数据库资源仍在明确同步代码中使用。一个 Session 不可由两个并发任务/线程同时操作，也不能全局缓存供所有请求共用。

输入 owner_id/created_by 是本地教学临时契约，不是认证方案。S 章节必须从验证后的当前用户推导这些值，移除客户端自报身份，并增加成员权限校验；本章 API 仅绑定回环地址，不可发布。

## 10. 故障实验：真正在 COMMIT 时失败

<Code language="python">{getOrmExample('commit_failure.py')}</Code>

```bash
uv run --locked python pg_sandbox.py -- python commit_failure.py
```

```text
two INSERT values accepted; deferred check awaits COMMIT
COMMIT failed
Session refuses reuse before rollback
rollback restored Session; next transaction committed one row
checked out: 0
```

额外的 commit_probe 表只属于本次故障实验，不改变业务四表。UNIQUE 被标记 DEFERRABLE INITIALLY DEFERRED，因此重复的 7 能先发送成功，commit 才拒绝。这与 flush 时 CHECK 失败是不同时间点，不能用后者冒充提交失败。

失败后继续 SELECT，会被 SQLAlchemy 的失效事务状态拒绝。显式 rollback 不只处理数据库，也重置 Session 的事务记账；然后开启新的工作单元插入 8 才有意义。关闭失败 Session 并用新 Session 处理下一请求也是正确政策。不要在异常捕获后继续把旧的待写对象当成已持久化对象。

本例错误是服务器明确拒绝约束，因而能断言没有提交。若提交期间网络断开，客户端可能不知道服务器是否已经提交；不能把“没收到成功”一律当成“绝对没写入”。真实服务需要幂等设计/查询确认，本章不伪装成已解决这种不确定性。

## 12. 三层练习：先作答，再展开

**解释题。** create_project 的第一个 flush 后已有 id。此时第二步失败，为什么项目仍可消失？为什么 id 不必再从 1 连续分配？

<details>
<summary>答案：可用的主键不等于事务已提交</summary>

flush 发送了 INSERT 并取回 identity，但仍处在调用层未提交的事务。第二步失败让整个事务回滚，项目行随之撤销；序列分配不承诺随事务回收，空洞不代表丢了业务记录。不要以连续 ID 作为验收。

</details>

**带提示修改。** 把 Session 关闭边界移除，再连发多个请求预测会发生什么。不要把泄漏版留在参考实现。提示：将池维持为 2，不增加 overflow，分别观察 HTTP 错误和借出计数。

<details>
<summary>答案：定位借用者，而不是先把池调大</summary>

没有可靠 close，已开始的读事务也可能长期占住连接。后续借用会等待到 pool_timeout，出现连接池超时而非数据库 CHECK 错误。恢复 with/依赖清理，并保证异常也穿过退出边界；重复请求后 checkedout 应回到 0。垃圾回收偶然释放不是政策，因此不能只凭一次没有超时就判通过。

</details>
