## 3. SELECT 的邏輯順序，不等於源碼中的書寫順序

用邏輯階段理解 A：FROM 找到 tasks → WHERE 保留 todo 且估時至少 20 的行 → SELECT 取 id/title → ORDER BY 按 id 排。結果是 `(1, 'Design API')` 和 `(4, 'Read SQL')`。這是理解模型，不保證執行器物理上照此掃描；優化器可以重排等價操作。

WHERE 的 `AND` 比 `OR` 結合得緊。例如“Launch 項目中 todo 或 doing”必須把兩個狀態用括號組合，否則 `OR status='doing'` 可能把別的項目也放進來。`=` 比較值，`<>` 表示不等，`IN` 表示屬於集合。不要寫 `==`，也不要用 SQL 條件的結果猜 Python truthiness。

篩選條件為 unknown 的行同樣不返回：F 的 `NULL = NULL` 輸出 `(null)`，`NULL IS NULL` 輸出 true。`description IS NULL` 得 id 1、4；`description = ''` 只有 id 2；`description = NULL` 一行也沒有。`COALESCE` 選擇第一個非 NULL 值，可用於顯示缺省值，但不能據此說缺失與零是同一種事實。

## 4. 排序與分頁：穩定，不代表凍結

數據庫表沒有默認顯示順序。B 用 `ORDER BY minutes DESC, id ASC`：分鐘多的在前，同分鍾時用唯一 id 打破平局；`LIMIT 2 OFFSET 1` 跳過一行再取兩行，得到 id 5、1。僅按非唯一字段排序，翻頁時同分記錄可換位；給查詢加 LIMIT 本身不能保證順序。

分頁參數也屬於業務輸入：本實驗 limit 必須是 1–100 的整數，offset 必須是非負整數，並拒絕 Python 的 bool 偽裝整數。限制頁大小是資源邊界，不是認證。穩定排序只能在當前結果上確定順序：第一頁取 1、2 後，另一請求刪除 1，再用 OFFSET 2 會得到 4、5，id 3 被跳過。測試真的執行這次刪除，並不只講“可能”。跨請求一致快照、遊標分頁和索引性能另行設計，本章不承諾大 offset 高效。

React key 幫助前端識別已收到的元素，不能決定服務器從數據庫挑了哪幾行。ORDER BY 決定結果順序，唯一的第二排序鍵解決同分歧義；但兩次請求之間的插入/刪除仍會改變 offset 位置。三者分別是 UI 身份、查詢順序和跨請求一致性，不能互相替代。

## 5. JOIN：按匹配關係生成結果，不是把對象自動嵌套

C 把 tasks 與 projects 按項目 ID 相等組合，再按 created_by 找 users。別名 t/p/u 讓同名 id 的來源明確。INNER JOIN 對每一對滿足條件的行生成一行，找不到匹配就沒有該結果；由於外鍵存在，每項種子任務能找到父項目和創建者。輸出仍是扁平行 `(task_id, title, project, creator)`，不是自動嵌套的 JSON。

D 使用 LEFT JOIN，以 projects 為保留方，即使沒有任務也產生一行，右側列都是 NULL。這解釋了兩種易錯計數：`count(*)` 數結果行，Empty 是 1；`count(t.id)` 只數非 NULL 的任務 ID，Empty 是 0。`sum` 在沒有非空輸入時是 NULL，報告明確選擇 `coalesce(..., 0)` 表達“沒有任務，總估時為零”。這不是把未知任務估時也定義成零。

G 把 `t.status='todo'` 放在 ON 中，先決定哪些子記錄可以匹配，再保留所有項目；結果 Launch/Docs/Empty 的待辦數為 1/1/0。若把該條件放到 WHERE，LEFT JOIN 補出的 NULL 行也會被過濾，Empty 就消失。選 ON 還是 WHERE 不是風格問題，而是需求不同。

再加 project_members 時要預測基數：Launch 三項任務乘以兩名成員，得到六行。此時 `sum(t.minutes)` 會錯誤翻倍。只統計任務數可以 `count(DISTINCT t.id)`；求估時不能簡單用 `sum(DISTINCT minutes)`，因為不同任務可能恰好同分鍾。正確方向是先按任務或項目聚合，再組合成員信息，或者根本不做不需要的 JOIN。

## 6. GROUP BY 與 HAVING：行與組是兩層過濾

D 把每個項目的匹配行收集成一組；SELECT 中輸出項目鍵/名及聚合值。E 先用 WHERE 排除 done，再按 project_id 分組求 minutes 總和，最後 HAVING 只保留至少 30 分鐘的組。結果只有 `(1, 75)`；Docs 的 20 沒到門檻。不要把 `sum(minutes)` 塞進 WHERE：該階段還沒有組的總和。

寫查詢前，先用一句話定義“一行結果代表什麼”。若答案是“一個項目”，SELECT 出任意一個任務標題就沒有明確含義；要麼改變分組粒度，要麼選擇合適聚合，而不是隨機包一層 min 讓語法通過。SQL 沒報錯只能證明語句可執行，不能證明分組符合業務。

<summary>帶提示修改答案：把 G 改成每個項目的未完成估時，保留 Empty</summary>

把 ON 中的狀態條件改為 `t.status <> 'done'`，SELECT 用 `coalesce(sum(t.minutes), 0)`，仍按項目分組。預期 Launch=75、Docs=20、Empty=0。若改到 WHERE，Empty 消失；若去掉 coalesce，Empty 是 NULL。三種結果都能解釋，卻只有第一種符合本題報告的契約。

## 7. CRUD：影響的是匹配集合，不是當前屏幕那一行

CRUD 對應 INSERT、SELECT、UPDATE、DELETE。INSERT 明確列清單，省略 identity 主鍵；`RETURNING` 讓同一條寫入返回數據庫實際生成的 id，不要用“SELECT 最大 ID”猜剛寫的記錄——別的連接也會寫。UPDATE/DELETE 的 WHERE 是數據安全邊界：沒有 WHERE 可能操作整張表；前端只選中一行不能改變它的含義。

## 8. 驅動、連接、遊標和參數分別做什麼

psycopg 是把 Python 調用轉換成 PostgreSQL 通信的驅動，不是數據庫，也不是 ORM。`connect` 與指定地址的服務器建立會話，返回連接對象；`cursor` 在該連接上執行命令並持有本次結果的讀取位置。`fetchone` 取下一行，沒行是 None；`fetchall` 取剩餘行，本實驗返回 tuple 列表。關閉遊標釋放結果資源，不等於提交事務或關閉連接；同連接的兩個遊標也不是兩個獨立事務。

從 list_tasks 追蹤數據：Python 驗證參數 → 選擇固定 SQL 結構 → execute 發送結構與參數 → 服務端解析、執行與約束檢查 → 驅動把結果轉成 Python 值 → fetchall 返回。SQL 不會在 Python 裡執行；數據庫連接失敗與輸入 ValueError、SQL 約束錯誤發生在不同層。

`%s` 是 psycopg 的值佔位符，不是字符串格式化操作。所有類型都用它，不按整數換成 `%d`；不要給佔位符加 SQL 引號；不要用 `%` 運算符、f-string 或字符串加法把值拼進 SQL。單參數的 `(title,)` 是單元素 tuple，逗號不能省。None 被適配成 SQL NULL，SQL 類型錯誤仍可能由服務器拒絕。

參數**不能替代列名、表名、ASC/DESC 等語法**。`SELECT %s ...` 傳入 `title` 只會返回字符串 title，不會讀取 title 列；測試實際證明這點。list_tasks 的 ORDERINGS 僅選擇作者寫死的兩個片段，再拼接片段，不拼用戶輸入。將來確實需要動態標識符時可用驅動的 Identifier 組合接口，但仍要限定用戶允許選擇的對象；引用安全不等於對象訪問授權。

## 9. 注入實驗與防護邊界

SQL 注入發生在“不可信數據被解析成 SQL 結構”這一邊界。錯誤反例是把 title 插進引號包裹的 SQL 文本；攻擊者可以關閉引號，再改變 WHERE 或添加命令。不要靠替換單引號列表與攻擊樣本比賽，正確做法是把值交給驅動參數通道。

```bash
uv run --locked python labctl.py reset --yes-reset
uv run --locked python demo.py
uv run --locked pytest -q
```

```text
todo [(1, 'Design API', 'todo', 30), (4, 'Read SQL', 'todo', 20)]
page [(3, 'Ship demo', 'done', 15), (4, 'Read SQL', 'todo', 20)]
totals [('Launch', 3, 90), ('Docs', 2, 60), ('Empty', 0, 0)]
unmatched payload []
literal stored [(6, "x' OR TRUE --")]
updated (6, 'doing')
deleted (6,)
tasks remaining 5
```

這是 reset 後的確定輸出；重複執行 demo 而不 reset 時，identity 會繼續增長。測試還存入 `'; DROP TABLE tasks; --`，精確查回原字符串，再確認 tasks 表仍有數據。證明的是這個驅動調用中的值未變成 SQL，不是證明整套系統永遠沒有注入。LIKE 參數中的 `%`/`_` 仍是模式通配符；參數化不會把模式自動變成字面搜索，也不會完成 XSS 防護、權限判斷或分頁成本控制。

故意把 sort 改成帶分號的字符串，預期 Python `ValueError`，尚未發出 SQL；把 project_id 改成 9999，預期 PostgreSQL `ForeignKeyViolation / 23503`；直接把 description 與 NULL 用等號比較，查詢成功但結果錯。能把這三類失敗分開，是排錯能力的一部分。
