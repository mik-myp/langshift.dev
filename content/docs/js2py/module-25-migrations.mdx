## 1. Editing a Python model does not upgrade an existing database

D04 connected the API to PostgreSQL. Now tasks need priority: 0 ordinary, 1 important, 2 urgent. Editing Task alone leaves the database without that column. Dropping tables and running create_all loses existing data. Reinstalling dependencies changes neither problem.

A migration is a reviewed transition between explicit database states. Shipping application code and upgrading data are separate actions. The acceptance criterion is not merely an empty database that starts successfully: records must exist before the upgrade and retain their identity and contents afterward.

| Chapter contract | Scope |
| --- | --- |
| Prerequisite | D04 mappings, connection/Session ownership and transactions |
| New capability | Alembic history, generation/review, data-preserving upgrades, staged compatibility, failure/recovery limits |
| Independent acceptance | Empty-to-head; field-by-field preservation; failed upgrades do not claim success; lossy downgrade is refused |
| Exclusions | No delete-and-rebuild upgrade, no universal lossless downgrade, no zero-downtime claim from a small-table example |

Download the [complete D05 lab](/learning-assets/js2py/d05-migrations.zip) and work in d05-migrations. It is self-contained and does not import D04. Displayed and downloadable code share canonical files. All database execution is local, not Pyodide.

Frontend work has no direct equivalent to schema migrations: changing a localStorage shape usually means hand-written compatibility code at read time. Alembic version scripts are that compatibility layer, but they act on one PostgreSQL database shared by all users — a wrong script affects everyone at once, which is why this chapter requires reviewing scripts before running them.

## 3. Three revisions are database states, not three application folders

A revision file links down_revision to revision. alembic_version records where this database has arrived; head is the end of the script graph. Our history is linear. An empty database can start at base, but an existing schema without an Alembic marker is not an empty database.

| Revision | tasks.priority | Compatibility |
| --- | --- | --- |
| 001_base | Absent | Exact D01–D03 four-table baseline |
| 002_expand | Nullable integer, no default | Old writers can omit it; transitional readers must accept NULL |
| 003_contract | Backfill NULL→0; DEFAULT 0; NOT NULL; CHECK 0..2 | Old writers omitting it still work; explicit NULL/out-of-range values fail |

priority is a teaching extension, not a rename of status. H done→status, note→description, retained minutes, identity-generated IDs and the User/Project/Member transition remain explicit. Authentication fields remain absent. The final Task mapping targets 003; it must not query a nonexistent column in 001.

A Git-patch analogy helps explain ordering and review, but reverting code does not reverse facts users created. Application version numbers also differ from database revisions. In deployment, migrations should be a controlled once-per-release action, not a race among every application worker's startup hook.

The ini file names the script directory without embedding credentials. migrate.py constructs Config for programmatic tests; CLI operations use the same env.py. That environment validates the URL, imports current metadata as the desired comparison target, and owns/disposes its online Engine. NullPool avoids retaining migration connections; it does not remove the obligation to close them.

configure sets comparison behavior and metadata. begin_transaction wraps revision execution. Ordinary PostgreSQL DDL and the data updates used here participate in that transaction, enabling tests to prove that revision markers, backfills and schema changes all roll back together. This is not a promise about every database or special operations such as CREATE INDEX CONCURRENTLY.

Historical revisions do not import the current Task class. Otherwise today's model edit could silently change what an old revision recreates. Current metadata describes a comparison target; revision scripts freeze historical definitions.

**First Alembic use: who calls a revision?** The download already contains `alembic.ini`, `migrations/env.py` and the revision template; do not run `alembic init` again in this lab. In each revision module, `revision` identifies the state reached by its upgrade, while `down_revision` identifies its predecessor (`None` for the initial revision). These are identifiers, not function calls; Alembic follows their links rather than sorting filenames to decide execution order.

For an online `python -m alembic upgrade head`, the CLI loads the configuration and runs `env.py`. Here `env.py` checks the sandbox URL, opens a connection and starts the migration transaction. Its `context.run_migrations()` lets Alembic compare the database's current revision with the script graph, select the missing steps and call each step's `upgrade()`. For a downgrade target, Alembic calls the corresponding `downgrade()` functions in reverse order. It maintains `alembic_version` as the steps run; a failure in this lab's transaction rolls back those markers together with the changes. Do not run a revision with `python migrations/versions/002_expand.py`: merely defining these functions does not apply a migration.

The imported `op` exposes Alembic's migration operations in that execution context. For example, the later 002 script's `op.add_column(...)` describes an `ALTER TABLE` on the migration connection; `op.get_bind()` returns that connection for historical-data SQL. These are explanations of calls in the complete scripts below, not standalone runnable snippets. This is **not a request's business Session**: D04's caller-owned Session handles a business unit of work, whereas `env.py` owns the connection and transaction for schema/history changes. A revision must not create a request Session or call a current business service to rebuild historical data.

Finally, **generating a file is not executing it**. `revision --autogenerate` inspects the database and current model metadata, then writes a candidate file for review; it does not apply that candidate's `upgrade()`. A later explicit `upgrade` command would apply the reviewed revision. Editing the model, generating the file and changing the database are three separate actions. Section 8 makes that distinction observable without applying the candidate.

## 6. Expand, backfill, enforce — identify every active reader and writer

<Code language="python">{getMigrationExample('migrations/versions/002_expand.py')}</Code>

<Code language="python">{getMigrationExample('migrations/versions/003_contract.py')}</Code>

Adding a nullable column first lets writers that name only old columns continue. A new reader that assumes an integer may encounter NULL during this stage; it must tolerate “unset” or wait until backfill/enforcement is complete. Revision-aware SQL prepares historical rows without querying through a final mapping prematurely.

003 fills only NULL with 0, preserving an explicit priority of 2, then installs the default, NOT NULL and CHECK. A default handles omitted columns on future inserts; it does not rescue explicit NULL or repair an existing 9. Transitional data must be audited, not magically cleaned by adding a constraint.

Compatibility is conditional. Old code using INSERT without column names, depending on SELECT * positions, or explicitly sending NULL can still break. Our old-writer assertion covers precisely named-column SQL that omits priority. A real contract step that removes an old field requires first retiring its readers/writers.

A full-table UPDATE and ALTER TABLE consume time, locks and write-ahead log. This example has small historical data. Large datasets may need bounded, resumable backfills with progress observation, lock-timeout policy and a deployment window. A single successful UPDATE is not evidence of zero downtime and is not a model for a long-running request transaction.

## 8. Autogenerate proposes a candidate; it cannot infer intent

Autogenerate compares metadata with the current database and can produce many column/index/constraint operations. It does not know that note→description is intended as a value-preserving rename. An add description + drop note pair may erase the old content. Successful generation, valid syntax and even an empty-database upgrade do not establish correctness.

A real test renames populated description to note, generates a candidate into a temporary script directory, checks that it contains add/drop, and proves the candidate was not applied: note still contains its text. Generated output is never automatically approved against user data.

**Runnable local tour: a new sandbox, a baseline, then a candidate only.** Use a fresh extracted scratch copy of `d05-migrations`, without extra revision files, and complete section 2's environment setup and `uv sync --locked` there. Do not edit the shared lab. Section 7 already ended with `exit`; its temporary database is gone. The following starts a **new** sandbox. Keep this terminal in its child shell until the final `exit` below; do not split the commands across separate wrapper invocations or remove the URL guard.

In that scratch copy's root, run this first. The first line enters the sandbox shell; run the remaining lines inside it:

Return to the **same still-open sandbox shell** and run the following block. The embedded Python is a complete local inspection program: it prints the generated candidate, reads the database revision and uses `inspect(connection).get_columns("projects")` to list actual columns. It opens/closes its own inspection connection and does not execute the candidate. If any command or assertion fails, stop and diagnose it; use `exit` to clean up before starting a fresh attempt, not `stamp` or a disabled guard.

```bash
python -m alembic revision --autogenerate -m "review candidate"
python -m alembic current
python - <<'PY'
from pathlib import Path
from sqlalchemy import inspect, text
from db import make_engine

candidates = list(Path("migrations/versions").glob("*_review_candidate.py"))
assert len(candidates) == 1, "Use a fresh scratch copy for this exercise"
print("candidate:", candidates[0])
print(candidates[0].read_text(encoding="utf-8"))
engine = make_engine()
try:
    with engine.connect() as connection:
        revision = connection.scalar(text("SELECT version_num FROM alembic_version"))
        columns = {column["name"] for column in inspect(connection).get_columns("projects")}
        assert revision == "003_contract"
        assert "review_note" not in columns
        print("database revision:", revision)
        print("review_note exists in database:", "review_note" in columns)
finally:
    engine.dispose()
PY
exit
```

Before `exit`, read the printed candidate: its filename/revision identifier varies, `down_revision` should be `003_contract`, `upgrade()` should add nullable `projects.review_note`, and `downgrade()` should remove it. A written downgrade is still only a candidate requiring review. The database inspection must print `database revision: 003_contract` and `review_note exists in database: False`. `current` no longer labels 003 as head because the **script** graph now has a new head; that does not mean the **database** has applied it. Do not run another `upgrade head` in this exercise. A metadata difference is expected now: the edited model and the unchanged database deliberately differ.

After `exit`, the wrapper returns to the parent shell and its cleanup output and `/tmp/d05-candidate-cleanup.json` must show `stopped=true`, `status_after_stop=3` and `removed=true`. This removes only its owned temporary cluster, not your edited model or candidate file. Keep those files in the scratch copy for review; use an untouched lab copy for later default tests. A new wrapper invocation creates a new database, not a continuation of this one.

Review in this order:

1. Does down_revision point to the agreed head? Did someone create another head concurrently?
2. Which operations add objects, and which remove or rewrite data? Is a rename misidentified?
3. How will existing NULLs, duplicates and invalid values be handled? Is a default client-side or server-side, and does it concern only future writes?
4. Which old/new readers and writers work at each stage? When must old writers stop?
5. What locks and backfill costs are possible? What state should be inspected after failure?
6. Which facts would downgrade discard? Should it refuse and require a forward fix or separately verified recovery procedure?

Alembic 1.20.0 has optional, default-off CHECK comparison by name. Even when enabled, a same-name expression change is not a semantic equivalence check. This environment explicitly enables type/default comparison, not that optional plugin, and does not claim check audits every constraint or row. Negative database tests remain necessary.

## 9. Failure experiment: invalid old data must not become a false success

At 002 there is no priority CHECK. A test stores 9 in one row and NULL in another, then upgrades. 003 first fills NULL with 0, but the later CHECK rejects 9. Acceptance requires the revision to remain 002, the second value to remain NULL, and the column to remain nullable without a default. This proves rollback of the earlier data update as well as the final DDL.

```bash
uv run --locked python pg_sandbox.py -- python -m pytest -q -k invalid_existing_data
```

Expect 1 passed with other tests deselected. The test explicitly chooses 9→2 as its repair policy before retrying. That is an example policy, not permission to rewrite production meanings arbitrarily. Investigate the source and decide the business repair before changing real rows; do not stamp past a failed upgrade.

For a connection interruption or nontransactional operation, do not assume this exact all-or-nothing outcome. Inspect actual schema, data and revision state. The verified claim is limited to the ordinary PostgreSQL transactional DDL used here.

## 10. Application rollback, schema downgrade and backup restore differ

An application rollback can run old code while keeping compatible new columns. Here, old inserts omitting priority still work against 003 because its default remains. Schema downgrade executes inverse structure operations: 003→002 preserves values but removes guarantees; 002→001 would delete priority, so populated tasks cause refusal.

Backup restoration returns a database to a recovery point and must account for later writes, downtime and recovery objectives. It is not another name for downgrade. We have not rehearsed production backup restoration or promised arbitrary destructive migrations can be undone without loss. If data really must be removed, separately review business impact and a tested recovery plan rather than deleting refusal checks.

## 12. Three exercises with separate answers

**Explain.** Why are “set DEFAULT 0” and “replace every historical NULL with 0” separate policies? Why cannot a transitional reader assume the final non-null int contract?

<details>
<summary>Answer: future defaults, historical repair and reader compatibility differ</summary>

A server default principally defines future inserts that omit a column. Our explicit UPDATE handles the existing NULLs rather than relying on optimizations of one particular ADD COLUMN form. Transitional storage allows NULL, so readers must accept it or wait. Explicit NULL is not repaired by a default.

</details>

**Guided review.** A generated candidate adds description and drops a populated note column. Explain why it cannot be approved as-is, and propose a value-preserving direction without executing the deletion.

<details>
<summary>Answer: establish rename intent and the compatibility window</summary>

If the two names represent one field, review a column rename rather than add/drop. But immediately renaming also breaks an old application still using note. A live transition may need expansion, compatible reads/writes, backfill, reader migration and only then removal. The generator knows neither business intent nor deployment order. The supplied test shows this limitation with a real candidate.

</details>

**Independent variation.** Add nullable archived_at to projects without inventing dates for old projects. Prove task/project history survives, old values stay NULL, and a genuine archive timestamp cannot silently disappear on downgrade. Choose the downgrade policy yourself first.
